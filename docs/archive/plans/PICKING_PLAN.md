## 0. 目标与判据

**目标**：选中一批订单 → 按 **SKU（款 × 色 × 码）** 汇总"要拣什么、各几件、图与供应商在哪" → 可导出拣货单。

**跑通判据**：任选一批未发货订单，拣货单里每个 SKU 的**件数**与**图**，与"订单明细逐单数一遍"一致；缺色/码的行**逐行标出来**，不静默按 0 或按 1 蒙。

## 3. 口径：**默认已定，不打扰用户**（2026-09-29 原则：能自动就不让人填）

| 项 | 默认 | 何时才回到人 |
| --- | --- | --- |
| 件数 | **订单行数量**；缺则按 1 件**并逐行标出** | 只有当"缺数量"行占比高到影响可用性时，才回去补数据源 |
| 范围 | **未发货 + 近 30 天**（一键生成）；店铺沿用导入归属 | 需更早/按店铺细分时，才展开"更多筛选" |
| 已拿货扣减 | **不扣**（拣货 ≠ 缺口）；另列"已拿"供参考 | 用户明确要"还剩多少没拿"时，走 `outstanding()` |

> 原则：**默认值写在界面上可见**（"未发货 · 近 30 天"），不藏在设置里。

### 3.1 P1 取证结论（2026-09-29 实测，只读聚合）
在真实库（`oi_orders` 42 行）量填充率：

| 字段 | 填充率 | 结论 |
| --- | --- | --- |
| `color` / `size` / 款编码（经识别链） | **42/42 = 100%** | ✅ SKU 粒度可用 |
| 订单状态 | 全 `pending` | ✅ "未发货"默认范围天然可用 |
| **供应商** | **`pl_products` 只有 1/27 填了 `supplier_id`** | ⚠️ 按供应商分组现在几乎全空 |

⇒ ① 拣货按款×色×码做准无障碍；② **供应商分组先别当主打**（第一版照常出该列，缺的行显示 `(未识别供应商)` 并计数，不静默糊成一组；要真按厂家分单先去产品库补 `supplier_id`）。

### 3.2 P2 取证结论（2026-09-29 实测，两份真实导出对齐）
| 事实 | 对口径的影响 |
| --- | --- |
| 订单报表**每一行**都有件数：`订单列表-6.xlsx` 175 块 `(商品数量:N piece)` **175/175 命中** | 订单侧可做逐行真值来源 |
| 多件真存在：块级件数分布 **1:165 / 2:8 / 3:2** | 件数必须逐行取；一期"恒按 1 件"会错 6% 行 |
| **同一商品以多个 SKU 出现在一张单里** | 结算"按商品合计件数"不能逐行复用 → 只在 `lines === 1` 时采用（`orderCost.ts` 件数优先级） |
| 拆行后「数量」列仍是整行值（splitter 不清空） | 不用它，取不到就标缺 |

**落地形态**：`qty`/`qtySource`（`settle`/`order`/`assumed`）逐行可见，缺的行进 `缺件数` 计数，件数 > 1 时界面出提示条。

### ⚠️ P2 暴露的**开放项**（未做，需拍板）
**件数 > 1 的行，成本与运费目前仍按 1 件计** —— 刻意非漏写：`ae_cost_map.unit_price_cents` 是单件成本（按件数放大成立），但运费不行（多件合并计费是运价岛开放项），单方面放大成本会让"成本×N、运费×1"像 bug；两者要一起改且会改变所有已展示毛利数字 → 等用户拍板。界面显式提示 + 单测钉住（`qty=2` 与 `qty=1` 的 shipping/cost/gross 逐项相同）。

### 3.3 P3/P4 的**刻意决策**（与原计划偏差，按代码现实回改）
**① 不做 `db` 能力域，只加一个宿主只读通道** —— 页面是内建模块，`DB_OPS` 能力域只为 UI 岛存在；加"没人消费的域"只会变死声明。⇒ 只加 `picking-rows` 一条只读通道。
**② 聚合与"范围口径"留渲染层纯函数，宿主只回投影** —— 件数解析（`parseRowQty`）、"已终结单不该拣"按状态原文（`bucketOfStatus`）、天数窗认 `order_time` 多写法（`dateKey`）的唯一实现都在渲染层，主进程再抄必漂移；且 SQL 里做字符串日期比较会静默丢行（`'08/…' < '2026…'`）。⇒ 宿主 `WHERE` 只留机械事实（`ship_time` 空 且 `status<>'shipped'`、可选店铺、上限），"剔除谁"由纯层做并**报出剔除数**。
**③ P5 的形态：域 op 与内建页共用同一份纯函数** —— `host.ts` 跑在渲染进程，能 `await import('@/lib/picking')`，岛侧 op 直接在宿主做完。⛔ **P5 已随 C2 撤回**（2026-09-30）：`DB_OPS.picking` 与守卫都删了。这条设计结论仍成立（现由 `shipping-rate`/`product`/`excel-copy` 三域活着），将来若真有岛要消费拣货，照 `docs/notes/2026-10-30-island-host-boundary.md` 开回即可；当时的守卫写法（岛内不得出现 `aggregatePicking` + 宿主真 `await import`，断言前先剥注释）仍有价值。

## 4. 界面原则（本线适用，源自用户 2026-09-29 三条）

1. **一键式**：主操作只有一个按钮（「生成待拣清单」），结果页直接给结论（SKU × 件数 × 图 × 供应商）。
2. **不暴露筛选面板**：默认条件以**文字标签**呈现，需要时才展开。
3. **只突出重点**：拣货时只关心 图/款色码/件数/供应商，其余放次级。
4. **缺数据逐行标**，不弹窗不阻塞。
5. **顺手回收旧界面多余控件**（见 P0）。

### 为什么是这个顺序
```
P1 先验口径与填充率 → P2 数量定了件数才不假 → P3 有口径才建通道（否则 op 形状反复改，一改就要岛发版）→ P4 页面最后做 → P5 发版放最后
```
**P1 价值不在功能，在取证**：`oi_orders.color` 是 AI 归类、`oi_orders.size` 依赖映射，填充率未知 —— 若色/码大面积缺失，拣货得先补数据而非先写页面。
