# ADR-002: 建立「主数据层」——基础数据独立维护、以 ID 关联、插件只读消费

## Status

**Accepted (2026-09-24)** — 决策人：项目方。四项裁定见下方「决策记录」：三层划分与四条硬约束**采纳**；
成本历史**现在就加生效日区间**（与本文原建议「保持当期」相反）；归一策略**只做精确匹配 + 人工指派**
（由真实数据确定）；域命名**定为规则**、新增按规则生成。来处：`docs/plans/DOMAIN_INTEGRATION_PLAN.md` 盘点结论 +
项目方提出的方向（"能独立维护基础数据、数据间建立关联关系，各插件基于这些做统计分析和业务"）。

> ⚠️ **2026-10-22 部分被 [ADR-003](ADR-003-shop-account-physical-merge.md) 取代**（方案已拍板、代码未开工）：
> 按该裁定，`sk_shops` 不再是「凭据无关的物理身份层」，而是店铺 + 账号 + 加密凭据同居一张表。
> **C1–C4 继续有效**，凭据边界下沉到 API 层（共享只读域 `shop` 不返回密文列，明文只经 owner 域 reveal）。
> 本文下方「关键设计点」保留为当时的论证，不再代表目标表结构；§5 域改名表中的 `shop-set` 也将随之失效。

## Background

`DOMAIN_INTEGRATION_PLAN.md` 的盘点结论是：当前 6 个业务域、27 个表，**功能之间串不起来的根因不是接口不够，
而是主数据这一层不存在**——店铺在 `sk_shop_sets`（邮箱账号套装）与三处自由文本
（`oi_orders.shop` / `purchase_sources.shop` / `ae_orders.shop_name`）里是两个不同的东西；
款式有 `style_code` 编码但没有主数据；成本与汇率是覆盖式更新，历史毛利不可复算。

项目方提出的方向是对的：**让基础数据可独立维护、彼此以关联关系连接、各插件基于它做统计与业务**。
这等价于引入一层 Master Data Management（主数据层），是 ERP / 电商中台的标准分层。

但方向本身有两个相反的失败模式，都需要在动手前用规则封死：

- **左滑**：继续"哪缺就加哪个 op"→ 每个功能各自维护自己那份店铺/款式文本，漂移照旧（现状）。
- **右滑**：把所有表塞进一个统一 schema、所有插件都能读写 → 域边界消失，回到重构前的巨石，
  且 `security.ts` 的 per-plugin 授权模型失去意义。

本 ADR 的目的是把方向固化成**可执行、可守卫**的边界，避免第三种滑法。

## Decision

采纳该方向，并限定为三条不可分的约束。

### 1. 数据分层——**只有主数据需要"统一 + 独立维护"**

| 层           | 定义                                       | 当前实例                                              | 写入权                     | 物理落点      |
| ------------ | ------------------------------------------ | ----------------------------------------------------- | -------------------------- | ------------- |
| **主数据**   | 描述"业务对象是谁"、跨功能复用、生命周期长 | 店铺、店铺账号套装、企业主体、供应商、产品/款式、平台 | **单点权威写入方**（唯一） | 宿主中立层    |
| **交易数据** | 描述"发生了什么"、有时序、量大             | 订单、采购单、付款、AE 订单明细、邮件、处理队列       | 产生它的域独占             | 各业务域      |
| **派生数据** | 由前两者算出来的                           | 利润、成本快照、店铺汇总、分组统计                    | 只读（现算或物化）         | 消费侧 / 视图 |

**交易数据不上收。** 把订单、采购单也"统一"进主数据层是本方向最常见的误读——那等于重建巨石。

### 2. 四条硬约束

| #   | 约束                                                                                                                 | 反例（现状）                                                                                                               |
| --- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| C1  | **单点写入**：每个主数据实体只有一个权威写入方，其余方一律只读                                                       | `purchase-db.ts#autoSourceRows()` 从 `oi_orders.shop` 把店名拷进 `purchase_sources.shop`——同一语义字段两个写入者，必然漂移 |
| C2  | **关联用 ID，不用名字**。`shop_id` / `style_id` 是终态；文本 join 只是迁移期形态                                     | 全部关联靠 `shop` 文本，Excel 多一个空格即归成两家店且不报错                                                               |
| C3  | **主数据的 schema 与 op 挂在宿主中立层**，不挂在可卸载的 UI 岛上                                                     | 店铺账号域 key 是插件 id `'shop-accounts'`；`DB_OPS` 里 key 混用插件 id 与业务域                                           |
| C4  | **保持 per-plugin `domains` 授权模型**（`security.ts` 现状不改）。跨域靠"共享**只读**域"开口子，**不开全局只读豁免** | —                                                                                                                          |

C3 的论证：`ui-plugins/*` 是市场分发、可卸载可降级的。若某个主数据表的 schema 与迁移逻辑由它独占定义，
卸载该岛 = 所有消费方断供。这与 `extensions/`（随宿主分发）vs `ui-plugins/`（市场分发）的分工直接相关。

C4 的论证：`security.ts:113-124` 要求 `db` 能力的每个 `domain` 都必须在 `manifest.capabilities[].domains`
里显式声明，缺省不放行。消费岛各自在 manifest 里声明 `domains:["shop"]` 并发一次版本即可，安全模型零改动。
粒度**按实体切**而非合成一个万能 `master` 域：`domains` 是岛**自报**的白名单，
域越粗，声明一次拿到的面越大，越权越隐蔽（`DOMAIN_INTEGRATION_PLAN.md` §3.4 的 G4）。

### 3. 需要补的两样基础设施（一建一缓）

| 缺什么             | 现状                                                                                                                                                        | 补法                                                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **共享只读域**     | `DB_OPS`（`src/core/plugin/host.ts:53`）是 `domain → op` 闭表白名单，当前 6 个域全被单个插件独占                                                            | 加一个 key（`shop`，后续 `product`），只挂只读 op。**不用动协议、不用动 preload、不用动 IPC 契约**——已走泛化的 `db.call(domain, op, payload)`，成本仅为一个对象字面量 |
| **主数据变更通知** | `eventBus.ts` 的 `PluginEvents` 只有 3 个**生命周期**事件（state-changed / activated / deactivated），无业务数据事件 → 主数据改了消费方不知道，只能重进页面 | ⏸️ **本轮不做**（G7）：S3 的统计走**显式调用**即可满足。触发补做条件见「When to revisit」第 5 条。                                                                    |

### 4. 第一刀：以「店铺」做纵切样例

不一次上 5 个实体。按 `DOMAIN_INTEGRATION_PLAN.md` §3 的 S1–S3 先把**店铺**这一条打通：

1. **S1** 立 `sk_shops`（`platform × name` UNIQUE，含 `shop_set_id` 软关联）+ `sk_name_map`（过渡映射，存量文本不改写）
2. **S2** 宿主加共享只读域 `shop`（按实体分域，不建万能域——G4），暴露店铺身份 op（写 op 只给 owner）
3. **S3** 消费岛试点：AE 利润按店铺维度切一次，验证「主数据 + 只读共享」这套骨架（变更通知本轮不做——G7）

跑通这条纵切 = 骨架被验证，其余 4 个实体是复制粘贴。

> **关键设计点（2026-10-22 已不再成立，保留为当时的论证）：`sk_shops` 不是把 `sk_shop_sets` 搬出去，
> 而是剥离出可共享的「身份层」。**
> `sk_shop_sets` 含凭据（有独立的 `reveal` op 与 `security()`/`secureStorage` 检查）。
> 消费方需要的只是"有哪些店铺、分别属于哪个平台/账号"，**绝不需要密码**。
> 凭据继续由 owner 岛独占、不进共享域。这从安全上正面论证了"身份层必须独立成表"，
> 而不只是为了 join 方便。
>
> ⚠️ **ADR-003 推翻了"必须独立成表"这一步**：店铺与账号物理合并后，凭据与身份同表，
> 但「消费方绝不需要密码」这个结论仍然成立 —— 它改由 **API 边界**保证（共享域不返回密文列、
> 明文只走 owner 域 reveal），而不是由物理分表保证。合并的理由与代价见 ADR-003。

### 5. 能力域命名规则（Q4 —— 新增域一律按此生成）

**规则（约束 `DB_OPS` 的域 key 与各岛 `manifest.capabilities[].domains`）**

| #   | 规则                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N1  | 域标识 = **业务实体 / 能力的单数名词**，kebab-case；**禁止**用插件 id                                                                                                           |
| N2  | 一个域 = **一个权威 owner**（唯一写入方）。owner、访问模式（`rw` / `ro`）、是否属主数据层，必须在域注册表处登记                                                                 |
| N3  | 粒度**按实体切**，不按插件 / 页面切；**不建万能域**（G4）                                                                                                                       |
| N4  | 三类域各有命名形态：主数据域用实体名（`shop` / `company` / `supplier` / `product`）；交易域用业务对象名（`order` / `purchase` / `payment`）；能力域用能力名（`excel` / `mail`） |
| N5  | 新增域必须**一次性**给出 owner + 访问模式 + op 上限（≤10），避免后续为加 op 反复给消费方发版                                                                                    |
| N6  | **存量域不为改名单独发版**：在因其它原因必须发版时顺手对齐（下表）                                                                                                              |

存量对齐映射——需要改的只有 3 个：

| 现域 key                   | 归入                                                           | 何时改                       |
| -------------------------- | -------------------------------------------------------------- | ---------------------------- |
| `excel-copy`               | `excel`（能力域）                                              | 下次发版                     |
| `shop-accounts`            | 拆为 `shop-set`（账号套装·含凭据）+ `company`（企业主体）      | **优先**：与 `shop` 撞名歧义 |
| `order-insight`            | `order`                                                        | 下次发版                     |
| `purchase` / `ae` / `mail` | 已合规（`ae` 是历史混合域，后续可拆 `ae-order` + `cost-rate`） | —                            |

> ⚠️ **2026-10-22 订正**：`shop-accounts → shop-set + company` 这一行随 ADR-003 失效 ——
> `sk_shop_sets` 将被删除，不存在 `shop-set` 实体。目标域划分是：
> `shop-accounts`（owner，读写，含工具账号）/ `shop`（共享只读，店铺身份）/
> `company`（企业）。本轮**不做**域拆分（见 ADR-003 §Consequences）。

> 为什么"顺手改"成本≈0：S2 本来就要给订单归类、利润追踪、店铺账号管家各**发一次版**
> （给它们的 manifest 加 `domains:["shop"]`）。既然 manifest 要动一次，域改名就搭同一班车，
> 不需要额外的发布轮次。

## Rationale

1. **主数据是唯一值得"统一"的东西**。交易数据天然属于产生它的域，派生数据可以随时重算；
   只有主数据被多方引用且需要唯一口径——它不统一，其余所有跨域统计都会得出不同答案。
2. **约束 C1 是这套方案的成败点**。过去几轮"修好了又坏"，坏的都是多点写入同一语义字段。
   只读共享是安全的；**多写共享是灾难**——所以 C1 与 C4 必须成对出现。
3. **C2 决定了迁移必须分步**。存量数据是自由文本，一次性加 `shop_id NOT NULL` 会炸掉现有数据。
   正确路径是：映射表（零迁移）→ 渐进回填 → 加约束。终态是强关联，但中间态必须允许文本共存。
   （`DOMAIN_INTEGRATION_PLAN.md` §3.4 的 G1 建议"暂不加 `shop_id` 列"即此意——**不是不建，是后建**。）
4. **C3 + C4 让这件事不需要动安全模型**。新增共享只读域是往闭表白名单加一个 key，
   风险面极小；而若选择"给插件全局只读权限"，就会把 `security.ts` 的全部价值抵掉。

## Consequences

正面：

- 6 个现在答不出来的业务问题（见 `DOMAIN_INTEGRATION_PLAN.md` §2.3，如"这个店铺这个月赚了多少"）
  从"要跨岛拼数据"变成"一次查询"。
- 新插件接入即有数据可用：声明 `domains:["shop"]` 即可读店铺身份，不必自己抓 Excel 或读别人的凭据表。
- 统计分析从"每个插件各算一套"收为"同口径"——这是后续所有报表可信的前提。

负面（明确接受）：

- **一次性数据债务**：`sk_name_map` 会长期存在（存量文本不清洗），需要有人负责收敛映射
  （`confidence` 字段即为此设）。这是有意的过渡成本，不是设计缺陷。
- **新增一层需要守护的契约**：主数据的域命名、owner 归属、只读/可写界限必须被测试钉住，
  否则"共享域"会慢慢变成"谁都能加 op"。应加结构守卫（参考 `tests/pluginTriage.spec.ts` 的做法）。
- **域命名需要一次收敛**：`DB_OPS` 现有 key 混用了插件 id（`excel-copy`/`shop-accounts`/`order-insight`）
  与业务域（`purchase`/`ae`）。既然只有 6 个域，现在改成本最低；拖到 15 个域再改会牵动所有 manifest。

## When to revisit

出现以下任一情况时应重新评估本决策：

1. **某个主数据实体出现第二个写入方** —— 说明 C1 被突破，需立刻回退而非"加个同步逻辑"。
2. **共享只读域开始出现写 op** —— 说明只读边界失效，应拆分为独立域或收回给 owner。
3. **交易数据被要求进入共享域** —— 说明分层被误解，需重新界定该实体的层级归属。
4. 产品库（`docs/features/PRODUCT_LIBRARY.md`）落地——其 `pl_*` 表与本文的 `sk_shops`/`sk_name_map`
   应在**同一层**（主数据层），届时需合并为一份主数据清单，避免出现两套"统一"。
5. **出现"一处写入、多处需重算"的真实场景**（如店铺改名后，多个岛的历史视图需同步刷新）——
   届时再补主数据变更通知（本文 §3 的"缓"，即 `DOMAIN_INTEGRATION_PLAN.md` §3.4 的 G7）。
   在那之前，消费方靠重进页面 / 显式调用即可，不要提前引入业务事件契约。

### Q3 的数据证据（为什么模糊匹配不可选）

取真实库 `~/Library/Application Support/seller-kit/sellerkit.db`（只读）中三处店铺名的实际取值：

| 来源                    | 实际值                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| `oi_orders.shop`        | 十店(24) · 十一店(7) · 八店(3) · 六店(3) · 七店(2) · 九店(2) · `Shop1105228632 Store`(1) |
| `purchase_sources.shop` | 十店(13) · 十一店(4) · 六店(3) · 七店(1)                                                 |
| `ae_orders.shop_name`   | `Demo Store`(1, `site=ES`)                                                               |

两条独立结论：

1. **模糊匹配救不了任何一处**：运营用的店名是内部编号（"十店"），平台店名是系统生成
   （`Shop1105228632 Store`），两者字符串毫无关系。任何相似度算法都无法把"十店"对上
   `Shop1105228632 Store`——**必须人工指派一次**，自动化的空间只在于"少让人指几次"。
2. **模糊匹配必然出错（不是"可能"）**：真实数据里同时存在 `十店` 与 `十一店`、`六店`/`七店`、`八店`/`九店`。
   "十店"是"十一店"的**子串**，两两编辑距离为 1。任何基于包含 / 前缀 / 编辑距离的自动合并，都会把
   **不同的两家店并成一家**，且按现有代码风格不会报错，只表现为统计数字悄悄变错——正是本项目
   反复吃亏的"静默失效"。

⇒ 归一策略：**精确匹配（去空白 + 全半角 + 大小写）自动归入，其余进「待指派」列表人工确认**；
相似度只用于**给待指派列表排序**，永不自动写 `ref_id`。

### 顺带确认的两件事（取证）

- `sk_shop_sets` 表内**确实没有店铺名字段**（列全集：`id / email / phone / company / alipay /
ziniao_account / erp_account / platforms / status / tags / note / secret_enc / secret_keys /
created_at / updated_at / opened_at / company_id`）——印证"店铺实体不存在"这一诊断。
- 同一张表里 **`company`（文本）与 `company_id`（关联）并存**——项目**已经走过一次「文本 → ID」的迁移**。
  C2 说的"终态用 ID、过渡期文本与 ID 并存"有现成先例，S1 直接照做，不必另创模式。
