# ADR-003: 店铺与账号物理合并为一张表（凭据边界下沉到 API 层）

## Status

**Accepted + 已落地 (2026-10-22)** — 决策人：项目方。同日完成 P0–P3（`shop.main` v1 已在真库执行，
落点见 `electron/shop-db.ts`，落地记录见 `docs/notes/2026-10-30-shop-account-merge-and-status.md` 文末）。
**部分取代** ADR-002 中「`sk_shops` 必须是凭据无关的物理身份层」这一条；
ADR-002 的 C1–C4（单点写入 / 关联用 ID / 主数据挂宿主中立层 / per-plugin 域授权）**继续有效**。
来处：`docs/plans/SHOP_ACCOUNT_REDESIGN_PLAN.md`（含真库只读取证与迁移方案）。

## Background

店铺账号域当前是四张表：`sk_shop_sets`（账号套装，含凭据）、`sk_shops`（平台店铺身份）、
`sk_companies`（企业）、`sk_mail_accounts`（邮件账号，外键指向 `sk_shop_sets`）。
用户提出的四个问题都指向同一件事——**同一份信息被要求输入多次**：

1. 一个紫鸟 / ERP 登录管理多个速卖通账号，但每新增一个店铺都要重输账号密码；
2. 店铺和店铺账号本可以合并；当前只管理速卖通，一个店铺邮箱不会关联多个店铺；
3. 手机号、扣运费的支付宝和企业是配对的，应放企业；国际支付宝密码每店可不同，应留店铺；
4. 列表需要按手机号 / 企业 / 支付宝 / 紫鸟 / ERP 联动筛选。

ADR-002（2026-09-24）当时把店铺身份与账号凭据**物理拆成两张表**，理由是：
消费方只需要「有哪些店铺」，绝不需要密码，物理分离可以从结构上保证凭据不进入共享只读域。

这条理由在安全上成立，但代价是：两表可选 1:1 → 列表必须并集、行身份有两个来源、
状态与开店时间两处存储、每次新增字段都要判断住哪张表。真库现状（2026-10-22 只读取证）：

| 事实 | 数值 |
|---|---:|
| 账号套装 / 店铺 / 企业 / 邮件账号 | 16 / 9 / 3 / 3 |
| 一个账号挂多家店 | **0** |
| 不同 ERP 登录 | **1**（12 个账号共用） |
| 重复邮箱（忽略大小写） | **0** |
| 两份状态产生差异 | **0**（全部 `active`） |

项目仍在开发期，数据量小且可人工整理。项目方裁定：**表结构以简单、好维护为先**，
数据层面的历史包袱可以在开发完成后人工整理。因此重新评估 ADR-002 的物理拆分。

## Decision

### 1. 店铺与账号物理合并为一张 `sk_shops`

`sk_shops` 同时承载：店铺身份（店名 / 平台 / 平台店铺 ID / 地址 / 站点）、
账号（邮箱 / 加密凭据）、企业引用、工具账号引用、状态 / 开店时间 / 标签 / 备注。
`sk_shop_sets` 删除。

店铺与账号不再是「两表 1:1 可选」，而是**同一行的两种完成度**：

| `name` | `email` | 含义 |
|---|---|---|
| 非空 | 非空 | 店铺 + 账号齐全 |
| 非空 | 空 | 只有店铺，账号待补 |
| 空 | 非空 | 只有账号，店铺待建 |
| 空 | 空 | 非法（`CHECK` + 写入函数双重拦截） |

「空态」用空字符串表达，**不引入哨兵值**（如 `name_key = '~account:12'`）。
空值不参与唯一性：店铺名与邮箱都改用**部分唯一索引**（`WHERE trim(...) <> ''`）。
老表的表级 `UNIQUE(platform, name_key)` 因此必须去掉，SQLite 只能重建表。

### 2. 工具账号独立成表 `sk_tool_accounts`

紫鸟 / ERP 是**登录**，不是店铺的属性：一个登录管多个速卖通账号，一条登录只有一份密码。
店铺行只存 `ziniao_account_id` / `erp_account_id`。删除被引用的工具账号时拒绝并显示引用数。
不做「每个店铺覆盖工具密码」——用户描述的现状与需求里都没有这个能力。

### 3. 手机号与支付宝归企业，国际支付宝密码归店铺

- `sk_companies.contact_phone` 复用为手机号，新增 `alipay_account`；
- 店铺侧只读展示企业手机号 / 支付宝，修改入口跳企业页；
- `alipayPwd`（国际支付宝密码）留在店铺行的加密字段，因为每店可不同。

### 4. 邮件账号外键改指 `sk_shops`

`sk_mail_accounts.shop_set_id` → `shop_id`，外键目标 `sk_shop_sets(id)` → `sk_shops(id)`，
保留唯一约束与 `ON DELETE CASCADE`。
**必须重建邮件表**：SQLite 的 `RENAME COLUMN` 只改列名，不会把外键目标从旧表改到新表。

### 5. 凭据边界从「物理分表」下沉到「API 层」

这是本 ADR 与 ADR-002 的核心分歧，也是必须写死的补偿约束：

- `sk_shops` 里确实有 `secret_enc` / `secret_keys`，但**共享只读域 `shop` 永不返回这两列**；
  查询必须使用显式列清单（`COLS`），禁止 `SELECT *`；
- 明文只经 owner 域 `shop-accounts` 的 reveal 操作按需返回，且继续受 `safeStorage` 加密与权限门约束；
- 消费方（拣货 / 统计 / 商品采集）仍只拿到「有哪些店铺」，拿不到任何密码；
- 守卫落在契约层：`tests/pluginTriage.spec.ts` 继续钉住共享只读 op 清单，
  新增的 op 不得进入 `DB_OPS.shop`；任何让 `shop` 域返回 `secret_enc` 的改动视为越界。

**接受的残余风险**：能直接读 SQLite 文件的代码（主进程内的新模块）理论上能拿到密文。
这与合并前一致（密文原本也在同一个库文件里），区别只是同一张表内相邻列。
缓解是显式列清单 + 共享域 op 白名单，而不是再加一张表。

### 6. 状态词表收敛为 `active / archived`

账号侧原来的 `paused / banned / closed` 与店铺侧 `active / archived` 是同一件事的两套说法；
真库全部为 `active`。统一为 `active / archived`，停用原因写备注。
不做软删除框架：有下游引用（商品 / 映射）的店铺只能停用，不能删除。

## Rationale

1. **开发期优先消除结构性复杂度**。两表 1:1 可选带来的并集查询、双行身份、双状态存储、
   「这次编辑要不要建档案」的判断，都是永久成本；重建两张表是一次性成本。
2. **用户的真实模型就是一店一账号**。真库「一个账号挂多家店 = 0」，再造多对多能力没有收益。
3. **共享只读域的安全性本来就不依赖表结构**。ADR-002 的 C4 是 per-plugin `domains` 授权，
   凭据安全由「共享域不暴露 reveal / 不返回密文列」保证；物理分表只是第二道防线，不是唯一防线。
4. **工具账号与企业是真正需要独立生命周期的主数据**，把它们留在独立表里收益明确；
   而店铺与账号没有各自独立的生命周期，拆开只会制造同步问题。

## Consequences

正面：

- 一张表、一个列表、一个编辑器、一次保存；没有 join、没有并集、没有双身份。
- 新增字段只改一张表；「补建店铺」「补账号」都是更新同一行，不需要重输另一侧信息。
- 紫鸟 / ERP 改密码只改一处；手机号 / 支付宝改一次全店铺同步。
- 店铺 id 1–9 原样保留，`pl_shop_sku` / `pl_shop_items` / `sk_name_map` 的引用不断。

负面（明确接受）：

- **一次性破坏性迁移**：重建 `sk_shops` 与 `sk_mail_accounts`，删 `sk_shop_sets`。
  SQLite 没有 SQL 级回滚，唯一退路是迁移前的 `VACUUM INTO` 备份。
- **凭据与身份同表**：所有读 `sk_shops` 的代码都必须使用显式列清单；
  一次 `SELECT *` 就可能把密文带进共享域。这条只能靠代码审查与契约守卫。
- **ADR-002 §5 的域改名行失效**：`shop-accounts → shop-set + company` 中的 `shop-set` 不再存在。
  本轮不拆域：`shop-accounts` 仍是 owner 域，`shop` 仍是共享只读域，`company` 独立域。
- **迁移期两套形状并存**：先补旧列、再重建，迁移代码必须同时理解新旧形状；
  迁移完成后旧列与旧表必须彻底消失，不能留下「兼容双读」。

## Alternatives considered

| 方案 | 为什么不做 |
|---|---|
| 逻辑合并（保留两张表，视图/查询层合并） | 列表要 `FULL OUTER JOIN`，行身份分「档案 id / 店铺 id」，状态两处、新建要判断 `profileTouched` —— 复杂度永久存在，只是从表挪到了代码 |
| 保留 `sk_shop_sets`，只把手机号 / 支付宝挪走 | 用户的第一个痛点（重复输紫鸟 / ERP）能解，但「店铺和账号合并」这条没解；两套列表与两套写入仍在 |
| 给空店名造哨兵 `name_key` | 派生键变成身份键，搜索 / 归一 / 导出都会碰到假值；以后补建店铺还要清洗。重建表是一次性成本，哨兵是永久债 |
| 做软删除 / 多平台 / 每店工具密码 | 当前无真实需求；真库平台只有一个值、每店工具密码不存在。等出现第二个真实场景再评估 |
| 继续 ADR-002 的物理分离，只加工具账号表 | 能解第 1、3 条，但第 2 条（合并）与「一个列表 / 一个表单」的目标无法达成，双表同步问题保留 |

## When to revisit

出现以下任一情况时重新评估：

1. **店铺需要管理第二个平台**（如 Temu / Shopee）—— 一店一账号的假设不再成立，
   需要重新设计账号与店铺的基数，而不是简单加一个平台下拉。
2. **需要按店铺覆盖工具账号密码**（同一 ERP 登录下不同店铺用不同密码）——
   说明「一条登录一份密码」的模型不够，需要在店铺行加覆盖字段。
3. **共享只读域开始需要凭据相关字段**（如「是否已配置邮箱授权码」之外的密文信息）——
   说明 API 边界失效，应拆回独立表或增加单独的只读安全域。
4. **店铺量级进入需要分页 / 虚拟滚动的规模**（当前 19 行）—— 需要重新评估列表查询与索引。
5. **企业 / 工具账号需要历史版本**（换绑要保留历史）—— 当前只存当前引用，历史需求出现时再加区间表。
