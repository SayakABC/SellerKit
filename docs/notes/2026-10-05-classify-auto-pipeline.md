# 订单归类的三层链路：确定性 / 指纹 / 模型各管什么，以及四个已取证的缺口

> 日期：2026-10-05 深夜 · 触发：用户要求删掉「归类核对」的「识别未归类」批量按钮，并问
> 「怎么做才能更方便归类 / 自动识别品类、颜色和 logo」⇒ 先盘点现状再谈方案。
> 涉及：`electron/order-db.ts` / `electron/product-db.ts` / `src/lib/orderClassifier.ts` /
> `src/lib/styleMatcher.ts` / `src/core/ai/openaiCompatible.ts` / `src/modules/today/classify.ts`。

## 结论先行

**归类的正确顺序是「映射 → 指纹 → 模型」，而前两层已经建好了。**
现在的问题**不是模型不够强，而是人工核对的结果没有回流到确定性层** ⇒ 同一件商品的订单在被
一条条重新判断，而本该"配一次、此后全自动"的那张表一直是空的。

> **2026-10-05 深夜补记：缺口 ①（回流）已实现**，见下面 §二 的即时更新与
> `docs/features/PRODUCT_LIBRARY.md` §3.5.1（为什么只写不覆盖 / 颜色只填不猜 / 失败不外抛）。
> **②③ 两个缺口仍在**（颜色口径两头打架、品类白名单未命中静默保留原词），
> 而 ④（`confidence` 无消费者）与"`logo` 不进指纹且无下游"**在回流落地后依然不是瓶颈**
> —— 回流把绝大多数重复订单从"每次都判"变成"配一次"，在这之后 `confidence` 才有意义（用来决定**哪些**要给人看）。
>
> **2026-10-05 深夜续二：②③ 已治**（颜色口径收成一份 + 品类的"未命中"不再静默），见 §六。
> ④（`confidence`）与 `logo` 仍排最后，理由不变。**另有一条重要的口径提醒**：②③ 改的是
> **L2 的归一口径**，而 L2 今天仍无入口 ⇒ 这两条修的是"等 L2 回来时它是对的"，**不是**今天的收益；
> 今天真实的收益来自同一轮里给核对页加的**输入建议词表**（让同一个词别各写各的）。

## 一、三层链路（现状，均已取证）

| 层 | 机制 | 落点 | 触发时机 |
| --- | --- | --- | --- |
| **L0 确定性** | 商品ID → 款 + 色（`pl_shop_sku`，只认 `status='confirmed'`） | `resolveOrderSku` → `autoAssignByMap` | **写时**：订单落库那一刻（`order-db.ts:1062` 附近） |
| **L0 回填** | 配完映射回头补存量未归款的订单 | `reassignOrdersByItemIds`（`order-db.ts:1117` 附近） | 映射写入成功后自动跑 |
| **L1 指纹** | `category + features` 归一化后算指纹；人工"点名某款"会把该指纹**记入该款** | `buildStyleFingerprint`（`styleMatcher.ts:33`）+ `oi_style_fingerprints` 表 | 识别落库 / 人工保存时 |
| **L2 模型** | VLM 出 `category / features / color / logo / style_name` → 归一化 | `createVisionEngine` → `classifyResult`（`orderClassifier.ts` 末尾） | 只在被调用时（现无入口） |

**L0 已升到「款 + 色」级**（颜色存 `pl_shop_sku.spec`），背景见
[商品ID 映射带上颜色](2026-10-05-mapping-carries-color.md) —— 也就是说**"品类 + 颜色"对已配映射的
商品早已是确定性的、零模型调用的**；模型真正要负责的只是"没配过映射的商品"。

## 二、缺口（四个，都有取证）

### 1. ⭐ 人工核对**不回填** L0 —— 这是最大的杠杆 —— ✅ **已实现（2026-10-05 深夜）**

归类核对页保存时走 `orderUpdate(reclassify)` + `orderStyleAssign`（`classify.ts:149` 起），
写的是**指纹 → 款**；它**从不写 `productSkuMap`**。而 `productSkuMap` 的渲染层调用方只有
「货与成本」的 `src/modules/goods/api.ts`。

> ⚠️ **2026-10-11 修掉的坑（读本节前必看）**：`saveCorrection` 原先是 `if (named && fingerprint)` ——
> **点名了款、但指纹是空串时不挂款**。而 `buildStyleFingerprint(category, features)` 在两者都空时返回
> `''`（`filter(Boolean)` 把空项筛掉），生产数据恰是这个形状（真库 `oi_orders.category` 非空 **0/23 行**、
> `oi_images.result_json` 全 `null` ⇒ VLM 从没跑过）⇒ **整条挂款 / 颜色记忆 / 回流一次都不跑**，
> 而界面一切正常、`toast` 还说"已保存"。现已是 `if (named)`（宿主 `assignOrderStyle` 的
> `fingerprint` 本来就是可选参数 —— 拦住它的是渲染层自己那道门）。详见
> [`2026-10-11-classify-color-not-effective.md`](2026-10-11-classify-color-not-effective.md)。

后果：用户在核对页把某商品判对了 10 次，第 11 条订单照样进待核对队列 ——
**人工工作量不随时间递减**，而这正是"更方便归类"要解的那件事。

佐证量级：真实库上 42 行订单的商品ID **去重后只有 17 个**
（见 [差距审查要读真库](2026-10-05-gap-audit-read-the-real-db.md)）⇒ 17 条映射即可覆盖绝大多数行。

**落点（实现后回填本节的"文件层"）**：`electron/order-db.ts` 的 `skuBackfillFromOrder()`
（在 `assignOrderStyle` 的**事务外**调用，回执并入 `order-style-assign` 的返回）+
`product-db.ts` 新暴露的 `resolveShopRef()` / `productIdByCode()`；界面侧 `classify.ts` 把
`skuBackfill` 透出来、`ClassifyPanel.vue` 用一句提示把"记住了"说出来。
**行为边界与理由见 `docs/features/PRODUCT_LIBRARY.md` §3.5.1**（只写不覆盖 / 颜色只填不猜 /
失败不外抛 / 只改品类·颜色的那次不触发）。守卫：`npm run product:sku:smoke` 的 8 条回流用例
（逐条做过变异确认会变红）+ `npm run today:ui` 的 3 条（含一条**反向**断言）。
⚠️ 踩到的一个假绿：提示断言**不能**在"通道被调用"那一刻取 DOM —— 假桥是同步记录调用的，
而那时刻 toast 还没进 DOM，反向断言会因此在"没渲染"与"没有那句话"之间恒绿。

### 2. 颜色口径**两头打架**（prompt 要描述式，归一化要字典式）—— ✅ **已治（2026-10-05 深夜续二，见 §六）**

- prompt 要的是"底色 + 花色"描述，示例 `藏蓝底白色条纹`（当时在 `openaiCompatible.ts` 的
  `VISION_PROMPT`，现已搬到 `visionPrompt.ts`）；
- 归一化是**整串精确字典匹配**：`COLOR_SYNONYMS[t] || t`（`orderClassifier.ts` 的 `normalizeColor`）。
  ⚠️ 下面几处只写**函数名**不写行号：本文件在 2026-10-05 续二里改过，行号会漂。

⇒ 凡是模型按 prompt 输出的描述式颜色，**一律原样穿透**（既没归并、也没报错），
`oi_style_colors` 会随措辞长出无穷款色。

### 3. 品类白名单**未命中就静默保留原词** —— ✅ **已治（2026-10-05 深夜续二，见 §六）**

`normalizeCategory` 的 `return exact || t` —— 白名单外的新词**不告警、不标记**，直接成为新指纹 ⇒
同款拆成多款（而这一层的代价很贵：拆了之后 L0 的款编码也跟着分叉）。同理 `features` 完全自由生成，
"字母印花 / 印花字母 / 字母图案"三种措辞 = 三个指纹。

### 4. `confidence` 解析了但**没有任何消费者**

`RecognitionResult.confidence` 有产出（`openaiCompatible.ts` 的 `analyze()` 里 `Math.min(1, ...)`），全仓 `grep confidence` 找不到
读取方 ⇒ 差得离谱的结果与稳稳正确的结果走**同一条落库路径**。

### 附带两条（不属于"识别质量"，但同属这条链路）

- **`logo` 不进指纹**（`buildStyleFingerprint(category, features)` 只有两个入参），
  且**全仓没有任何展示或下游消费者** —— 它只存在于订单表、能被搜索、在归类核对页可编辑；
  导入时恒写空串（`importSheet.ts:180`）⇒ logo 当前唯一来源就是识别/人工。
  **含义：把力气花在提升 logo 识别上，今天几乎换不来任何收益**，除非先给它一个下游用途。
- **免图订单拿不到 L0**：`autoAssignByMap` 第一行 `if (!rec.imageId) return;`
  （理由正当：归款的落点是把**图片**挂到款色上），而免图导入是被支持的 ⇒ 这类订单只能靠指纹或人工。

## 三、还有一件现成的、但闲置的东西

`oi_queue`（待识别队列：`batch_no` / `status` / `fail_count` / 断点续跑）**整套还在维护**：
10 个 IPC 通道（`src/types.ts`）、数据层（`order-db.ts` 队列段）、`order-db-smoke` 的队列用例 ——
但**渲染层零调用方**（原岛下架后没有任何页面用它）。

⇒ **要做"导入时后台识别"，队列不用重写**；若最终不做，它就与 `readEngine`/`recognizeOrder` 一样
属于"要么给个归期、要么删掉"的待办。

## 四、待拍板

识别入口的形态（导入时后台跑 / 逐行「识这张图」/ 只出建议不落库）与上面四个缺口的取舍
**尚未拍板** —— 本条只记录现状与取证，方案落地后另开一条并注明取代关系。

**2026-10-05 深夜补充（① 落地之后）**：单域 op 预算与"哪些该做"的判断没变，但**优先级变了** ——
① 回流已经把"同一件商品的重复订单"从每次判断降成配一次，剩下的省力空间在**界面操作本身**：
按商品分组的批量确认（一次把同商品的多行一起确认）、键盘流逐行核对。
这两条**都不碰识别链路**，能立刻减少点击量；② 与 ③（颜色口径 / 品类白名单）属于"减少拆款"，
在回流之后才值得投入（款已经能稳定复用了，措辞漂移的代价才显出来）。
`confidence` 与 `logo` 仍然排在最后：它们的前置条件（有消费者 / 有下游用途）都还不存在。

> **2026-10-05 深夜续：上面这两条界面省力已落地**，见下方 §五。

## 五、界面省力（2026-10-05 深夜 已落地）

回流解决的是"同一件商品不必反复判断"，但它不解决**界面上看不出来**这件事：
一页 30 行里哪几行是同一个商品、定完这一条会不会顺带把别的也解决，原来全靠用户自己记。
本轮把这两件补上（**纯界面层，一行都没碰识别链路**）：

1. **「同商品」徽标 + 本页商品数**
   - `OrderRecord.itemId` 由**主进程**从 `raw_fields` 推出（`mapOrderRow` 调 `extractSkuFields`
     —— 与回流写映射**同一个函数**）。刻意**不让渲染层自己正则匹配**：两处各写一套列名族，
     就会出现"徽标说同商品、回流却按另一个键记"（本仓最忌的两块口径打架）。
   - 行上标「同商品 ×N」（只在 N>1 时出现）；指标条多一格「本页 N 个商品」——
     这一格才是**真正要做多少决定**的量（30 行可能只有 12 个商品）。
     没有商品ID 的报表（免图导入）整格**不显示**：显示「0 个商品」会被读成坏了，
     而事实是这份数据没有这个维度。
   - ⚠️ 已知**欠算**：分组键用店铺**原文**，而回流用归一后的店铺实体 ⇒ 同一家店写法不同
     （多一个空格 / 全角括号）时会少算。刻意不修（要修就得把店铺归一下沉到渲染层，
     必与 `sk_name_map` 分叉）：徽标是**提示**不是承诺，少算只会让人多核对一次，
     不会把两件商品混成一件。
2. **键盘流**：行内按回车＝保存这一行，焦点自动交给**顶上来的**那一条。
   保存会把该单置为已核对（`updateOrder` 里 `corrected = 1`）⇒ 它离开待核对列表、
   后面的行整体上移一位，所以"下一条"在取数之后**正好落在同一下标**上。
   （钉在订单 id 上会找不到元素，症状是"焦点丢了"，很难查。）

### 这一轮的守卫踩点（两条，都值得记住）

- **徽标必须三种情况各占一行夹具**（同商品 / 商品只此一行 / 没有商品ID）。
  只放前两种，"凡有商品ID 就标"这种错法照样全绿（实测变异就是这么写的）；
  只放后一种，"徽标恒显示"照样全绿。
- **焦点断言必须先把夹具对齐宿主的"已核对即离表"**：列表不缩水时，焦点"回到第 N 行"
  永远成立，根本分不出"往下走了一格"和"原地没动"。本轮为此给假桥加了
  `__emulateCorrected` 开关，**默认关**（本页前半段的断言要反复操作同一行，
  列表中途开始缩水那些断言就没法写），到键盘流那一段才打开 ——
  变异 `focusRowIdx: idx → idx + 1` 在那之后当场变红。
- **主进程侧的口径只能由数据层冒烟守**（`npm run order:smoke`）：假桥里的 `itemId` 是**夹具给的**，
  宿主忘了 select `raw_fields` 时 `today:ui` 照样全绿（夹具"太干净"把真实缺陷盖住了）。

## 六、②③ 的口径收成一份 + 核对页能选（2026-10-05 深夜续二 已落地）

### 6.1 颜色：两头对齐，而不是把宽的那头砍掉

原状：prompt 要「底色+花色」的描述（示例 `藏蓝底白色条纹`），归一化做**整串**字典精确匹配 ⇒
描述式**原样穿透**，同一个颜色两次措辞不同就成两个款色。

修法是**两头都动**（只动一头必留缝）：

| 头 | 改法 |
| --- | --- |
| 提示词 | `color` 字段改为**注入** `COLOR_WHITELIST`（枚举），并明确"分不清主次的多色选`印花`；确要表达配色按 `底色+花色` 写且**底色在前**" |
| 归一化 | `normalizeColor` 升级为 **字典 → 词表 → 描述式解析 → 原样保留**：按 `+ / 、 底 配 带 和 与` 分段，逐段做"整段精确 + **最长前缀回退**"，取**第一个**认得出的段（即底色） |

三条刻意的取舍：

1. **词表由字典的值域派生**（`[...new Set(Object.values(COLOR_SYNONYMS))]`）而不是手写一份 ——
   手写必然出现"字典能归一成 A、词表里没有 A"，那正是同一个病换个地方复发。
2. **不做"任意位置"扫描**：`灰蓝色` 判成 `灰色`（主色在前），不是 `蓝色`。扫任意位置等于全靠猜。
3. **认不出仍原样保留**：颜色是款色（SKU 级）的维度，**错并**（两色合一色）比**拆**（一色成两色）
   更难发现、更难回退 —— 宁可拆。

### 6.2 品类：不强行合并，但**不再静默**

`normalizeCategory` 的 `return exact || t` 保持不变（品类是**指纹第一段**，错并比拆贵得多）。
"静默"由**两条可见的路**治掉：

- `CATEGORY_WHITELIST` 现在**直接注入** `VISION_PROMPT`（模型只会从里面选，不再有"第二份列表"）；
- 核对页的品类输入挂 **datalist 建议 = 标准词表 + 本库已用过的写法** ⇒ 用户看得见系统里已经有哪些写法，
  第二次遇到同一个词时**选中同一个**，自己不声不响地收敛。
  ⚠️ 刻意**不把用户输入悄悄改写成词表里的词**：那才是真正的"静默改判"，比写得不一致更难查。
  词表里覆盖不到的现实品类（帽子 / 汉服 / 围巾）就靠"库内写法"这一半收敛。

建议列表里**排除了「其他」**：它在 `EMPTY_LIKE` 里属空值语义（归一化后是空串、不进指纹），
把它列成可选值等于教用户选一个会被清空的词。

### 6.3 ⚠️ 一条通用约束：提示词必须住在**纯模块**里才能被单测

`VISION_PROMPT` 原在 `src/core/ai/openaiCompatible.ts`，而那个文件 `import '@/core/network/request'`
→ `src/core/services/ipc.ts` **顶层就求值 `window.electronAPI`** ⇒ **node 环境的 vitest 一 import 就抛**。
于是"提示词的枚举必须与归一化词表同源"这条不变量只能退化成"扫源码文本"（模式写歪就恒绿）。

现在提示词在 `src/core/ai/visionPrompt.ts`（只依赖 `@/lib/orderClassifier` 这个纯函数），
`tests/visionPrompt.spec.ts` 可以直接断言 `VISION_PROMPT` 里含的正是 `COLOR_WHITELIST.join('|')` 的结果。
**别把它挪回 `openaiCompatible.ts`。**

### 6.4 守卫与变异（逐条确认会变红后复原）

- 新增 `tests/visionPrompt.spec.ts`：品类枚举注入 / **颜色枚举注入** / 自证非空转（`join('|')` 长度下限）/
  多色写法与解析规则成对。
- `tests/orderClassifier.spec.ts`：描述式各分支（`底` / `+` / `、` / 斜杠 / 前缀回退 / 不扫任意位置 /
  认不出原样保留）+ 词表自洽（每一项都能被自身归一命中）。
- `today:ui` 131 → **135**：品类建议"list 指向的 datalist 存在且非空"、内容含词表与库内两半、
  **不**推荐「其他」、颜色同理。
- 变异 4 组：提示词颜色枚举换成字面量（`visionPrompt.spec` 红）· 摘掉前缀回退（描述式用例红）·
  建议只留词表（"帽子"那条红）· `list` 属性写歪（"datalist 存在"那条红，且颜色那条**仍绿** ——
  证明两条断言各自独立，不是一条恒真的合并断言）。

## 七、跨域关联：订单 ↔ 产品 ↔ 拿货（2026-10-05 深夜续三，**只查未改**）

起因是一句提问："今天里的归类统计跟货与成本有关联上吗？导入的商品ID 会关联产品吗？
最终能不能按产品来归类统计去拿货？" 三个都答"能"，但**各自的成立条件不同**，混起来会记错账。

### 7.1 ⭐ 唯一的关联锚点是 `code`，且两域**共享同一个编号空间**

- `oi_styles.code` 与 `pl_products.code` 是**同一个 `STYLE-xxx` 序号池**。这不是巧合：
  `order-db.nextStyleCode()` 用 `SELECT code FROM oi_styles UNION SELECT code FROM pl_products` 取 max+1，
  代码注释写明了不这么做的后果 —— "只查前者会让 `STYLE-005` 被产品库先占用、又发给下一款识别 ⇒ 撞
  `pl_products` 的唯一键（表现为「识别建款失败」，报错却指向产品库，**方向全反**）"。
- `product-db` 侧注释亦明说「code / name 不可批量改：**编码是跨域关联锚点**」。
- `resolveStyle()` 新建款时**同时** `adoptProduct({ code, name })` 同步进产品库（D1 之后展示名唯一权威在
  `pl_products`，`oi_styles` 只留 `code` + `fingerprint`）。
- **三处 join 早已存在**：`pickingRows`（拣货）、`shippingRows`（算钱）、`listStyles`（今天页的识别库款列表）
  都是 `LEFT JOIN pl_products p ON p.code = s.code`；唯一实现是 `styleNameJoin()`（缺表时降级为空串）。

⇒ 所以"关联"这件事在**数据层早就做了**，不需要新建外键。谁要改这三处 join，先看 `styleNameJoin`。

### 7.2 三个问题各自的答案

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 「今天」的归类统计关联上货与成本了吗 | **数据层已通，统计口径没通** | 款列表 join 产品库拿名字；但核对页三个数（待核对 / 未归类 / 识别库 N 款）全按 `oi_*` 算，**没有一个是产品/供应商维度** |
| 导入的商品ID 会关联产品吗 | **会**（三个前提同时成立才关联） | `autoAssignByMap` = 有图 ∧ raw_fields 有商品ID ∧ `pl_shop_sku` 有 `confirmed` 映射 |
| 能按产品统计去拿货吗 | **数据上已经通了，拿货单也已是这个形态** | `pickingRows` 按款色码汇总、供应商经 `pl_products.supplier_id` 带出；缺的只是"今天这边能按产品看" |

### 7.3 ⚠️ 结构性缺口：订单挂款挂在**图片**上，不在订单上

`oi_orders` **没有 style 列**；归属是 `o.image_id → oi_images.style_color_id → oi_style_colors.style_id → oi_styles.code`。
于是订单→款有**两条路径**：

- **路径 A（主图）**：识别 / 人工核对走这条。`autoAssignByMap` 首行 `if (!rec.imageId) return;` ⇒
  **免图订单永远进不了产品维度**（这就是 §二 附带那条"免图订单拿不到 L0"的实际后果）。
- **路径 B（商品ID 映射）**：`(店铺, 商品ID) → pl_shop_sku → pl_products.code`，**不需要图**。

⇒ 要"按产品统计去拿货"，正路是**路径 B**，也因此 §2.1 的回流（把核对结论写回 `pl_shop_sku`）价值最大 ——
它同时把路径 A 的结论**沉淀成路径 B 的输入**。

### 7.4 真库现状（2026-10-05 夜，`~/Library/Application Support/seller-kit/sellerkit.db`）

| 观察 | 值 |
| --- | --- |
| `oi_orders` | 9 行，**全部有图**（9 张 `oi_images`），**全部有可识别商品ID** |
| 商品ID 的键名 | 是 `"产品ID":"1005012742360018"`，命中 `ITEM_ID_KEYS` 的 `/产品\s*ID/i` |
| 店铺 | 6 家（十/十一/六/七/八/九店）**全部已归一**（`sk_name_map.ref_id > 0`，`platform='ae'`） |
| `pl_shop_sku` | **0 行** ⇒ 已挂款色的图 **0** 张、`oi_styles` **0** 款 |
| `pl_products` | **27** 个（`STYLE-002`…`STYLE-029`，name 是「虎头袄」「连帽拉链外套」这类**款式名**） |

⇒ **三个前提全部满足，唯一缺的就是"配映射"这一步**（人工没去配，而回流才刚落地上线）。
配一条 `(店铺, 商品ID) → 产品`，路径 B 立刻通 —— 这比"提升识别准确率"见效快得多。

### 7.5 会不会"按产品统计"永远少算

**会，两处**：① 免图订单（路径 A 的硬限制，见 7.3）；② 「同商品」徽标的分组键用的是店铺**原文**、回流用归一后的
店铺实体 ⇒ 同一家店写法不同会**少算**（刻意不修：修就得把店铺归一下沉到渲染层，必与 `sk_name_map` 分叉）。
两处都只会**少算**、不会把两件商品混成一件 —— 这个方向是刻意的（少算只是多核对一次，错并要回溯全部历史）。

## 八、核对页的**产品维度**指标条（2026-10-05 深夜续四，已落地 —— **2026-10-10 已整条拆除**）

> ⚠️ **本章所述的东西已于 2026-10-10 全部拆除**：用户对页头那排「待核对 / 未归类 / 识别库 / 已配产品」
> 指标条的原话是「我看不太懂，用户肯定也会很懵」⇒ 整条撤掉，连带 `orderSkuRollup` 通道退场
> （`electron/product-db.ts` 的 `resolveOrderSkuRollup` / `MAX_ROLLUP_ROWS` / `OrderSkuRollup`、
> `order-handlers.ts` 的 `order-sku-rollup`、preload 暴露键、`src/types.ts` 与 `src/core/services/ipc.ts`
> 的声明、两处冒烟里的断言）。**下面这一章保留作历史记录**，它记录的判断（口径与归款同源、
> 三种状态分开、守卫分三段）在别处仍然成立；但其中提到的 `cl-metric-product` 三态、
> `today:ui` 的四条断言、`ipc:shape:smoke` 的 §⑥ **都已不存在**，别再照它去改代码。
> 拆除的判据与替代守卫见 [`2026-10-10-classify-panel-rework.md`](2026-10-10-classify-panel-rework.md) §二。

§7.4 的结论是"只差配映射这一步"，而**配映射的收益在界面上看不见** —— 于是本轮给「归类核对」
（发货台第 2 步）的指标条补一格产品维度。这一格不是"再放一个数字"，它的作用是**让配映射的收益显形**：
配一条，(店铺, 商品ID) 的后续订单就直接归类、不再进这一页。

```
待核对 9 | 未归类 9 | 识别库 0 款 | 本页 9 个商品 | 已配产品 0 个 · 供应商 0 家（本页商品还没配映射）
```

### 8.1 口径：与归款**同一份**匹配规则，不新写一套

调用方（核对页）手上只有**订单行原文**（`shop` 是报表里的店名），所以入参是 `{shop, itemId}[]`，
归一与匹配全在主进程：

| 步骤 | 复用的东西 |
| --- | --- |
| 店铺原文 → (店铺 id, 平台) | `resolveShopRef` —— 与落库（`autoAssignByMap`）、回流（`skuBackfillFromOrder`）、待关联队列**同一份**规则 |
| (平台, 店铺 id, 商品ID) → 产品 | `resolveSkuBatch`（一次算完一批）—— 只认 `status='confirmed'` 的**映射行** |

**刻意不认跨店池行**（`source='shop-import'` / `shop_id=0`）：那与归款同口径（`skuMappingSql()` 的补集）。
两处若不一致，症状是"核对页说这一页配了 3 个产品、真去拿货只有 2 个"。

另外两条跳过规则都朝**少算**方向，且与 `resolveOrderSku` 对齐：

- 店铺没归一 / 没有商品ID ⇒ 这一行**无从查起**（不是"没配上"）；
- 映射指向的产品**已删**（悬空指针）⇒ 按未命中。

`supplier_id = 0`（还没关联厂家）**不计家数** —— 把它算成"一家供应商"会让这个数虚高。

### 8.2 三种状态必须长得不一样（这一格最容易做成"恒显示 0"）

| 状态 | 显示 | 为什么 |
| --- | --- | --- |
| 有商品ID、一个都没配上 | `已配产品 0 个 · 供应商 0 家` + **（本页商品还没配映射）** | `0` 是一个**待办**，必须说清缘故；单看会读成"数据坏了" |
| 没取到（通道不可用 / 产品域未建） | **整格不显示** | "没取到"≠"一件都没配"，两者下一步动作完全不同 |
| 这份报表**没有商品ID 列** | **整格不显示**（与「本页 N 个商品」同规则） | 这个维度本就不存在，显示 `0` 会被读成坏了 |

⇒ 渲染层用 `null` 表示"没取到"、用 `{products: 0}` 表示"查过了、没有"，**刻意不合并**。
它也**不拦页面**：产品维度是附加信息，取数失败时核对列表照常可用。

### 8.3 守卫分三段（一段都省不掉）

| 层 | 守什么 | 在哪 |
| --- | --- | --- |
| 数据层 | 口径本身：去重 / 未归一 / 悬空产品 / 供应商去重 / 池行不算 | `product:sku:smoke`（+6 项） |
| preload 载荷 | 渲染层的**裸数组** → `{rows}` 的包装真的过到主进程 | `ipc:shape:smoke`（+3 项） |
| 界面 | 请求带哪些键、格子画的是宿主回来的数、三种状态各长什么样 | `today:ui`（+4 项） |

⚠️ **假桥看到的是裸数组**（假桥替的是 preload **上面**那一层）⇒ "包装对不对"在界面冒烟里**根本测不到**，
只能由 `ipc:shape:smoke` 端到端对穿。这条正是 2026-10-04 那次「成功但空」的同族风险
（详见 `2026-10-04-preload-payload-shape.md`）。

### 8.4 变异（7 组，逐组确认变红后复原）

| 变异 | 变红的那条 |
| --- | --- |
| preload 键名 `rows` → `items` | `ipc:shape:smoke` §⑥ 两条（症状：`success=true` 而 `products=0`） |
| `supplier_id = 0` 也算一家 | 「未关联厂家不算一家」 |

### 8.5 已知边界

本页若把同一件商品拆成两种店铺写法（多一个空格 / 零宽字符），店铺原文去重算两次、`resolveShopRef`
都命中同一家店 ⇒ **产品/供应商仍各只算一次**（这两个数是**产品级**的）。分子分母不在这里暴露，
所以不会出现"本页 2 个商品、3 个已配"这种自相矛盾的读数。
