# 「今天」升级为发货台：六步收进一页多页签（不跳页）

> **一句话**：把「导入 → 归类 → 拣货 → 算钱 → 拿货 → 对账」六步从"点一步跳一个模块"
> 改成**同一页的七个页签**，点击就地切换（懒加载 + 保活），人不再被弹出当前页。
> 落点 `src/modules/today/**`，**零迁移 / 零新 IPC / 零能力域 / 岛不发版**。
>
> 触发（用户原话）：「将每日发货流程中的每一步都挪到宿主中，可以在一个页面中的多个tab中，
> 避免点击后跳转到其他页面，丝滑操作」。拍板两项：**扩「今天」**（导航不增项）、**六步全内建**。

---

## 1. 为什么是"页签"而不是"跳转"—— 先说清代价

旧形态（S2 落地的四步流程卡）点一步 = `switchModule(id)`：模块被卸载、下一个挂载，
中间状态（表单、已生成的清单、滚动位置）**全丢**，回来还得再点一次导航。
一天几十单的重复操作里，这个代价是实打实的。

`AppShell.vue` 的工作区是单个 `<component :is="activeView" v-if="activeView" />`，
**没有 `KeepAlive`** —— 这是"切模块就重建"的根因。本次**没有动外壳**（那是全局行为，
影响所有模块），而是在「今天」页**内部**建页签系统：`defineAsyncComponent` + `<KeepAlive>`。
好处是影响面可控、可单独回退；代价是"只有今天页有这待遇"（见 §6 的后续）。

## 2. 四条设计决定（都有"不然会怎样"）

| 决定 | 不然会怎样 |
| --- | --- |
| **点步骤走 `go(tabId)`，不走 `switchModule`** | 只是"看起来没跳"——`switchModule` 一旦派发，外壳照样把本页卸掉重挂 |
| **懒挂载**：`defineAsyncComponent`，第一次点才 import | 七个页签里两个是上千行的整页视图（各自进页就取数），全量挂载 ⇒ 打开就慢、还白跑一堆 IPC |
| **保活**：`<KeepAlive>` 包动态组件 | 切走就销毁 ⇒ 回到拣货页签，刚生成的清单没了、要重生成 |
| **`token` 把保活的代价还回去** | 保活会让"导入之后"切回拣货页签看到的还是**导入之前**那份清单，用户以为没生效（比不保活更糟） |

`token` 是最容易被漏掉的一条：**保活 = 数据变旧**，必须有一个"数据变了"的信号打到各面板。
实现：容器 `bump()` → `token.value += 1`；面板 `watch(() => props.refreshToken, ...)` 重取。
拣货面板的重取**有条件**（`if (generated.value)`）—— 本页的"一键语义"是"进页不自动取数"，
冒烟有断言钉着，不能因为外面推了个信号就破例。

## 3. 各步视图**复用整页视图**，不写第二份

`PickingView` / `OrderCostView` 加一个 `embedded` prop，页签里直接嵌它们，只做两件事：

1. 藏掉**标题两行**（`wb-head__main`）—— 外层页签已经交代了"这是哪一步"；
2. 接到 `token` 时重算。

**不复制一份"页签版"**：那种作法必然分叉（同一件事两处摆，岛内「拣货」页签
2026-10-05 发布前撤回就是这个理由）。复用同一份组件 ⇒ 屏幕上与页签里**结构上不可能不一致**。

⚠️ **踩到的真 bug（变异测试抓到的）**：第一版把 `embedded` 写成"整个 `<header>` `v-if="!embedded"`"，
于是**动作按钮一起被藏了** —— 拣货页的「生成待拣清单 / 导出带图 xlsx / 更多」、算钱页的
「刷新 / 更多 / 未归属」都在那个 header 里。症状是"点开拣货页签只有空态、没法操作"。
**修法：只藏 `wb-head__main`，`wb-head__actions` 保留**（并加 `.is-embedded .wb-head__actions{margin-left:0}`
当工具栏用，否则按钮会被 `margin-left:auto` 顶到右边像飞了）。

> 一般化：**给整页视图加"内嵌模式"时，要按"信息层级"藏，不能按"容器"藏。**
> 页头里"标题/说明"是信息，"动作"是能力 —— 藏信息可以，藏能力就是功能缺失。

## 4. 页签名成了**新的一类入口名**（守卫要跟着扩）

六步收进一页之后，文案里出现「去「归类核对」页签」「在「生成拣货单」页签」这类说法。
`tests/uxEntryNames.spec.ts`（悬空入口名守卫，判据是"文案让用户去的地方必须真存在"）
一眼把它判红 —— 它只认**模块名**与**岛 displayName**。

正确的处理不是豁免（`ALLOWED_NON_ENTRY` 是给"页面上看得见的控件文字"用的），
而是**把页签名当入口名收进 `known`**：用户真的点得到它们，凭什么不算入口？

做法：页签名在 `src/modules/today/flowCtx.ts` 的 `SHIPPING_TAB_NAMES` 里**只写一处**
（`TodayView.vue` 的页签定义按 id 取用），守卫按同一条路径读它，并加了"来源非空"的自证
（正则写歪会静默返回 `[]` ⇒ "页签名全部悬空"这条判据形同虚设）。

## 5. 一条**假守卫**：按"调用总数"断言，被另一个调用方喂饱

`today:ui` 里"导入订单后已生成的拣货单自动重算"这条，第一版数的是 `pickingRows` 的**调用总数**：

```
变异（拿掉 PickingPanel 的 :refresh-token）⇒ 冒烟照样 ALL PASS
```

原因：`pickingRows` 有**两个调用方** ——
① 容器每次 `reload()` 都调 `{limit:2000}`（只为页签徽标/总览卡要个汇总数）；
② 拣货面板点「生成」时调 `{shop, includeShipped}`（**没有 limit**）。
`bump()` 会触发容器的 `reload()` ⇒ 总数照样涨 ⇒ 断言恒绿。

**判据：跨模块共用的 IPC，断言必须按入参区分调用方**（本项目里两边的形状本来就不同，
`limit` 的有无就是分界）。改完变异立刻变红，并且**暴露出上面 §3 那个"生成按钮不见了"的真 bug** ——
修好后这条断言的输出是 `生成后=1 导入后=1`（生成真的发生了、没重算），一眼能读懂。

> 一般化：**"调用次数增加了"不是"我关心的那件事发生了"。**
> 只要那个 IPC/函数有第二个调用方，计数型断言就只是在测"系统还活着"。先问一句
> "还有谁会调它"，再决定按什么维度计数。

## 7. 三步内建完成（同日晚：拿货 / 结算对账 / 归类核对 从岛收编）

用户追加原话：「把归类核对和拿货对账都移到宿主中，归到今天菜单中，可以决断一下哪些是在
流程中有用的，去掉那些没用的功能」。完整明细在方案 `docs/plans/DAILY_SHIPPING_FLOW_PLAN.md`
§6 S8 执行记录·阶段二~四，这里只记**可复用的结论**。

### 7.1 两条守卫写法（这次各抓到一个）

- **假桥要替的是 preload 上面那一层，载荷形状以 `src/types.ts` 的声明为准**：
  `orderImageThumbBatch(items)` 渲染层传的是**裸数组**，归一成 `{items}` 是 preload 干的事 ——
  假桥写 `p.items` ⇒ 恒空数组 ⇒ 界面全是空占位且**不报错**（静默失败，与 preload 注释里记过的
  那次同源）。**写假桥先看 types.ts 的签名，别照 handler 写**（handler 收到的已是归一后的形状）。
- **验 `A && B` 两个过滤条件，夹具必须"各缺一样"**：要有"只缺 A 的行 / 只缺 B 的行 / 都不缺的行"。
  第一版把"已归类"那条写成**无图** ⇒ 「识别只挑未归类的行」恒绿（排除它的是"没图"，
  `!styleCode` 根本没被验到）。且当某条件在**更早的步骤**就抛错时（无图行在读图前就 throw），
  必须换一个**后置的可观测点**（队列大小 / 进度文案）来验它 —— 读图次数抓不到它。

### 7.2 收编岛功能时的裁量清单（"哪些在流程里有用"）

砍：队列中间层（宿主导入**直落订单表**，`oi_queue` 是多余一层）· 行内改**主数据**
（款式展示名归「货与成本 › 产品」）· 非每日动作的页（识别库 / 透视 / 明细 / 设置 —— 设置已在
宿主「设置 → 识别」）· 要新开 IPC 才能实现的"导出对账汇总"（数字屏幕看得见，不属每日动作）。
留：付款的**退款**类型（真实业务：厂家退次品）。
裁量结论写进了两个面板的头注释，与岛对照得回来。

### 7.4 收编之后又删了一个：归类核对的「识别未归类」批量按钮（同日深夜）

用户拍板删除。它是全页**唯一的批量动作**，删掉后归类核对只剩逐行核对 —— 即"只留必然正确的那条路"。
删的三条理由（慢 20~60s/张且绑住界面 · 范围是"当前页"不是"所有未归类" · **直接落库**而非先给建议）
与"保留但暂无调用方的两个识别原语"都写进了 `ClassifyPanel.vue` 的头注释。

**这一步带出一条通用纪律**：**删功能必须同时留一条"它不在了"的反向断言**，否则按钮被加回来时
冒烟照绿、也没人会想起它当初是被有意拿掉的。本次落在 `today:ui` 的 `classify` 段：
`!card('cl-recognize') && !card('cl-stop') && !card('cl-progress')`，并在注释里写明"要加回来就改这条"。
非空转的证明挂在紧邻的下一条 report 上（**同一个** `card()` 取到了 `cl-query` / `cl-reload`
两个真元素 ⇒ 上一条不可能是"查不到任何元素才恒绿"）。

⚠️ 顺带回顾 §7.2 的裁量判据：这条批量识别**不属于"每日动作"**（它是可选的加速手段），
所以按当时的标准它本就该被质疑 —— 只是内建时照搬了岛的功能，没在同一轮里追问。
`docs/notes/2026-10-05-classify-auto-pipeline.md` 记了盘点结论：真正该做的是让**人工核对的结果回流
确定性层**，而不是把逐张识图自动化。
