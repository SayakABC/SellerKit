# 归类核对 › 待核对订单：颜色是「以图为准」的记忆落点

「今天 › 归类核对 › 待核对订单」（`src/modules/today/tabs/ClassifyPanel.vue`）按用户口径重做。
表面是"删两列、放大图、加个下拉"，真正难的是**三条不许做坏的判断**：
① 撤掉的东西**能力去哪了**要逐条答；② 颜色取值有**三支优先级**，夹具必须一行一支；
③ 「款式列表」的驱动表从识别池换成产品库——换完之后，一条**旧断言本身变成了错的**。

## 一、用户口径（五条）与落地

| 口径 | 落地 |
| --- | --- |
| 列表图片展示不全 | 本页把基座 `.wb-thumb` 覆盖成 64px + `object-fit: contain` |
| 品类 / Logo 两列去掉 | 表头 9 → 7 列；字段**仍原样回传**（不显示 ≠ 抹成空串） |
| 匹配到款后取**该款的颜色**让用户选；记住"图片地址 → 颜色"，同图下次自动选中；该款没这个色就让用户自己选 | 颜色格 = 该款色卡下拉（默认值三支优先级见 §3） |
| 归属款选项应来自**货与成本的产品库**（当前展示不全） | `order-db.listStyles()` 驱动表：`oi_styles` → `pl_products` |
| 「待核对 / 未归类 / 识别库 / 已配产品」指标条去掉 | 整条撤掉，连带 `order-sku-rollup` 通道退场（零消费者即删） |

## 二、撤掉一个东西时，三件事要一起做

**① 能力去哪了，要写清楚**（不是"不显示了"）。品类是主数据、在「货与成本」维护；Logo 等
「印花 logo 管理」做出来再加回来 —— 写在组件头注释里，而不是让下一个人猜。

**② 反向守卫要钉在"能力真的不在"，且能自证非空转。**
- 表头（7 列）与**控件**两处都要钉：只钉表头会漏掉"列撤了、输入框还在原地写值"这种半拉子改法
  （最糟的一种：看不见却仍在写）。`!card('cl-cat-41') && !card('cl-logo-41') && !card('cl-cat-options')`。
- "指标条没了"这条，同一条 `report` 里先确认**面板与表格真的在**（同一个 `card()` 查找函数、
  同一时刻），否则 `!card('cl-stats')` 可能只是"这一页压根没挂上"。

**③ ⭐ 连带通道的守卫：判据必须是"有没有人**读**这个键"，不是"通道被调了几次"。**
`orderSkuRollup` 的桩删掉之后，"调用次数 == 0"是**恒真**的（读不到就无所谓调用）——
一条标准的假守卫。本轮改法：假桥的兜底分支把**没人实现的键**记进 `__unhandled`，
断言改成"这个键没被人读过"。顺带它也把"本页偷偷用了什么没实现的键"暴露出来
（实测输出里有 `platform` / `settleOrders` / `aeRateList`，与本页无关但一眼看得见）。

## 三、颜色：一条字段，三支优先级，夹具要三行

取值顺序（**每一支都要落在该款的色卡里才作数**）：

1. 图记住的颜色（宿主存在 `oi_images.style_color_id` 上，订单列表联表出来是 `o.styleColor`）；
2. 订单自己的颜色列（上一轮人工核对留下的值）；
3. 都不在色卡里 ⇒ **留空让用户自己选**。

夹具与判据必须**一行一支**，否则错法照样全绿：

| 行 | 款 | 图记住 | 订单自己的 | 期望 | 打的是哪种错法 |
| --- | --- | --- | --- | --- | --- |
| P-42 | S1（色卡 黑/白） | 白 | **黑** | **白** | "永远取订单自己的颜色"——两个值都在色卡里，只有期望值不同才分得开 |
| P-45 | S1 | 印花 | 黑 | 黑 | 去掉第 2 支（只认记住的色）后它会空着 |
| P-44 | S1 | 印花 | 印花 | **空** | "替他改判"（把别的款的色塞进来 / 随便选一个） |

另有一条**这一页特有的**坑：`isDirty` 的基准**不能**用行字段。颜色格显示的是
`initialColor()` 推出来的值（可能是"图片记住的颜色"），它与 `o.color` 不是一回事 ⇒
拿 `o.color` 比，**每行一进页面就是脏的**，「保存」全亮着，"改了才让存"这条守卫当场失效。
故 `Draft` 里带 `baseColor` / `baseStyle`，比它们。

**布局是「一个格子两种控件」而不是两个格子**（有名款 ⇒ 色卡下拉；无名款 / 该款还没录颜色 ⇒
自由输入 + `datalist`）。分成两格会让人以为"款的颜色"和"订单的颜色"是两回事 ——
在这个页面上它们不是。

## 四、「点名了款却没给颜色 ⇒ 不许保存」怎么才算验过

背景：宿主落库时颜色是款色的主键之一（`oi_style_colors(style_id, color)`），空颜色会落出
一个**没有名字的款色**，而界面上看不出任何异常。

判据**必须连着三条**，只断言"保存禁用"是不够的 —— 那会被"这行本来就不脏"满足（恒绿）：

1. 换款后原颜色不在新色卡里 ⇒ 清空 + 出现缺色提示；
2. 此时「保存」`disabled === true`；
3. **补上该款的某个颜色后，同一行立刻可保存** —— 它才证明卡住的是缺色、不是"没改动"。

## 五、⭐ 换驱动表之后，一条旧断言自己变成了错的

`listStyles()` 从 `oi_styles` 驱动改成 `pl_products LEFT JOIN oi_styles`（识别池有、产品库没有的
行以空名补在末尾 —— 少一行比多一行难查得多）。用户报的"归属款展示不全"就是前者：
**产品库里手工新建、还没出过订单的款在识别池里没有行**。

副作用在 `scripts/style-authority-smoke.cjs` 的 B7：它断言"删掉识别池那一行 ⇒
`listStyles().length === 0`"。换驱动表后**产品库还有这个款 ⇒ 列表里就该还有它**，
旧断言从"守着一件对的事"变成了"要求一个错的结论"。改法是把它反过来：
**它必须仍在列表里、名字跟产品库走**，并在断言里写明"别改回 `length === 0`"。

> 通用教训：**改一个函数的驱动源时，去 grep 它的全部既有断言** ——
> 里面很可能有一条断言的**期望值本身就是旧驱动源的产物**，它变红不是"改坏了"，
> 而是"这条断言在阻止修复"。判据是：把该断言改成新语义后，它是否在说一件**该成立的事**。

## 六、两个实测踩到的坑（都值得进硬约束）

**① 模板里写 markdown 粗体 ⇒ 屏幕上就是一串星号。**
说明文字写成 `再从**这个款的颜色**里选一个`，Vue 模板**不解析 markdown**，冒烟日志里
原样打印出 `再从**这个款的颜色**里选一个`。本轮为此加了一条守卫：

```
面板上可见的文案没有漏出 markdown 记号（** 与反引号）
```

判据读的是**渲染出来的 `textContent`**（源码里有没有写不算）。当场变异确认：
把 `**` 写回模板 → rebuild → **恰好只有这一条变红**（PASS 148 / FAIL 1），复原后 149/0。

**② 注入模板串里不能有反引号 —— 本轮又踩两次。**
一次是注释里写 `` `calls('orderStyleAssign')` ``；一次更隐蔽：断言里想检查反引号，
写成 `indexOf` 配一个字面量反引号，直接把 `ASSERT_SCRIPT` 模板串提前闭合。
症状是 `node --check` 报**文件末尾的 brace 不配**（`Unexpected token '}'` 指向 `main()` 的
收尾处），离真正的行有三百多行远。写法：`String.fromCharCode(96)`。

**③ 工程侧：本轮有一次改动被写回覆盖。**
改完 `ClassifyPanel.vue` 的一行文案后，过了一轮操作它又变回旧内容（mtime 对得上）。
之后的做法：**每次改完立刻 `md5 -q` 记一下，rebuild 后复查 md5 是否一致**。
本轮的守卫是"改完 → 变异 → 复原"，正好在变异那一步把它暴露出来（变异没打进去、
但冒烟却红了 —— 该红的红在了不该红的时刻，也是一个可用的信号）。
