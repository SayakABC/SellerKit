# 「图片展示不全」二次复报：尺寸不够 + 窄窗口下图列塌成 12px，以及两个范围的样式

日期：2026-10-12（承接同日第一轮 `2026-10-12-classify-reopen-corrected.md`）

用户原话（两件事）：

> 1. 待核对订单页面的图片展示不全，请修复
> 2. 已核对和待核对页面的样式也有问题，请修复

动手前先取证（本仓纪律：布局/视觉问题的判据是人眼 + 几何，不是 DOM 结构），
取证结论推翻了两个想当然的假设，最后落在一条**只有窄窗口才复现的真 bug** 上。

## 一、取证：图从来不缺角，缺的是尺寸；而"缺"在窄窗口下会恶化成"没有"

| 查了什么 | 结论 |
| --- | --- |
| 主进程 `thumbDataUrl`（`electron/order-handlers.ts`） | **等比缩放、不裁切**（`scale = maxEdge / max(w,h)`）⇒ 图不会被裁掉 |
| CSS `.cl-table .wb-thumb` | `object-fit: contain`（上一轮刚从 `cover` 改过来） |
| 真库 35 张图的像素尺寸（`.backup` 副本 + `sips`） | **31 张方图**（800×800 等）、4 张竖版 ⇒ "商品照多是竖版、cover 会裁上下"这个注释在**这份真库上不成立** |
| 同一投诉的历史 | **2026-10-10 就报过一次**"图片展示不全"，当时的修法是 `cover→contain` + `40→64px`。**原话复现** ⇒ 上一轮的修法不够，剩下的问题只能是**尺寸** |
| 既有页面的既定解法 | `goods/api.ts:189` 原话："认款要看清印花/领型/颜色，256 不够" ⇒ 表格小图 + **点开看原图**（`order-read-image` 不缩放）。`PoolPane` 已落地，归类核对页两者都没有 |

于是图片侧做两件事：**表格图 64 → 96px** + **点开看原图**（⤢ 角标常显）。

## 二、真正的 bug：窄窗口下，图列被 auto 布局压扁，图变成 12px 细条

改完 96px 跑 `today:ui`，新加的「已核对范围也出图」当场打红：

```
contain/12pxx96px/nat=8x8/maxW=100%/btn=12/td=32   ← 图 12px 宽、列 32px 宽
```

顺链条查下去，根因是三件事叠起来：

1. **`--dump-dom` 不传 `--window-size` ⇒ 无头 Chrome 视口只有 800×600**。应用外壳（侧栏 + 内边距）一占，面板可用宽只剩 **579px**。
2. **`.wb-table` 是 `table-layout: auto`**：列宽由"各列首选宽之和 vs 表格可用宽"决定，**差多少就从每列抠**。已核对范围各列都是窄文本（只读格），首选宽之和很容易超过可用宽 ⇒ **图列从 112px 被抠到 32px**。
3. 基座 `img { max-width: 100% }` 随即生效 ⇒ 图被缩到 **12px**。

**待核对范围只是侥幸逃过**：颜色/归属款两格是下拉框，把整表撑宽，差额摊到了别的列上。同一个窗口宽度下，两个范围一个好看一个坏 —— 这正是用户说的"已核对和待核对页面的样式也有问题"。

> ⚠️ 取证时的一个反向发现：`contextBridge` 暴露的属性是**只读**的 ——
> 我想在截图脚本里 `api.orderImageThumbBatch = ...` 覆盖假桥，赋值**静默失败**。
> （`classify-shot.mjs` 里改成在桥装好之后重新赋值同一个键才生效。）

### 修法：图列要有自己的地板，不能指望图片有多大

```css
.cl-thumb-col { width: 112px; min-width: 112px; }   /* 列的地板 */
.cl-thumb-btn  { width: 96px; height: 96px; }        /* 格子里那个块的定尺 */
```

两处都要，理由不同：

- `td` 的 `min-width` 是**列宽**的下限；
- 按钮的定尺是这一列 **min-content** 的来源 —— 只给 `img` 设宽时，`max-width: 100%` 会让 Chrome 按图片**固有尺寸**算该列下限，而缩略图固有尺寸很小（主进程 `maxEdge` 256，冒烟夹具 8×8）⇒ **列该塌还是塌**。这是本轮实测踩到的：第一版只加 `td { min-width }` 之前，先试过只动 img，没用。

代价（写进注释）：窄窗口下整表会比容器宽一点 ⇒ 横向滚动。`.wb-table-wrap` 本来就为此准备着（首列 sticky），且**与待核对范围在同一窄窗口下的行为一致** —— 不是新引入的不一致。

## 七、可复用的教训

- ⭐⭐ **`--dump-dom` 不传 `--window-size` ⇒ 视口只有 800×600**。这既是坑（量出来的几何不是用户看到的），
  也是一台**免费的窄窗口测试机** —— 本轮唯一的真 bug 就是它暴露的，1440 下截图完全正常。
- ⭐⭐ **`table-layout: auto` 下，一列里放固定尺寸的图时，地板必须由 CSS 给**。
  差额从每列抠；`img { max-width: 100% }` 会让 Chrome 按**固有尺寸**算该列 min-content，
  缩略图固有尺寸很小 ⇒ 列照样塌。**别指望图片自己兜底。**
- ⭐ **方图夹具分不出 `object-fit: fill` 与 `contain`**（格子本身就是方的）⇒ 要判 contain 必须有一张竖版。
- ⭐ **连点竞态要把第一次的响应拖慢才造得出来**（同步桩下坏实现也绿）。
- ⭐ **同一个投诉原话复现时，先问"上一轮修的那一层是不是不够"**，而不是从头再查一遍裁切。
- ⚠️ `contextBridge` 暴露的属性**只读**，覆盖假桥要重新赋同一个键，不能改属性。
