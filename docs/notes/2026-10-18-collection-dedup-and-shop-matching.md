# 2026-10-18 整店采集：去重失效 + 商品落「未关联店铺」

> 采集端 `ae-profit` 0.4.0 → 0.5.0；宿主 `shop-item-db` 加记忆表与 v2 迁移。
> 用户报障原文：「现在采集没有去重，之前已经采集过40条数据了，剩余23条未采集，
> 但本次采集还是采集了所有数据，并出现在待关联采集商品中了，并且未关联店铺」。

## 一、真库取证（先看事实，再动代码）

拷 `seller-kit/sellerkit.db` 只读查 `pl_shop_items`：

| shop_id / store_key | 条数 | `scraped_at` 时间窗 |
|---|---|---|
| `6 / ''`（九店） | **40** | 10-17 22:09 ~ 22:12 |
| `0 / 'Shop1105671703 Store'`（未登记桶） | **63** | 10-18 00:24 ~ 00:28 |
| `4 / ''`（七店，别的店） | 8 | 10-16 |

- 两桶 `item_id` **交集 40** ⇒ 同一款在库里存了两行；逐条对比**两侧 SKU 行数、标题逐字相同** ⇒ 纯冗余副本，不是两次不同的采集结果。
- 未登记桶独有 **23** 条，全部 `sku_json` 非空（本轮确实采到了）。

`sale` 侧登记信息（这才是第二条根因）：

| shop | name | platform_shop_id | shop_url |
|---|---|---|---|
| 6 九店 | `九店` | `Shop1105671703 Store` ← **填的是店名** | `aliexpress.com/store/1105671703` ← **数字也不是真 storeId** |

采集帧带来的是 `storeId=1105668759` / `name=Shop1105671703 Store`。于是
`matchShopByStore` 的三级证据（归一 URL → storeId → 店名全等）**三级全落空** ⇒ 落未登记桶。

**时间线把两个根因串起来**：22:09 采 40 条落未登记桶 → 用户登记九店，`shop-upsert`
触发一次 `adoptShopItemsForShop` 把它们搬进 `shop_id=6` → 00:24 又采 63 条，
三级匹配仍落空（用户没再保存过店铺 ⇒ 收养不重跑）⇒ 落回未登记桶 ⇒ 与已归店的 40 条并存。

## 二、根因 A：跨轮去重的真源头搞错了

上一轮（10-17）加的去重台账 `aeWalkSeen` 在**扩展本地** `chrome.storage.local`。
它只认「**这一套扩展在这个浏览器**采过的款」，对下列场景一无所知：

- 用户第一次用的就是 0.3.0（没有 seen 台账）⇒ 升级到 0.4.0 后第一次点采集必然全量重跑；
- 换浏览器 / 清扩展数据 / 换机器 / 重装扩展 ⇒ 台账空。

用户那 40 条正是旧版扩展采的 ⇒ 本地台账里一条都没有 ⇒ 第二次点采集把 63 条全采全推。
**"采没采过"的事实在宿主库里**（`pl_shop_items` 有行），宿主才是权威。

### 修法

- **宿主**新增只读端点 `GET /ae/shop-items/known?url=&storeId=&name=`（`ae-receiver.ts`
  的 `handleItemsKnown`），底层 `shop-item-db.listScrapedItemIds()`。
  - **匹配口径必须与 `upsertShopItems` 同源**（同调 `matchShopByStore`）：问的时候算
    A 店、写的时候算 B 桶，去重会「问的和写的不是一家」而静默失效。
  - 同时覆盖**未登记桶**的行：店还没登记的用户也得能去重。
  - token 两处都收（header 优先 / query 兜底）；**刻意不套 60 次/分的 ingest 限速窗口**
    —— 大店铺批量采集时它会被自家 ingest 挤掉，而它恰好是「少采」的那一环，挤掉就退化成全量重采。
- **扩展** `startWalk` 改为：本地 `aeWalkSeen` 与宿主清单**取并集**灌台账（`fetchKnownFromHost`）。
  - 查不到**不阻断采集**，但原因落 `walk.knownError`，popup 明写「未向主程序核对已采清单
    ……可能重复采集」—— 否则用户只看到"又全采了一遍"，分不清是主程序没连上还是真有新货。
  - `force`（整店重采）连宿主那半也不认。

### ⭐ 清单只列「采到过 SKU 矩阵」的款

`listScrapedItemIds` 的 WHERE 带 `sku_json <> '' AND sku_json <> '[]'`。
这不是保守，是必需：采集分两层——**列表轻采**（无 SKU）与**详情重采**（带矩阵）。
用户在列表阶段跑完就停，库里就有只有列表信息的行；把它们当"已采过"让扩展跳过，
那些款**永远拿不到 SKU 矩阵**，而界面上看着"库里已有、不用再采"。**「存在」≠「采到」。**

## 三、根因 B：收养是一次性的，记忆丢了

`adoptShopItemsForShop` 只在 `shop-upsert`（用户保存店铺那一刻）跑一次。
用户当初没把 URL/店铺ID 填对（platform_shop_id 填成店名），1、2 两级此后**恒落空**，
于是之后每次采集都落未登记桶。

### 修法：收养记忆表 `pl_shop_store_keys(store_key → shop_id)`

- 写入：`adoptShopItemsForShop` **无条件**写（哪怕本次 `adopted=0`——"这个桶键归这家店"
  是登记那一刻的结论，与桶里此刻有没有行无关）；v2 迁移按 `sk_shops` 三个身份键反查回填。
- 读取：`matchShopByStore` 的**第 4 级证据**，三级全落空后按「店名 → 归一 URL → storeId」
  优先级查表。
- `JOIN sk_shops` 是必要防线：记忆指向的店可能已被删 ⇒ 落一个悬空 `shop_id`
  比落未登记桶更难发现（界面显示店名、认款却写不进去）。

记忆表只在**用户已登记过该店**的前提下产生 ⇒ 仍然不自动建店、不跨店乱挂。

## 四、存量修复：v2 迁移合并重复行

`shop-item.main` v2 `mergeDuplicateUnregisteredRows`：

1. **记忆回填**：按 `sk_shops` 三键反查未登记桶 `store_key`，认得出的登记进记忆表；
2. **无主行收养**：桶里该店**还没有**同 `item_id` 的行 ⇒ 搬进该店，`store_key` 归一为 `''`；
3. **同款重复**：该店**已经有**同 `item_id` 的行 ⇒ 已登记行的空字段 ← 未登记行的非空值、
   `scraped_at` 取**较新**者，然后删掉未登记那行（冗余副本）。

认不出的桶**一律不动**：那是真的"店还没登记"，界面提示「店铺未登记」是正确提示，
静默塞进某家店才是把两家的货混在一起。

⚠️ 迁移体里**不能**调 `ensureSchema()` / `ensureShopItemSchema()`：`ensureShopItemSchema`
本身就跑 `migrate()` ⇒ 迁移体回调本函数 ⇒ 无限递归。记忆表 DDL 由 `dbMigrate(SCHEMA)`
在 `migrate()` 之前建好。
⚠️ `sk_shops` 是**店铺域**的表，而本迁移跑在 `ensureShopItemSchema()` 里 —— 那一层的契约
是「不保证店铺域已建」。按 `db.ts` 的跨域读纪律用 `tableExists('sk_shops')` 缺表降级，
而不是抛 `no such table`（那会被误读成"迁移 SQL 坏了"）。

## 五、顺手清掉一条一直红着的过期断言

`shop-item-db-smoke.cjs` 的「同名不自动落库」断言 2026-10-17 就该改：那天给
`matchShopByStore` 加了**第 3 级证据（店名全等）**，口径已变（用户实测「采集的商品没归到
已登记的店，把店铺名称改成和采到的一致才归位」），断言没跟着改 ⇒ 一直红。
按当前口径重写为两条：**店名全等且已登记 ⇒ 归该店**；**没登记过 ⇒ 仍落未登记桶**（守住
「不自动建店」）。

两条迁移版本断言也从 `=== 1` 改成 `>= 1`：本域迁移是版本化追加的，写死数字会让每加一个
版本这两条用例假红（"某一轮测试总数"同理，不是常量）。

- **变异复核**：扩展 5 条 + 宿主 7 条逐条打红后复原。

### 三个"打不红"的教训（都是真盲区，不是误报）

1. **只看旁证字段**：新增用例先只断言 `walk.fromHost === 2`，变异"宿主清单不用了"
   照样绿——`fromHost` 只是记录字段。补**双向行为断言**（队列里真的没有 A1/A2、
   帧里真的只有 A3）才打红。
2. **两条路互为兜底**：摘掉「登记时写记忆」后仍绿，因为 v2 迁移的回填**也**写了记忆表。
   补一条"先把版本记满（禁掉迁移回填）、只可能由登记产生"的用例。
3. **夹具 `reset()` 漏清新表**：`reset()` 不清 `pl_shop_store_keys` ⇒ 上一条用例的记忆
   **跨用例泄漏**，"认不出的桶不许乱塞"那条怎么变异都不红。补进 `reset()` 才生效。
   （同源坑：`git stash` 对这两个文件无效——它们从未提交过，不在索引里。）

### 变异脚本自身的三次翻车（"工具没跑起来"当判失败处理）

- `[] && x` 中空数组是 **truthy** ⇒ 第一版 M1 变异是**空操作**，报了"没打红"。
- 反向替换把 `?` 号参数插到三元表达式位置 ⇒ TS1005/TS1127 编译失败，**不是**测试红。
- 切片拼接写坏源文件 ⇒ `ae-receiver.ts` 报"没有导出成员"。

用户期间自己跑了一次应用（`npm run dev` 边跑边 `tsc`），修复已在其真实库生效。
只读直查 `sellerkit.db`：

- `shop_id=6（九店）= 63 条`，`shop_id=0（未登记桶）= 0 条`，重复行已消除；

## 八、遗留（用户侧动作，不在代码里）

1、2 两级匹配才是正路。
