# 「待补清单」：把散在三处的数据缺口收成一张可点的单子

> 2026-10-19 · 落地于 `src/lib/dataHealth.ts`（判定）+ `src/modules/shop-accounts/components/HealthPane.vue`（界面）
> 入口：「基础数据 › 待补清单」（侧栏第四组）

## 一、它解决的是哪件事

前三轮（商品ID 认店 / 订单图定色 / 克重去掉颜色条件）把**代码**接通之后，剩下的问题不再是代码，
而是**数据还欠着什么**。可这些缺口散在三个页面里：

| 缺口 | 原来要去的页面 |
| --- | --- |
| 订单没认款 / 颜色还是「未分类」 | 发货台 › 归类核对 |
| 认到的款在产品库里没有 / 尺码对不上 / SKU 没克重 | 基础数据 › 产品管理 |
| 款没填进价 | 基础数据 › 进价 |

用户要回答"我现在最该补哪一样"，得跑三页数三遍，而且**数法各不相同**（单 / 个 SKU / 款）。
清单把六类检查摆在一屏，每类写清：**不补会怎样 · 差在哪几行 · 去哪补**。

## 二、六类检查与各自的判据

| 类别 | 判定 | 单位 | 去处 |
| --- | --- | --- | --- |
| 订单没认到款 | `styleCode` 为空（按"店铺 + 商品ID"合并明细） | 单 | 发货台 › 归类核对 |
| 订单颜色还是「未分类」 | `styleColor === '未分类'`，明细里列出订单上的平台色名 | 单 | 发货台 › 归类核对 |
| 认到的款在产品库里没有 | `styleCode` 非空但 `pl_products.code` 里找不到 | 单 | 产品管理 › 建档与关联 |
| 订单尺码在产品里没有 | `canonSizeKey(订单码)` 不在该款**在售**变体的尺码集合里 | 单 | 产品管理 › 建档与关联 |
| SKU 没填克重 | `pl_variants.weight_g <= 0` 且未归档 | 个 SKU | 产品管理 › 建档与关联 |
| 款没填进价 | 产品行 `pl_products.cost_cents <= 0`（2026-10-21 C2 起；旧口径 `ae_cost_map` 已随表删除） | 款 | 基础数据 › 进价 |

真库（2026-10-19 克隆）当场的样子：未认款 12 单 · 「未分类」35 单 · `STYPE-001` 5 单（产品库里没有这个款）
· 尺码对不上 6 单（S/M） · 缺克重 126 个 SKU · 缺进价 2 款。

## 三、三条硬规矩（都是本仓踩过的同类问题）

1. **不新开一套口径**。输入全部取自既有取数口（订单主干投影 / 产品列表 / SKU 列表 / 进价表），
   与各自页面上的数字**同源**。清单不重算业务，只做「分组 + 排序 + 说人话」。
   - 冒烟里有一条专门验这件事：上游「进价」那几步刚给 S2 填过价，清单立刻从 2 款变 1 款
     （静态快照的实现会仍然显示 2 款 ⇒ 红）。
2. **数字与明细同一份数据**。`n` 由 `items` 累加得出，绝不另写一条 COUNT
   —— 否则会出现"标题说 47 单、下面只列了 12 行"，整页都不可信。
   变异：把 `n = Σ items[].n` 改成 `items.length`，7 条用例立刻红。
3. **不跨类相加**。单位不同（单 / 个 SKU / 款），页头只说"还欠几类"。
   这与 `MasterDataView` 组徽标那条"别把组内各项的数加起来"是同一条道理。

## 四、几个容易写错的细节

- **尺码要过 `canonSizeKey`**：产品写 `3XL`、订单写 `XXXL` 是同一个码。不归一就会凭空造出一批"缺码"。
  但**不碰** `S/M/L/XS`（`XS ≠ S`），也不猜 `均码`。
- **归档变体不算"这个码有"**：归档 = 用户已经不用它 ⇒ 拿它当"有"，清单会一直显示"齐了"而实际发不了货。
- **款不存在时不再计入后两类**：款都不在产品库，"这款有没有 S 码"无从谈起。同一单只报一次（`continue`）。
- **色名去重按等值、不按子串**：真实库同款既有 `Khaki` 也有 `K`，用 `includes` 判重会把 `K` 吞掉，
  而清单看起来只是"少一个色"。
- **「未分类」这个占位值跨进程有两份字面量**（主进程 `MAPPED_FALLBACK_COLOR` / 渲染层 `UNCLASSIFIED_COLOR`）。
  单测里读 `electron/order-db.ts` 比对，避免一边改了、清单把已定色的单重新报一遍（**不报错**、永远清不掉）。

## 五、口径边界（写出来，免得下一个人以为少算）

- 订单只看**最近 2000 单**（宿主 `order-shipping-rows` 的硬上限）。到上限时页头会写
  「已到上限，更早的单没算进来」—— 只少报，不多报。
- 发货台总览卡的缺口只算**今天导入的那批**，两个数字不一样是**口径不同**，不是谁错了。
  这句话写在界面上，否则用户会拿两页的数字互相质证。
- **店名未归一不在这里**：它已经是「基础数据 › 店铺登记」的徽标，取数走 `shopApi.summary()`（另一条链）。
  同一件事摆两个地方 = 改一处忘一处。
- **运价表缺失不在这里**：那是"有没有配"，不是"哪一行没填"，没有明细可列。

## 六、跳转接线（两条路都要接）

「去补」用的是 `switchModule`：

| 类 | action | 落点 |
| --- | --- | --- |
| 未认款 / 未定色 | `switchModule('today','classify')` | 发货台 › 归类核对页签 |
| 款 / 尺码 / 克重 | `switchModule('shop-accounts','goods')` | 基础数据 › 产品管理（组内页签） |
| 进价 | `switchModule('shop-accounts','cost')` | 基础数据 › 进价 |

- 同模块那一半由 `MasterDataView.applySwitchAction` 接（已有）。
- **跨模块那一半这次新加**：`TodayView` 原来**不消费 action**，跳过去只会停在「总览」——
  按钮写着"去认款"、落地是一张总览卡，是"指路指到半路"。现在读 `__switchModuleAction`（模块不在场）
  + 监听 `switch-module`（模块已在场，`activateCore` 对同模块早退，marker 没人消费）。
  认不出的 action 原样不动（不许把 `tab` 设成一个不存在的 id）。
- 没有做"顺便把筛选条件带过去"（如产品列表的「缺克重」筛选）：`switchModule` 的 action 只到"哪一屏"，
  再往下没有协议。清单已经把**款编码 / 商品ID**写在明细里，到那一页搜一下就到 —— 塞一个
  "看起来筛了其实没筛"的跳转更糟。

## 七、验证

- 单测 `tests/dataHealth.spec.ts` **15 例**：六类各一条、归档/归一/合并/去重/口径常量/跳转源码级钉各一条，
  外加两条自证非空转（补上缺口数字必须变；标题数 = 明细累加）。
- 变异六条，各自只红目标：`n` 改成 `items.length`（7 红）、尺码不归一（1 红）、归档也算（2 红）、
  款不存在不 `continue`（1 红）、`switchModule` 目标写错（1 红）、`TodayView` 不监听（2 红）。
- 界面冒烟 `master-data:ui` 新增 **13 条**：六块都在、六个数字逐一对上、反向样本（S1 不该出现在缺克重表）、
  页头只报"类"不报和、组内跳转、重挂载重算、补齐后点「重新核对」变"数据齐了"、跨模块落「归类核对」页签。
  窄视口那一遍也绿（新页是一列块，没有两栏布局）。
- 门禁：`tsc` / `vue-tsc` / `verify` / `verify:docs` / `build` / 全量 `vitest` / `today:ui` / `master-data:ui`。

## 八、已知未做

- **没有徽标**（与 `goods` 同例）：算一次要扫全部订单 + 全部 SKU，而 `loadCounts` 每次进模块都跑；
  这一页是"专门点进去看"的，不是每天扫一眼的仪表盘。要加先问"这份取数成本值不值"。
- **不能一键补**（比如批量给某款加 S/M 码）：补数据大多要问工厂/供应商，能做的只是"告诉你去哪、差什么"。
- 清单**不落库**（每次打开现算）：落一份快照就有"快照过期"的新问题，而这些都是只读查询。
