# 订单的颜色一直就在报表里：从「产品属性:Color:5」定色

> 2026-10-20。归色补第四级 `parseOrderPropsColor` + `order.main` v5 回填 + 连带修掉「悬空映射」。

## 现象（真库 51 单）

| 状态 | 行数 |
| --- | --- |
| 归到真实色 | 4 |
| 挂占位色「未分类」 | 35 |
| 完全没归色 | 12 |

44 单落「未分类」意味着**不同颜色的订单在拣货单上长得一模一样** —— 这不是"数据不好看"，
是发错色的直接来源。追下去发现：颜色唯一来源是「订单图 → 采集 SKU 色图」，而这 44 单的商品
**从没被采集过**（`pl_shop_items` 里没有行）⇒ 那条路恒空。可报表里明明写着：

```
【1】<标题>
(产品属性:Color:5,Size:5XL,Ships From:China Mainland)
(产品数量:1 piece)
```

`Color:5` 就是平台色名（`1..15` / `Khaki` / `Picture color4` 都是这种写法），
跟图一点关系都没有。以前 `oi_orders.color` 恒空，是因为**没人解析过这段文本**。

## 取数口径（`electron/aeMoney.ts`）

`parseOrderPropsColor(rawFields)`：

1. 有独立「颜色」列（`颜色` / `color` / `colour`）⇒ 以列值为准（一列一值，天然没歧义）；
2. 否则扫承载规格的列（`产品信息` / `商品信息` / `规格` / `属性` / `sku props`），
   取里面**所有** `Color:<值>`（全角冒号也认），按 `colorAliasKey` 等值去重；
3. **去重后只剩一个才返回**；0 个或 2+ 个一律 `''`。

真库分布正好用得上这条规则：**49/51 单唯一**，**2 单一单多色**（同一张订单含 4 个 SKU 行、
颜色 `10` 与 `6`）—— 那 2 单必须定不出来。取第一个 = 静默错色。

三条纪律：
- **不看图、不依赖采集**：采集通道的订单 `image_id` 恒空、采集没覆盖的商品没有色图，这条路才是它们的唯一出路；
- **不校验"像不像颜色"**：`1..15` 这种纯编号是正当平台色名，黑名单式校验会误伤且不报错（同 `normalizeSkuSize`）；
- **不接采集帧格式**（`Picture color+XXXL+China Mainland` 没有冒号）：那是 `parseSkuProps` 的地盘，两条口径不混。

## 归色顺序（`autoAssignByMap`）

映射里配的色 → 图片**已有**真实色（不动）→ 订单图反查采集色 → **报表规格串** → 已有平台色名 → `未分类`。

规格串刻意排在「按图反查」**之后**：图那条有采集快照作证据、同一份快照还能定克重；
两者都在时以图为准 ⇒ **以前能定的行一个都不变**，这一级只多救回以前定不了的行。

`insertOrder` 同时把平台色名写进 `oi_orders.color`（这一列的既有语义就是"订单上的平台色名"，
`dataHealth` 拿它当"订单上的颜色：5 / 10"的辨认提示）。

## 「认一次色」的原文来源补了第二级

`rememberColorFromAssignment` 以前只从采集侧取原文（`orderColorByItemImage`）。没有采集快照的商品
（本机 44/51 单）⇒ 原文恒空 ⇒ **用户认了色也记不下**，下一批照样落 `5`，人工量不随时间递减。
现在原文 = 采集色 ‖ 报表规格串色。

⚠️ 仍然是**外部事实**：绝不取 `oi_orders.color` —— `saveCorrection` 先写订单再点名款，
拿它当 from 就是"键与目标同值"，永远记不下（这条纪律上一轮已经踩过）。

## v5 回填（存量单）

`order.main` v5：`SELECT ... WHERE TRIM(COALESCE(color,'')) = ''` → `parseOrderPropsColor` → UPDATE 该列。

- **只补空值**：已有值要么是采集帧逐行解析的、要么是人工核对写下的结论，迁移不许覆盖人的结论；
- 不碰 `raw_fields` / `updated_at`（原文保真，回滚只是一条 UPDATE）；
- **迁移里不跑重放**：本步骤跑在 `ensureOrderSchema` 的 `ensureProductSchema()` 之前，
  款色表还没保证存在；重放仍由进页自愈（`replaySkuMappings`）负责。

真库克隆实测：回填 **49 单**，随后重放补上 **32 行**归属，「未分类」**35 → 5**。

## 连带修掉：映射指向已删产品 ⇒ 队列里"看起来已关联"

回填+重放后仍有 11 单认不出，原因不在颜色：**2 条映射指向已删除的产品 `9802`**
（映射行不随产品删除消失，没有外键级联），而 `resolveOrderSku` 把这种映射当**未命中**
（绝不替人猜一个产品）。可队列与批量解析按映射表算「已关联」⇒ 这些商品**连待办都不进**，
用户看到"11 单认不出、却没有一处能点"。

修法：`product-db.shopSkuQueue` 与 `resolveSkuBatch` 的映射集合 `JOIN pl_products`（只算产品还在的），
与 `resolveOrderSku` 同一口径。点名款能直接改对它 —— `upsertSkuMappings` 本来就按
`(平台, 店铺, 商品ID, spec)` **整行替换**，不依赖产品 id 是否还在。

## 守卫

- `tests/aeMoney.spec.ts`（+9）：唯一色 / 属性顺序无关 / 全角冒号 / 同色多行 / 大小写等价 /
  **多色 → 空** / 颜色列优先 / 采集帧格式不接 / `propsColorTokens` 取全量。
- `product-sku-smoke`（+4）：报表规格串定色①（无采集快照也能定，且认一次后同款自动翻译）、
  ②（一单多色保持未分类）、v5 只补空值、映射悬空回到待办。
- 变异（各只红目标断言）：去掉第四级 → ①红；多色取第一个 → ②与单测红；回填不限空值 → v5 红；
  不从句外学对照 → ①红；队列 / 批量各去掉 `JOIN` → 悬空那条分别红。

## 边界

- **一单多色**：色不可定，落「未分类」（人工）。
- 没有规格串 / 采集帧格式：不归这条链路。
- 剩下 14 单的构成（真库）：11 单悬空映射（点名款即可）、2 单「十五店」还没配映射、
  1 单是被忽略的噪声店名。

## 下一步（本轮没做，先说清）

**改店铺的「平台」会静默废掉该店全部映射**：`pl_shop_sku.platform` 在写映射那一刻从店铺实体抄下来，
而 `normPlatform` 就是 `toNameKey`（只折叠空白/不可见字符，**不折叠大小写**）——
把店铺平台从 `ae` 改成 `aliexpress`（或 `AE`）之后，`resolveOrderSku` 用新平台去查 ⇒ 全部不命中，
映射列表里看着还在、订单一条都认不出。真库现在 9 家店都是 `ae`，所以还没炸。
修法与「悬空映射」同一思路：平台改了就同批把映射行的平台一起搬过去（要在 handler 层编排，别让 `shop-db` 直写产品域的表）。
