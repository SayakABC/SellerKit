# 映射重放：不给人一个按钮，让页面自己把历史漏网补上

> 2026-10-20。落地 `order-db.replaySkuMappings` + 两处进页自愈（「待补清单」「归类核对」）。
> 结论先行：**这条链路不该有「请人工点一下」的入口**，它是确定性事实的重新套用。

## 1. 为什么会有「映射在、订单没吃到」

真实库取证（51 行订单，`/tmp/skdb/y.db` 克隆）：

| 状态 | 行数 |
| --- | --- |
| 完全定（款 + 色都定） | 4 |
| 款定了、色还是 `未分类` | 38 |
| 有图但没定款 | 9 |

其中 **9 行"没定款"里有 6 行的商品ID 已经在 `pl_shop_sku` 里、且 `status='confirmed'`**。

根因不在认款逻辑，而在**写映射的那条路径不回填**：

- `assignOrderStyle`（人工核对）→ 调 `rememberSkuMapping` → 内部 `reassignOrdersByItemIds([itemId])`，会回填；
- `upsertSkuMappings`（「建档与关联」里配映射）→ **`out.reassigned` 从未被赋值，也不调回填**。

于是"先导单、后配映射"的商品永远停在未归款。而且它和"这根商品没配过映射"在界面上**完全同形** ——
用户既看不出差别，也没有任何入口能触发它。

## 2. 决策：不给按钮，改成进页自愈

第一版方案是加一个「重放映射」按钮。改成自愈的理由（用户 2026-10-20 明确的产品原则）：

> 保证数据准确的同时，尽量减少人工介入；开始编码前先考虑有没有更好的方式。

按这条原则，这个动作不满足"需要人"的条件：

- 输入是**已被确认过的映射**，输出是**唯一确定的**（同一输入必得同一输出）；
- 唯一不确定的只是"有没有漏"，而那正是这一步要算出来的；
- 让人点一下，只是把"系统该自愈"变成"人记得点" —— 多一个可能被忘记的步骤。

落地为两处**进页时**自动执行（都在取数之前）：

| 入口 | 为什么在这里 |
| --- | --- |
| 基础数据 › 待补清单 | 它要报"还欠多少"，不先自愈就是在报旧数 |
| 发货台 › 归类核对 | 用户每天真正会进的那一页；漏网行在这里和"没配过映射"同形 |

两处都只 `onMounted` 一次（见 §4），且都用同一份 `replaySkuMappings`（幂等）。

## 3. 四条硬边界（少一条就会出事）

1. **只碰"未定/占位"**：候选行 = `style_color_id IS NULL` 或 `color = '未分类'`（或调用方显式点名的平台色名）。
   挂在真实颜色上的一律不动 —— 全库重放最怕的就是顺手改判历史结论。
2. **`dryRun` 只报数、不写库**：报数不能以改库为代价，否则"看一眼"就等于"悄悄执行一次写入"。
3. **幂等**：第二次跑 `fixedRows = 0`。页面会反复进，不幂等就是每次进页都重写库。
4. **自动修完必须说出来**：两页各有一行"已按现有映射自动补了 N 行归属"，`N = 0` 时整块不渲染。
   静默改库会让人以为数据本来就是这样 —— 比不修更糟。

## 4. 踩到的坑：挂 `token` 的 watch 上 ⇒ 一次进页跑 21 次

第一版把自愈也挂在 `watch(token)` 上（理由听起来正当："数据变了就重放"）。冒烟实测 **调用 21 次**：
`token` 在本页保存一行、翻一页、别处 `bump()` 都会变 —— 跟着它重放 = 每动一下把全表扫一遍。

更关键的是**语义上也不需要**：

- 新订单落库那一刻已经走过 `autoAssignByMap`（写时触发），恰恰不需要重放；
- 重放治的是**历史漏网**，进页一次就够。

修法：`onMounted → bootstrap()`（自愈 + 取数），`watch(token) → load()`（只取数）。
断言同时收紧成 `=== 1`，把"又挂回 token 上"这件事变成一条会红的守卫。

## 5. 验证

- `scripts/product-sku-smoke.cjs` +2：
  - ① 先导单后配映射 → `dryRun` 报得出但不写、真跑补上、再跑 0 改动（幂等）；
  - ② 人改成白色、映射是黑色 → 重放后仍是白色（**夹具必须让映射色 ≠ 人工色**，否则覆盖了也看不出来 —— 第一版就是恒绿的）。
- 变异：
  - 去掉 `dryRun` 分支的 `continue`（dryRun 也写）→ 用例① 红；
  - **候选筛选 + `autoAssignByMap` 结论守卫同时拆掉** → 用例② 红（只拆一层仍绿：两层是冗余保护，不是断言无效）。
- `master-data:ui` +1：夹具加两行"映射在、订单没吃到"（O-6/O-7），断言"补了 2 行 + `noColor` 是 1 单"。
  变异：把自愈挪到取数之后 → `noColor` 变 3 单、断言红（**这条钉的是顺序**）。
- `today:ui` +2：调用发生且 `=== 1`；没有可补时**不显示**回执（回执不是常驻横幅）。
- 门禁：`tsc` / `vue-tsc` / `verify` / `verify:docs` / `build` / 全量 vitest / `product:sku:smoke` / 两页 UI 冒烟。

## 6. 没做 / 下一处更根本的触发点

- **店铺归一之后**没有自动重放该店铺的订单。而 `resolveOrderSku` 的键是 `(platform, shop_id, item_id)`
  三元组 —— 店铺没归一，认款必然落空。所以"先导单、后登记店铺"这条路仍会留漏网，
  只是现在**有人进那两个页面时会自愈**。真要根治，触发点应该挪到"店铺归一/改绑"之后
  （跨域：`shop-db → order-db`，要先过 `check-cross-domain-edges.mjs`）。
- 采集通道（`source='collect'`）落库时 `image_id=NULL`，而 `autoAssignByMap` 第一句就是
  `if (!rec.imageId) return` ⇒ **采集订单不会自动归款**，重放也救不了（它们连候选行都进不去）。
  这条要么补图（用采集主图/色图当订单图），要么另开一条不依赖图片的归款路径。
