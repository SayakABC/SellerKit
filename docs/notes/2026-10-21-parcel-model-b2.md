# 包裹模型（一单多包 / 按商品行拆数量）—— 阶段 B2 落地

> **状态**：🟢 已落地（2026-10-21）· 数据层 + IPC + 拆包抽屉 + 两条守卫
> **读者**：架构 / 开发者
> **归属**：`docs/plans/ORDER_PURCHASE_MODEL_SIMPLIFY_PLAN.md` 阶段 B 的 **B2**（B1 拆表已于同日落地，行 id 约定见 `2026-10-21-order-table-split-b1.md`）

---

## 1. 一句话

`parcels` + `parcel_lines` 两张表（**新增、不改老表**）+ 「归类核对」行内「拆包」抽屉；
一个订单可以装成多个包，**一个商品行的件数可以拆到两个包里**；总运费/总重是 Σ 包裹（派生，不落库），
**任一个包缺值就是 null，不是"已知部分之和"**。

---

## 2. 数据模型

```
parcels(id, order_no, label, tracking_no, carrier, ship_cents, weight_g, note, created_at, updated_at)
parcel_lines(id, parcel_id → parcels, order_item_id → oi_order_items, qty, created_at,
             UNIQUE(parcel_id, order_item_id))
```

四条口径（改表前先读）：

1. **键是 `order_no`，不是订单主键**：B1 拆表前 `oi_orders` 一行 = 订单×商品图，一单天然多行、没有
   "订单主键"可指。`order_no` 是这单的唯一身份（AE 订单号全局唯一），B1 拆出订单主表后它正好就是主表的业务键，
   **数据不用改**。
2. **`ship_cents` / `weight_g` 可空（NULL = 还不知道），不给 DEFAULT 0** —— 与 `oi_orders` 的金额列同一条纪律。
   0 是"这包没花钱"，混起来会把"缺运费"算成"零运费"，利润凭空变大。
3. **总运费 / 总重派生**（`parcelTotals`）：任一个包缺值 ⇒ 整单 `null` + `shipMissing/weightMissing` 计数。
   界面据此说"还有 N 个包没填"，**不报一个看起来正常的和**。
4. **`UNIQUE(parcel_id, order_item_id)`**：同一行在同一个包里只有一条记录，数量写在那一条上 ——
   "同一行在同一包里记两次"在结构上不可能。

---

## 3. 拆包规则（只有一处实现）

`electron/order-db.ts` 的 `setParcelLineQty(parcelId, orderItemId, qty)` 是**唯一写入口**：

| 情况 | 行为 |
| --- | --- |
| `qty <= 0` | 从该包移除这一行 |
| 包与行**不属于同一张订单** | 拒绝，理由「这个商品行不属于该包裹所在的订单」 |
| 超过该行**还能拆**的件数 | 拒绝，理由带具体数字（「最多还能放 N 件」） |
| 该行 `qty` 未知（导入侧没解析出件数） | 不做上限校验（上限就是不知道），但仍要求 `qty > 0` |

"还能拆几件"只有一处算法（`parcelRemaining`）：界面显示与写入校验**共用**它。
两处各减一遍，必然有一天界面放行、落库拒绝（或反过来超拆）。

## 4. 界面落点（"界面上在哪里维护"的答案）

**「今天 › 归类核对」行内「拆包」按钮 → 右侧抽屉**（`src/modules/today/tabs/ParcelDrawer.vue`）。

- 为什么在归类核对：这一页是"逐单干活"的地方，一单一行看得见订单号；
  拆包与核对是**两件事**（核对待定"这行是什么款"，拆包定"这些件怎么装箱"），
  所以**两个范围（待核对/已核对）都给这个入口**，且不占「保存 / 确认无误」那组动作的位置。
- 行内徽标「拆包 ×N」（`order-parcel-counts` 批量问一次）：解决"不记得自己拆过没"。
  关掉抽屉会重算 —— 徽标不更新等于"看不到自己做过的事"。
- 抽屉里：上面是**这单的商品行**（件数 / 已分包 / 还能拆 / 放入哪个包），下面是**包裹卡片**
  （包名 / 运单号 / 承运 / 运费元 / 重量克 + 箱内明细）。
- **每次写成功都用主进程回的整单状态重绘**，不做本地推测：拆包天然是"多个包互相挤件数"，
  本地推测和库不一致时，用户看到的是"我明明点了保存"。

## 5. 与 B1（拆表）的关系（B1 已落地，2026-10-21）

- `parcel_lines.order_item_id` 指向 `oi_order_items.id`；B1 迁移**原样保留**了拆表前的 `oi_orders.id`，
  所以包裹明细的数据一条没动（真实库对照：51/51 行 id 不变）。
- 订单级 `总物流费 / 总克重` **没有落库**：B2 定案由 `parcelTotals(order_no)` 实时派生
  （一个数字一处实现，不先存一份再等着漂移）。
- 因此 B2 与 B1 的耦合只有"行 id 不许重排"这一条 —— 它写进了 B1 的迁移不变量，有
  `schema:smoke` 与真实库克隆双重守卫。

## 6. 守卫（怎么证明它没坏）

| 层 | 断言 |
| --- | --- |
| `scripts/order-db-smoke.cjs`［包裹］1 组 20+ 断言 | 拼错单号不造孤儿包 · 3 件拆 2+1 · 超拆被拒且理由含"还能放几件" · 跨单被拒 · **有包缺运费时总运费必须 null** · 补齐后才相加 · 改数量是覆盖不是追加 · 清 0 = 移出 · 删包连明细一起删 |
| `scripts/order-db-smoke.cjs`［9］4 条写入口守卫 | 空单号拒绝 · 导入不能往采集单追加 · **采集重推清包裹**（旧包 999 → 总运费必须变 null）· 采集不能替换导入单 |
| `scripts/today-ui-smoke.mjs`［parcel］7 条 | 入口在 · 徽标 ×2（真读 counts）· 抽屉开出来 · **出参单号非空** · 页头汇总 2 包/¥30.00 · **超拆被拒要显示理由** · **被拒后回读整单** · 新建包裹 2 包 → 3 包 |

> ⚠️ 这组 UI 断言当场抓到一个真 bug：拒绝理由被"回读"清空了（`load()` 开头清 `errorText`），
> 界面表现为"点了没反应"。修法是**先回读、再挂理由**（`ParcelDrawer.setLineQtyValue` 里有注释）。
> 这正是"假成功"最容易藏的地方：写操作失败 + 随后重绘 = 理由一闪而过。

## 7. 明确没做的事

- **运费没有接进利润**：`orderCost.ts` 仍读行级 `weight_g` 快照 + 运价表。
  `parcelTotals(order_no)` 已经可用，但"有包裹时用包裹总运费"的消费侧属于阶段 C 的前置。
- **没有"自动分包"**：按 SKU 行/重量自动装箱的规则没定，先只做人工拆。

## 8. 包裹的生命周期收尾（B1 一并落地）

| 动作 | 包裹怎么处理 |
| --- | --- |
| `deleteOrder(行 id)` | 明细被删后，**没有明细占着的空壳包一并删**；还装着别的商品行的包不动（`order-db.ts#deleteOrder`） |
| `clearAll()` | `parcels` 与订单/明细一起清空（不留孤儿包） |
| 采集重推同一单 | 整单替换会换掉全部明细 id ⇒ **先清该单的 `parcel_lines` + `parcels` 再替换**；否则旧包变空壳、继续污染 `parcelTotals` |
| 删单个包 | 显式先删 `parcel_lines` 再删包（不依赖连接级 `PRAGMA foreign_keys`） |
