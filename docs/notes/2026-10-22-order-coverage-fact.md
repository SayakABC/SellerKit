# 「哪张订单的货齐了」从推测变成事实 —— 差的是 `purchase_sources.order_item_id`（2026-10-22）

## 结论

用户问「拿完货后，怎么才能知道哪些订单的货拿完了？」，当时的答案是**看不了**：全应用最细只到
款色码，订单级的"齐了"不存在。但**分配逻辑其实早就在跑** —— 生成拿货单时
`purchase-db.autoSourceRows()` 已经按 `oi_order_items.id` 做 FIFO（"这 N 件补给哪几条订单行"
当时就算出来了），只是最后一步**把 `oi.id` 扔了**，只存了店铺名。

所以这不是一次功能设计，而是一次**补边**：给 `purchase_sources` 加一列 `order_item_id`，
把已经算出来的结论存下来。今天的"已拿"因此从「款色码总量近似」升级成「逐行精确」。

## 为什么之前回答不了：两条缺边

| 边 | 状态 | 后果 |
|---|---|---|
| 拿货单 → 订单行 | `purchase_items` 无 `order_no`；`purchase_sources` 有分配结果但**只存了 shop** | "这 1 件补给了哪张单"库里不存在 |
| 拿货 → 订单（时间） | `oi_orders.ship_time` 只来自导入报表的「发货时间」列 | 应用内**没有**"这单货齐了"这个动作 ⇒ 提交拿货单在系统里是零事件 |

四处可能被用来回答这个问题的界面，都不是按订单判定的：

- **总览四格**：当天整体汇总，`还差 0` 只说"今天这批总量齐了"；
- **拿货页厂家卡**：款色码粒度，拿齐的行**从缺口消失**，没有"已齐"可回看；
- **拣货清单**：未发货订单，与拿没拿无关；
- **对账页**：纯金额（拿货 / 已付 / 已退 / 欠款）。

## 数据链（一处算、一处拼键）

```
oi_order_items ─┐
                ├─ autoSourceRows() 按件 FIFO → purchase_sources.order_item_id
purchase_items ─┘                                    │
                                                     ▼
                              purchase-order-coverage（只读 IPC）
                                rows: 未发货+非终结行 × covered 件数
                                unattributed: 无归属台账（items − 已归属差额）
                                                     │
                              coverageInputs()（列名/键只在这里翻译一次）
                                                     │
                              planCoverage() → groupByOrder() → coverageSummary()
                                   │                    │
                        总览 dailyShip()        「按单核对」两段清单
```

**总览与清单必须是同一份实现**：两处各算一遍，总览说"全齐了"、清单说"还差 1 件"是必然会发生的
（本仓铁律 5：每个数字只能有一处实现）。

## 口径与边界（都要在界面上说出口）

- **存量只能补"能由事实唯一确定"的行**：该（拿货单, 款色码）组里只有一条来源行 + 该款色码在
  未发货订单里只有一条候选行 + 那条只覆盖 1 件 —— 三者同时成立才认。真库实测 13 条来源行里
  只有 3 条符合（其余要么候选不唯一，要么所在单是草稿）。猜错的代价是**把别的单宣布成已齐**。
- **`order_item_id = 0` 是合法取值**，不是脏数据：历史单没归属、这次拿多了的尾巴也没有订单行可指。
  它们进 `unattributed` 池子，按款色码先到先得摊，摊到的部分标 `estimated`，界面写明"按款色总量估算"。
- **范围两边不同，且是对的**：`outstanding()` / `orderCoverage()` = 全部未发货订单（货和钱跨天结转），
  总览四格 = 今天导入的那批（第 1–2 步的口径）。所以"总览说齐了"不等于"没有单还差点货"。
- **未识别款不摊池子**：款编码为空时 `takenKeyOf` 会拼出空键，把"同色同码的不同商品"并成一格，
  凭空宣布已拿是漏货式的静默错。与 `outstanding()` 的 `have = 0` 同口径。

## 顺带修掉的两处既有偏差（`autoSourceRows`）

今天它们只让"店铺成本分摊"少记几行（不致命），但一旦变成"哪单齐了"的判据，就会给出
**看着很正常、实际错了**的答案：

1. **没有范围过滤**：查订单行时缺 `ship_time='' AND status<>'shipped' AND NOT 终结`
   （`outstanding()` 有）⇒ 会把这次拿货分给**已发货甚至已取消**的订单；
2. **件数当行数跳**：`skip -= 1` 每行只跳 1 件，而需求按件算（`SUM(COALESCE(NULLIF(qty,0),1))`）
   ⇒ 一单买 2 件时多跳一行、少记来源。改成按件跳过、`qty` 记该行被覆盖的件数。

## 守卫（每条都问过"改坏哪一行它会红"）

| 守卫 | 改坏什么会红 |
|---|---|
| 池子按**订单行 id 升序**摊（传入顺序倒置） | 改成按数组顺序摊 ⇒ 摊给后下的那一单 |
| 一件台账只被吃掉一次（两行各要 1 件、台账 1 件 ⇒ 合计 1） | 扣减后不回写池子 ⇒ 合计变 2 |
| 精确 + 池子不重复（已按行归属的那件不再从台账扣） | 两段都扣 ⇒ 已拿虚高、缺口提前变 0 |
| 未识别款不摊（故意在池子里放空键记录） | 用空串键去匹配 ⇒ 已拿凭空 +2 |
| 冒烟：可以发货的是**哪一张**（I-1 而不是 I-2） | 忽略 `covered` ⇒ 变成 0 单；按款色总量摊 ⇒ 摊错单 |
| 冒烟：两段互斥（齐了的单不出现在「还差」里） | 分桶判据写错（`covered >= qty` 写成 `> 0`） |
| 冒烟：件数守恒（共 6 件 / 已拿 1 件） | 件数退回按行数算 |
| 冒烟：取数走 `purchase-order-coverage` | 退回读 `purchase-taken` 整条台账 |

变异实测：把 `dailyShip(all, { taken })` 退回成"整个台账当池子"，四格数字与进度条**同时**变红。

## 没做什么（以及为什么）

- **不加"标记已发货"按钮**：发货时点是平台回传的（`oi_orders.ship_time` 来自导入报表），
  应用内没有这个动作。造一个本地开关只会和平台数据打架 —— 这一屏只回答"货到齐了没有"。
- **不给历史拿货单补订单号**：`purchase_items` 没有订单号，历史数据无从追溯；能补的只有
  "唯一确定"的那几条（见上）。界面用 `estimated` 把这层不确定性说出来，比给一个假装精确的数好。
- **不做跨天的时间线**：`orderCoverage()` 给的是"当前状态"，不回答"哪天齐的"。要时间线得先有
  "齐了"这个事件的落点，而它正是本轮刻意不造的那个字段。
