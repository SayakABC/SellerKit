# 拖到「常用色」上归类：落点是字典，不是另一个 chip

**结论（2026-10-24 用户口径「拖动颜色里的项，拖动到常用色中进行归类，最终存储的以常用色为主，
最终存储颜色的图片保留一张」）**

1. **落点改成顶部那排「常用色」**：把下面某个颜色 chip 拖到某个常用色上松手，那个色就归到这个
   规范名下。下面那排 chip 只有 22px 高、里面还嵌着输入框，是"拖动不方便"的根 —— 顶部是 10 个
   固定靶子，每个自带色块和名字，不会拖到"旁边那一格"。
   落到另一个 chip 上的合并**保留**（处理两个色都不在字典里的情况，如 `香芋紫`）。
2. **勾 = 矩阵里真有这个色名**（`trim` 后全等）。没有就保持原始状态，不拿近似色冒充打勾。
   这个判据同时决定"拖上去会发生什么"，**两处必须是同一个函数**（`hasColor`），否则会出现
   "打了勾，拖上去却改了名"。
3. **两种语义，落库色名一律取字典写法**（`classifyMatrixColor`）：
   - 目标色**已在矩阵里** ⇒ 并进那一行（`mergeMatrixColor`：格连同 `variantId` 一起搬、行序不变），
     再把目标行色名统一成字典写法；
   - 目标色**还不在矩阵里** ⇒ **原地改名**（`cells` / `variantId` / `imageUrl` 一个都不动）——
     "采集来的 `藏蓝` 归到 `藏青`"是改标签，不是删旧建新。
4. **一个色只留一张色图**：图挂在 `SkuMatrixRow.imageUrl`（一个字段），合并时优先保目标行的、
   目标行没图才用源行的。图**不按格存**是刻意的 —— 按格存会让"同一个色下十条 SKU 挂着三张
   互相矛盾的图"成为可能。

## 四个坑（都真的踩到了）

1. **`onChipMove` / `pointerup` 原来挂在 `.mx-colors` 上** ⇒ 鼠标一离开那一条就收不到
   `pointermove`，**根本拖不到上面的常用色**（不是"瞄准难"，是事件根本不来）。改挂**根元素**
   `.mx`，另加 `window` 级 `pointerup` 兜底：松手落在组件外（矩阵表格、抽屉空白）也必须收尾，
   否则状态卡在"拖动中"（鼠标已抬起、界面还灰着一片）。
2. **往"刚点常用色新建的空白行"上合并会删旧建新**：同码冲突原本无条件保留目标格，
   而新行没 `variantId` ⇒ 已落库那条被丢、保存时删掉再造一条（编码 / 状态 / 历史一起没）。
   现在冲突格里**目标格没 id 就接过源格的 id**；真会消失的 SKU 数单独用 `dropped` 数
   （`conflicts` 是"同码格数"，不是"少几个 SKU" —— 拿它写回执会谎报损失）。
3. **`.mx-color__img` 挂在颜色 chip 上，不在矩阵行上**：第一版断言量 `[data-act="ed-row"]`
   里的图片数，得到 `imgs/row=0` 的假红。断言前先问"这个元素属于哪一层"。
4. **收尾不能假设一定弹「放弃改动」**：本步最后把 `黑` 改名成 `藏青` 又并回 `黑`，净结果与库里
   一致 ⇒ 保存计划是空的，抽屉**直接关**（这本身是个好信号，已加成断言）。写收尾要先判 dialog
   再点，否则 `clickText` 会在 4s 后抛"找不到可点击元素"，把一条通过了的步骤报成失败。
5. （老坑重犯）**注入脚本的注释里又写了反引号** —— 整段模板串被截断，报的却是
   `SyntaxError: Unexpected identifier 'mx'`，指向注释里的一个词。写"这样的东西"时一律用中文引号。
6. **`<img>` 在 Chromium 里默认可拖**：色图现在既是显示也是**拖动手柄**，不关掉原生拖放就会在
   按下时先起一个 `dragstart`，指针事件随之断掉（表现：拖不动）。已加 `draggable="false"` +
   `-webkit-user-drag: none` + `user-select: none`。**这条合成事件抓不到**（冒烟 `--dump-dom`
   发不了可信输入）—— 所以取证靠 `goods:shot` 里的 CDP 真鼠标探针，而不是靠"冒烟全绿"。
