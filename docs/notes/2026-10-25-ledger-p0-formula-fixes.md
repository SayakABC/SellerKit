# 记账 P0：三处口径错误是"写代码时才暴露"的，不是设计时能看出来的

## 结论（下次改记账相关代码前先看这五条）

1. **未结清 = 净往来 `+` 已结算净额**（方案原文写的是减号）。
   代入"我欠 1000、已付 1000"：减法得 `−1000 − 1000 = −2000`（越结越欠），加法才是 0。
   `已结算净额 = Σpay − Σreceive` 是**对净往来的调整量**（付出为正），不是"已结掉多少钱"。

2. **结算上限必须按"方向"取，不能按净额取。**
   同一个供应商常常既欠我钱（退货/返利）又该我付（新货款）。应收 5000、应付 3000 时净额只有 2000，
   拿 `|净额|` 当上限会把"该付的 3000"判成超额 —— 这笔账永远结不掉。
   故往来要给**六个数**：应收 / 应付 / 净往来 / 已结算 / 未结清 / 分方向未结清（应收方向、应付方向）。

3. **合并相关人（B 路）不写 `bk_transfers`。**
   原方案写"未结算条目改挂 + 写一条结转"，那是**把同一笔钱算两遍**：条目的余额已经随改挂带过去了。
   正确 = 只改挂未结算条目，已结算条目留在原人（与它的结算单一起）。
   验收判据因此可以断言：**合并后原人的未结清必须为 0**。
   ⚠️ 但 **残额兜底分支要保留**：若改挂后算出来原人未结清仍 ≠ 0（例如原人此前靠 `bk_transfers`
   承接过别人的余额，那部分不随条目走），才写一条 transfer 把它带过去。正常路径恒为 0、写不进去。
   判据是"残额 ≠ 0 才写"，不是"永不写"—— 别照本条标题把兜底删了。

4. **结算行的唯一性必须是部分唯一索引 `UNIQUE(entry_id) WHERE active = 1`。**
   内联 `UNIQUE(entry_id)` 会让"撤销结算"功能直接废掉：结算单作废了，但这批条目仍被旧结算行占着，
   永远无法重新结算。作废时把结算行 `active=0`（不删，保留"这张单当时结了哪几条"的痕迹）。

5. **`period` 用 SQLite 生成列，不要用 JS 派生落库。**
   `period TEXT GENERATED ALWAYS AS (substr(biz_date,1,7)) STORED`：任何写入方都给不错，
   也不需要主进程/渲染层各写一遍 `slice(0,7)`（两边口径一歪，跨月那几笔就漏进某个月且不报错）。

## 一条被结构强制的分工

分摊算法**只能**在渲染层 `src/lib/ledger.ts`，主进程只做守恒断言。
原因不是风格：`tsconfig.electron.json` 的 `rootDir: "electron"` 使主进程**无法** `import '../src/lib/…'`
（TS6059）。所以别试图"主进程也算一遍"—— 真出现非渲染层写入方（Excel 批量导入 / 定时生成）时，
只能在 `electron/` 下新拆一个同算法模块（届时 `src/lib/ledger.ts` 改为 import 它，或反之），
并给两边补 parity 用例；**不要**把算法复制成第二份。

同理，`partyLedger.ts`（JS 口径）与 `ledger-db.ts` 的台账 SQL 是两份实现，靠
`npm run ledger:smoke` 的 `[7]` 段用固定期望值钉住同构。改一边必须看另一边。

## 取证

```bash
npx vitest run tests/ledger.spec.ts tests/partyLedger.spec.ts   # 26 + 22 例
npx tsc -p tsconfig.electron.json && npm run ledger:smoke        # 31 项真库断言
```

- 符号：`src/lib/partyLedger.ts` 文件头 §2/§3；单测「已付出去的结算冲减欠款」「分方向余额之差恒等于净额」
- 方向上限：`src/lib/partyLedger.ts` 的 `canSettle` 注释；单测「混方向：应收 5000 / 应付 3000 时两笔都能结」；
  数据层 `scripts/ledger-db-smoke.cjs` 段 `[7]` 同名用例
- 合并：`electron/ledger-db.ts` 的 `mergeParty` 注释；冒烟段 `[6]`「合并后原人未结清必须为 0」
- 部分唯一索引：`electron/ledger-db.ts` 的 `LEDGER_SCHEMA` 里 `uq_bk_settle_line_entry`；
  冒烟「撤销结算：作废 + 结算行失活，条目恢复可结」
- 生成列：`bk_entries` DDL 的 `period` 行；冒烟「period 由生成列派生」

## 没改的东西（别顺手"修"）

- 「结算时顺手记一笔支出」在结构上就写不进去：`bk_entries` 没有"结算来源"字段（RK-03 的防线）。
- 分摊行没有业务写入口，也不允许手改单行（会变成第二份真相）。
- 已结算条目只允许改备注/科目/日期；改金额/方向/范围/店铺/相关人一律拒（先撤销结算）。
