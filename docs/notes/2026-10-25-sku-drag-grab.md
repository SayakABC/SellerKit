# 拖色的"区域太小"不是尺寸问题，是**只有 26px 能按**：抓手扩到整条 chip、落点改最近邻、另给一条不用拖的路

**日期**：2026-10-25 · **用户口径**：「现在的拖动区域太小，操作太不方便了，请重新设计」。

**与旧笔记的关系**：不取代任何一条。承接
[`2026-10-24-product-editor-two-pane`](2026-10-24-product-editor-two-pane.md)、
[`2026-10-24-sku-matrix-compact`](2026-10-24-sku-matrix-compact.md)（版面）、
[`2026-10-25-sku-weight-by-size`](2026-10-25-sku-weight-by-size.md)（克重粒度）。
这一轮只动**颜色行上的手势**（拖色归类 / 合并），不动矩阵格、不动克重。

## 先量：到底"小"在哪

改之前用探针（复用 `goods-shot` 的假桥 + CDP）在 1440×900 真机渲染下量了这一排：

| 量的是什么 | 实测 | 后果 |
| --- | --- | --- |
| 一条颜色 chip | **125 × 30** | 看着不小 |
| 里面**能按住**的部分 | **26 × 26**（只有色图） | 整条 125px 里 96px 是 input 与 ✕ |
| 落点（常用色胶囊） | **42 × 22** | 宽高都只有 chip 的 1/3 |
| 胶囊底边 → 颜色行顶边 | **6px** | 拖错一格就落到隔壁语义 |
| 判定方式 | `elementFromPoint` **点中矩形** | 偏 20px 就等于没拖 |

决定性的一条是第二行：`onChipDown` 当时写着 `if (el?.closest('input,textarea,select')) return;`
（本意是"色名要能拖选文字"）。于是**手指落在色名上的概率远大于落在色图上**，
表现就是用户说的「拖不动 / 区域太小」——**不是控件的像素不够，是可抓的像素太少**。

## 三处改动

### 1. 抓手：整条 chip（含色名）都能起拖，但只在竖向

`closest('input') ⇒ return` 换成"记下它是不是输入框"，由**方向**分意图：

- 垂直位移 ≥ 10px 且明显大于水平 ⇒ **拖这一行**（先把已经拖出的文字选区 `removeAllRanges()` 清掉）；
- 否则 ⇒ 原生行为（拖选文字）。

为什么用方向而不是"加一个抓手图标"：颜色行是横排的，人已经从**下面那一行**往上拖，
竖向是这条手势的天然主轴；横向拖选文字也同样是天然主轴。两者不冲突，不需要多一个 10px 的抓手条
去挤本来就要换行的色名。

### 2. 落点：从"点中矩形"改成"离谁最近"

`resolveDropAt` 不再问 `elementFromPoint`（它只回答"指针底下是谁"，落在 6px 缝里就是"没人"），
改为对 `[data-mx-pc]` 与 `[data-mx-row]` 逐个算**矩形外扩后的距离**（横向 16px / 纵向 12px），
取最近的一个：

- 有效落点 **42 × 22 → 74 × 46**（约 3.7 倍），落在胶囊之间的空隙里也算最近的胶囊；
- 胶囊行与颜色行只隔 6px，靠"谁更近"天然互斥 —— 定优先级会把这 6px 判给上方，
  而人从下方拖上来时正是要在这里判"我要并进隔壁行"；
- 副作用是好的：指针压在 chip 内的 input 上、压在两个 chip 的 4px 间隙里，都有稳定答案。

顺带把可点尺寸抬了一档：色图 26 → **28**、胶囊 22 → **24**（前者是抓手，后者是落点，
都只有几十像素，2px 就是 8% 的命中率）。

### 3. 不用拖的那条路：色名候选

拖动是把两件事画在**一个连续手势**上，天生要求精度。而"这一色该叫什么"本质是**挑一个词**。
所以点进色名框就给出候选（`Teleport` 到 body + `fixed`，否则会被 `.mx-colors` 的
`overflow-y: auto` 裁掉一半）：

- 分两组：**归到常用色**（主路径，落库色名取字典写法）/ **并入其它颜色**（两个色都不在字典里时的兜底）；
- 每项写明"会发生什么"，但只有四个字（`归类` / `并入已有` / `合并两行`）——
  写全（"归类（原地改名，SKU 不丢）"）会占掉一半宽度、把色名挤成省略号，且重复 9 遍；
- ↑↓ 选、Enter 采用（**必须 preventDefault**：这个组件挂在表单里，不拦会连带提交）、Esc 收起；
- 打开时机：`focus` **和** `click` 都要 —— 关掉之后焦点还在框上，再点一下不会再触发 `focus`；
- 收起时机：`blur`、点浮层外（`document` 级 `pointerdown`）、开始拖动。
  光靠 `blur` 不够：点到矩阵格子/空白处时焦点**没有转移**，input 不 blur ⇒ 菜单一直飘着挡矩阵。

两条路都通向同一个 `classifyInto` / `mergeColorInto`：**落库语义只有一份**。

## 遗留（知情不做）

- 浮层不跟随滚动：`.mx-colors` 那一排滚动时它停在原处。它的生命周期是"点一下、挑一个"，
  跟随需要监听 scroll + resize 重算 rect，收益低于复杂度；真要滚就先收起（点外面即收）。
- 窄窗口（默认 1000×700）下浮层可能盖住矩阵头两行 —— 它本来就是覆盖层，选完即收。
- 矩阵格的拖动（跨格填充）仍未提供：`2026-10-25-sku-weight-by-size` 里已判定
  "加入=敲数、取消=Delete"之后，跨格拖动只是另一种批量填，收益不如行头/列头开关。
