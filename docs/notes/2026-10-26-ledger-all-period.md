# 记账明细「全部日期」：一个选项背后有四个静默失败点

日期：2026-10-26
触发：明细页只能按月看，查一笔往年的账要一个月一个月往回翻。

这个功能本身很小（一个按钮 + 一个 `if`），但它把「期间」这个词在四层里同时放大了一遍：
状态层、主进程查询、跨页共享、偏好持久化。每一层出错的共同点是**没有报错**。

## 一、哨兵值可以存在，但不能发出去

状态层用 `ALL_PERIOD = 'all'` 表示全部，因为 `''` 太危险：偏好文件里的月份一旦丢了，
`''` 会被主进程当成"不过滤"，界面**静默**变成全部期间，而用户以为自己在看本月 ——
数字全对、范围全错，是最难发现的一类。用一个与 `YYYY-MM` 不可能撞车的值，坏数据只会落回本月。

但**发请求时必须换成"不带这个字段"**：

- 主进程（`electron/ledger-db.ts`）的判据是 `if (filter.period) where.push('e.period = ?')`，
  它只 `slice` 不校验格式。传 `'all'` 不会抛错，只会拼成 `e.period = 'all'`，查出 0 行。
- 于是"点了全部，列表一片空白"看起来像没有数据，而不像参数传错。

合计那一路同理，但要传 `''`（`ledgerSummary({ period: '' })`），与「往来」页的对账恒等式
本来就是同一个口径 —— 那里早就有"全期间"的用法，这次是把它接到明细页上，不是新造一个。

## 二、口径必须写在标签上

`XXXX年X月 · 整月` ↔ `全部日期 · 累计`。

不写成泛泛的"本月"是有原因的：明细页顶部合计**只认期间、不跟筛选联动**（选店铺后合计仍是整月的，
否则公共支出会被整笔算进单店）。既然这个数不跟筛选走，用户就只能靠标签知道它是哪一段的数。
全部日期下继续说"整月"，等于告诉用户一个错误的期间。

## 三、全部日期下翻月：从"本月"往回翻

`shiftMonth` 原来是 `month.value.split('-')`。当 `month === 'all'` 时：

```js
const [y, m] = 'all'.split('-').map(Number);   // y = NaN, m = undefined
`${NaN}-${NaN}` === 'NaN-NaN'                   // 合法字符串，任何存在性检查都不报错
```

主进程只 `slice`，于是 `e.period = 'NaN-NaN'` → 一条都没有，还是不报错。
修法是翻月前先判断：全部日期时以**本月**为基准，`‹` = 上一个月，`›` = 下一个月。

单店页（`ShopView.vue`）与汇总页（`SummaryView.vue`）各有一份自己的 `shiftMonth`，
三处都要改 —— 这是这个仓库既有的重复实现，改一个漏两个照样是"翻一下之后一条都不剩"。

## 四、哪些页能算全期间，要按**取数能力**判

三个页签共享同一个 `month` 状态，所以用户在明细页点了「全部」，切到单店/汇总时
`month === 'all'` 一定会到那里。两种做法：

- 那两页显示"请选具体月份"（拒绝）；
- 或者让它们也真算全期间。

按"能不能算"逐个判，而不是按"页面该不该有这个概念"：

| 内容 | 全期间可行？ | 原因 |
|---|---|---|
| 明细列表 / 期间合计 | ✅ | 流量，跨月相加有意义；合计走 SQL 聚合，不受 1000 行上限影响 |
| 单店收支 / 科目分布 / 公摊明细 | ✅ | `shopBreakdown` 不传 `period` 就是全期间，语义成立 |
| 汇总页各店累计 | ✅ | 累计比按期相加更自然 |
| 单店页「订单收入对照」 | ❌ | `orderShippingRows` 按月拉、有 2000 行上限；跨月必然截断，算出来的只是**下限** |

最后那条是关键：截断后的订单收入如果照常显示，会得出"记账收入比订单收入多"这种
**方向性错误**的结论。所以全部日期下不取数、两项显示 "—" 并写清原因 ——
宁可少一个对照，不可多一个错结论。

## 五、顺手补的两处

1. **导出**：文件名与表头期间跟着变成「全部日期」；列表撞上 `LIST_LIMIT` 时在筛选说明里追加
   「导出只含当前显示的这些」。不写的话，用户以为整本账都导出来了 —— 表头写着"全部日期"尤其危险。
2. **导入 / 记一笔完成后不再自动跳月**：原来的逻辑是"记的是别的月份的账就切过去，否则看不到"。
   全部日期下本来就看得见，硬切会把用户刚选的期间改掉。

## 验证

- `tests/ledgerPeriod.spec.ts`（新增 6 例）：默认本月 / 全部时不带 period + 合计传空串 /
  从全部切回具体月份 / 翻月不是 `NaN-NaN` / 偏好 `all` 能还原 / 坏值回落本月。
  mock 只做 `storage` + `api` 两层，断言的是**发出去的请求**，不是屏幕上的数字。
- `scripts/ledger-ui-smoke.mjs`（新增 5 条）：最决定性的一条是
  **从上个月（空态）点「全部」→ 必须变回 6 行**。空月变有数据，说明真的没按月过滤；
  如果只在本月点「全部」，行数前后都是 6，传不传 period 都看不出来。
- 变异三处，逐一变红：
  1. `filter.period` 直接传 `month.value`（把 `all` 发出去）→ ① 组 2 例红；
  2. `init()` 的偏好还原去掉 `ALL_PERIOD` → ③ 组红（"设定不生效"型）；
  3. `shiftMonth` 不判全部 → ② 组红，报错就是 `expected 'NaN-NaN' to be '2026-09'`。

第三条尤其值得记：`NaN-NaN` 不会抛异常、不会被 `if (period)` 判假、也不会被任何
"这个值存在吗"的检查拦住。只有一条**格式断言**（`/^\d{4}-\d{2}$/`）能抓住它。

## 踩到的老坑（第 N 次）

- 假桥是模板字符串，**断言代码块里的注释不能出现反引号** —— `node --check` 当场报
  `SyntaxError: Unexpected identifier`。
- macOS 的 BSD `grep` **不支持 `a\|b` 交替**，`grep "ALL_PERIOD\|isAllPeriod"` 静默返回无命中，
  一度以为改动丢了。用 `grep -E` 或 Grep 工具。
