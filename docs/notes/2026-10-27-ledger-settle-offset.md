# 互抵结清：一张单核销两边，只走差额

日期：2026-10-27
触发：用户问「往来里收入和支出相同的情况下，结算还需要付钱？」——账上净额 0，
点结算却提示"应付方向可结 ¥1000"。

## 一、"净额为零 ≠ 两清"是设计，不是 bug

系统给每个人同时记两条账轨（应收 / 应付），结算按**条目逐笔核销**，不做净额轧账。
于是"应收 1000、应付 1000"在页面上是：

- 净往来 ¥0、未结清 ¥0（看起来两清）
- 可收 ¥1000、可付 ¥1000（实际两笔都没结）

用户只看到前一行，自然会问"为什么还要付钱"。

不按净额当上限是方案 §6.2 修正 2 定过的：同一个供应商既欠我钱（退货/返利）又该我付
（新货款）时，净额更小会把"该付的那笔"误判成超额，这笔账永远结不掉。

> 真正的缺口不是口径，而是**没有"互相抵掉"的入口**。用户的两笔账在业务上要相抵，
> 系统只能逼他"付一张 + 收一张"，资金流水凭空多一进一出。

## 二、行业口径：核销（clearing）/ 冲抵（offsetting）

| 系统 | 做法 | 关键点 |
|---|---|---|
| 用友 / 金蝶 | 「往来核销 → 应收冲应付」生成往来转账单 | 一张单同时减两边余额，不走资金流水 |
| SAP FI | Clearing（F-32 客户清账） | 同一往来人的 debit/credit item 互清，剩余项保留 |
| QuickBooks / Xero | Bill Credit / Pay down | 用信用额度冲应付 |
| 合思 / 汇联易 | 借款单核销报销单 | 报销金额 − 借款余额 = 实际打款 |

共同点：**单据记毛额、资金流记净额、两者分开存**。会计上还有一条硬约束 ——
只允许**同一往来对象**内部抵销，不能跨人。本实现照此：互抵单必须同一个 `party_id`。

## 三、毛额落库，资金流派生（唯一一处口径）

`bk_settlements.amount_cents` 对互抵单记的是**行和**（毛额 1400），不是实付 600。

为什么不让它记净额：

1. `createSettlement` 有一条对账断言 `Σ结算行 == 单据金额`。改成净额就失效 ——
   而这条断言是"手改金额"与"勾错条目"的唯一区分手段（方案 §6.3 原始理由）。
2. 净额可能是 0（各 1000 完全对冲），而 `amount_cents` 有 `CHECK (> 0)`。
3. 两套口径一旦并存，下次改代码的人一定会混用其中一个。

实付由 `payCents - receiveCents` **派生**：`listSettlements` 现算、`createSettlement` 返回，
不落库。界面显示的"付 ¥600"与单据里的 1400 是同一份数据的两种视图，不是两个数。

## 四、余额算法必须改成"按条目 kind 聚合"

原实现按**单据 direction** 汇总已结算金额：

```sql
SUM(CASE WHEN direction = 'pay' THEN amount_cents ELSE 0 END) AS settled_pay
```

互抵单的 direction 是 `offset`，两个 SUM 都落到 0 —— 结了等于没结，`可收/可付` 一点不减。
改成按**结算行所关联条目的收/支**聚合：

```sql
SUM(CASE WHEN e.kind = 'expense' THEN l.amount_cents ELSE 0 END) AS settled_pay
SUM(CASE WHEN e.kind = 'income'  THEN l.amount_cents ELSE 0 END) AS settled_receive
```

对存量普通单是等价的（它们只含同一类行），但顺手也把"单据方向与条目方向不一致"这种
历史脏数据的影响消掉了 —— 余额从此只信条目，不信单据上那个标签。

**两侧必须各减各的毛额。** 只减净额的话，应付 1000/应收 400 互抵后应付归零、应收还剩 400，
用户会被引导去再收一次已经抵掉的钱。单测与冒烟各有三条守着这个（变异测试：把两侧改回净额，
`partyLedger.spec.ts` 红 3 例、`ledger-db-smoke` 红 3 项）。

## 五、迁移：SQLite 改不了 CHECK，只能重建表，但顺序不能照抄

`direction` 的 CHECK 从 `('pay','receive')` 放开 `'offset'`，只能重建表。项目里已有先例
（`product-db.ts` 的 `normalizeSkuUniqueKey`），但**不能照抄它的顺序**：

它先 `ALTER TABLE ... RENAME TO ..._legacy`。对 `bk_settlements` 这么做的话，SQLite 3.25+
会把子表 `bk_settlement_lines.REFERENCES bk_settlements` 的**文本**改写成 `_legacy`；
老表一 DROP，结算行就指向一张不存在的表。而本项目 `foreign_keys` 是 OFF（从未开启），
**不会报错** —— 迁移"成功"、schema 已经歪了，属于最难查的一类。

所以走另一条顺序：建 `_rebuild` 新表 → 拷数据 → `DROP` 老表 → `RENAME` 新表。
子表引用的是 `bk_settlements`，换名后正好指回新表。迁移末尾补回随老表消失的索引，
并按 `MAX(id)` 重置 `sqlite_sequence`（不重置会让新单复用已发出的 id）。

`ledger-db-smoke.cjs` 有一条专门造老形状再迁移的用例，断言：CHECK 放开、老数据还在、
子表外键文本仍指向 `bk_settlements`、索引补回、新 id 大于旧 id。

## 六、界面：把"能互抵"写在用户会卡住的地方

两个方向都有余额时，弹层多一行提示（`data-act="settle-offset-tip"`），
否则用户只会看到"应付方向可结 ¥1000"，回到最初那个困惑。

互抵模式下：

- 候选不再按方向过滤，每条前面多一列「收/支」
- 汇总拆开写「支出 ¥1000 · 收入 ¥400」，右侧单独给「资金流 付 ¥600」
- 只勾单边时**提交直接禁用**并提示改选方向 —— 放过去用户会以为"抵过了"，实际只清了一边

## 七、两个测试坑

1. **UI 假桥必须跟着实现 offset 分支**。假桥里如果只按 direction 汇总，界面照样"全绿"，
   但它测的是假桥自己。`settleSides()` 就是为此加的：与主进程同一口径（按条目 kind 拆毛额）。
2. **夹具不能预置"两边都有余额"的人**。他会改变往来台账人数、合计、对账恒等式、
   改挂下拉选项 —— 七条与互抵无关的断言全要跟着改具体数值，而那些数字正是它们要守的东西。
   改成流程末尾 `window.__smokeLedger.addOffsetFixture()` 按需插入，既有断言一个不动。

## 八、仍然不做

- **部分核销**：单据金额恒等于结算行之和，一条条目只能整条结清。要"先付一半"仍需撤销重结。
- **跨人抵销**：只在同一个 `party_id` 内允许（会计上也需要双方确认的抵销依据）。
