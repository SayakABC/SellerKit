# 批量操作不是「加一排复选框」：以「归类核对」批量定款为例

> 2026-10-28 · 「发货台 › 归类核对」第二阶段。上一篇是
> `docs/notes/2026-10-28-classify-style-picker.md`（把下拉换成带图选择器）。
> 这一篇讲的是**用户第二遍抱怨**之后才做对的那件事。

## 症状与它的真实形状

第一版解决的是"看不准"（下拉只有文字、判据却是图）。上线后用户立刻给了第二句话：

> 归属款还是只能一个一个选，这样路径太长了，需要点击、选择、关闭、确认。

四个动作被逐个点名，说明他数的不是"决策"，而是**点击数**。而第一版恰好把点击数又加了一点
（多了一个"确定"按钮）。这件事的教训不在于"弹层做错了"，而在于：

**判断一个操作该不该批量，先数"同一个决定重复了几次"，而不是先加复选框。**

真库数：待核对 42 行，按「店铺 + 商品ID」去重只有 **17 个商品**。也就是说 60% 的"决定"
是同一个决定的重复 —— 这些行本来就该一次做完。**批量的最小单位是商品，不是行。**

## 三条设计结论

### ① 批量的单位要按「业务上相同的那些行」定，不能按"勾中的行"定

"勾了 5 行 → 给它们定同一个款"看起来最直接，但它对**跨商品**的勾选是错的：5 行可能属于 5 款。
反过来"一行一个选择器"又退回了逐行。

正确的形态是**分组**：弹层里按商品列卡片，每组选一次款。只有一个商品时它自然退化成
"一个款选择器"（`bp-groups` 整块不渲染），不需要两套 UI。

⚠️ 分组键必须与页面上「同商品 ×N」徽标**用同一个函数**（`src/lib/classifyBulk.ts` 的
`productKeyOf`）。各算一份的典型症状：徽标说这 3 行同商品，弹层却拆成 3 组（或反过来）——
用户不会报"分组错了"，只会说"这功能不太准"。

⚠️ 没有商品ID 的行**各自成组**。把它们合在一起 = 把两件不相关的商品按同一个款落库，
而这种错在下游（取图 / 拿货 / 算钱全按「款 + 色」匹配）既不会报错、也查不出来。

### ② 按钮上的数字必须等于**真的会被处理**的行数

勾了 5 行、其中 1 行有未保存的改动 ⇒ 按钮写「确认无误（4）」，旁边另写"其中 1 行有未保存的改动"。

原因：「确认无误」**不写任何字段**，只翻 `corrected` 位。它一旦把脏行带走，用户刚填的款/色
就静默丢了 —— 真库 2026-10-11 那 23 行 `corrected=1` 而 `color` 全空，就是这么来的。
而"整体拒绝"（原实现：任一行脏就不许批量确认）也已经被证明不好用：用户得先逐行保存。

**跳过 + 把数字说准**是唯一既不丢东西、又不用回头重做的做法。同理，批量定款里"颜色对不上"的行
不落库、留在列表并**重新勾上** —— 那就是"接下来还要做"的那几行，取消勾选等于把它们混回 30 行里。

### ③ 批量落库的失败面要分开报，不能只说"完成"

串行逐行写库没有事务边界（`saveCorrection` 是两条宿主通道），部分失败是**可能**的。回执必须
分成三类：`已存 N 行` / `M 行要先选颜色` / `K 行保存失败`。谎称"全部成功"比失败本身更糟 ——
用户会到对账页上才发现差了几行，而那时已经想不起来是哪一次操作。

配套的一条：批量动作只 `bump()` **一次**（`saveOne` 加 `defer`）。逐行 bump 会让 30 行变成
30 次整页重载，而批量操作的全部意义就是把这个数降到 1。这条很隐蔽 —— 功能看着都对，
只是"批量保存比逐行保存还慢"。

## 「一次点击」的那一步：下标，不是 id

主按钮「保存并下一条」= 落库 + 接上下一行。实现上只有一处容易错：

**"下一条"必须用下标记录，不能用订单 id。** 保存会把该行置为已核对、它随即离开列表、
后面的行整体上移一位 ⇒ "下一条"正好落在它原来的下标上。钉在 id 上会找不到那一行，
症状是"焦点/弹层丢了"，很难查。（`applyFocus` 早就有这条注释，这次是同一个坑的第二次。）

⚠️ 赋值时机也要注意：`nextAfterSave = idx` 必须在 `saveOne` **之前**。`bump()` 触发的
`load()` 与本次 continuation 谁先跑没有保证，先赋值 ⇒ 无论谁先，`load()` 结束时都能看见它。

## 门禁层面学到的三件事

### 1. 改掉一个被断言的**语义**时，反向断言比正向断言重要

「全部确认无误」原来钉的是 `orderMarkCorrected({all:true})`。把它改成"按筛选取 id"时，
正向断言（`JSON.stringify(...) === '{"all":true}'`）必然要改 —— 但只改成"是数组"是不够的：
一个永远发空数组的实现也能过。

真正该钉的是**"全程一次都不许发 `{all:true}`"**。这条断言的价值不在当下，而在半年后有人
"为了省一次往返"把它改回去时，屏幕上会跳出一句话解释为什么不能。

### 2. 夹具"靠漏网才能通过"的状态，迟早会红

改完之后三条空态断言连环红，根因不在产品代码：

- 旧实现发 `{all:true}`，夹具的数组分支不记 id ⇒ 夹具里永远有一行"漏网"的待核对行，
  "数据回来后表格跟着回来"因此**侥幸**通过；
- 新实现真的按 id 标记 ⇒ 五行全部已核对 ⇒ 表格当然回不来。

修法是显式清掉"本次会话已核对"的集合（`window.__correctedIds = []`），并在注释里写清为什么。
这不是"为了让断言通过而改夹具" —— 恰恰相反：原状态掩盖了"这条断言其实一直在测一个假前提"。

### 3. 断言"空态文案"要等文案，不能等元素

空态元素在 `rows` 变空的那一刻就挂上了，而"今天还没有导入订单 / 今天这批都核对完了"取决于
`counts`（同一批取数里算的）。只等元素会读到上一帧的文案 —— 那种红看起来像"状态判错了"，
其实只是断言读早了。

## 顺带修掉的一个 P0

「全部确认无误」原来走 `UPDATE ... WHERE corrected = 0`：**全库、不带导入日、不带搜索词**，
还顺带把克重与进价快照钉死。页面上 5 行、库里 300 行未核对 ⇒ 那 295 行一起被确认。

这类 bug 的特征是**界面上完全看不出来**：点了以后行确实消失了、数字也变小了，一切"正常"。
它只有在"回头看某天的单，发现全被标成已核对、价格却是当时的"时才会暴露 —— 而那时账单已经发出去了。

**凡是"批量"按钮，先问一句：它的作用域与用户看得见的这一屏，是同一个范围吗？**
