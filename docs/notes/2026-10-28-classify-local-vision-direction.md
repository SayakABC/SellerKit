# 不接云端模型时，「归类核对」怎么自动认出款式与颜色

日期：2026-10-28 · 触发：用户提问"不搭服务器、不接云端大模型，能不能自动识别图片里的款式和颜色并归类"，
随后拍板「**不接云端 API**；本地技术只要成熟、精准、跨平台、对性能要求不高都可以」。

本文记录**判断、路线与实测数据**（§一~§七 为判断，§八 为 82 张真图上的实测结论）。

## 一、先看真库能撑起什么（2026-10-27 那份 `sellerkit.db`，只读查询）

| 观测 | 值 |
| --- | --- |
| 订单 / 款 / 款色 | 70 单 · 13 款 · 85 个款色 |
| 图片 | 101 张，**内容指纹去重后仍是 101**（没有重复图可复用） |
| 已挂款色的图 | 82 张，分布在 **70 个款色**上 ⇒ 平均每色 **1.17 张** |
| 商品ID 映射 | 47 条 `pl_shop_sku` |
| 款参照图 | `pl_products` 19 个，**只有 11 个有首图**（`pl_images` 12 行）；`pl_variants` 457 行跨 21 个产品，`color` 全非空 |
| VLM 历史 | `oi_images.result_json` **全 null** ⇒ 指纹/特征层从未产生过数据 |

三条推论：

1. **这是闭集问题，不是开放世界识别。** 13 个款、70 个款色 —— 候选空间只有几十个。
   在这个规模上，任何"预训练大模型 + 微调"的路线都是过度工程，而且没有训练数据。
2. **参照图不全才是硬前提。** 11/19 个款有首图、每色 1.17 张 —— 检索法的上限由它决定，
   补 8 张款首图的成本远低于调一个模型。
3. **82 张已归类图能跑 1-NN，但标不了阈值。** 70 个类、每类 1 张，留一法一定过拟合；
   阈值只能先用经验值上线，再靠"采纳即入库"的样本积累逐步收紧。

## 二、像素解码不是解法，是地基（回答"像素解码能解决当前的问题吗"）

**不能。** 它只是把 JPEG 变成 `Uint8Array` 的那一步 —— 没有它任何图像算法都跑不起来，
但它本身不含任何"这是哪个款、什么颜色"的信息。**真正的解法是"在参照图里找最近邻"**，
像素解码只是这条链的第 0 步。

它值得单独说，是因为成本几乎为零且跨平台：Electron 内置的 `nativeImage` 可以
`createFromPath(p).resize({ width: 128 }).toBitmap()` 拿到 BGRA，**不需要 sharp / canvas / jimp
任何一个原生依赖**（项目目前一个都没有）。特征函数写成 `src/lib` 下的一个纯函数模块
（暂名 imageFeatures，只吃 `Uint8Array + w + h`），vitest 直接可测，不 import Electron ——
这是本仓"提示词/算法必须住纯模块"那条纪律的同一手法。

> ⚠️ **2026-10-28 实测更正：这条"零依赖解码"只在 JPEG 上成立。**
> 用项目自带 Electron（44.4.1）主进程 `nativeImage.createFromPath` 解码真库 82 张已归类图：
> **14 张 jpg 全部成功，68 张 webp 全部 `isEmpty()` 即 `decode empty`**。而订单图落盘格式里
> webp 占 83%（`order-images/` 101 个文件里绝大多数是 .webp，`file` 判定为 `Web/P VP8`）。
> ⇒ 结论是**解码位置必须换**：走渲染层 `createImageBitmap` / `<img>` + canvas（Chromium 原生支持 webp），
> 或在主进程引 `sharp`（原生依赖，多平台预编译二进制）。这条与"用不用小模型"无关，
> 是任何像素方案的前置条件。取证脚本与命令见 §八。

## 三、三条候选路线（都不联网、不搭服务）

| 方案 | 做法 | 预期 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A 传统 CV（推荐主线）** | 款：灰度 dHash + 边缘方向直方图 → 在参照图库做 1-NN；色：前景主色聚类 + Lab ΔE 在该款**已有色集**内选 | 款 Top3 ~70-85%，纯色款色 ~80-90% | 零依赖、纯 CPU 毫秒级；印花/多色必弃权；对摆拍角度敏感 |
| **B 本地小模型** | `onnxruntime-web`（WASM，无原生依赖）+ CLIP ViT-B/32 `q8`（85MB）出 embedding 做近邻 | **已实测**：款 Top1 93.6% / Top3 98.7%（剔近重复后 91.1%），弃权后建议精度 98.6%；**判色 AUC 0.52 ≈ 随机，不要用它判色** | 分发 +85MB 模型（安装包约翻倍）；WASM 单图 46-165ms；详见 §八 |
| **C 系统原生** | macOS Vision `VNGenerateImageFeaturePrint`（系统内置、零下载、质量好） | 高 | 只有 mac；要 Swift helper + 签名公证。项目 mac + win 双分发 ⇒ 只能作 mac 增强项，不能作主线 |

## 四、推荐主线：四层信号，命中即停

```
L0   商品ID 映射（pl_shop_sku）           → 款 + 色，零图像
L0.5 图片内容指纹命中（oi_images 已有）    → 同一张图必同一结论
L1   结构特征 1-NN（灰度 dHash + 边方向）  → 款 Top3 + margin 门槛
L2   该款色集内 Lab ΔE 最近               → 色 Top1 + 阈值
└──  任一层的把握不够 ⇒ 弃权，保持人工
```

三个设计约束（都是从本仓已踩过的坑倒推的）：

1. **款和色必须解耦。** 判款只用灰度结构特征、**不掺颜色**；判色时只在"这款已有的那几个色"
   里选（`oi_style_colors` / `pl_variants.color`）—— 不是从色板猜绝对色名。
   这与现有数据模型完全同构（款 = 指纹，色 = 款色），错一次不会连累另一维。
2. **弃权优先。** Top1 与 Top2 的 margin 不够、ΔE 超阈值、或前景色熵高（判为印花）⇒ 不给建议。
   理由是本仓既有纪律：**错并（两色合一）比拆更难发现、更难回退**。
3. **建议只预填，保存仍由人触发。** 2026-10-11 那次"点保存提示成功、款色还是未分类"证明：
   自动落库的静默失败比不做更贵。

## 五、落地顺序（按 ROI，不是按技术含量）

| 阶段 | 做什么 | 为什么排这里 |
| --- | --- | --- |
| P0 | 补齐款首图（19 个里 8 个没有）+ 继续培映射 | 所有视觉方案的硬前提，且比调模型便宜 |
| P1 | 图指纹复用 + 同商品批量确认（已有） | 零算法就能砍掉大部分重复决策 |
| P2 | **先只做颜色**（受限色集 + ΔE + 弃权） | 色是拿货单与算钱的必需字段，错了人一眼能看出 |
| P3 | 款检索（Top3 + margin），采纳即把该图写入该款参照集 | 增量变准，不需要训练 |
| P4 | 可选：本地 CLIP / macOS FeaturePrint | 只在 P3 的留一法测出不达标时才上 |

## 六、为什么这一轮先把旧的识别链删掉

云端识别链（`src/core/ai/**`、`readEngine`/`recognizeOrder`、「设置 › 识别」、`order-api-key-*`）
自 2026-10-05「识别未归类」按钮删除起就**零调用方**。留着它的真实效果是：
用户在设置里填了 API Key，而**没有任何地方会用它** —— 这是比"没有功能"更坏的假象。
`oi_queue`（待识别队列）同理：没有生产者，只剩一张永远空着的表。

删除范围与门禁读数见 `CHANGELOG.md` 同日条目；连带修掉的"孤图清理从未生效"见 `order-db.ts`
的 `listImageLocalPaths` 注释。

## 七、还没拍板

- 颜色建议的落点是"只填当前行的色名"还是"顺带写回图-色记忆"（后者收益大，但等于自动改数据）。
- 阈值标定的样本从哪来：真库只有 70 单，可能需要先人工核对 100-200 张作为评测集。
- 85MB 模型的**分发形态**：随包（安装包 114MB → 约 215MB，每次更新都传）还是首次启用时下载
  （则"离线可用"这个前提又被打破，需要用户明确接受一次联网）。

## 八、方案 B（本地小模型）实测结论 —— 2026-10-28

做法：真库 82 张已归类图 → Electron 解码成 224×224 RGB 裸像素 → CLIP ViT-B/32（`q8` 量化，
85MB）出 512 维 embedding → 留一法近邻。脚本留在 `/tmp/lv-spike/`（不属于仓库：
它依赖真库里**本机才有**的用户数据，入不了库）。

### 8.1 款（style）：可用，且是真信号

| 指标 | 实测 |
| --- | --- |
| Top1（留一法，n=78） | **93.6%** |
| Top3 | **98.7%** |
| 剔除"参照里有近重复图"后的 Top1（n=56） | **91.1%** ← 真实力，不是记忆 |
| 同款图对的近重复占比 | 433 对里 cos≥0.95 只有 14 对（≥0.98 只 1 对）⇒ 数据本身没有大量重复图 |

弃权阈值（按 Top1−Top2 的 margin 卡）：

| margin | 覆盖率 | 采纳后的精度 |
| --- | --- | --- |
| ≥0.01 | 98.7% | 94.8% |
| ≥0.02 | 91.0% | **98.6%** |
| ≥0.05 | 73.1% | 100% |

⇒ 设计落点：`margin ≥ 0.02` 作为默认弃权线，**4 张里弃权不到 1 张、采纳的几乎全对**。

### 8.2 色（color）：不是模型问题，是**数据问题**

| 实测 | 结果 | 说明 |
| --- | --- | --- |
| 可评估样本 | **21 / 82** | 61 个款色只有 1 张图 ⇒ 留一法把它自己拿走后该类无参照，**结构上无法评** |
| CLIP 判色 AUC（同色对 vs 异色对） | **0.522** | ≈ 随机。CLIP 关注形状/物体，**对颜色几乎不敏感**，不该用它判色 |
| 纯像素主色集合匹配 AUC | **0.729** | 有信号：同色对 ΔE 中位数 **1**（几乎一模一样）；但 p90 = **34**（人眼一眼能看出不同色） |
| 同色对 ΔE 分布 p50/p90 | 1 / 34 | ⇒ 约 **10-20% 的"同色"标签自相矛盾** |

标签噪声的直接取证（`oi_style_colors` id=57，名"红色"，SUST-012 下的 4 张图）：

| 图 | 实测主色 | 平台色文本 |
| --- | --- | --- |
| img 39 | `#f4cd47` 黄 | `Color:10` |
| img 65 | `#141010` 近黑 | `Color:12` |
| img 66 | `#130f0f` 近黑 | `Color:6` |
| img 67 | `#c92732` 红 | `红色` |

同一"款色"下 4 张图实测是 **黄 / 黑 / 黑 / 红**。两条独立原因叠加：

1. 平台色名是数字（`Color:10/12/6`），本身无语义；
2. 订单图是**listing 图**，同一 listing 多 SKU 常共用近似展示图，**图未必体现该 SKU 的真实颜色**；
3. 另外商品是"上衣+裤子套装"，一张图里天然有 2 个色块 ⇒ "这张图是什么颜色"本身是**不适定问题**
   （必须先定义"判哪个色块"，比如只判上衣）。

⇒ **色不要交给模型，也暂时不要上线"自动判色"。** 先做两件更便宜的事：
① 判色只在"该款已有色集"内做（候选通常 2-3 个）；② 修正标签（把"红色"里那 3 张黄/黑图
重新归到正确款色）。没有第 ② 步，任何判色精度都是假的。

### 8.3 运行与分发成本（同一台 M 系 Mac 实测）

| 项 | `onnxruntime-node`（原生） | `onnxruntime-web`（WASM） |
| --- | --- | --- |
| session 建立 | 165 ms | 288 ms |
| 单图推理 | **11 ms** | **46 ms**（4 线程） / **165 ms**（单线程） |
| 分发包增量 | **+65~87 MB / 每个平台**（`node_modules` 里 291MB 需裁剪，且要 `asarUnpack *.node`） | **+16~26 MB** 一个 wasm，全平台同一份 |
| 原生依赖 | 要 rebuild + 架构匹配（mac arm64/x64、win x64 各一份） | **无** |
| 跨平台一致性 | 三份二进制，行为可能不同 | 同一份 wasm |

⇒ **选 WASM。** 46-165ms/张 对"用户点一次、等一两秒"的交互毫无压力，换来的是
"零原生依赖 + 双平台一份产物"。原生那 11ms 的 4 倍优势买不到任何用户可感知的差别，
却要在 mac/win 各维护一份二进制与 asarUnpack 规则。

### 8.4 综合判断

- **B 方案可行**，但它不是"更准的 A"，而是**分工**：**款用 CLIP（91%），色用像素（ΔE 集合匹配）**。
- 三个真实阻碍，按代价排序：① 85MB 模型的分发形态；② webp 解码位置（见 §二更正）；
  ③ 颜色标签本身不可信（先修数据，不是先上模型）。
- 12 个款里有 4 个只有 1 张图 ⇒ 这 4 款在留一法里连评估都进不去，实际使用中只能靠人工先建一次档。
