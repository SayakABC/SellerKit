# 订单驱动的归类改造：结论与分期方案

> **取代关系**：本文把同日三条归类笔记（`2026-10-28-classify-local-vision-direction.md` /
> `2026-10-28-classify-style-picker.md` / `2026-10-28-classify-bulk-ops.md`）收拢成一条主线。
> 那三条的**取证仍然有效**（尤其 vision 笔记 §8 的 82 张真图实测读数），但"以图判款"不再是主线，
> 退为「解析不出时的兜底」与「跨 listing 提款」。

## 0. 一句话

归类键一直在订单里。改造只做一件事：**把建档从前置条件，降级为按需命名 + 按需合并。**

## 1. 结论（八条）

1. **键 = `(店铺, 产品ID, Color 原值)`**，从订单原文解析。纯函数、零网络、零模型、
   `vitest` 直接可测。真库 74/75 行可解析。
2. **Color 的语义不可信、分组力可用。** `Color:1` 同时出现在 7 个 listing
   （瑜伽裤 / 棉袄 / 雨衣 / 印花外套）⇒ 它**只能当键，永不当色名**。标准化只作用于给人看的标签。
3. **款不"建"，款是"合"出来的。** 默认 **1 个 listing = 1 个款**；只有"合并能少做一次决定"时
   （同供应商、同成本、人眼确认同款）才合并。款有三个身份——统计单元（listing）/ 拿货成本单元（真款）/
   展示名——现在被压成一个，这才是维护量的根源。
4. **三道门，各拦各的下游**：店铺归一（硬，3 项）→ 拿货前检查（硬，本次要拿的款）→ 进价（软，可跳过）。
   **门的位置取"它保护的那个动作"，不取"它所属的数据种类"。** 色名不进门。
5. **门的状态必须派生，绝不存"已完成"标志。** 每次进页面按当前库重算 `缺 N 项`；存标志的后果是
   第二次导入后标志说"已完成"而有 5 个新款没供应商——即本仓"派生非幂等就必然漂移"。
6. **拿货单不为不确定的数据做决定。** 色未确认的行绝不并进任何"款+色"汇总行；宁可让用户点 6 次看 6 张图。
7. **图片只做两件事**：给键命名、提示"跨 listing 可能是同一款"。**不用它做归类键**——
   键的错误方式是"解析不到 ⇒ 弃权"（可观测可回滚），图的错误方式是"看起来很像 ⇒ 并错"（不可观测）。
8. **不做**：CLIP 判色（AUC 0.522 ≈ 随机）、微调分类头（样本差两个数量级 + 闭集）、
   `sqlite-vss`（已停止维护，82 张全量余弦是微秒级）、视觉聚类分组（键已存在，聚类只引入不可判定的合并）。

### 2.1 ⚠️ 一条推翻先前假设的实测：`oi_order_items.color` 已在混用

```
75 行：color 空 2 行；color 与原文 Color 相同 72 行；不同 1 行
不同的那一行：[表内 color = "红色", 原文 Color = "5"]
```

`color` 列**当前就是平台原值**（导入写它），但它**已经被人改过一次**（`5` → `红色`）。
即：同一个字段同时承担「键」与「标签」。这正是本轮要拆的那件事，而且**必须在存量里拆**——
那一行的键已经永久丢失（只剩 `raw_fields` 里还留着 `5`，所以可回填，且回填后该行历史关联会变）。

### 2.2 证据：先建款会建出空壳，且会重名

```
SUST-007 老卫衣     0 个 listing
SUST-014 老卫衣     0 个 listing   ← 同一个名字建了两次
SUST-008 三条杠 0 · SUST-015 连帽老卫衣 0
SUST-017 老卫衣套装 0 · SUST-018 轩禄风衣 0 · 欢喜-黑色-001 0
```

"老卫衣"建了两次不是手滑：没有 listing 可挂时，人无法判断"这个款是不是已经建过了"。
**款只有在挂上实物（listing / 供应商 / 成本）之后才有内容。**

### 2.3 归属事实存在了一个错的地方

`pl_shop_items`（71 行）**没有 `product_id` 列**；"这个 listing 属于哪个款"只记在
`pl_shop_sku.product_id` 上（每个 listing 恰好 1 行、`spec='*'`）。所以 71 个 listing 里
只有 47 个有款归属，24 个悬空——"款挂在哪"在表结构上说不清。

## 3. 数据模型改动

**原则：键与标签分离；事实不可变；派生必幂等。**

| # | 改动 | 性质 | 说明 |
| --- | --- | --- | --- |
| 1 | `oi_order_items` + `platform_item_id TEXT NOT NULL DEFAULT ''` | 加列 | 键的一半。导入时从 `raw_fields.产品ID` 写入，**此后只读** |
| 2 | `oi_order_items` + `platform_color_raw TEXT NOT NULL DEFAULT ''` | 加列 | 键的另一半。从 `raw_fields` 的 `产品属性` 段解析，**永不人工写**；空值合法（1/75） |
| 3 | `oi_order_items.color` **降级为人工标签** | 语义变更 | 导入不再写它；它只承载"人给的颜色词"。存量那 1 行 `红色` 保留，键从第 2 列取回 |
| 4 | 新表 `oi_variant_keys` | 新表 | 键 → 款色的**唯一且可复用**落点，同时是合并/别名的记录 |
| 5 | `pl_shop_items` + `product_id INTEGER`（可空） | 加列 | 让"listing 属于哪个款"有唯一、可逆的存放点 |
| 6 | `oi_style_colors.color` 只存人给的名字；`''` = 未命名 | 语义变更 | 不再被任何解析结果自动写入 |

```sql
CREATE TABLE oi_variant_keys (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  shop_id        INTEGER NOT NULL,
  item_id        TEXT    NOT NULL,
  color_raw      TEXT    NOT NULL DEFAULT '',
  style_color_id INTEGER NOT NULL,
  state          TEXT    NOT NULL DEFAULT 'auto',
  created_at     TEXT    NOT NULL DEFAULT (datetime('now','localtime')),
  UNIQUE(shop_id, item_id, color_raw)
);
```

- `state`：`auto`（导入自动建）/ `named`（人给过名）/ `merged`（人显式并到别的键的款色）。
- **N:1 是合法的**（那 9 次人工合并就是 N:1），所以映射必须是一张表，不能靠"同键行的
  `style_color_id` 相同"来派生——后者在订单被清理后会丢链接。
- `color_raw` **不做任何归一**（不 trim 大小写以外的处理、不映射标准色）。归一化只发生在展示层。
- 迁移走 `sellerkit-host-schema-migration`（本项目 45 条铁律里有 3 条是加列/重建表的坑）。

## 4. 三道门

| 门 | 位置 | 类型 | 判据 | 当前规模 | 阻断点 |
| --- | --- | --- | --- | --- | --- |
| 门 1 店铺归一 | 导入后、归类前 | **硬** | `DISTINCT oi_orders.shop` 里未归成店铺实体的个数 > 0 | 3 项 | 归类结果不可信（键含 `shop_id`，不归一必分叉） |
| 门 2 拿货前检查 | 生成拿货单前 | **硬** | 本次涉及的款下 `state <> 'named'` 的行数 > 0，或缺 `supplier_id` | 本次要拿的款 | 提交拿货单 |
| 门 3 进价 | 出对账单 / 利润前 | **软** | 拿货单行缺 `cost_cents` | 有单才填 | 不阻断，按"未计价"出数 |

**不在门里**：色名（58 项，随时可给，不拦统计）、款合并（不合并也能拿货，只是同一厂家分行）。

三条实现铁律：**① 门的状态派生不存档 ② 门带作用域不带布尔 ③ 门只拦动作不拦浏览**。
落点复用现成：`src/modules/today/TodayView.vue` 的 `TABS[].badge` 已经是缺口数字
（`${gaps.style} 未归类` / `${s.purchase.gap} 款色`），升级成"可点开的清单"即可，**不新建状态机**。

## 5. 分期

| 阶段 | 做什么 | 风险 | 依赖 |
| --- | --- | --- | --- |
| **P0** | 新增 `variantKey.ts`（`src/lib/` 下）纯函数（解析 `raw_fields` → 键）+ 单测 + **只读统计视图** | 零 | 无 |
| **P1** | §3 的 1/2/5 三列 + 回填（从 `raw_fields` 重算）+ 导入时写入 | 低（纯加列） | P0 |
| **P2** | 导入即 ensure `auto` 款色 + 写 `oi_variant_keys`；`oi_style_colors` 不再被自动写名字 | 中（要幂等守卫） | P1 |
| **P3** | 命名页：一个 listing 的 N 个色键一屏填完（左图右框），可跳过 | 中 | P2 |
| **P4** | 合并：拿货页在"同 `supplier_id` 下 ≥2 个未合并 listing"时提示，一次操作 N→1 | 中（必须可拆） | P1 |
| **P5** | 门 1/门 2 接线（复用 `badge` → 缺口清单）+ `FIRST_RUN_STEPS` 第三步改成"看统计"（**已落地，见 §9.9**） | 低 | P2/P4 |
| **P6**（可选） | CLIP 兜底：只处理 P0 解析不出的行（真库 1 行） | 高（85MB 模型分发 + webp 解码） | 全部 |

P3 的交互形态是硬要求：**一个 listing 常有 4-6 个色键，必须一屏批量填**。
做成"点开一个、填一个、关掉、下一个"就是用户抱怨过的那四个动作再来一遍。

## 7. 明确不做（附理由）

| 不做 | 理由 |
| --- | --- |
| CLIP 判色 | 真库 AUC 0.522 ≈ 随机（82 张实测）；用它判色等于掷硬币 |
| 微调分类头 | 50 条纠错覆盖 50 个类各 1 条；且它是**闭集**，第 14 款出现时只能输出最像的旧类 |
| `sqlite-vss` / ANN | 已停止维护；`loadExtension` 要 ABI 匹配 + `asarUnpack *.node` + 双平台二进制。82 张全量余弦是微秒级，到 5000 张再谈 |
| 视觉聚类分组 | 键已经存在，聚类只引入"不可判定"的合并；且错并比拆更难发现 |
| 缓存"识别结果" | `oi_images.fingerprint`（内容 SHA-256）已经保证"同一张图必同一结论"，向量层是重复建设 |
| 前移全量准备清单（一道大门） | 会让真前置从 3 项放大到约 136 项，且数据是流，"齐了"这个状态不存在 |

## 8. 遗留与风险（改造不解决，但要记账）

1. **历史欠账一次性显形**：上线首日 61 个裸数字色名 + 11 个空/未分类会同时变成"未命名"。
   必须给**收敛路径**（按 listing 分组、组内可"复制上一个的名字"、不命名不阻断任何数字），不是一张待办清单。
2. **34% listing 无款归属**：所以"不合并必须能拿货"是硬约束；否则这 24 个直接卡死。
3. **`oi_styles`（13 条，只有 `code`+`fingerprint`、**无 `name` 列**）与 `pl_products`（19 条，有名字）
   是两套并行的"款"，无关联字段，靠人脑对齐。**改造后只新建 `pl_products` 一份**，`oi_styles` 冻结不再新建。
4. **`pl_variants` 457 行只服务克重/成本，与归类无关**。改造后 `pl_products`/`pl_variants` 不再承担认款职责——
   这条不定，下次还会有人为了统计去填 457 行 variant。
5. **`Color` 值可能整批缺失**（picture color 场景）：此时 `(item, color_raw)` 退化成 listing 级 ⇒ 颜色维丢失但分组不错。
   补法是"同键多 fingerprint 就拆"，需检测项；见 vision 笔记的 L1/L2/L3 分层。

### 9.3 与方案的偏差（记账）

1. **只落了 1 列**（`variant_key`），§3 的另两列（`platform_attr_values` 属性值 ID 链、`oi_variant_keys.color_value_id`）延后：
   它们只服务"命名能省多少次"，不影响分组对不对。当前导出里该列**被导入丢弃**（`raw_fields` 只留 12 列），
   所以先补导入白名单才谈得上用，属独立一步。
2. ~~**P3 命名页 / P4 合并提示 / P5 三道门 / P6 CLIP 均未做**~~ —— **P3、P4 已于当晚补齐**（见 §9.5 / §9.8）；
   P5 三道门 / P6 CLIP 仍未做。
3. **占位款名留空**（不是自动填标题）：命名是人的判断，自动填一个"像名字"的东西只会让人不再去核。
   代价是 `pl_products` 里新增的 9 个款目前显示为 `AE-<商品ID>`。

### 9.4 守卫（`order:smoke` 新增 [13]，9 条；[14][15] 见 §9.5）

### 9.5 P3 落地（命名板）+ 一处必须同批修的口径分裂

#### (1) 命名板：一屏填完，可跳过

| 项 | 落点 |
| --- | --- |
| 取数 | `variantNamingBoard()`：按 `店铺+商品ID`（= listing）分组，组内是色键；未命名的排前面，组间按"还有几个待办"排 |
| 色名写入口 | `renameStyleColor(styleColorId, name)`：**只改 `oi_style_colors.color`、不动 `code`**（`code` 是拿货单/对账引用的稳定标识）；同款重名提前判、给一句人话（不吐 `UNIQUE constraint failed`） |
| 款名 / 厂家写入口 | `saveStyleBasics(styleId, { name?, supplierId? })`：写产品主数据（`pl_products`），**只写改过的那一项**；两步同一事务 |
| 界面 | `VariantNamingCard.vue`：一个 listing 一块，组头是「款编码 + 款名 + 厂家下拉」，下面是 N 个色输入框（一屏 6 个 listing，可再展开） |
| 不改的东西 | 色名不进门、不阻断任何数字：没起名的色在统计/拿货里照常出数，只是显示成平台原文（`5`） |

两条被实测钉住的细节：

1. **款名与厂家必须同一入口、但只送改过的那一项**。`undefined`（不改）与 `0`（清空厂家）在 IPC 上是两件事。
   一律送全量字段的实现会把"我只改个款名"变成"顺手把厂家清成 0"，拿货页随即多出一批未指定厂家的货。
   `today:ui` 的断言钉的就是 payload 里**有没有** `supplierId` 这个键（变异实测：改成无条件送 ⇒ 立刻红）。
2. **保存按钮不能靠 `disabled` 收口**。按钮的 `disabled` 绑在"有改动"上，而改动是同一 tick 里 dispatch 出来的
   —— Vue 要到下一个 microtask 才重绘，同步 click 打到的还是 disabled 的按钮（"点了没反应"）。
   所以界面文案写"填完按回车即存"，冒烟也走回车。

#### (2) 同批修：投影层的款色口径分裂（**这条不修，P2 的成果在拿货页看不见**）

改造前"改装色"只走图，于是所有投影层都 `LEFT JOIN oi_style_colors sc ON i.style_color_id = sc.id`。
改造后款色先落在**订单行**上，投影层若仍只认图，同一行会"统计说已归类、列表说没归类"：

| 观测（真库只读） | 值 |
| --- | --- |
| `oi_order_items.style_color_id > 0` 且 `oi_images.style_color_id = 0` 的行 | **9 / 75** |
| 症状 | 待核对列表仍显示"未归类"、订单利润页款编码空、拣货/拿货页标"未识别款 · 无供应商" |

修法：把身份表达式收成**一份**导出片段 `ITEM_STYLE_COLOR_ID = COALESCE(NULLIF(oi.style_color_id,0), i.style_color_id, 0)`，
`ITEM_STYLE_COLOR_SRC` 与四处投影 JOIN（`shippingRows` / `listOrdersPage`（count + rows）/ `updateOrder` 回读 /
`pickingRows` / `purchase-db` 的缺口候选与 FIFO 需求行）全部改读它。
跨域边按登记制补：`picking-db → order-db { ITEM_STYLE_COLOR_ID }`、`purchase-db` 的符号表加同名符号。

顺带改掉一处**内连接**：`purchase-db` 的 FIFO 需求行原本 `JOIN oi_images`，无图的行直接查不出来
（采集通道的行 `image_id` 恒空）—— 那等于"没图的货不用拿"。

#### (3) 假桥的一处结构性缺陷（已修）

`today:ui` 的 `orderVariantNaming` 桩原来回**夹具活引用**。真 IPC 是结构化克隆，页面拿到的从来不是主进程的对象；
回活引用会让"页面顺手改了夹具"在冒烟里既看不出、又不会红。已改成深拷贝。

### 9.8 P4 落地（款合并）+ 一处落点变更

#### (1) 「合并」在库里是两件不同的事，所以明细有两种

| 情况 | 做法 | 为什么 |
| --- | --- | --- |
| 目标款下**有同名色** | **改键**：把源色的 `variant_key` 改指到目标色，源色行**留着不删** | 删了源色就拆不回去（合并的第一条验收是可拆） |
| 目标款下**没有同名色** | **搬色**：`oi_style_colors.style_id` 改到目标款 | 色 id 不变 ⇒ 键、订单行、套装拆件**一个都不用动**，是最不容易出错的路径 |

色配对**只按同名**（归一化后相等），不按位置、不按相似度：猜错会让两个不同色的库存并成一色，
而拿货单照样能打印、照样能下单 —— 错得悄无声息。剩下的色由人在命名板改个同名再合一次即可。

#### (2) 撤销必须按**批次**，不能按行

一次 N→1 在 `oi_style_merges` 里写 N 行（一源一行）。第一版按行 id 撤销，真库副本实测
`restored=1` —— 只拆掉了最后一个源款，界面却报"已拆开"。改成 `batch_id` 后 `restored=6`。

#### (3) 落点从「拿货页」改到「归类核对」

计划原本写的是拿货页（"同一件货开两张单"最肉疼的地方）。实测不行：拿货页是固定高度 flex +
内部滚动，插一块折叠卡会把厂家宫格的卡尾按钮挤出可点区 —— `today:ui` 的几何守卫
（`elementFromPoint` 命中按钮自身）直接红，且那不是断言过严，按钮是真的点不到。

改挂「归类核对」，和命名板并排：两者是同一件事的两个动作（**人给结构**）—— 给色起名、
认出一件货有两个链接。人刚看完一屏 listing，判断成本最低。

#### (4) 真库副本读数（`cp -c` 克隆，真库未动）

| 观测 | 合并前 | 合并后 | 拆开后 |
| --- | --- | --- | --- |
| 拣货行 / 款数 | 75 / 19 | 75 / **17** | 75 / 19 |
| 拿货缺口 行 / 需求件 / 缺口件 | 63 / 74 / 74 | 62 / **74** / **74** | 63 / 74 / 74 |
| 未归类行 | 0 | 0 | 0 |

行数 63→62 是**同名色同码聚合**（两行的 `(款, 色, 码)` 变成同一组），件数守恒 —— 这是合并该有的样子。
合并候选：真库 22 个款里 **10 个已指定厂家**，落在 3 个厂家组（集雨 5 / 福旺 3 / 欢喜 2）；
其余 12 个款没有厂家，不进候选（"同厂家"是这一组候选的唯一依据，不猜）。

### 9.9 P5 落地（门 1 / 门 2 接线 + 首跑第三步）+ 收尾时挖出的两个真问题

#### (1) 门 1：店铺归一，**只报告不拦**

`shopNormalizeGate()`（`electron/shop-db.ts`，新通道 `shop-gate`）：`DISTINCT oi_orders.shop` 里
还没归成店铺实体的那些，按**订单行数**聚合并排序，返回 `{ pending, orders }`。

- **"未归一"只有一个实现**：套用 `listUnmapped()`，本函数只加"作用域收窄到订单 + 聚合行数 + 排序"。
  （`purchase_sources.shop` 里只出现在拿货单的旧店名**不**进这个门 —— 那不影响归类口径。）
- **不硬拦任何按钮**：它保护的是**数字口径**（键里含店名，同店两种写法会分裂成两个款色），
  而归类在导入那一刻就已经发生 —— 事后拦动作只能做成"点不到的门"，用户看到的是一片禁用的按钮
  却说不出该去补什么。提示条只给两条路：去「店铺账户」归一，或继续（数字口径自己心里有数）。
- 通道里**不**调 `ensureOrderSchema()`：为了一个只读判断去建别域的表，不合适。

#### (2) 门 2：拿货前检查，拦在**写入口**而不是按钮

`purchaseGateOf(rows)`（`src/lib/picking.ts`，纯函数，6 条单测）：

| 判据 | 为什么 |
| --- | --- |
| `styleColorId <= 0` ⇒ 拦 | 开进单里以后，这行再也对不上账（改个色名就失联） |
| 该款 `supplierId === 0` ⇒ 拦 | 开单会直接报"厂商不存在"（错得晚，还错在写库那一刻） |
| **色名未命名不拦** | 58 次输入变成门槛 = 没人再敢用。色名只是标签，门只拦**身份** |

拦在 `createFromPick` 开头（唯一写入口），**不禁用按钮**：一张卡上常常只有一两行有问题，
禁用整卡会挡掉本来能拿的货。文案写清"先去补什么"，并把"标暂不拿"作为第三条路给出来。

#### (3) `FIRST_RUN_STEPS` 第三步语义翻转

原来是「点一款认款」（刻意不给按钮，因为落点就在本页）。归款变成导入时自动完成后，
这一页已经没有"必须在这里做"的第三步了 —— 改成「看要拿什么」，配真按钮跳「发货台 › 拿货」。
留一句"就在这一页"是最坏的选择：它把用户留在唯一没事可做的那一页。
`goods:ui` 同时断言 `fr-step-here` **不再存在**（防止有人把老文案加回来）。

#### (4) 偏差记账：§6 门 2 判据写的是「按钮 disabled」，实际是「点下去被拒绝」

判据文字见 §6。改的原因：用户的 2026-10-12 拍板是"拿货页不加硬拦"，而且按卡禁用会误伤。
**判据本身没变**（不确定的数据不能进拿货单），变的只是拦截位置 —— 从"不许点"到"点了给你原话"。

#### (5) 收尾时 `picking:smoke` 报红 2 项 —— 都是真问题，不是断言过时

**(a) 同一张图被多个变体键共用时，后进的行改判先归好的行。**
`assignByVariantKey` 的注释写着"只补空"，实现却是 `setImageStyleColor` 全量投影
（`WHERE image_id = ?`）。AE 的图是商品的、色是 SKU 属性 ⇒ **一个商品多个色共用一张主图是常态**，
症状：同款两色的单，先导的那色变成后导的色。
修法：`setImageStyleColor(..., { onlyUnset: true })`（只补没有结论的行），
`rememberVariantBinding` 同步从"按图取键"改成"按行上确实持有这个结论取键"。
人工改图（识别确认 / 纠正 / 点名归款）仍走全量 —— 那本来就是"这张图整片改成 X"。

**(b) 「先导订单、后配映射」的回填静默失效（P2 引入的回归）。**
`reassignCore` 的候选判据是"图上没结论 / 占位色"，P2 让**导入即归类**之后这两条再不可能成立
⇒ 用户配完映射**看不到任何变化**，和"没配过"长得一模一样（铁律④的静默失败）。
判据换成「这条结论是不是系统猜的」（`guessedScSql`，SQL 片段 + JS 版共用一份）：

| 判据（两条事实，都可重算） | 不成立时意味着 |
| --- | --- |
| 该色上没有 `state <> 'auto'` 的键绑定 | 命名过 / 合并过 ⇒ 人认过 |
| 色名仍等于订单行的原文色 | 改过色名 ⇒ 人认过（与命名板的 `named` 派生同一口径） |

猜的 ⇒ 映射可以改（`reassignCore` 候选 / `autoAssignByMap` 的 ②③④ / 映射带色分支 / 无图行分支四处共用）；
人认过的 ⇒ 一律不动，**重导同一份 Excel 也不会把人工色名改回映射色**。
