## 1. 改的是版式与手势，不动数据模型

**结论**：用户口径「重新设计编辑产品页面，当前页面太杂乱，SKU 的编辑也很不方便」。
抽屉从「560px 单列滚到底」改成**整窗高两栏**：
左栏 320px（主图 / 基本信息 / 价格与状态 / 备注，分节用一条细横线分隔，不套框），
右栏吃满剩余宽高（吸顶工具条 + 规格 + 矩阵 + 编码 / 老数据）。抽屉宽 `min(1040px, 94vw)`
—— 仍然让列表露出可见的一条，抽屉"改的时候对照列表"的初衷没变。

**取证**：版式几何（`npm run goods:shot`，1440×900，视口 757）：
`drawer 1040×757 · col 320 · main 719 · spec 221 · table 233 · foot 53`；
改前 `drawer 560 · table 高度受 40vh 限制`。
截图：`.cache/goods-shot/sku-matrix-1440x900.png`（另附 `sku-wizard-1440x900.png` 验共用组件在 640px 里没坏）。

## 4. SKU 的批量手势（新增，全部有守卫）

**结论**：

- **列头 = 整列开关、行名 = 整行开关**。这两处在矩阵里本来就是"这一列 / 这一行"的代表，
  又刚好是**只读标签**（改名在规格区），可以安全承担这个动作。语义是"**应该是**"而不是
  "反过来" ⇒ 幂等（已经全开时点一下 = 整列/整行取消），连点两下回到原状。
  `setMatrixRowCells / setMatrixColumnCells`（`src/lib/skuMatrix.ts`）。
- **按住拖过几格 = 连续勾选 / 取消**。`pointerdown` 刻意**不直接改**：那样一次普通点击会被算
  两次（down 改一次、click 翻回来）。所以 down 只记目标状态，等真的掠过**另一格**才动手，
  并把起点补上；`pointerup` 后用一个 0ms 的 `suppressClick` 挡掉"拖完那一下"的 click。
- **克重格按 Enter ⇒ 同一列的下一格**（不是下一行、也不绕回第一格 —— 绕回去会让人以为
  自己没离开过，接着把值打到已填好的格上）。定位靠 `data-cell-row` / `data-cell-size`。

**取证**：手势守卫（`npm run goods:ui` 的 `sku-bulk-toggle` 步，当轮 344 → **351 项**）：
点列头 ⇒ `cells=1 weights=["320"]`（只取消这一列，另一列的 320 原样在）；再点 ⇒ `cells=2`；
点行名 ⇒ `cells=0 stat=1 色 × 2 码 · 0 个组合`；再点 ⇒ `weights=["",""]`；
Enter ⇒ `active=ed-weight r1 sL`。收尾「放弃改动并关闭」，那一刻 SKU 写入为 0。
单测：`tests/skuMatrix.spec.ts` 43 → **47 例**（整行开/关、整列开/关、幂等与越界不造行）。
**变异两条都红**（确认守卫不是空转）：`toggleColumn` 恒传 `true` ⇒ 「点列头 ⇒ 只取消这一列」
红（`cells=2 weights=["320","333"]`）；`focusNextWeight` 去掉"同列"判据 ⇒ 「Enter 跳下一格」红
（`active=ed-weight r0 sM`）。

**源**：`2026-10-24-product-editor-two-pane`（2026-10-24）

## 10. 导入模板需求的真实形状是三轮问答问出来的

**结论**：用户原话：「导入产品的 Excel 模板需要增加图片地址字段，去除类目字段，还需要增加 SKU 和克重」。
用户第一句要的是「图片地址 + 去类目 + SKU + 克重」四个字段，但**行粒度没说**。这轮最重要的教训：
**克重在库里是 SKU 级属性（`pl_variants.weight_g`），加它就等于改导入的行粒度** —— 一行一款则一个克重格对应不了多规格。最后落的是：

- 一行一个款；「颜色」一格一个；「尺码 / 克重」可多值**按顺序一一对应**（个数不等 → error）。
- 中途用户提出 JSON 方案（SKU 格填 `[{"color":"红",...}]`），评估后**放弃**：Excel 里手写 JSON（中文引号、转义）比三列顺序对应更容易错，且错误更难看懂。

**取证**：门禁（逐条单看退出码）：`tsc -p tsconfig.electron.json` 0 · `vue-tsc` 0 · `verify` 0（**188/184，+1 = `product-extract-images`**）·
`verify:docs` 0 · `build` 0 · `vitest` 36 文件 / 626 用例 · `product:smoke` 0 · `product:xlsx:smoke` 0 ·
`goods:ui` **223 = 201 + 11 + 11** 三遍 ALL PASS · `today:ui` 0 · `plugins:island:smoke` 4/4。

**源**：`2026-10-09-product-template-rework`（2026-10-09）

## 11. 「图片地址」列的最终形态：图给人看，路径给机器读

**结论**：Excel **没有**"图片作为单元格内容"的存储格式（Excel 365 的 `=IMAGE()` WPS/旧版不认）。嵌进 xlsx 的图是**浮动对象**，读不回来（按锚点猜行会在用户插行时静默错位）。
所以「图片」列是**双通道**：导出嵌真图（人看）+ 文本列填**本机缓存路径**（机器读，同机往返离线可用）；导入只认嵌入图按锚点行归位（防错位：非数据行 / 一行多图 / 读不到，逐条 warning）。文本地址**明确不认**（warning 说明）。
落盘复用 `pl_images`（SHA-256 去重）+ `pl_products.image_id`，零新表零新列。

**取证**：`pl_images` + `pl_products.image_id`，零新表零新列。

**源**：`2026-10-09-product-template-rework`（2026-10-09）

## 12. ⭐ 两条路径、两套字段名，校验器只认了一套

**结论**：导入是两遍模型：**解析**（`parseProductRows`，SKU 错误记进 `cellErrors`）→ 预览 → **提交**（界面回传行结果，同一些错误在行结果上叫 `skuErrors`）。`validateImportRows` 两遍都用，但只认 `cellErrors` ⇒ **提交时预览标了「跳过」的行带着空 SKU 照样落库**（IMP-3 实测进了 items）。

教训的一般化：**同一个校验器被两条路径共用时，"同一种错误"在两条路径上的字段名必须一起认** —— 否则预览的合格性和提交的合格性是两套口径，而冒烟只在预览那半断言（"第 4 行标成跳过"是绿的），提交那半没人看。变异复核时两条守卫（单测 + 冒烟 items 断言）都红，才算闭环。

顺带：单测要选**只有提交路径才有的形状**（只给 `skuErrors`、不给 `cellErrors`），否则解析路径的兜底会让用例恒绿 —— 又是"互为兜底的两条路径只断言结果会蒙对"那一类假守卫（老坑新犯）。

**取证**：IMP-3 实测进了 items。

**源**：`2026-10-09-product-template-rework`（2026-10-09）

## 13. 夹具语义要跟实现一起改

**结论**：冒烟夹具原先把嵌入图**刻意**给不合格行（验"图不改变合格性"）。提交 bug 修好后，那一行被剔除 ⇒ 主图数归 0 ⇒ "结果页报主图数"断言反而红了。这不是实现错，是**夹具没跟上新语义**。改成两张图两种命运：第 2 行（合格 → 成主图）+ 第 4 行（不合格 → 图跟行走），一次覆盖两件事。

同类：导出克重断言写 `320,`（夹具初值），但冒烟前文的 save 步已把黑 M 改成 275 ⇒ 导出读的是**库的当下值**，期望值必须跟着流程走（`320,275`）—— 断言期望值要问"**此刻**库里的真实状态是什么"，不是"夹具最初写的什么"。

**取证**：期望值 `320,` → `320,275`。

**源**：`2026-10-09-product-template-rework`（2026-10-09）

## 18. 展开区重设计：不是溢出，是没有分组

## 19. 展开区去克重：「搬走 ≠ 删守卫」

**结论**：用户口径：「展开区信息太多了，克重信息只放在编辑页就好」。落法：展开区「SKU 克重」子表整块退场，换成**只读 SKU 清单**（规格 + 编码，允许换行 —— 基座 nowrap 会在 ~220px 卡片里裁掉长规格名）；克重的编辑与术语解释（`gloss('weight')`）整体归「编辑」抽屉；主列表「n · 缺 m」保留（它是待办标记不是克重数值）。

要点：展开区现场那 4 条克重断言退场，但要补上"搬去哪、谁在守"——新增 3 条反向守卫（无 `data-act="weight"` / 清单整块只读 / 说明指路）+ 2 条抽屉写入守卫（全量提交字段齐 / 存完关抽屉不弹确认）。哪条都不能"因为搬走就删掉"。
变异复核：把克重输入塞回展开区 ⇒ 两条新守卫各自可读 FAIL（`weightInputs=2` / `controls=2`）。`goods:ui` 226 → **227**（205+11+11）。

**取证**：`weightInputs=2` / `controls=2`；`goods:ui` 227 = 205+11+11。

**源**：`2026-10-09-product-template-rework`（2026-10-09）

## 22. 进价不搬存储：落点是 `ae_cost_map`，不是 `pl_products`

**结论**：用户原话：「货与成本导入导出数据模版中增加进价字段」，随后提议
「进价是不是应该放在 `pl_products`，改价作用到新导入的订单、历史订单用老价格，
可以在订单表中增加价格快照」。
**结论：不搬存储。** 两个诉求现有架构已满足；提议的方案改动面大 5–8 倍，且会反噬
"历史订单用老价"这件事本身。
成本**不是单一来源**，一列存不下：

| 来源      | 写入方                                                                       | 形态                        |
| --------- | ---------------------------------------------------------------------------- | --------------------------- |
| `purchase` | 拿货对账**自动同步**（`electron/purchase-handlers.ts:25` → `syncPurchaseCosts()`） | 按 `(款, 拿货日期)` **多行** |
| `manual`   | 手工 / 导入（`ae-db.costMapUpsertManual`）                                    | 手工价                      |

`pl_products` 一列只能存一个当前价 ⇒ 拿货价的历史区间会丢。而 `pl_products` 无价格列是
**ADR-002 Q2** 的裁定；P4a（2026-09-24）专门把 `ae_cost_map` 改成「多行 + 生效区间」并落了
`ae:smoke` 回归，就是为了「成本历史可复算」。

**取证**：`electron/purchase-handlers.ts:25` → `syncPurchaseCosts()`；`ae-db.costMapUpsertManual`；ADR-002 Q2。

**源**：`2026-10-09-product-cost-in-io`（2026-10-09）

## 23. 不需要「订单表加进价快照」

**结论**：「改价作用到新订单、历史订单用老价」**已经是现有行为**：

```
算钱页 electron …/OrderCostView.vue:695   拉 orderShippingRows + aeCostMapList
      ↓
pickUnitCost(costs, 款编码, 订单日期)      ← src/lib/orderCost.ts:431
      ↓  按 effective_from 回查「该订单下单时生效的价」
```

改价 = 插一条 `effective_from=今天` 的 `manual` 行 → 今天起的单用新价、之前的单用旧价。

**而加快照列会反向破坏它**：订单**导入那一刻最可能还没有价**（用户先导订单、后慢慢补进价），
快照会抄成 `NULL` 且事后补不回 ⇒ 历史订单变成「无成本」。区间回查没有这个问题（补价后立刻能算）。
另：订单有**两条摄取通道**（`oi_orders.source` = `import` / `collect`），快照要在两条都算价。

**取证**：`OrderCostView.vue:695`；`src/lib/orderCost.ts:431`。

**源**：`2026-10-09-product-cost-in-io`（2026-10-09）

## 24. 进价的落地形态与三条口径

**结论**：

- 模板 / 导出表头（`PRODUCT_EXPORT_HEADERS`）：
  `款编码 | 款式名 | 供应商 | **进价(元)** | 图片 | 颜色 | 尺码 | 克重 | 状态 | 备注`
- 导入：`parseCostYuan`（元 → 分）→ 行上带 `costCents` → 主进程 `product-handlers` 调
  `electron/product-cost-sync.ts#applyManualCosts` → 写
  `ae_cost_map(source='manual', effective_from=导入当日)`。跨域编排收在宿主一处（同 `purchase-cost-sync.ts`）。
- 列表页 / 预览表：读 `aeCostMapList()` + `pickUnitCost(costs, code, today)` 显示**当前生效价**。

三条口径（每条都是「错了不会报错」的那种）：

1. **空 = 不修改**（`null`），**不是清 0** —— 与克重「没写就不覆盖」同族；否则「导出 → 导回」一次抹掉全部价。
2. **非法值**（负数 / 非数字 / 超两位小数）→ **error 剔行**，不猜数字（进价直通成本链路）。
3. **幂等**：值与库内现价相同则**不写** —— 否则「导出 → 原样导回」每天新增一条区间行。

**取证**：`parseCostYuan` / `costCents` / `applyManualCosts` / `aeCostMapList()` / `pickUnitCost(costs, code, today)`。

**源**：`2026-10-09-product-cost-in-io`（2026-10-09）
