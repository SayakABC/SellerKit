## 1. 未结清 = 净往来 `+` 已结算净额（方案原文写的是减号）

**结论**：未结清 = 净往来 `+` 已结算净额（方案原文写的是减号）。
代入"我欠 1000、已付 1000"：减法得 `−1000 − 1000 = −2000`（越结越欠），加法才是 0。
`已结算净额 = Σpay − Σreceive` 是**对净往来的调整量**（付出为正），不是"已结掉多少钱"。

**取证**：原文题注 —— 三处口径错误是"写代码时才暴露"的，不是设计时能看出来的。

```bash

npx tsc -p tsconfig.electron.json && npm run ledger:smoke        # 31 项真库断言
```

- 符号：`src/lib/partyLedger.ts` 文件头 §2/§3；单测「已付出去的结算冲减欠款」「分方向余额之差恒等于净额」

## 2. 结算上限必须按"方向"取，不能按净额取

**结论**：结算上限必须按"方向"取，不能按净额取。
同一个供应商常常既欠我钱（退货/返利）又该我付（新货款）。应收 5000、应付 3000 时净额只有 2000，
拿 `|净额|` 当上限会把"该付的 3000"判成超额 —— 这笔账永远结不掉。
故往来要给**六个数**：应收 / 应付 / 净往来 / 已结算 / 未结清 / 分方向未结清（应收方向、应付方向）。

**取证**：

```bash
npx vitest run tests/ledger.spec.ts tests/partyLedger.spec.ts   # 26 + 22 例
npx tsc -p tsconfig.electron.json && npm run ledger:smoke        # 31 项真库断言
```

- 方向上限：`src/lib/partyLedger.ts` 的 `canSettle` 注释；单测「混方向：应收 5000 / 应付 3000 时两笔都能结」；
  数据层 `scripts/ledger-db-smoke.cjs` 段 `[7]` 同名用例

**源**：`2026-10-25-ledger-p0-formula-fixes`（2026-10-25）

## 3. 合并相关人（B 路）不写 `bk_transfers`，但残额兜底分支要保留

**结论**：合并相关人（B 路）不写 `bk_transfers`。
原方案写"未结算条目改挂 + 写一条结转"，那是**把同一笔钱算两遍**：条目的余额已经随改挂带过去了。
正确 = 只改挂未结算条目，已结算条目留在原人（与它的结算单一起）。
验收判据因此可以断言：**合并后原人的未结清必须为 0**。
⚠️ 但 **残额兜底分支要保留**：若改挂后算出来原人未结清仍 ≠ 0（例如原人此前靠 `bk_transfers`
承接过别人的余额，那部分不随条目走），才写一条 transfer 把它带过去。正常路径恒为 0、写不进去。
判据是"残额 ≠ 0 才写"，不是"永不写"—— 别照本条标题把兜底删了。

**取证**：合并：`electron/ledger-db.ts` 的 `mergeParty` 注释；冒烟段 `[6]`「合并后原人未结清必须为 0」。

**源**：`2026-10-25-ledger-p0-formula-fixes`（2026-10-25）

## 4. 结算行的唯一性必须是部分唯一索引 `UNIQUE(entry_id) WHERE active = 1`

**结论**：结算行的唯一性必须是部分唯一索引 `UNIQUE(entry_id) WHERE active = 1`。
内联 `UNIQUE(entry_id)` 会让"撤销结算"功能直接废掉：结算单作废了，但这批条目仍被旧结算行占着，
永远无法重新结算。作废时把结算行 `active=0`（不删，保留"这张单当时结了哪几条"的痕迹）。

**取证**：部分唯一索引：`electron/ledger-db.ts` 的 `LEDGER_SCHEMA` 里 `uq_bk_settle_line_entry`；
冒烟「撤销结算：作废 + 结算行失活，条目恢复可结」。

**源**：`2026-10-25-ledger-p0-formula-fixes`（2026-10-25）

## 6. 分摊算法只能在渲染层 `src/lib/ledger.ts`，主进程只做守恒断言

**结论**：分摊算法**只能**在渲染层 `src/lib/ledger.ts`，主进程只做守恒断言。
原因不是风格：`tsconfig.electron.json` 的 `rootDir: "electron"` 使主进程**无法** `import '../src/lib/…'`
（TS6059）。所以别试图"主进程也算一遍"—— 真出现非渲染层写入方（Excel 批量导入 / 定时生成）时，
只能在 `electron/` 下新拆一个同算法模块（届时 `src/lib/ledger.ts` 改为 import 它，或反之），
并给两边补 parity 用例；**不要**把算法复制成第二份。

**取证**：`tsconfig.electron.json` 的 `rootDir: "electron"` ⇒ TS6059；数据与类型门禁实跑：

## 19. 哨兵值可以存在，但不能发出去：`ALL_PERIOD = 'all'`

**结论**：状态层用 `ALL_PERIOD = 'all'` 表示全部，因为 `''` 太危险：偏好文件里的月份一旦丢了，
`''` 会被主进程当成"不过滤"，界面**静默**变成全部期间，而用户以为自己在看本月 ——
数字全对、范围全错，是最难发现的一类。用一个与 `YYYY-MM` 不可能撞车的值，坏数据只会落回本月。

但**发请求时必须换成"不带这个字段"**：

- 主进程（`electron/ledger-db.ts`）的判据是 `if (filter.period) where.push('e.period = ?')`，
  它只 `slice` 不校验格式。传 `'all'` 不会抛错，只会拼成 `e.period = 'all'`，查出 0 行。
- 于是"点了全部，列表一片空白"看起来像没有数据，而不像参数传错。

**取证**：触发：明细页只能按月看，查一笔往年的账要一个月一个月往回翻。
`electron/ledger-db.ts` 的 `if (filter.period) where.push('e.period = ?')`（只 `slice` 不校验格式）。

## 21. 口径必须写在标签上：`XXXX年X月 · 整月` ↔ `全部日期 · 累计`

**结论**：`XXXX年X月 · 整月` ↔ `全部日期 · 累计`。
不写成泛泛的"本月"是有原因的：明细页顶部合计**只认期间、不跟筛选联动**（选店铺后合计仍是整月的，
否则公共支出会被整笔算进单店）。既然这个数不跟筛选走，用户就只能靠标签知道它是哪一段的数。
全部日期下继续说"整月"，等于告诉用户一个错误的期间。

**取证**：明细页顶部合计只认期间、不跟筛选联动（选店铺后合计仍是整月的，
否则公共支出会被整笔算进单店）。

## 22. 全部日期下翻月：以「本月」为基准往回翻，否则得到合法的 `NaN-NaN`

**结论**：`shiftMonth` 原来是 `month.value.split('-')`。当 `month === 'all'` 时：

```js
const [y, m] = 'all'.split('-').map(Number);   // y = NaN, m = undefined
`${NaN}-${NaN}` === 'NaN-NaN'                   // 合法字符串，任何存在性检查都不报错
```

主进程只 `slice`，于是 `e.period = 'NaN-NaN'` → 一条都没有，还是不报错。
修法是翻月前先判断：全部日期时以**本月**为基准，`‹` = 上一个月，`›` = 下一个月。

单店页（`ShopView.vue`）与汇总页（`SummaryView.vue`）各有一份自己的 `shiftMonth`，
三处都要改 —— 这是这个仓库既有的重复实现，改一个漏两个照样是"翻一下之后一条都不剩"。

**取证**：变异验证：`shiftMonth` 不判全部 → ② 组红，报错就是 `expected 'NaN-NaN' to be '2026-09'`。
`NaN-NaN` 不会抛异常、不会被 `if (period)` 判假、也不会被任何"这个值存在吗"的检查拦住。
只有一条**格式断言**（`/^\d{4}-\d{2}$/`）能抓住它。
三处 `shiftMonth`：明细页、`ShopView.vue`、`SummaryView.vue`。

**源**：`2026-10-26-ledger-all-period`（2026-10-26）

## 23. 哪些页能算全期间，要按**取数能力**判

**结论**：三个页签共享同一个 `month` 状态，所以用户在明细页点了「全部」，切到单店/汇总时
`month === 'all'` 一定会到那里。两种做法：那两页显示"请选具体月份"（拒绝）；或者让它们也真算全期间。

按"能不能算"逐个判，而不是按"页面该不该有这个概念"：

| 内容 | 全期间可行？ | 原因 |
|---|---|---|
| 明细列表 / 期间合计 | ✅ | 流量，跨月相加有意义；合计走 SQL 聚合，不受 1000 行上限影响 |
| 单店收支 / 科目分布 / 公摊明细 | ✅ | `shopBreakdown` 不传 `period` 就是全期间，语义成立 |
| 汇总页各店累计 | ✅ | 累计比按期相加更自然 |
| 单店页「订单收入对照」 | ❌ | `orderShippingRows` 按月拉、有 2000 行上限；跨月必然截断，算出来的只是**下限** |

最后那条是关键：截断后的订单收入如果照常显示，会得出"记账收入比订单收入多"这种
**方向性错误**的结论。所以全部日期下不取数、两项显示 "—" 并写清原因 ——
宁可少一个对照，不可多一个错结论。

**取证**：`shopBreakdown` 不传 `period` 即全期间；`orderShippingRows` 按月拉、2000 行上限。

**源**：`2026-10-26-ledger-all-period`（2026-10-26）

## 26. 全期间的验证：6 例单测 + 5 条冒烟 + 三处变异逐一变红

**结论**：全期间的验证靠断言"发出去的请求"，而不是屏幕上的数字；三处变异逐一变红才说明断言有效：

- `tests/ledgerPeriod.spec.ts`（新增 6 例）：默认本月 / 全部时不带 period + 合计传空串 /
  从全部切回具体月份 / 翻月不是 `NaN-NaN` / 偏好 `all` 能还原 / 坏值回落本月。
  mock 只做 `storage` + `api` 两层，断言的是**发出去的请求**，不是屏幕上的数字。
- `scripts/ledger-ui-smoke.mjs`（新增 5 条）：最决定性的一条是
  **从上个月（空态）点「全部」→ 必须变回 6 行**。空月变有数据，说明真的没按月过滤；
  如果只在本月点「全部」，行数前后都是 6，传不传 period 都看不出来。

第三条尤其值得记：`NaN-NaN` 不会抛异常、不会被 `if (period)` 判假、也不会被任何
"这个值存在吗"的检查拦住。只有一条**格式断言**（`/^\d{4}-\d{2}$/`）能抓住它。

## 27. 老坑（第 N 次）：假桥模板字符串里的反引号、macOS BSD `grep` 不支持 `\|` 交替

**结论**：两个反复踩到的老坑：

  一度以为改动丢了。用 `grep -E` 或 Grep 工具。

**取证**：`node --check` 报 `SyntaxError: Unexpected identifier`；
