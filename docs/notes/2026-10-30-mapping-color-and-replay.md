## 1. 映射从产品级升到「款 + 色」级，颜色存 `pl_shop_sku.spec`

**结论**：把「商品ID → 产品」的映射从**产品级**升到**款 + 色**级（用户拍板的 G4）：配一次，该商品之后的所有订单自动带出款编码与颜色，不再"每单看一眼图"。

**取证**：

| 事 | 落点 |
| --- | --- |
| 颜色**存哪** | `pl_shop_sku.spec`（`'*'` = 未指定）。**不新增列、不动 `pl_variants`** |
| 变体关联 | 写库时按 `(product_id, 色)` 反查一个变体填 `variant_id`（0 = 该色还没录变体）—— 不让用户把颜色选两遍 |
| 匹配语义 | `resolveOrderSku` 去掉写死的 `spec='*'`，改 **`ORDER BY (spec='*' OR spec='') ASC, id ASC`**（**带色行优先**） |
| 颜色来源 | `autoAssignByMap` 的颜色顺序改为 **映射配的色 → 订单原文色 → `未分类`** |
| 拣货投影 | `pickingRows` 的 `color` 改为 **款色 → 订单原文**（原名 `oi_orders.color`，实测恒空/占位） |
| 回填 | 新增 `reassignOrdersByItemIds()`；`product-sku-map` handler 写成功后**自动回填存量订单** |

涉及：`electron/product-db.ts` / `order-db.ts` / `picking-db.ts` / `src/modules/goods/components/ProductPicker.vue` · 方案背景见 `docs/plans/DAILY_SHIPPING_FLOW_PLAN.md` §3.1/§3.2。

**源**：`2026-10-05-mapping-carries-color`（2026-10-05）

## 2. 为什么用 `spec` 而不是 `variant_id`

**结论**：颜色是**商品ID 的属性**（同一商品ID 的所有订单必然同色），而 `pl_variants` 的粒度是 **款 × 色 × 码** —— 映射只需要"款 + 色"，选哪一行变体是任意的。`spec` 是自由文本"规格"，装颜色天然合适，且 `resolveOrderSku` 的升级注释本来写的就是「精确 spec 优先、回落 `*`」。

**取证**：`product-db.ts:1139`（"精确 spec 优先、回落 `*`"的注释）。`variant_id` 仍然填，但只作"尽力关联"（供下游按变体取克重/图），不参与匹配。

**源**：`2026-10-05-mapping-carries-color`（2026-10-05）

## 3. 归款是**写时触发**的 ⇒ 任何"后配的映射"都必须要回填

**结论**：`autoAssignByMap` 只在 `insertOrder` 那一刻跑。而真实操作顺序常常反着来（**先导订单、后配映射**）—— 没有 `reassignOrdersByItemIds`，用户配完映射**看不到任何变化**，只能把 Excel 重导一遍。

**取证**：同类先例：`syncPurchaseCosts` 上线前的拿货单没进 `ae_cost_map`（见 `purchase-cost-sync.ts`）。回填只处理本次写入的那些商品ID。

> **【历史记录】回填只碰未归款的图**（人工纠正 / AI 识别结论优先，自动归款永不覆盖）—— 此为 2026-10-05 口径，已被 2026-10-10 的补色通道取代。

> **2026-10-10 起范围扩大**：还覆盖挂在占位色「未分类」上的图（**改色回填** —— 用户给商品补上颜色后，这些"归了款但没色"的订单跟着补色）；挂在**真实颜色**上的图仍一律不动。见 `docs/notes/2026-10-30-mapping-color-and-replay.md`。

**源**：`2026-10-05-mapping-carries-color`（2026-10-05）、`2026-10-10-mapping-recolor-backfill`（2026-10-10）

## 4. 「填充率 ≠ 可用」的第二张脸：读了口径不对的列

**结论**：`pickingRows` 一直返回 `color = oi_orders.color`（订单原文），而 `styleColor`（映射/识别的结论）另有其列。拣货单用前者 → **映射配好的颜色在拣货单上被丢掉**，症状是"我明明配了色，拣货单还是没色"。⇒ 凡是"订单原文"与"识别/映射结论"并存的场景，都要明确**谁是权威**并写在 `color` 这类中性字段的注释里。

**取证**：`pickingRows` 的 `color = oi_orders.color` 与 `styleColor` 两列并存。

**源**：`2026-10-05-mapping-carries-color`（2026-10-05）

## 5. ⚠️ 建表语句与迁移必须同向，否则"新库"是最不忠实的夹具

**结论**：`oi_styles` 曾三处自相矛盾（**本轮抓到的最值钱的一条**）：建表有 `name`、三处 INSERT 写 `name`、迁移却 `DROP COLUMN name`，文件头注释还写着"列保留、写入空串哨兵"。后果：**老库上任何"新建款"的路径必抛 `no such column: name`**；而**冒烟建的是新库（有 name 列）→ 恒绿、线上必崩**。

**取证**：

| 位置 | 内容 |
| --- | --- |
| 建表 `order-db.ts:236` | `name TEXT NOT NULL`（新库**有**该列） |
| 三处 INSERT（识别建款 ×2、映射归款 ×1） | 都写 `name`（固定空串哨兵） |
| 迁移 `migrateOrderSpine` | 对老库 `ALTER TABLE oi_styles DROP COLUMN name`（老库**没有**该列） |
| 文件头注释 | 写着"列保留、写入空串哨兵"（与迁移**相反**，是过时残留） |

`insertOrder` 的注释还写着"不 catch 是有意的：这里能抛的只有真异常" —— 于是这个异常被当成"不该发生"。

**修法**：统一到"**无该列**"（迁移的意图），建表去掉 `name`、三处 INSERT 去掉 `name`、迁移里的"历史名交接"与 `DROP COLUMN` 都**先探列再动**。改完 `picking:smoke` 在新库（无 name）上仍全绿 —— 这一步同时证明了"夹具形状终于等于线上形状"。

**可带走的判据**：**夹具建表的形状若不是最旧的那个形状，它就不是夹具，是安慰剂。** 凡"只在某个版本之前的库里才存在"的结构差异（删列、改主键、改唯一键），冒烟要么走"最老形状 → 跑迁移"这条路，要么两条形状各测一次。

**源**：`2026-10-05-mapping-carries-color`（2026-10-05）

## 8. 「未分类」= 兜底占位名，不是识别结果

**结论**：它是 `autoAssignByMap` 的**兜底色名**：`MAPPED_FALLBACK_COLOR = '未分类'`（模块私有）。颜色顺序 = **映射色 → 订单原文色 → 兜底**。映射只到款级（`spec='*'`）且订单侧颜色列为空/占位时，只剩兜底可落 —— 款是对的，**颜色从未被配过**。

**取证**：`electron/order-db.ts:1158`（`MAPPED_FALLBACK_COLOR`）、`electron/order-db.ts:1220-1222`（颜色顺序）。

"在归类核对选了颜色"救不了它：核对页（`skuBackfillFromOrder`）只把**当时带色**的结论回写成映射色；颜色为空/占位时**有意只写款级 `*`**（"颜色只填不猜"，见 `docs/features/PRODUCT_LIBRARY.md` §3.5.1）。

**真库实测（2026-10-10，只读）**：

```sql
SELECT COUNT(*), SUM(color='未分类') FROM oi_style_colors;              -- 6 | 6
SELECT COUNT(*), SUM(spec='*'), SUM(note=''), SUM(source='manual') FROM pl_shop_sku;  -- 8 | 8 | 8 | 8
SELECT COUNT(*) FROM oi_images i JOIN oi_style_colors sc ON sc.id=i.style_color_id
 WHERE sc.color='未分类';                                               -- 9
```

`oi_style_colors` 6 行**全**是 `未分类`；`pl_shop_sku` 8 行**全** `spec='*'`、`note=''`、`source='manual'`（note 全空 ⇒ 不是经核对页回流的写入 —— 那条路径会写 note "归类核对页点名某款时记住"；它们来自「货与成本 › 商品ID 映射」的认款）；`oi_images` 9 张挂在 `未分类` 上。⇒ 前提都齐，只差"把颜色配上去"这个动作。

**源**：`2026-10-10-mapping-recolor-backfill`（2026-10-10）

## 9. 补色通道语义一：改色 = 改同一条绑定

**结论**：**改色 = 改同一条绑定**（`electron/product-db.ts` `upsertSkuMappings`，twin 分支）：5 列键 `(platform, shop_id, item_id, spec, product_id)` 只在 `spec` 上对不上、且该商品名下**同产品**恰好一条手动行时 → **UPDATE 它的 `spec`**，而不是并排新增。

**取证**：为什么不是"随便把旧行删掉/替换"：**同商品把不同颜色绑到不同产品是既有合法形态**（`resolveOrderSku` 的"带色行优先"就是为它设计的）⇒ 判据必须带"同产品"，那种写入是**新增一条绑定**，不能替换；同产品已有 2+ 条（历史数据）也无从判断该动哪条，维持新增。

症状为何必须修：并排留下旧条款级行时，它**永远命中不了**（只取一条、带色行优先），却留在映射列表里，人以为它已经变了。

**源**：`2026-10-10-mapping-recolor-backfill`（2026-10-10）

## 10. 补色通道语义二：回填覆盖「未归款 + 占位色」

**结论**：**回填覆盖「未归款 + 占位色」**（`electron/order-db.ts` `reassignOrdersByItemIds`）：查询从"只碰 `style_color_id IS NULL`"放宽为 `style_color_id IS NULL OR sc.color = '未分类'` —— 否则补色只在库里改了映射，订单们还挂着「未分类」，用户看不出发生过什么。

**取证**：**挂在真实颜色上的图一律不动**：人工纠正 / 识别结论 / 上次补的色都算数 —— 改一次映射不能把历史订单全洗一遍。⚠️ 直接后果：**补过一次色之后再改映射色，订单不会再跟着变**（它们已挂在真实颜色上）—— 这是有意为之。

**取代关系**：`docs/notes/2026-10-30-mapping-color-and-replay.md` 中「回填只碰未归款的图」一句，自本文起扩为「未归款 + 占位色」。

## 15. 「映射在、订单没吃到」的根因：写映射的路径不回填

**结论**：根因不在认款逻辑，而在**写映射的那条路径不回填**：`assignOrderStyle`（人工核对）→ 调 `rememberSkuMapping` → 内部 `reassignOrdersByItemIds([itemId])`，会回填；而 `upsertSkuMappings`（「建档与关联」里配映射）→ **`out.reassigned` 从未被赋值，也不调回填**。于是"先导单、后配映射"的商品永远停在未归款，而且它和"这根商品没配过映射"在界面上**完全同形**。

**取证**：真实库取证（51 行订单，`/tmp/skdb/y.db` 克隆）：

| 状态 | 行数 |
| --- | --- |
| 完全定（款 + 色都定） | 4 |
| 款定了、色还是 `未分类` | 38 |
| 有图但没定款 | 9 |

其中 **9 行"没定款"里有 6 行的商品ID 已经在 `pl_shop_sku` 里、且 `status='confirmed'`**。

## 16. 决策：不给按钮，改成进页自愈

**结论**：**这条链路不该有「请人工点一下」的入口**，它是确定性事实的重新套用。第一版方案是加一个「重放映射」按钮，改成自愈的理由（用户 2026-10-20 明确的产品原则）：

> 保证数据准确的同时，尽量减少人工介入；开始编码前先考虑有没有更好的方式。

按这条原则，这个动作不满足"需要人"的条件：输入是**已被确认过的映射**，输出是**唯一确定的**（同一输入必得同一输出）；唯一不确定的只是"有没有漏"，而那正是这一步要算出来的；让人点一下，只是把"系统该自愈"变成"人记得点" —— 多一个可能被忘记的步骤。

**取证**：落地为两处**进页时**自动执行（都在取数之前）：

| 入口 | 为什么在这里 |
| --- | --- |
| 基础数据 › 待补清单 | 它要报"还欠多少"，不先自愈就是在报旧数 |
| 发货台 › 归类核对 | 用户每天真正会进的那一页；漏网行在这里和"没配过映射"同形 |

两处都只 `onMounted` 一次（见 §18），且都用同一份 `replaySkuMappings`（幂等）。落地 `order-db.replaySkuMappings` + 两处进页自愈。

**源**：`2026-10-20-replay-mappings-on-load`（2026-10-20）

## 17. 四条硬边界（少一条就会出事）

**结论**：重放只有在这四条同时成立时才安全。

**取证**：

1. **只碰"未定/占位"**：候选行 = `style_color_id IS NULL` 或 `color = '未分类'`（或调用方显式点名的平台色名）。挂在真实颜色上的一律不动 —— 全库重放最怕的就是顺手改判历史结论。
2. **`dryRun` 只报数、不写库**：报数不能以改库为代价，否则"看一眼"就等于"悄悄执行一次写入"。
3. **幂等**：第二次跑 `fixedRows = 0`。页面会反复进，不幂等就是每次进页都重写库。
4. **自动修完必须说出来**：两页各有一行"已按现有映射自动补了 N 行归属"，`N = 0` 时整块不渲染。静默改库会让人以为数据本来就是这样 —— 比不修更糟。

**源**：`2026-10-20-replay-mappings-on-load`（2026-10-20）

## 18. 坑：挂 `token` 的 watch 上 ⇒ 一次进页跑 21 次

**结论**：第一版把自愈也挂在 `watch(token)` 上（理由听起来正当："数据变了就重放"）。冒烟实测 **调用 21 次**：`token` 在本页保存一行、翻一页、别处 `bump()` 都会变 —— 跟着它重放 = 每动一下把全表扫一遍。语义上也不需要：新订单落库那一刻已经走过 `autoAssignByMap`（写时触发），恰恰不需要重放；重放治的是**历史漏网**，进页一次就够。

**取证**：修法：`onMounted → bootstrap()`（自愈 + 取数），`watch(token) → load()`（只取数）。断言同时收紧成 `=== 1`，把"又挂回 token 上"这件事变成一条会红的守卫。

**源**：`2026-10-20-replay-mappings-on-load`（2026-10-20）

## 19. 重放的验证

**结论**：冒烟 +2（`product-sku-smoke`）、UI +1/+2，两条变异各自钉住 dryRun 与候选筛选。

**取证**：

## 20. 没做 / 下一处更根本的触发点

**结论**：两处留下的漏网，都不是重放能解决的。

**取证**：

- **店铺归一之后**没有自动重放该店铺的订单。而 `resolveOrderSku` 的键是 `(platform, shop_id, item_id)` 三元组 —— 店铺没归一，认款必然落空。所以"先导单、先登记店铺"这条路仍会留漏网，只是现在**有人进那两个页面时会自愈**。真要根治，触发点应该挪到"店铺归一/改绑"之后（跨域：`shop-db → order-db`，要先过 `check-cross-domain-edges.mjs`）。
- 采集通道（`source='collect'`）落库时 `image_id=NULL`，而 `autoAssignByMap` 第一句就是 `if (!rec.imageId) return` ⇒ **采集订单不会自动归款**，重放也救不了（它们连候选行都进不去）。这条要么补图（用采集主图/色图当订单图），要么另开一条不依赖图片的归款路径。

**源**：`2026-10-20-replay-mappings-on-load`（2026-10-20）

## 21. 克重取数：两条各自独立的原因（都在真库上量过）

**结论**：订单进得来、款也认得，但运费算不出，界面只写「缺克重」。人去产品库把克重填了，**还是缺**。

**取证**：

| 断点 | 数据事实 | 后果 |
|---|---|---|
| 颜色是两个世界 | 订单上的色是**平台色名**：`7`、`Khaki`、`Photo color`、`printing 04`；产品库里是用户自己的色名：`黑色`/`白色`/`红色` | `skuWeightKey(款, 色, 码)` 逐字节比 ⇒ 一条也命中不了 |
| 尺码是两种写法 | 产品 SKU 写 `3XL/4XL/5XL`，同一批订单写 `XXXL` | 就算颜色对得上也命中不了 |

真库取证（51 单 / 19 款 / 365 变体）：

- 精确命中（款+色+码）只有 **4/51**；
- 「款+码」层：**83/83** 个「款×码」的**各色克重完全一致**，0 例各色不同重；
- 尺码：4 条 `XXXL` 的订单在产品侧一条都对不上（产品只有 `3XL`）。

**源**：`2026-10-19-weight-key-drops-color`（2026-10-19）

## 22. 定性：不是"色名没配"，是"颜色不该进这个键"

**结论**：上一轮设想的方案是「让用户把平台色配一次我的色名（`(productId, 平台色) → variant`）」。真库一看不可行：平台色名里有一半是**数字**（`1`…`15`），连猜都没有依据；让人逐色配一遍，等于把"多色逐色配映射"这件刚被证伪的事换个壳重做一遍。而克重本身在实测里**与颜色无关**（83/83 各色同重）⇒ 正确做法是让颜色**退出克重的判定条件**，而不是给两套色名建字典。

**取证**：83/83 各色同重；平台色名 `1`…`15` 等数字形态。

**源**：`2026-10-19-weight-key-drops-color`（2026-10-19）

---

## 23. 改法（纯层，无表结构、无落库值变化）

**结论**：`src/lib/orderCost.ts` 五处改动，规则只留一处。

**取证**：

1. `canonSizeKey(size)` —— **只用于建查表键**：全角→半角、`XXL`/`xxl`→`2XL`、`XXXL`→`3XL`。**不碰** `S/M/L/XL/XS`（`XS` 与 `S` 是不同码），不猜 `均码`/`70B`，认不出原样返回。
2. `skuWeightKey` 的码段改走 `canonSizeKey`（建表与查表两端共用，故天然对称）。
3. 新增 `skuSizeWeightKey(款, 码)` = 颜色留空的同一形态键。
4. `resolveWeightG` 两级：`款+色+码` → **`款+码`** → `null`。
5. 新增 `buildSkuWeightIndex(variants, codeOf)` —— 从产品 SKU 行建查表，**折叠键只在"各色确实同重"时产出**：该款该码的**在售**变体全部填了克重、且值完全一致。任一没填 / 任一不同重 → 不产出。

`src/core/services/skuWeights.ts` 退化成「取数 + 调纯函数」，规则只有一处。

**源**：`2026-10-19-weight-key-drops-color`（2026-10-19）

## 24. 三条"宁可少算"的纪律

**结论**：折叠键的存在与否，一律宁可少算。

**取证**：

- **少算优于错算**：折叠键不存在时继续报「缺克重」（人看得见、会去补），绝不拿某个颜色的重量顶上 —— 顶错了是发错货。
- **无色行不建精确键**：颜色为空的变体建出来的键就是「同款同码」键，会让"各色不同重"绕过判定。
- **归档变体不参与折叠判定**（不发货，不该挡住），但它的精确键照样生效。

**源**：`2026-10-19-weight-key-drops-color`（2026-10-19）

## 26. 守卫与仍然不解决

**结论**：`tests/orderCost.spec.ts` +7，五条变异各只红目标断言；订单色名与缺失尺码仍要靠人补。

**取证**：`tests/orderCost.spec.ts` +7：尺码归一（`XS≠S`、`XXXL==3XL`）、折叠键不可冒名精确键、两级查询优先级、折叠边界（全填同重 / 有没填 / 有不同重 / 归档 / 无色行 / 无款编码）。变异五条各只红目标断言：去尺码归一 → 尺码用例红；去第二级 → 两级用例红；不要求全填 → 「有没填」红；不同重也折叠 → 「不同重」红；无色行建键 → 「无色行」红。门禁：`tsc` / `vue-tsc` / `verify` / `verify:docs` / `build` / `vitest` / `today:ui` / `order-profit:ui` / `shipping-rate:ui`。

仍然不解决：**订单上的颜色仍旧显示平台色名**（`7` / `Khaki`）。这是"事实"而非 bug；要显示成 `黑色` 需要人给一次对应，属 UX 能力，本轮不做。它**不再阻塞运费**，因为克重已不看颜色。`S/M` 这类"产品侧没有这个码"的情况要靠建款时补齐尺码，代码无从推断。
