## 1. 用户口径（五条）与落地

**结论**：「今天 › 归类核对 › 待核对订单」（`src/modules/today/tabs/ClassifyPanel.vue`）按用户口径重做。
表面是"删两列、放大图、加个下拉"，真正难的是**三条不许做坏的判断**：① 撤掉的东西**能力去哪了**要逐条答；
② 颜色取值有**三支优先级**，夹具必须一行一支；③ 「款式列表」的驱动表从识别池换成产品库——换完之后，
一条**旧断言本身变成了错的**。

| 口径 | 落地 |
| --- | --- |
| 列表图片展示不全 | 本页把基座 `.wb-thumb` 覆盖成 64px + `object-fit: contain` |
| 品类 / Logo 两列去掉 | 表头 9 → 7 列；字段**仍原样回传**（不显示 ≠ 抹成空串） |
| 匹配到款后取**该款的颜色**让用户选；记住"图片地址 → 颜色"，同图下次自动选中；该款没这个色就让用户自己选 | 颜色格 = 该款色卡下拉（默认值三支优先级见 §5） |
| 归属款选项应来自**货与成本的产品库**（当前展示不全） | `order-db.listStyles()` 驱动表：`oi_styles` → `pl_products` |
| 「待核对 / 未归类 / 识别库 / 已配产品」指标条去掉 | 整条撤掉，连带 `order-sku-rollup` 通道退场（零消费者即删） |

**取证**：上表即原文口径与落地对照。

**源**：`2026-10-10-classify-panel-rework`（2026-10-10）

## 2. 撤掉一个东西时，三件事要一起做

**结论**：

**① 能力去哪了，要写清楚**（不是"不显示了"）。品类是主数据、在「货与成本」维护；Logo 等「印花 logo 管理」做出来再加回来
—— 写在组件头注释里，而不是让下一个人猜。

**② 反向守卫要钉在"能力真的不在"，且能自证非空转。**

- 表头（7 列）与**控件**两处都要钉：只钉表头会漏掉"列撤了、输入框还在原地写值"这种半拉子改法（最糟的一种：看不见却仍在写）。
  `!card('cl-cat-41') && !card('cl-logo-41') && !card('cl-cat-options')`。
- "指标条没了"这条，同一条 `report` 里先确认**面板与表格真的在**（同一个 `card()` 查找函数、同一时刻），否则 `!card('cl-stats')`
  可能只是"这一页压根没挂上"。

**③ ⭐ 连带通道的守卫：判据必须是"有没有人读这个键"，不是"通道被调了几次"。**
`orderSkuRollup` 的桩删掉之后，"调用次数 == 0"是**恒真**的（读不到就无所谓调用）—— 一条标准的假守卫。本轮改法：假桥的兜底分支
把**没人实现的键**记进 `__unhandled`，断言改成"这个键没被人读过"。顺带它也把"本页偷偷用了什么没实现的键"暴露出来
（实测输出里有 `platform` / `settleOrders` / `aeRateList`，与本页无关但一眼看得见）。

**取证**：上述判据代码与 `__unhandled` 实测输出。

**源**：`2026-10-10-classify-panel-rework`（2026-10-10）

## 3. 颜色：一条字段，三支优先级，夹具要三行

**结论**：取值顺序（**每一支都要落在该款的色卡里才作数**）：

1. 图记住的颜色（宿主存在 `oi_images.style_color_id` 上，订单列表联表出来是 `o.styleColor`）；
2. 订单自己的颜色列（上一轮人工核对留下的值）；
3. 都不在色卡里 ⇒ **留空让用户自己选**。

**取证**：夹具与判据必须**一行一支**，否则错法照样全绿：

| 行 | 款 | 图记住 | 订单自己的 | 期望 | 打的是哪种错法 |
| --- | --- | --- | --- | --- | --- |
| P-42 | S1（色卡 黑/白） | 白 | **黑** | **白** | "永远取订单自己的颜色"——两个值都在色卡里，只有期望值不同才分得开 |
| P-45 | S1 | 印花 | 黑 | 黑 | 去掉第 2 支（只认记住的色）后它会空着 |
| P-44 | S1 | 印花 | 印花 | **空** | "替他改判"（把别的款的色塞进来 / 随便选一个） |

**源**：`2026-10-10-classify-panel-rework`（2026-10-10）

## 6. 「点名了款却没给颜色 ⇒ 不许保存」的判据必须连着三条

**结论**：背景：宿主落库时颜色是款色的主键之一（`oi_style_colors(style_id, color)`），空颜色会落出一个**没有名字的款色**，
而界面上看不出任何异常。判据**必须连着三条**，只断言"保存禁用"是不够的 —— 那会被"这行本来就不脏"满足（恒绿）：

1. 换款后原颜色不在新色卡里 ⇒ 清空 + 出现缺色提示；
2. 此时「保存」`disabled === true`；
3. **补上该款的某个颜色后，同一行立刻可保存** —— 它才证明卡住的是缺色、不是"没改动"。

**取证**：上述三条。

**源**：`2026-10-10-classify-panel-rework`（2026-10-10）

## 7. 换驱动表之后，一条旧断言自己变成了错的

**结论**：`listStyles()` 从 `oi_styles` 驱动改成 `pl_products LEFT JOIN oi_styles`（识别池有、产品库没有的行以空名补在末尾 ——
少一行比多一行难查得多）。用户报的"归属款展示不全"就是前者：**产品库里手工新建、还没出过订单的款在识别池里没有行**。

副作用在 `scripts/style-authority-smoke.cjs` 的 B7：它断言"删掉识别池那一行 ⇒ `listStyles().length === 0`"。换驱动表后
**产品库还有这个款 ⇒ 列表里就该还有它**，旧断言从"守着一件对的事"变成了"要求一个错的结论"。改法是把它反过来：
**它必须仍在列表里、名字跟产品库走**，并在断言里写明"别改回 `length === 0`"。

通用教训：**改一个函数的驱动源时，去 grep 它的全部既有断言** —— 里面很可能有一条断言的**期望值本身就是旧驱动源的产物**，
它变红不是"改坏了"，而是"这条断言在阻止修复"。判据是：把该断言改成新语义后，它是否在说一件**该成立的事**。

**取证**：B7 断言原文。

**源**：`2026-10-10-classify-panel-rework`（2026-10-10）

## 10. 坑三：本轮有一次改动被写回覆盖

## 12. 这个页面前是"单向阀"：完成的行再也回不来

**结论**：「发货台 › 归类核对」的待核对表按定义只查 `corrected = 0` 的行：

```ts
// src/modules/today/classify.ts（改前）
listPending(opts) → ipc.orderList({ corrected: false, … })   // 只要待核对
```

而写 `corrected` 的两条路径**都只写 1**：

| 路径 | 行为 |
| --- | --- |
| `orderUpdate`（「保存」） | 顺手把该行 `corrected = 1` |
| `orderMarkCorrected`（「确认无误」/「全部确认无误」） | 把点名的行 / 全表置 1 |

⇒ **两条路都是单向的**。全仓 grep 不到任何一处会把 `corrected` 写回 `0`。于是：已核对的行**没有任何屏幕能看见**
（它按定义不在待核对列表里）；用户核对完一轮、发现某行颜色/款选错了 —— **没有任何入口能回去改**；真库现场（2026-10-11 夜）：
`oi_orders` 23 行**全部** `corrected = 1`（当天导的 23 行都被"确认无误"过了）。

这是一个纯粹的**能力缺口**，不是 bug。上一轮修完「设颜色不生效」之后，用户核对过的行才真的写对了数据；紧接着就撞上
"写错了也回不去"。两件事恰好在同一条链上前后脚暴露。

**取证**：上述代码与 `23 行全部 corrected = 1`。

**源**：`2026-10-12-classify-reopen-corrected`（2026-10-12）

## 14. 数据层：只翻 `corrected` 这一位

**结论**：`electron/order-db.ts` 新增 `reopenOrdersCorrected(ids)`：

```ts
export function reopenOrdersCorrected(ids: number[]): number {
  const list = [...new Set(ids)].filter((n): n is number => Number.isInteger(n) && n > 0);
  if (!list.length) return 0;
  const d = getDb();
  const placeholders = list.map(() => '?').join(',');
  const r = d
    .prepare(`UPDATE oi_orders SET corrected = 0 WHERE id IN (${placeholders})`)
    .run(...list);
  return Number(r.changes);
}
```

三条刻意的设计：

1. **只翻 `corrected` 一位** —— 不碰 `category` / `color` / `logo`。退回是"我要重做"，不是"把你之前的判断抹掉"；
   重做时用户手里的草稿还在，改完再保存一次即可。
2. **刻意没有 `all` 分支** —— 一次退回整批是不可逆的（退回后无法区分"本来就没核对"和"我刚退回来的"），且用户看不出
   到底退回了多少行。这与 `markAllOrdersCorrected`（批量置 1）**不对称是有意的**：确认可以一键（错了一行还有列表兜底），
   退回不行。
3. 复用 `markOrdersCorrected` 的入参清洗（去重 / 只留正整数），空列表直接返回 0。

**取证**：上述代码。

**源**：`2026-10-12-classify-reopen-corrected`（2026-10-12）

## 17. 页头范围切换：两个可点的范围

**结论**：原页头是一条只读计数「待核对 X · 已核对 Y」（上一轮刚做的"动作计数"）。本轮把它变成**两个可点的范围**：

- `.wb-seg` 分段控件（与「货与成本」的「待关联队列 / 已建立映射」同一套基座），两个范围各带计数徽标
  （`cl-count-pending` / `cl-count-corrected`）；
- 切到「已核对」⇒ 列出**今天这批**已核对的行，每行一个「退回待核对」(`cl-reopen-<id>`)；
- 已核对范围的**颜色 / 归属款两格变成只读文本**（`cl-ro-color-<id>` / `cl-ro-style-<id>` —— 没有输入控件可改），
  操作列只有「退回待核对」；
- 「同商品」徽标、说明句、「全部确认无误」按钮**都只在待核对范围出现**；
- 空态按范围分叉：已核对空态给 `cl-goto-pending`（切回待核对），待核对空态给 `cl-goto-corrected`（「看已核对的 N 行」）；
- `setScope()` **回到第 1 页**、保留搜索词 —— 换范围后页码还停在第 3 页会直接看到空表。

⚠️ **两处刻意的守卫**：`applyFocus` / `onRowEnter` 开头都加 `if (scope.value !== 'pending') return;` —— 键盘流
（回车保存、焦点落到顶上那一行）只在待核对范围有意义，已核对范围没有可编辑格。

⚠️ **计数与产品库那两份取数不跟着换** —— 只有分页那一份按 `scope` 选 `listCorrected` / `listPending`。计数条两个数必须
**同屏同时可见**（它是"这一轮做了多少"的唯一证据），跟着范围换会变成"切过去才知道有多少"。

**取证**：上述锚点名。

**源**：`2026-10-12-classify-reopen-corrected`（2026-10-12）

## 18. 纪律：退回与确认**互为镜像**

**结论**：第一版按直觉写了「退回一行本来就待核对的行 ⇒ 返回 0」，`order:smoke` 当场打红 —— 实测 `changes = 1`。
`UPDATE … SET corrected = 0 WHERE id IN (…)` 命中即算一次，**它不问原来的值是不是 0**。于是把语义定成一条，
并在用例名里写明：

> **退回与确认互为镜像：都按点名的 id 直接写目标值（不额外要求"原状态不是它"）。**

这与 `markOrdersCorrected` 的既有行为**对齐**（它也只按 id 置 1，不校验原来是不是 0）。两条通道"点谁写谁"是同一条规矩，

## 22. 追加一条能力的通用结论（五条）

**结论**：

1. **"能力是单向的"是一类独立的缺口** —— 它与"功能坏了"症状完全不同：界面全绿、数据也写对了，只是**没有回头路**。
   发现它的方法不是看代码，而是问一句「用户做错了这一步，怎么改？」本轮答案是"屏幕上看不到那批行、也回不去"。
   同类的还有：已确认/已提交/已归档/已忽略。
2. **补一条反向能力时，先问"正反两件事是不是同一条规矩"** —— 退回与确认都是"点名即写目标值"，于是校验、入参边界、
   SQL 形状可以完全对称；但**对称不等于都做** —— 批量确认有列表兜底，批量退回不可逆，两者刻意不对称。
3. **同一份视图的两个范围，取数口径要一起审** —— 只有"分页那一路"跟着范围换，计数与外部数据源（产品库）**不换**；
   换错了的症状是"切过去才知道有多少"或"两个数互相矛盾"。
4. **只读格与可编辑格必须是两种形状** —— 已核对范围的颜色/归属款换成纯文本（不是 `disabled` 的输入框），
   让"这里改不了、要退回才能改"在屏幕上一眼可见。
5. ⭐**夹具的两个取值必须不同**（P-46 款色「黑」/订单色「灰」）—— 两个值相同 ⇒ 优先级断言恒绿。这与
   `2026-10-11-purchase-image-by-size.md` 的"假桥给所有输入同一个输出是最隐蔽的空转"是同一类错误。

**取证**：同上。

## 24. 批量操作不是「加一排复选框」：先数"同一个决定重复了几次"

**结论**：第一版解决的是"看不准"（下拉只有文字、判据却是图）。上线后用户立刻给了第二句话：

这些行本来就该一次做完。**批量的最小单位是商品，不是行。**

## 25. ① 批量的单位要按「业务上相同的那些行」定，不能按"勾中的行"定

**结论**："勾了 5 行 → 给它们定同一个款"看起来最直接，但它对**跨商品**的勾选是错的：5 行可能属于 5 款。反过来
"一行一个选择器"又退回了逐行。正确的形态是**分组**：弹层里按商品列卡片，每组选一次款。只有一个商品时它自然退化成

## 41. 像素解码不是解法，是地基

**结论**：**不能**解决"自动认出款式与颜色"。它只是把 JPEG 变成 `Uint8Array` 的那一步 —— 没有它任何图像算法都跑不起来，
但它本身不含任何"这是哪个款、什么颜色"的信息。**真正的解法是"在参照图里找最近邻"**，像素解码只是这条链的第 0 步。

【历史记录】它值得单独说，是因为成本几乎为零且跨平台：Electron 内置的 `nativeImage` 可以
`createFromPath(p).resize({ width: 128 }).toBitmap()` 拿到 BGRA，**不需要 sharp / canvas / jimp 任何一个原生依赖**
（项目目前一个都没有）。特征函数写成 `src/lib` 下的一个纯函数模块（暂名 imageFeatures，只吃 `Uint8Array + w + h`），
vitest 直接可测，不 import Electron —— 这是本仓"提示词/算法必须住纯模块"那条纪律的同一手法。

> ⚠️ **2026-10-28 实测更正：这条"零依赖解码"只在 JPEG 上成立。** 用项目自带 Electron（44.4.1）主进程
> `nativeImage.createFromPath` 解码真库 82 张已归类图：**14 张 jpg 全部成功，68 张 webp 全部 `isEmpty()` 即 `decode empty`**。
> 而订单图落盘格式里 webp 占 83%（`order-images/` 101 个文件里绝大多数是 .webp，`file` 判定为 `Web/P VP8`）。
> ⇒ 结论是**解码位置必须换**：走渲染层 `createImageBitmap` / `<img>` + canvas（Chromium 原生支持 webp），
> 或在主进程引 `sharp`（原生依赖，多平台预编译二进制）。这条与"用不用小模型"无关，是任何像素方案的前置条件。

**取证**：`14 张 jpg 全部成功 / 68 张 webp 全部 decode empty`。

**源**：`2026-10-28-classify-local-vision-direction`（2026-10-28）

## 43. 推荐主线：四层信号，命中即停

**结论**：

```
L0   商品ID 映射（pl_shop_sku）           → 款 + 色，零图像
L0.5 图片内容指纹命中（oi_images 已有）    → 同一张图必同一结论
L1   结构特征 1-NN（灰度 dHash + 边方向）  → 款 Top3 + margin 门槛
L2   该款色集内 Lab ΔE 最近               → 色 Top1 + 阈值
└──  任一层的把握不够 ⇒ 弃权，保持人工
```

三个设计约束（都是从本仓已踩过的坑倒推的）：

1. **款和色必须解耦。** 判款只用灰度结构特征、**不掺颜色**；判色时只在"这款已有的那几个色"里选
   （`oi_style_colors` / `pl_variants.color`）—— 不是从色板猜绝对色名。这与现有数据模型完全同构（款 = 指纹，色 = 款色），
   错一次不会连累另一维。
2. **弃权优先。** Top1 与 Top2 的 margin 不够、ΔE 超阈值、或前景色熵高（判为印花）⇒ 不给建议。理由是本仓既有纪律：
   **错并（两色合一）比拆更难发现、更难回退**。
3. **建议只预填，保存仍由人触发。** 2026-10-11 那次"点保存提示成功、款色还是未分类"证明：自动落库的静默失败比不做更贵。

**取证**：上述分层块。

## 49. 方案 B 的运行与分发成本：选 WASM

**结论**（同一台 M 系 Mac 实测）：

| 项 | `onnxruntime-node`（原生） | `onnxruntime-web`（WASM） |
| --- | --- | --- |
| session 建立 | 165 ms | 288 ms |
| 单图推理 | **11 ms** | **46 ms**（4 线程） / **165 ms**（单线程） |
| 分发包增量 | **+65~87 MB / 每个平台**（`node_modules` 里 291MB 需裁剪，且要 `asarUnpack *.node`） | **+16~26 MB** 一个 wasm，全平台同一份 |
| 原生依赖 | 要 rebuild + 架构匹配（mac arm64/x64、win x64 各一份） | **无** |
| 跨平台一致性 | 三份二进制，行为可能不同 | 同一份 wasm |

⇒ **选 WASM。** 46-165ms/张 对"用户点一次、等一两秒"的交互毫无压力，换来的是"零原生依赖 + 双平台一份产物"。
原生那 11ms 的 4 倍优势买不到任何用户可感知的差别，却要在 mac/win 各维护一份二进制与 asarUnpack 规则。

## 56. 常用色归类的六个坑（都真的踩到了）

**结论**：

1. **`onChipMove` / `pointerup` 原来挂在 `.mx-colors` 上** ⇒ 鼠标一离开那一条就收不到 `pointermove`，**根本拖不到上面的常用色**
   （不是"瞄准难"，是事件根本不来）。改挂**根元素** `.mx`，另加 `window` 级 `pointerup` 兜底：松手落在组件外（矩阵表格、
   抽屉空白）也必须收尾，否则状态卡在"拖动中"（鼠标已抬起、界面还灰着一片）。
2. **往"刚点常用色新建的空白行"上合并会删旧建新**：同码冲突原本无条件保留目标格，而新行没 `variantId` ⇒ 已落库那条被丢、
   保存时删掉再造一条（编码 / 状态 / 历史一起没）。现在冲突格里**目标格没 id 就接过源格的 id**；真会消失的 SKU 数单独用
   `dropped` 数（`conflicts` 是"同码格数"，不是"少几个 SKU" —— 拿它写回执会谎报损失）。
3. **`.mx-color__img` 挂在颜色 chip 上，不在矩阵行上**：第一版断言量 `[data-act="ed-row"]` 里的图片数，得到 `imgs/row=0`
   的假红。断言前先问"这个元素属于哪一层"。
4. **收尾不能假设一定弹「放弃改动」**：本步最后把 `黑` 改名成 `藏青` 又并回 `黑`，净结果与库里一致 ⇒ 保存计划是空的，
   抽屉**直接关**（这本身是个好信号，已加成断言）。写收尾要先判 dialog 再点，否则 `clickText` 会在 4s 后抛
   "找不到可点击元素"，把一条通过了的步骤报成失败。
5. （老坑重犯）**注入脚本的注释里又写了反引号** —— 整段模板串被截断，报的却是 `SyntaxError: Unexpected identifier 'mx'`，
   指向注释里的一个词。写"这样的东西"时一律用中文引号。
6. **`<img>` 在 Chromium 里默认可拖**：色图现在既是显示也是**拖动手柄**，不关掉原生拖放就会在按下时先起一个 `dragstart`，
   指针事件随之断掉（表现：拖不动）。已加 `draggable="false"` + `-webkit-user-drag: none` + `user-select: none`。
   **这条合成事件抓不到**（冒烟 `--dump-dom` 发不了可信输入）—— 所以取证靠 `goods:shot` 里的 CDP 真鼠标探针，
   而不是靠"冒烟全绿"。

**取证**：上述六条。

## 59. 修法：图列要有自己的地板，不能指望图片有多大

**结论**：

```css
.cl-thumb-col { width: 112px; min-width: 112px; }   /* 列的地板 */
.cl-thumb-btn  { width: 96px; height: 96px; }        /* 格子里那个块的定尺 */
```

两处都要，理由不同：`td` 的 `min-width` 是**列宽**的下限；按钮的定尺是这一列 **min-content** 的来源 —— 只给 `img` 设宽时，

⇒ **列该塌还是塌**。这是本轮实测踩到的：第一版只加 `td { min-width }` 之前，先试过只动 img，没用。

代价（写进注释）：窄窗口下整表会比容器宽一点 ⇒ 横向滚动。`.wb-table-wrap` 本来就为此准备着（首列 sticky），

## 67. 缺款 / 缺色是"界面死路"，不是数据限制（2026-11-02）

**结论**：用户原话「不存在款或不存在款色时就没办法进入下一步，必须要基础数据中去建款和色」。
去查数据层，**上游早就不限制**：`assignOrderStyle` → `ensureStyleByCode`（产品库里没进过识别链的款
补一行占位款）+ `ensureStyleColor`（款色没有就地 INSERT）；`productUpsert` / `productNextCode` /
`productVariantUpsert` 三支通道也都在。卡住的是三处**只有说明、没有入口**的地方：

| # | 卡点 | 改前 | 改后 |
| --- | --- | --- | --- |
| ① | 产品库为空 | 「归属款」格退化成一句灰字 | 格子永远可点，弹层里能建 |
| ② | 款不在列表 | 空态只写"去产品管理建档" | 列表尾部「＋ 新建款」（编码预填） |
| ③ | 款色卡没有这个色 | 只给 chips、**没有输入框** ⇒ `needColor` 恒真 | 从**颜色库点选**（`ColorPalette`），保存时建款色 |

**为什么必须修**：流程第 3 步的判据是 `gaps.style > 0`（没款的行数）。一行定不了款，整条发货流程
停在"等第 2 步"——用户感受到的是"软件不让走"，而不是"这里缺个按钮"。

**三条口径**：

1. **就地建档 = 真的建档**：新款写 `pl_products`，新色写 `oi_style_colors`（款级事实，下游取图 /
   算钱 / 拣货读的就是它）。不做"只服务这一单"的临时款 —— 那会把同一件货拆成两个真相。
2. **弹层仍然不写库**：`create` 只 emit，落库由父层那**一条** `productUpsert` 做，回执再
   `acceptCreated()` / `failCreate()` 送回表单。两处各写一套必然分叉。
3. **色只能从颜色库点选，不给自由文本**：要给这个款加一个库里还没有的色，走末尾「＋ 新增颜色」
   （写 `md_colors`、同名幂等、加完所有款都能选到）。关掉弹层不会在库里留下没人用的色。

⚠️ **没有写 `pl_variants` 的"无尺码色行"**（原计划在这一页顺手补一行，实测不可行）：
`variantUpsert` 的判据是「颜色和尺码要成对填写」，`product-db-smoke.cjs` 专门钉了这条；
硬写会绕过不变量，而且商品抽屉的 `isLegacyVariant`（`!color || !size`）会把它归进
「只有名称 · 旧」那一栏 —— 对刚建的色是误导。**要"产品管理也看得见"，正确落点是产品域把
已学到的款色渲染成矩阵空行（"有颜色、没勾码"本来就合法），不是造一行假 SKU。**

**颜色区第一版是错的，留档**：第一版补的出口是一个**自由文本输入框**（「＋ 新色」自己打色名）。
用户当场否掉 ——「在款中增加颜色不能填名称，否则又会造成颜色库中的数据重复」。这个判断是对的：
一旦允许"给某一个款随手起个色名"，`深灰 / 深 灰 / 深灰色` 就会各存一份，颜色库从此不再有单一真源，
而下游（SKU 编码取 `md_colors.id`、别名、合并）全按色名/色 id 关联，噪声进去就难清。
所以现在颜色区**一个可输入的框都没有**（弹层打开时 `sp-colors` 里 `<input>` 数 = 0），
要新色只能走颜色库的唯一写入口 `addColorToDict` → `md-color-create`（`ensureColorId` 同名幂等，
并挡掉纯数字色号）。**新增完只是进了库**，成为这个款的色仍是「保存」那一步的事。

**回落表不能当色名写进业务表**：`colorDictNames` 在字典没读到时回落到内置常用色
（`COMMON_COLORS` = `黑`/`白`/`灰`），而字典种子是 `黑色`/`白色`/`灰色` —— 两套写法不同。
所以这一页多判一次 `colorDictLoaded`：没读到就**只列款色**、不给「＋ 新增颜色」，
并在提示里说清"关掉重开，仍读不到就不能在这一页定色"。宁可少一个按钮，也不让界面自己
生产一份"库里没有的色名"（那正是这次要治的病）。

**款色 ∪ 颜色库，两张表都要列**：只列款色 ⇒ 缺色仍是死路；只列库色 ⇒ 识别链早就学过、但字典还没
整理的那些名字会凭空消失（屏幕上没有任何"缺"的迹象，比死路更难查）。合并时款色排前面、去重；
有"不在颜色库里"的款色时，提示里点明"去「基础数据」可以合并成同一个色"（合并工具在那页）。

**取证**：`today:ui` 383 → **396** 全绿。变异复核：
① 颜色区塞一个 `<input>` ⇒ 恰 2 条红（"颜色区里没有可输入的框" + "只摊开颜色库那一个输入框"）；
② `acceptCreated` 不选中新款 ⇒ "建完弹层不关且新款被选中"那条红；
③ 去掉「＋新建款」的 `data-act` ⇒ 恰 1 条红。

⚠️ **两个夹具坑**：

1. 假桥的 `orderStyleList` 原来回**同一个数组引用**。真实 IPC 会结构化克隆（每次新引用），
   而界面里 `StyleList` 的 `filtered` 是按 `props.styles` 身份缓存的 computed ⇒ 同引用时**不重算**，
   症状是"建完款、列表里却没这一行"。假桥改成 `STYLES.slice()`。
2. 色点断言不能再写成 `sp-color-黑`（把色名拼进 `data-act`）。`ColorPalette` 所有色点共用
   `data-act="sp-pal-common"`，具体是哪一个是 `data-color`；选中态类名是 `is-current`（不是表格行
   那个 `is-on`）。旧写法在色名带空格时选不中，且同名锚点出现 N 次时 `card()` 只拿第一个 ——
   断言会静默指向错的色，恒绿。

`StyleList.vue`、`ClassifyPanel.vue`。
