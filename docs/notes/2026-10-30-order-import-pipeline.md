## 1. 导入回执从"一句人话"升级成结构化回执，零新通道

**结论**：统一导入的返回值从"一句人话"升级成**结构化回执**（`title` / `landed` / `next`），
今天页把它渲成一张常驻卡 —— 落点说清"存到哪儿、在哪看得到"，下一步是**真按钮**。
零新 IPC 通道、零新表、零能力域变更、岛无需发版。

**取证**：用户原话"现在的流程还是不够直观，导入订单后，接下来不知道要做什么，并且数据也不知道去哪了"；
旧实现的 `message` 其实写得挺全（判据 + 导了多少行 + 拆行 + 主图 + 店铺）。

## 8. 等待判据必须钉在"只有新结论才具有的特征"上

**结论**：统一导入有两条 message **共享子串**：

- 商品信息表：`没认出这个文件是什么。逐张体检：…这类文件**不用再导入**了…`
- 认不出的文件：`没认出这个文件是什么。逐张体检：…`

冒烟等"junk 那条结论出现"用的是 `flat(el).indexOf('没认出') >= 0` —— 它**在上一条（商品信息表）还挂在界面上时就已经满足**，
于是 waitFor 立刻返回，紧接着的"认不出时不给下一步按钮"断言读着**旧回执**判成了红（那条红是真的在报"read 了错的对象"，
但它长得像"新功能没实现"）。

两层修法（都做了）：

- **根因**：`importExcel` 在**选定文件之后**先 `receipt.value = null` —— 识别/落库期间界面不该还挂着上一条结论
  （用户会把它当成这次的结论）。放"选定之后"而不是"函数开头"，是为了不因"用户取消选文件"而抹掉已有回执。
- **判据**：冒烟的完成信号从整段 message 换成**标题**（`[data-act="import-title"]`）—— 它是唯一的，不会被旧值满足。

通用教训：**"结论出现了"这类等待判据，必须钉在只有新结论才具有的特征上**。同类 message 之间的公共子串
（尤其模板化的开头语）是隐形陷阱，批量导入、重复导入时最容易撞。

**取证**：上述两条 message 原文与 `flat(el).indexOf('没认出') >= 0` 判据。

**源**：`2026-10-05-import-receipt-next-step`（2026-10-05）

## 9. 改文案 → 先升级断言（不是改文案去迁就实现）

**结论**：回执从"一行字"拆成四段后，原来那种 `flat(card('import-result')).indexOf('订单报表') >= 0` 的整段
`textContent` 拼串判据就不能再用了：`textContent` **不给相邻元素插分隔符**，拆元素会把相邻文本粘成
`去「货与成本」维护下一步` 这种串。

做法（顺序不能反）：

1. **先把判据钉到语义锚点上**（`import-title` / `import-detail` / `import-landed` / `import-next`），逐元素断言；
2. **再**动结构。容器 `data-act="import-result"` 与其中 `import-detail` 承载的**原 message 全文**一字未改，
   于是"这次导入完了没"这类既有判据继续成立。

**取证**：上述判据代码。

**源**：`2026-10-05-import-receipt-next-step`（2026-10-05）

## 11. 断言全绿 ≠ 界面没问题 —— 一定要看一眼真截图

**结论**：断言全部钉在 `data-act` 锚点里的几个词上，于是**两个文案 bug 一个都抓不到**，
是"把冒烟脚本的 `--dump-dom` 换成 `--screenshot`"拍出来才看见的：

- **自相矛盾**：`kind === null` 分支一律用「**没认出**这个文件是什么…」当 message，而「商品信息」表是
  **已经认出来了**的那支 ⇒ 回执卡标题写「商品信息」表、正文写"没认出"。
- **markdown 星号漏进界面**：检测层的体检记录里带着 `**不用再导入**`，界面上**星号按字面渲染**。
  这些字符串是**用户可见文案**，不是文档 —— 写文案时别把 markdown 标记带进去。

一般化：**锚点类断言只能保证"这几个词还在"，管不了"读起来对不对"**。改动用户可见文案时，收工前
**至少拍一张真图**看一遍（成本：复用假桥冒烟脚本、改两个 token）。顺带还有一条：`--screenshot` 拍到的是
**某一帧**，想冻结在中间状态就在 `step('x');` 后插 `return;`。

**取证**：上述两个 bug 与 `--screenshot` 手法。

**源**：`2026-10-05-import-receipt-next-step`（2026-10-05）

## 18. 导入侧不要重复踩的三条

**结论**：

- 别把「店铺名」当作"报表没有店铺列"的默认回落（`detectShopColumn` 无命中就该返回空串）——
  店铺是自由文本，猜错一次就是把两家店的账并到一起。
- 带图导入会让导入变慢（每行一次下载，走 `order-download-image` 的 URL/内容指纹复用）。
  重复导入同一份文件不会重复落盘、也不会重复落行（image 命中 → 同 `(order_no, image_id)`）。
- AI 款式识别队列**没有**搬进宿主：那是"识别"不是"导入"，仍在「订单归类」岛（岛是可选加工手段，见
  `2026-09-30-plugin-vs-host-boundary.md`）。

**取证**：同上。

## 19. 一个页面只能有**一条**点击路径，但可以有**多个投放方式**

## 23. 重入守卫是必要的，但它会**静默吞掉**并发的拖放

**结论**：`runImport` 开头 `if (importing.value) return;`。理由：导入非幂等，而投放区"整块可点"、连点两下很容易。
代价：**导入进行中拖进来的文件会被无声忽略**（界面此时显示"正在识别并入库…" + `cursor: progress`，
所以不算"假动作"，但确实什么都没发生）。

**这条守卫在冒烟里制造过一次假红**（值得记，因为它长得像"功能没实现"）：

- 序列：点区块（拉起对话框）→ `waitFor(selectExcel 计数 +1)` → `waitImportIdle()` → 派发 drop。
- `waitFor` 的第一个探针是**同步**跑的，而假桥的 `selectExcel` 也是同步记录 ⇒ 第一条 `waitFor` 在第一跳就满足；
  此刻 `importing` **还没置位**（`runImport` 要等 `selectExcelFile()` 的 promise 落地才走到那一行）⇒
  `waitImportIdle` **当场返回**（按钮此刻仍可点）。
- 于是 drop 与上一轮导入**并发**：`runImport` 的守卫把 drop 吞掉 ⇒ `orderInsert+0`，回执还停在上一条（junk）的
  结论上 —— 现象是"拖了没反应"，很容易被读成"投放区没接上"。
- **完成信号不能只看"按钮可点"**：本页用「回执换成认不出的结论 **且** 按钮恢复可点」当整轮结束。

**取证**：上述序列与 `orderInsert+0` 读数。

**源**：`2026-10-11-today-import-dropzone`（2026-10-11）

## 24. "某 IPC 被调用" ≠ "这一轮业务结束"

## 61. ②③ 的口径收成一份：颜色两头对齐，而不是把宽的那头砍掉

**结论**：修法是**两头都动**（只动一头必留缝）：

| 头 | 改法 |
| --- | --- |
| 提示词 | `color` 字段改为**注入** `COLOR_WHITELIST`（枚举），并明确"分不清主次的多色选`印花`；确要表达配色按 `底色+花色` 写且**底色在前**" |
| 归一化 | `normalizeColor` 升级为 **字典 → 词表 → 描述式解析 → 原样保留**：按 `+ / 、 底 配 带 和 与` 分段，逐段做"整段精确 + **最长前缀回退**"，取**第一个**认得出的段（即底色） |

3. **认不出仍原样保留**：颜色是款色（SKU 级）的维度，**错并**（两色合一色）比**拆**（一色成两色）更难发现、更难回退 ——

## 65. 唯一的关联锚点是 `code`，且两域共享同一个编号空间

**结论**：

- `oi_styles.code` 与 `pl_products.code` 是**同一个 `STYLE-xxx` 序号池**。这不是巧合：`order-db.nextStyleCode()` 用
  `SELECT code FROM oi_styles UNION SELECT code FROM pl_products` 取 max+1，代码注释写明了不这么做的后果 ——
  "只查前者会让 `STYLE-005` 被产品库先占用、又发给下一款识别 ⇒ 撞 `pl_products` 的唯一键（表现为「识别建款失败」，
  报错却指向产品库，**方向全反**）"。
- `product-db` 侧注释亦明说「code / name 不可批量改：**编码是跨域关联锚点**」。
- `resolveStyle()` 新建款时**同时** `adoptProduct({ code, name })` 同步进产品库（D1 之后展示名唯一权威在 `pl_products`，
  `oi_styles` 只留 `code` + `fingerprint`）。
- **三处 join 早已存在**：`pickingRows`（拣货）、`shippingRows`（算钱）、`listStyles`（今天页的识别库款列表）都是
  `LEFT JOIN pl_products p ON p.code = s.code`；唯一实现是 `styleNameJoin()`（缺表时降级为空串）。

⇒ 所以"关联"这件事在**数据层早就做了**，不需要新建外键。谁要改这三处 join，先看 `styleNameJoin`。

## 67. 结构性缺口：订单挂款挂在**图片**上，不在订单上

## 70. 【历史记录】核对页的「产品维度」指标条：已落地，2026-10-10 已整条拆除

**结论**：【历史记录】用户对页头那排「待核对 / 未归类 / 识别库 / 已配产品」指标条的原话是"我看不太懂，用户肯定也会很懵"
⇒ 整条撤掉，连带 `orderSkuRollup` 通道退场（`electron/product-db.ts` 的 `resolveOrderSkuRollup` / `MAX_ROLLUP_ROWS` /
`OrderSkuRollup`、`order-handlers.ts` 的 `order-sku-rollup`、preload 暴露键、`src/types.ts` 与 `src/core/services/ipc.ts`
的声明、两处冒烟里的断言）。它当初的形态与判断（口径与归款同源、三种状态分开、守卫分三段）记录如下，
但其中提到的 `cl-metric-product` 三态、`today:ui` 的四条断言、`ipc:shape:smoke` 的 §⑥ **都已不存在**，
别再照它去改代码。拆除的判据与替代守卫见 [`2026-10-10-classify-panel-rework.md`](2026-10-30-order-classify-panel.md) §二。

当初解决的问题：§68 的结论是"只差配映射这一步"，而**配映射的收益在界面上看不见** —— 于是给「归类核对」（发货台第 2 步）
的指标条补一格产品维度。这一格不是"再放一个数字"，它的作用是**让配映射的收益显形**：配一条，(店铺, 商品ID) 的后续订单
就直接归类、不再进这一页。

```
待核对 9 | 未归类 9 | 识别库 0 款 | 本页 9 个商品 | 已配产品 0 个 · 供应商 0 家（本页商品还没配映射）
```

**口径**：与归款**同一份**匹配规则，不新写一套。调用方（核对页）手上只有**订单行原文**（`shop` 是报表里的店名），
所以入参是 `{shop, itemId}[]`，归一与匹配全在主进程：

| 步骤 | 复用的东西 |
| --- | --- |
| 店铺原文 → (店铺 id, 平台) | `resolveShopRef` —— 与落库（`autoAssignByMap`）、回流（`skuBackfillFromOrder`）、待关联队列**同一份**规则 |
| (平台, 店铺 id, 商品ID) → 产品 | `resolveSkuBatch`（一次算完一批）—— 只认 `status='confirmed'` 的**映射行** |

**刻意不认跨店池行**（`source='shop-import'` / `shop_id=0`）：那与归款同口径（`skuMappingSql()` 的补集）。
两处若不一致，症状是"核对页说这一页配了 3 个产品、真去拿货只有 2 个"。另外两条跳过规则都朝**少算**方向，
且与 `resolveOrderSku` 对齐：店铺没归一 / 没有商品ID ⇒ 这一行**无从查起**（不是"没配上"）；映射指向的产品**已删**
（悬空指针）⇒ 按未命中。`supplier_id = 0`（还没关联厂家）**不计家数** —— 把它算成"一家供应商"会让这个数虚高。

**三种状态必须长得不一样**（这一格最容易做成"恒显示 0"）：

| 状态 | 显示 | 为什么 |
| --- | --- | --- |
| 有商品ID、一个都没配上 | `已配产品 0 个 · 供应商 0 家` + **（本页商品还没配映射）** | `0` 是一个**待办**，必须说清缘故；单看会读成"数据坏了" |
| 没取到（通道不可用 / 产品域未建） | **整格不显示** | "没取到"≠"一件都没配"，两者下一步动作完全不同 |
| 这份报表**没有商品ID 列** | **整格不显示**（与「本页 N 个商品」同规则） | 这个维度本就不存在，显示 `0` 会被读成坏了 |

⇒ 渲染层用 `null` 表示"没取到"、用 `{products: 0}` 表示"查过了、没有"，**刻意不合并**。它也**不拦页面**：
产品维度是附加信息，取数失败时核对列表照常可用。

**守卫分三段（一段都省不掉）**：

| 层 | 守什么 | 在哪 |
| --- | --- | --- |
| 数据层 | 口径本身：去重 / 未归一 / 悬空产品 / 供应商去重 / 池行不算 | `product:sku:smoke`（+6 项） |
| preload 载荷 | 渲染层的**裸数组** → `{rows}` 的包装真的过到主进程 | `ipc:shape:smoke`（+3 项） |
| 界面 | 请求带哪些键、格子画的是宿主回来的数、三种状态各长什么样 | `today:ui`（+4 项） |

⚠️ **假桥看到的是裸数组**（假桥替的是 preload **上面**那一层）⇒ "包装对不对"在界面冒烟里**根本测不到**，
只能由 `ipc:shape:smoke` 端到端对穿。这条正是 2026-10-04 那次「成功但空」的同族风险
（详见 `2026-10-04-preload-payload-shape.md`）。

**变异（7 组，逐组确认变红后复原）**：

| 变异 | 变红的那条 |
| --- | --- |
| preload 键名 `rows` → `items` | `ipc:shape:smoke` §⑥ 两条（症状：`success=true` 而 `products=0`） |
| `supplier_id = 0` 也算一家 | 「未关联厂家不算一家」 |
| 悬空产品算命中 | 「映射指向的产品已删 → 按未命中」 |
| 去掉"未归一店铺跳过" + 改用允许池行的解析 | 「店铺未归一…不计入」——**池行夹具让这条可判别**（只放一个查不到的行，任何实现都给出 0，恒绿） |
| 渲染层不过滤空商品ID | 「只带有商品ID 的行」（载荷 3 → 4 条） |
| 去掉「（本页商品还没配映射）」 | 「显示 0 并说明缘故」 |
| 取数失败时归零（而不是整格隐藏） | 「那一格整格不显示」 |

**已知边界**：本页若把同一件商品拆成两种店铺写法（多一个空格 / 零宽字符），店铺原文去重算两次、`resolveShopRef`
都命中同一家店 ⇒ **产品/供应商仍各只算一次**（这两个数是**产品级**的）。分子分母不在这里暴露，所以不会出现
"本页 2 个商品、3 个已配"这种自相矛盾的读数。

**取证**：上述形态串、两张表与变异表。

**源**：`2026-10-05-classify-auto-pipeline`（2026-10-05）
