## 1. 拆表一句话：主表 + 明细，且明细 id 原样保留

**结论**：`oi_orders` 从「一行 = 订单×商品图」拆成 **`oi_orders`（订单主表，一单一行，`order_no UNIQUE`）**+
**`oi_order_items`（明细，一 SKU 一行）**。**整次迁移的关键不变量：明细 `id` 原样保留拆表前旧 `oi_orders.id`** ——
所以 `parcel_lines.order_item_id`、采购来源等一切"按行 id 指"的下游零迁移。主表 `id` 才是新自增。

**取证**：状态：🟢 已落地（2026-10-21）· `order.main` v8 · 真实库克隆迁移验证通过。

**源**：`2026-10-21-order-table-split-b1`（2026-10-21）

## 2. 拆分口径（迁移 v8）

**结论**：

- 主表按 `order_no` 归组，订单级字段取同单 **`MIN(id)`** 那行（同单多行本该同值；万一不一致以最老那行为准）。
- **空订单号的旧行各自独立成一单**：`order_no = '__empty__' || id`。宁可多几条主表，也不把"不知道是不是同一单"的行并掉，
  更不丢行。⚠️ 这个占位**只服务历史迁移**：拆表后新写入的空订单号一律**明确拒绝**（见 §4）。
- 明细逐行搬行级字段，`order_id` 指回主表。
- **同款合并不在迁移里做**（`style_color_id + size` 相同也不并）：合并是汇总层语义，物理层要保留 SKU 粒度 ——
  拆包、取图、按行核对都靠它。需要合并时用 `GROUP BY`。
- 迁移前旧表 rename 为 `oi_orders_legacy_split`，成功后才 DROP；`sqlite_sequence` 追平主表 `MAX(id)`。
- 新库判据：主表没有 `raw_fields` 列（那是行级列）⇒ 已是新形状，迁移直接跳过。

**取证**：上述六条口径。

**源**：`2026-10-21-order-table-split-b1`（2026-10-21）

## 3. 真实库对照（验收证据）

**结论**：克隆真实库（`order.main` = v6、51 行 import、0 行 collect、尚未建包裹表），跑 v7 + v8 后逐项比对：

| 项 | 结果 |
| --- | --- |
| 版本 | v6 → **v8** |
| 行数 | 51 旧行 → **47 主表 + 51 明细**（少掉的 4 行 = 同单多图归并到同一主表行） |
| 明细 id | **51/51 原样保留** |
| 行级字段 | 逐行与迁移前一致（图片 / 尺码 / raw_fields / 款类色 / 核对位 / 件数 / 款色 id / 克重 / 进价 / 创建时间） |

## 4. 写入口约定一：空订单号 = 明确拒绝

**结论**：主表 `order_no` 是 `NOT NULL UNIQUE`，旧实现"用 NULL 占位"现在**必撞约束**。导入侧解析层（`importSheet`）
本来就跳过缺单号的行；DB 层再 throw 一句能看懂的错误，且**不留下半条主表行**（事务回滚）。不要在 DB 层重新引入
"无单号也能落"的旁路。

**取证**：同上。

**源**：`2026-10-21-order-table-split-b1`（2026-10-21）

## 5. 写入口约定二：同一订单号只容一个摄取通道

**结论**：

| 通道 | 写法 | 撞车时 |
| --- | --- | --- |
| 导入（Excel） | 按 `(order_no, image_id)` 幂等，逐 SKU 追加 | 主表是采集单 → **拒绝**（`insertOrder`） |
| 采集（扩展推送） | 同一单号**整单替换** | 主表是导入单 → **拒绝**（`upsertCollectedOrder`） |

为什么必须互斥：导入是"一行一行追加 + 报表金额"，采集是"整单删了重插 + 采集金额"。混在一起时，采集下一次重推会把导入的行
全删掉，而且同一个 `order_no` 上会同时存在两套金额口径。采集订单在扩展侧已下线，但历史采集单与将来重开采集仍会撞上 ——
`ae-db.upsertOrderBatch` 对每条失败现在会打一条 `console.warn`（回执只有 `skipped` 计数，没有原因）。

**取证**：上表。

**源**：`2026-10-21-order-table-split-b1`（2026-10-21）

## 6. 写入口约定三：重采集 / 删除 / 清空时的包裹收尾

**结论**：

| 动作 | 包裹怎么处理 | 不做的后果 |
| --- | --- | --- |
| 采集重推同一单 | 先清该单 `parcel_lines` + `parcels`，再整单替换明细 | 明细 id 全换，旧包变 0 明细空壳，仍进 `parcelTotals` 求和 |
| `deleteOrder(行 id)` | 删完后收掉**没有明细占着**的包 | 空壳包让整单运费被拖成 `null`，界面多一张空卡片 |
| `clearAll()` | `parcels` 与订单/明细一起清 | 孤儿包永远查不到、却占着汇总 |
| 删单个包 | 显式先删 `parcel_lines` 再删包 | 连接级 `PRAGMA foreign_keys` 未开时留孤儿明细 |

**取证**：上表。

## 12. 最终数据模型之二：订单-商品关联表（一单多行）

**结论**：

| 字段 | 说明 |
| --- | --- |
| 订单ID / 商品ID / 图片 / 尺码 / 颜色 / 数量 / 关联产品ID / 店铺ID / 状态 | 现有 + 需补 |
| **克重**（新增，行级） | 从产品 SKU 查；**在归类核对「确认无误」时**钉死（关联产品ID+颜色确定后才查得到 SKU） |
| **实际进价**（新增，行级） | ⚠️ **不在导入时**，而是拿货单填价落账后回写（见 §14 时序） |

> **同款合并是「汇总层」，不是「存储层」**：关联表**保留 SKU 级粒度**（每行 = 一个 SKU 规格），拿货/展示时按
> 「关联产品ID+颜色+尺码」聚合合并显示。这样拆包才能「按单个商品拆 + 拆分合并行数量」—— 物理行是 SKU 级，
> 拆包只是给 SKU 行分配数量到不同包裹。

**取证**：上表与引注。

**源**：`2026-10-21-order-purchase-model-simplify`（2026-10-21）

## 13. 最终数据模型之三：包裹表（新增，支持一单多包）

**结论**：

| 字段 | 说明 |
| --- | --- |
| id | 包裹主键 |
| order_id | 归属订单 |
| 包裹号 / 物流单号 | 外部追踪号 |
| **克重** | 本包裹克重（默认 = 所含 SKU 行克重之和） |
| **物流费** | 本包裹运费（按包裹克重查运价） |
| 包含订单行 | 多对多：`parcel_lines(parcel_id, order_item_id, qty)` |

> （各包裹分到部分数量）。一单多包时订单表 `总物流费` = Σ 包裹物流费；单包 = 该包裹物流费。

## 14. 时序（核心结论）

**结论**：

```
导入订单 ──► 归类核对（确认无误时，一次性钉死）──► 拿货页面 ──► 拿货单(填实际进价) ──► 拿货落账
   │                    │                                              │
   │ 只落原始订单        │ 颜色/产品ID/尺码 确定后：                      │ 回写: 关联表.实际进价
   │ （不钉克重/运费）    │ ①查 SKU 克重→钉关联表行                       │ (替代旧 ae_cost_map 落点)
   │                    │ ②Σ克重→查运价→钉订单表总克重/总物流费           │
   └────────────────────┴──────────────────────────────────────────────┘
```

- **克重/运费都在「归类核对确认无误」时钉死**（用户已拍板）：此时颜色/产品ID/尺码/收货国全齐，克重才查得到 SKU、
  运费才算得出。**导入时只落原始数据**，不钉克重/运费。
- **实际进价**：拿货单填价后**回写**订单关联表，不是导入时（导入时拿货单还没填）。
- 这是「实际进价」从「款级区间表」迁移到「订单行级快照」的落点变化。

**取证**：上述时序图。

**源**：`2026-10-21-order-purchase-model-simplify`（2026-10-21）

## 18. 产品域两个新增字段（用户已拍板）

**结论**：

1. **`pl_products` 加 `进价`（成本单价，分）**：产品表存「**当前**进价」（维护入口，产品页展示 + 新订单默认进价）；
   订单关联表存「**导入/拿货时**快照」。两者并存不冲突：一个答「现在多少钱」，一个答「那单当时多少钱」。
   退役 `ae_cost_map` 后，`manual-costs`（手工进价）的落点从「区间表」改为「产品表当前进价」；`purchase-cost-sync`
   （拿货对账同步）的落点改为「订单关联表实际进价」。
2. **`pl_variants` 加 `image_id`（SKU 图片，引用 `pl_images`）**：**用途是「认色」**，不是装饰：采集回来的颜色不可信
   （`Picture color` 占位、平台色名≠自家色名），需人工对照图片逐色校正。每色一图 = 认色的工作界面素材。
   落点走窄接口（`variantImageAttach/detach`，同 `pl_products.image_id` 的 `imageAttach/detach` 模式），不进 `variantUpsert` 全量提交。

**取证**：同上。

**源**：`2026-10-21-order-purchase-model-simplify`（2026-10-21）

## 21. 审查发现（2026-10-21 复审）

**结论**：

1. **克重/运费钉死时点已定**：统一在「归类核对确认无误」时（不是导入时）—— 已并入 §14 时序。
2. **同款合并 vs 拆包已解耦**：合并是汇总层、拆包是物理层。关联表保留 SKU 级粒度，`parcel_lines` 带 `qty` 支持拆分合并行数量。
3. **进价回写范围待定死**：拿货单按「款色尺码」汇总，回写订单行时须明确「只写该拿货单覆盖的行、且不覆盖已写的旧行」——
   避免后拿的价污染历史订单。
4. **`pl_variants.image_id` 的认色工作流**：认色 = 归类核对页「选款色」动作，SKU 图片用于辅助展示该款各色，
   **不另建认色页面**（避免重复建设）。

**取证**：同上。

## 22. 分阶段执行计划（草案）

**结论**：按「快照前置」与「拆表」拆成两个独立工程，互不阻塞；每阶段门禁全绿再进下一阶段。

**阶段 A：快照前置（不改表结构，先加字段钉快照）**

1. **`pl_products` + `进价`**、**`pl_variants` + `image_id`**（两条 `ALTER`，走 `ensureProductColumns`/`ensureVariantColumns` 补列）。
2. **订单表 + `总克重`/`总物流费`**、**关联表 + `克重`/`实际进价`**（快照写在「归类核对确认无误」与「拿货落账」两处）。
3. **利润引擎 `orderCost.ts`** 改读快照字段（克重/运费/成本），不再实时查 `sr_rate_snapshots`/`pl_shop_sku`/`ae_cost_map`。
4. **`manual-costs` 落点改产品表**、**`purchase-cost-sync` 落点改关联表**（进价回写范围按 §21 第 3 条定死）。
5. 验证利润数字与改造前一致（门禁：`<order-profit>:ui` + `vitest run`）。

**阶段 B：拆表 + 包裹（大工程，独立立项）**

1. 订单表拆「订单 + 订单商品关联」两表，`order_no` 幂等。
2. 建 `parcels` + `parcel_lines(parcel_id, order_item_id, qty)`（一单多包，支持拆分数量）。
3. 改写全部下游：`shippingRows`/`pickingRows`/`settleLines` 对齐/颜色回填/利润引擎。
4. 归类核对页加「包裹拆分」入口（按单个商品拆、可拆数量）。

**阶段 C：退役表**

1. `ae_cost_map` 消费方全部迁走后删表。
2. `ae_settle_lines` 待平台结算轨决策后再定去留。

## 23. C2 定稿：明细行两个成本字段（2026-10-21）

**结论**：本节收敛 §18：早前定过「进价 + 实际进价」两个快照，实现侧只落了后者（A5 的 `cost_cents`），预估一直实时查
`ae_cost_map`。删表前把两字段补齐。执行细则见 `docs/archive/plans/ORDER_PURCHASE_MODEL_SIMPLIFY_PLAN.md` §5「C2 定稿」。

| 字段 | 语义 | 写入时点 |
| --- | --- | --- |
| `oi_order_items.cost_cents` | 进价（预估，当时生效价） | 归类核对「确认无误」 |

## 24. 「哪张订单的货齐了」：从推测变成事实

**结论**：用户问「拿完货后，怎么才能知道哪些订单的货拿完了？」，当时的答案是**看不了**：全应用最细只到款色码，
订单级的"齐了"不存在。但**分配逻辑其实早就在跑** —— 生成拿货单时 `purchase-db.autoSourceRows()` 已经按 `oi_order_items.id`
做 FIFO（"这 N 件补给哪几条订单行"当时就算出来了），只是最后一步**把 `oi.id` 扔了**，只存了店铺名。所以这不是一次功能设计，
而是一次**补边**：给 `purchase_sources` 加一列 `order_item_id`，把已经算出来的结论存下来。今天的"已拿"因此从「款色码总量近似」
升级成「逐行精确」。

**取证**：上述函数名 `autoSourceRows()`。

**源**：`2026-10-22-order-coverage-fact`（2026-10-22）

## 25. 为什么之前回答不了：两条缺边

**结论**：

| 边 | 状态 | 后果 |
|---|---|---|
| 拿货单 → 订单行 | `purchase_items` 无 `order_no`；`purchase_sources` 有分配结果但**只存了 shop** | "这 1 件补给了哪张单"库里不存在 |
| 拿货 → 订单（时间） | `oi_orders.ship_time` 只来自导入报表的「发货时间」列 | 应用内**没有**"这单货齐了"这个动作 ⇒ 提交拿货单在系统里是零事件 |

四处可能被用来回答这个问题的界面，都不是按订单判定的：**总览四格**（当天整体汇总，`还差 0` 只说"今天这批总量齐了"）；
**拿货页厂家卡**（款色码粒度，拿齐的行**从缺口消失**，没有"已齐"可回看）；**拣货清单**（未发货订单，与拿没拿无关）；
**对账页**（纯金额：拿货 / 已付 / 已退 / 欠款）。

**取证**：上表与四处界面。

**源**：`2026-10-22-order-coverage-fact`（2026-10-22）

## 26. 数据链：一处算、一处拼键

**结论**：

```
oi_order_items ─┐
                ├─ autoSourceRows() 按件 FIFO → purchase_sources.order_item_id
purchase_items ─┘                                    │
                                                     ▼
                              purchase-order-coverage（只读 IPC）
                                rows: 未发货+非终结行 × covered 件数
                                unattributed: 无归属台账（items − 已归属差额）
                                                     │
                              coverageInputs()（列名/键只在这里翻译一次）
                                                     │
                              planCoverage() → groupByOrder() → coverageSummary()
                                   │                    │
                        总览 dailyShip()        「按单核对」两段清单
```

**总览与清单必须是同一份实现**：两处各算一遍，总览说"全齐了"、清单说"还差 1 件"是必然会发生的（本仓铁律 5：每个数字只能
有一处实现）。

**取证**：上述数据链块。

**源**：`2026-10-22-order-coverage-fact`（2026-10-22）

## 27. 口径与边界（都要在界面上说出口）

**结论**：

- **存量只能补"能由事实唯一确定"的行**：该（拿货单, 款色码）组里只有一条来源行 + 该款色码在未发货订单里只有一条候选行 +
  那条只覆盖 1 件 —— 三者同时成立才认。真库实测 13 条来源行里只有 3 条符合（其余要么候选不唯一，要么所在单是草稿）。
  猜错的代价是**把别的单宣布成已齐**。
- **`order_item_id = 0` 是合法取值**，不是脏数据：历史单没归属、这次拿多了的尾巴也没有订单行可指。它们进 `unattributed`
  池子，按款色码先到先得摊，摊到的部分标 `estimated`，界面写明"按款色总量估算"。
- **范围两边不同，且是对的**：`outstanding()` / `orderCoverage()` = 全部未发货订单（货和钱跨天结转），总览四格 =
  今天导入的那批（第 1–2 步的口径）。所以"总览说齐了"不等于"没有单还差点货"。
- **未识别款不摊池子**：款编码为空时 `takenKeyOf` 会拼出空键，把"同色同码的不同商品"并成一格，凭空宣布已拿是漏货式的静默错。
  与 `outstanding()` 的 `have = 0` 同口径。

**取证**：上述 `13 条 / 3 条` 读数。

**源**：`2026-10-22-order-coverage-fact`（2026-10-22）

## 28. 顺带修掉的两处既有偏差（`autoSourceRows`）

**结论**：今天它们只让"店铺成本分摊"少记几行（不致命），但一旦变成"哪单齐了"的判据，就会给出**看着很正常、实际错了**的答案：

1. **没有范围过滤**：查订单行时缺 `ship_time='' AND status<>'shipped' AND NOT 终结`（`outstanding()` 有）⇒ 会把这次拿货分给
   **已发货甚至已取消**的订单；
2. **件数当行数跳**：`skip -= 1` 每行只跳 1 件，而需求按件算（`SUM(COALESCE(NULLIF(qty,0),1))`）⇒ 一单买 2 件时多跳一行、
   少记来源。改成按件跳过、`qty` 记该行被覆盖的件数。

**取证**：上述 SQL 片段。

**源**：`2026-10-22-order-coverage-fact`（2026-10-22）

## 29. 订单级覆盖的守卫（每条都问过"改坏哪一行它会红"）

**结论**：

| 守卫 | 改坏什么会红 |
|---|---|
| 池子按**订单行 id 升序**摊（传入顺序倒置） | 改成按数组顺序摊 ⇒ 摊给后下的那一单 |
| 一件台账只被吃掉一次（两行各要 1 件、台账 1 件 ⇒ 合计 1） | 扣减后不回写池子 ⇒ 合计变 2 |
| 精确 + 池子不重复（已按行归属的那件不再从台账扣） | 两段都扣 ⇒ 已拿虚高、缺口提前变 0 |
| 未识别款不摊（故意在池子里放空键记录） | 用空串键去匹配 ⇒ 已拿凭空 +2 |
| 冒烟：可以发货的是**哪一张**（I-1 而不是 I-2） | 忽略 `covered` ⇒ 变成 0 单；按款色总量摊 ⇒ 摊错单 |
| 冒烟：两段互斥（齐了的单不出现在「还差」里） | 分桶判据写错（`covered >= qty` 写成 `> 0`） |
| 冒烟：件数守恒（共 6 件 / 已拿 1 件） | 件数退回按行数算 |
| 冒烟：取数走 `purchase-order-coverage` | 退回读 `purchase-taken` 整条台账 |

变异实测：把 `dailyShip(all, { taken })` 退回成"整个台账当池子"，四格数字与进度条**同时**变红。

**取证**：上表与变异实测。

**源**：`2026-10-22-order-coverage-fact`（2026-10-22）

## 30. 订单级覆盖没做什么（以及为什么）

**结论**：

- **不加"标记已发货"按钮**：发货时点是平台回传的（`oi_orders.ship_time` 来自导入报表），应用内没有这个动作。
  造一个本地开关只会和平台数据打架 —— 这一屏只回答"货到齐了没有"。
- **不给历史拿货单补订单号**：`purchase_items` 没有订单号，历史数据无从追溯；能补的只有"唯一确定"的那几条（见 §27）。
  界面用 `estimated` 把这层不确定性说出来，比给一个假装精确的数好。
- **不做跨天的时间线**：`orderCoverage()` 给的是"当前状态"，不回答"哪天齐的"。要时间线得先有"齐了"这个事件的落点，
  而它正是本轮刻意不造的那个字段。

**取证**：同上。

**源**：`2026-10-22-order-coverage-fact`（2026-10-22）
