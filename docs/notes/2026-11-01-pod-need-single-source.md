# 净需件只有一份状态口径（图案报单）

> 取代关系：2026-11-01 施工结论，**不取代** `2026-11-01-mango-collect-and-pod-conclusions.md`（那是采集侧结论）；
> 本文只讲"报单净需件怎么算、覆盖率不到 60% 时凭什么还能报单"。

## 结论

1. **`pod_order_need` 视图刻意不落地。** 计划（`docs/plans/MANGO_INGEST_AND_POD_PLAN.md` 附录 A）原本要用一条
   SQL 视图算净需件，而它必须筛"待发货集合" —— 那份口径的唯一实现是 `src/lib/mangoStatus.ts` 的正则规则
   （芒果不同页面给「等待卖家发货 / 待发货 / 待卖家发货」）。在 SQL 里手写 `biz_status IN ('待发货', …)`
   就是**第二套口径**，"发货台说 3 单待发、报单说 5 件要印"就是这么来的。
2. **改成两段、只留一份口径**：`electron/pod-need.ts` 只做投影（订单行 + 绑定索引 + 图案余量，原样搬）；
   `src/lib/podNeed.ts` 做聚合（按图案求和 → 扣余量 → 算张数），`isWaitingShip` 全仓**只在那里被调用一次**。
3. **覆盖率不到 60% 也能进 M4 的唯一理由：把"没绑完"变成看得见的数。** 真库此刻 560 个槽位覆盖 2/16 家店，
   75 个待发订单行里只有 **4 行**能匹配到图案。只汇总"已绑定"会得到一张看似正常、实则漏掉九成订单的报单 ——
   所以未绑件数进报单汇总（`unboundPieces` / `unboundRows`）、写进导出清单**第 2 行**、覆盖率条把
   「≥60% 且塌陷 100%」并成一个结论（`src/lib/podBinding.ts` 的 `podCoverageOf`）。
   **没有这层显式化就不许进 M4**（这条已写进计划 §7 的批注）。

## 三条口径（各自都能静默出错）

| 口径 | 错的后果 |
| --- | --- |
| 件数按**行**算，不按"单"算；`qty` 为空按 1 件计并计入 `assumedRows` | 一单三行三个图案，按单算会让净需件偏小 → 料不够，等发现了再补 |
| 余量按**件**扣、扣到 0 为止（负余量不进净需件） | 把负余量当"欠料"加进去，够料的图案也会被再买一次花纸 |
| 未绑定的待发件**单独计数**并显示 | 报单看着正常、实际漏掉九成订单（比多报贵得多） |

另外两条（写在代码注释里，这里只留位置）：报单 zip 里只认 `artwork_image_id`（红线 7，传错整批报废）；
报单时不扣余量（印花完成才扣，报单只是意向）。

- 真库（`~/Library/Application Support/seller-kit/sellerkit.db`）只读副本：
  ```bash
  npm run pod:worklist -- --expect 560,50
  ```

  （把报单 zip 拆开读回来，含"图稿字节 ≠ 预览图字节"）。
