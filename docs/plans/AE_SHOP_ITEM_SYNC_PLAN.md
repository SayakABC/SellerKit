# 速卖通店铺商品采集 → 「商品 ↔ 产品」映射维护 · 方案

> 方案主文档（评估 + 架构 + 界面交互设计 + 路线）。跨端交互协议与 SellerKitExtensions 的分工，  
> 沿用 `docs/features/PROFIT_TRACKER.md`（订单采集）的同一套纪律：本文件只管「商品采集」这一条新链。  
> 状态：**待评审**（未动任何代码）。

## 0. 结论（先读这段）

1. **可行，且是已有能力的延伸而非新系统。** 通道（`electron/ae-receiver.ts`，127.0.0.1:46211，X-Ae-Token）、  
   扩展仓库（SellerKitExtensions，MV3）、落点表（`pl_shop_sku` / `pl_products` / `pl_variants`）、  
   认款写路径（`product-sku-map` → `upsertSkuMappings`）**全部已存在并在产**。  
   本方案新增的只有：1 个采集端点、1 张快照表、`sk_shops` 1 列、右栏 1 个视图段、1 个建款向导。
2. **店铺地址不是"备注字段"，是采集帧与店铺实体的精确连接键。** URL 在店铺级唯一  
   （`aliexpress.com/store/<id>/…`），比店名可靠得多 —— 店名会改、会多种写法，URL 不会。  
   这给了「创建店铺时填地址」一个真实的功能理由，而不只是"多记一笔"。
3. **采集解决的是"店里有什么"，不解决"这是哪个款"。** 认款（商品→款）永远由人做  
   （本仓既有纪律：映射是人的决定，`sk_name_map` 只存 manual）。扩展把商品ID、标题、图、  
   售价、SKU 矩阵搬进来，人只做判断最重的那一步。
4. **最大的新增价值在 SKU 矩阵**：色 × 码矩阵从采集直接预填建款向导 —— 今天  
   `pl_products` + `pl_variants`（款 / 色 / 码 / 克重）全靠手工建档，这是货与成本最重的手工段。
5. **SKU 色图可以闭合"按图匹配"的环（§8，2026-10-12 增补）**：采集每色图 URL → 认款时采纳为  
   款色绑定图 → 订单同图（同 URL 或同内容）经既有去重分支自动继承款色；未认款前的同图命中  
   只作「建议 + 一键确认」，不静默写。

## 1. 现状分析（代码取证）

### 1.1 「货与成本」四页签与数据域

| 页签（`src/modules/goods/tabs.ts`） | 作用域                                   | 落的表                                           |
| ------------------------------- | ------------------------------------- | --------------------------------------------- |
| 建档与关联（两栏工作台）                    | 左栏款（`ProductPane`）/ 右栏商品池（`PoolPane`） | `pl_products` / `pl_variants` / `pl_shop_sku` |
| 店铺登记                            | 原始店名 → 店铺实体归一                         | `sk_shops` / `sk_name_map`                    |
| 供应商                             | 厂家主数据                                 | `suppliers`                                   |
| 进价                              | 款级成本唯一手工入口                            | `ae_cost_map`（`manual` 行）                     |

数据模型要点（全部有代码取证）：

- `sk_shops`：`platform × name_key` UNIQUE；`platform_shop_id` 为稳定业务键（部分唯一索引）；  
  **没有地址列**（本方案要补的）。`electron/shop-db.ts:141-176`。
- `pl_products`：款。`code`（`STYLE-xxx`，与 `oi_styles.code` 共用序号池，是跨域唯一锚点）、  
  `supplier_id`、`category`、`image_id`。`electron/product-db.ts:98-113`。
- `pl_variants`：SKU = 款 × 色 × 码，带 `weight_g`（克重是 SKU 属性）。  
  `UNIQUE(product_id, name)`，`code` 非空时全局唯一。`electron/product-db.ts:1612-1631`。
- `pl_shop_sku`：商品ID 映射表，唯一键 `(platform, shop_id, item_id, spec, product_id)`；  
  `spec` 承载**颜色**（`'*'` = 未指定）；`status` ∈ `confirmed/invalid`；  
  **两个种群靠谓词区分**：池（`source='shop-import' OR shop_id=0`，`skuPoolSql()`）vs  
  归款映射（补集 `skuMappingSql()`）。`electron/product-db.ts:804-939`。
- `pl_images`：产品图缓存，内容 SHA-256 命名去重，落 `userData/product-images/`。  
  `electron/product-db.ts:1633+`，落盘唯一实现 `landImageBuffer`（`product-handlers.ts:469`）。

### 1.2 认款链路（已经闭环的部分）

```
订单导入 ─► oi_orders.raw_fields「商品ID」列
                │  实时聚合（buildQueueView，不建缓存表）
                ▼
        待关联队列（店铺未归一行 = shopUnresolved，不许写映射）
                │  人认款：product-sku-map → upsertSkuMappings（单事务）
                ▼
        pl_shop_sku（confirmed，spec=颜色，variant_id 按色反查）
                │  落库时 resolveOrderSku 命中（先查映射，查不到才 AI 兜底）
                ▼
        订单自动归到「款+色」；回流 reassignOrdersByItemIds 补历史；补色 skuBackfillFromOrder
```

**这条链是通的**：`today:ui` 238 / `product:sku:smoke` 41 组断言守着它。  
新方案不新开写路径 —— 采集来的商品认款，走的**就是这条**。

### 1.3 已存在的扩展基础设施（关键复用）

| 件             | 位置                                          | 状态                                                           |
| ------------- | ------------------------------------------- | ------------------------------------------------------------ |
| localhost 接收端 | `electron/ae-receiver.ts`                   | 产：随应用自启（`main.ts:37`），token 鉴权、body≤1MB、单批≤100、60次/分限速、路径白名单 |
| 订单 schema     | `ae-order/v1` / `v2` 双收                     | 产：v1 便捷字段由接收端映射为 fees 科目                                     |
| 扩展仓库          | `SellerKitExtensions`（独立 repo，MV3）          | 已建：content script + options 页 + protocol.js 常量               |
| 接入引导形态        | `ui-plugins/ae-profit/src/AeProfitView.vue` | 产：接收端在线/离线状态行 + 复制 curl 样例                                   |
| 协议权威文档        | `docs/features/PROFIT_TRACKER.md`           | §5 通道协议 / §9 合规边界（本人店铺、人工触发、限流）                              |

### 1.4 三个断点（本方案要补的）

1. **待关联队列只包含"订单里出现过的商品"**（`buildQueueView` 的输入就是 `oi_orders`）。  
   新店、新品、还没下单的 SKU **永远进不来** —— 主数据因此永远比订单慢一步。
2. **建款与 SKU 全手工**：`pl_products` + `pl_variants` 的色/码/克重只能一条条录  
   （导入 Excel 是另一条手工准备路径）。
3. **`sk_shops` 没有地址列**：采集帧带回来的店铺 URL 无处安放，也没法做精确匹配。

## 2. 可行性评估

### 2.1 扩展能拿到什么（速卖通卖家后台，本人登录态）

| 数据                      | 来源页              | 进 SellerKit 的用途                      | 可靠性                      |
| ----------------------- | ---------------- | ------------------------------------ | ------------------------ |
| 商品ID（product_id）        | 商品管理列表           | **认款锚点**，与订单 Excel「产品ID/SKU」列同口径     | ✅ 稳                      |
| 商品标题                    | 列表 / 详情          | 队列与商品段展示（让人认得出是哪个）                   | ✅ 稳                      |
| 主图 URL                  | 列表 / 详情          | 商品段缩略图；认款时可采纳为款主图（既有"只补空"规则）         | ✅ 稳（远程 URL，需主进程下载）       |
| 每色 SKU 图 URL            | 详情页 SKU 矩阵（选色换图） | **色级锚点**：认款时采纳为款色绑定图 → 订单按图归到色（见 §8） | ✅ 稳（色→图 1:1；码不单独配图）      |
| 售价（区间原文）                | 列表 / 详情          | 参考信息；**不做成本推导**                      | ✅ 稳                      |
| SKU 矩阵（色 × 码 × 单价 × 库存） | 商品详情             | **建款向导预填** `pl_variants`（色/码），人补克重   | ⚠️ 需逐条打开详情页；新老后台结构不同     |
| 类目                      | 详情               | 预填 `pl_products.category`            | ✅ 稳                      |
| 商品状态（在售/下架/审核）          | 列表               | 展示；下架商品在列表里标出                        | ✅ 稳                      |
| 店铺名 / 店铺 URL / 店铺ID     | 店铺页 / 后台全局       | 店铺精确匹配 + 「打开店铺」入口                    | ✅ 稳                      |
| 克重 / 包装重量               | 详情属性             | ——                                   | ❌ 不可靠：多数类目不填，**不采集、不预填** |
| 进货成本                    | ——               | ——                                   | ❌ 平台不提供，永远手工（「进价」页签）     |

> 结论与 PROFIT_TRACKER §3 同构：**平台不给的（成本/克重）不强求；平台给的（商品与 SKU 结构）全拿。**

### 2.2 必须由用户手动做的（每个都有理由）

| 动作              | 为什么不能自动                                       |
| --------------- | --------------------------------------------- |
| 认款（商品 → 款）      | 标题相似 ≠ 同款。本仓铁律：自动合并不可逆、猜错就是把两个款的账并到一起         |
| 指定供应商           | `supplier_id` 是采购域主数据，平台无对应                   |
| 补克重             | 平台数据不可靠（见上表）                                  |
| 维护进价            | 平台不提供成本                                       |
| 颜色归一            | 采集到的颜色是平台原文；入库前要过既有颜色词表（`normalizeColor` 描述式） |
| 建款决策（code/name） | `code` 是跨域锚点，一旦发出不复用；向导只预填，保存由人点              |
| 登记店铺（平台/名称确认）   | 与既有纪律一致：**不自动建店铺**；未登记进"待登记"提示条               |

### 2.3 风险与对策

| 风险                                | 对策                                                                          |
| --------------------------------- | --------------------------------------------------------------------------- |
| 卖家后台改版（最高风险，PROFIT_TRACKER §9 已列） | 选择器集中配置 + 单条失败跳过并计数；**保底通道**：商品段支持粘贴/导入商品ID清单（列表页结构比详情页稳定，先采列表、详情按需采）       |
| 详情页逐条打开 → 采集慢                     | 分两级：列表页轻采（ID/标题/图/价/状态）一次一批；SKU 矩阵重采仅在用户对某个商品点「采 SKU」时单条触发；扩展侧限流（既有 60 次/分） |
| 图片是远程 URL                         | 主进程统一下载 → `landImageBuffer` 同款去重落 `pl_images`；失败不外抛（该商品无图，不影响入库）            |
| 采集帧的店铺未登记                         | **不自动建店**：落 `shop_id=0` + 展示原文 + 「现在登记」按钮（复用队列既有 `shopUnresolved` 形态）       |
| 本地通道暴露                            | 复用既有防线：loopback + token + 大小/频率上限；本方案不新开端口                                  |
| 合规（平台条款/风控）                       | 只采本人店铺、人工触发、不无人值守翻页、不绕过登录/验证码（PROFIT_TRACKER §9 同款声明）                       |

### 2.4 结论

**可行。** 判断依据不是"爬虫技术上行不行"，而是三点工程事实：  
① 通道/鉴权/限流已在产；② 落点表与认款写路径已在产；③ 店铺地址给出精确连接键。  
工作量集中在**采集端选择器 + 一张快照表 + 一个视图段 + 一个向导**，主程序侧无新写口径。

## 3. 整体方案

### 3.1 三段架构

```
┌─ SellerKitExtensions（Chrome 扩展 · 采集端）───────────────────┐
│ 新模块「商品采集」：商品管理列表页（轻采）+ 详情页（按需重采）      │
│   → ae-shop-item/v1 帧（store 信息 + items[]，每项含 skus[]）    │
└───────────────────────────┬────────────────────────────────────┘
                            │ POST /ae/shop-items/ingest（X-Ae-Token，复用 46211）
┌───────────────────────────▼────────────────────────────────────┐
│ SellerKit 主进程（ae-receiver 扩展）                            │
│   形状校验 → ae-shop-item/v1 schema 校验 → 店铺匹配 → 落库        │
└───────────────────────────┬────────────────────────────────────┘
                            │ 语义化 IPC（新通道 3 个，§3.6）
┌───────────────────────────▼────────────────────────────────────┐
│ 渲染层「货与成本」                                              │
│   店铺登记（+店铺地址） · 右栏「店铺商品」段 · 建款向导            │
│   认款 → product-sku-map（既有写路径）→ pl_shop_sku confirmed     │
└────────────────────────────────────────────────────────────────┘
```

### 3.2 通道（复用接收端，不新开端口）

- 新路径 `POST /ae/shop-items/ingest`，与 `/ae/ingest` 同 token、同限速、同大小上限。
- 帧 schema `ae-shop-item/v1`（宽容模式：必填仅 `store.url` 与 `items[].itemId`，未知字段进快照）：

```jsonc
{
  "schema": "ae-shop-item/v1",
  "store": { "url": "https://www.aliexpress.com/store/123456/index.html",
             "name": "我的店", "storeId": "123456" },
  "items": [{
    "itemId": "1005006123456789",     // 商品ID（认款锚点，归一口径 toSkuKey）
    "title": "女士纯棉短袖T恤 2026夏季新款",
    "imageUrl": "https://ae01.alicdn.com/….jpg",
    "priceText": "US $5.99 - 8.99",
    "category": "T-Shirts",
    "status": "在售",                   // 平台原文，入库不解释
    "url": "https://www.aliexpress.com/item/….html",
    "skus": [ { "color": "Black", "size": "L", "price": "8.99", "stock": 120 } ]
  }]
}
```

- `skus` 可缺省（列表页轻采不带）；详情页重采带。同一商品再次采集 = upsert 覆盖快照。
- 双 schema 预留：`v1` 起；字段演进靠"未知字段进 raw_json"（PROFIT_TRACKER §6.1 同款策略）。

### 3.3 数据层（三处改动）

**① 新表 `pl_shop_items`（店铺商品快照）**

```sql
CREATE TABLE IF NOT EXISTS pl_shop_items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  shop_id INTEGER NOT NULL DEFAULT 0,      -- 0 = 店铺未登记（匹配不到）
  store_key TEXT NOT NULL DEFAULT '',      -- 未登记时存店铺归一名，供提示条展示
  item_id TEXT NOT NULL,                   -- 归一的商品ID（toSkuKey）
  title TEXT NOT NULL DEFAULT '',
  image_url TEXT NOT NULL DEFAULT '',      -- 远程主图 URL
  image_id INTEGER NOT NULL DEFAULT 0,     -- 下载入库后的 pl_images(id)，0=未下载/失败
  price_text TEXT NOT NULL DEFAULT '',
  category TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT '',         -- 平台状态原文
  url TEXT NOT NULL DEFAULT '',
  sku_json TEXT NOT NULL DEFAULT '',       -- SKU 矩阵快照（建款向导用）
  raw_json TEXT NOT NULL DEFAULT '',       -- 整帧快照（≤64KB）
  source TEXT NOT NULL DEFAULT 'ae-scrape',
  scraped_at INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  UNIQUE(shop_id, item_id)
)
```

**为什么新开一张表，不塞 `pl_shop_sku` 的池种群**：池/映射靠 `skuPoolSql()` 与  
`skuMappingSql()` **互为补集**这条不变式活着（`listSkuMappings`、队列 `mappedKeys`、  
`resolveOrderSku` 全依赖它）。采集行带 `shop_id>0` 且 `source='ae-scrape'`，  
会掉出两个谓词的并集之外 —— 一个"两边都查不到"的第三种群，正是这套设计最怕的东西。  
快照表同时把语义钉死：**`pl_shop_items` = 平台事实（店里有什么），  
`pl_shop_sku` = 人的决定（这是什么款）**，两张表两种写入者，不互写。

**② `sk_shops` 加 `shop_url` 列**（`electron/shop-db.ts` 的 `ensureShopColumns()` 模式：  
建表语句 + `PRAGMA table_info` 补列两处同向；老库 `CREATE TABLE IF NOT EXISTS` 不动存量表）。  
全量提交链路同步加字段（`ShopUpsertInput` / handler / preload / `types.ts` / `ipc.ts` 顶层包装 —— 契约五处）。

**③ 图片入库**：新通道 `shop-item-image-fetch`（主进程 `net` 下载 → `landImageBuffer` 去重 →  
回填 `pl_shop_items.image_id`）。失败不外抛、单张失败不影响其它（既有 `adoptOrderImages` 同款纪律）。

### 3.4 店铺匹配规则（按证据强度排序，接收端执行）

1. `store.url` 与 `sk_shops.shop_url` **精确相等**（URL 店铺级唯一，等价于 `platform_shop_id` 的角色）；
2. `store.storeId` 与 `platform_shop_id` 精确相等；
3. 店铺名同名唯一命中 → **只作建议**（`autoShopId`），不自动写；
4. 都不到 → `shop_id=0` + `store_key`，界面走「待登记」提示条（同队列 `shopUnresolved` 形态）。

> 地址因此有了下游读者：它是采集帧唯一的精确连接键。登记时填了地址的店，采集即自动归位；  
> 没填的店，提示条点名"它还没登记地址/平台"，按钮直达「店铺登记」。

### 3.5 写入口（零新写口径）

| 动作        | 走既有路径                                                           | 说明                                                             |
| --------- | --------------------------------------------------------------- | -------------------------------------------------------------- |
| 认款        | `product-sku-map` → `upsertSkuMappings`                         | 勾选采集商品 → 关联到左栏当前款 / 弹层选款；`spec` 颜色、`variant_id` 反查、回流、补色全部原样生效 |
| 建款并关联     | `product-upsert` + `product-variant-upsert` + `product-sku-map` | 向导只是把三次既有调用按"预填 → 人确认"组织起来，主进程无新判断                             |
| 采纳商品图为款主图 | 既有"只补空"规则                                                       | 认款成功且该款 `image_id=0` 时顺手采纳（`adoptOrderImages` 同款边界）            |

### 3.6 IPC 新增清单（契约五处同步：handler + preload + types.ts + ipc.ts 包装 + 界面）

| 通道                      | 方向   | 用途                                   |
| ----------------------- | ---- | ------------------------------------ |
| `shop-items-list`       | 渲染→主 | 店铺商品段列表（按店铺/认款状态/搜索 + 分页）            |
| `shop-items-summary`    | 渲染→主 | 每家店：采集数 / 已认款数 / 最近采集时间              |
| `shop-item-image-fetch` | 渲染→主 | 下载远程主图 → `pl_images` → 回填 `image_id` |

写入与图片采纳**零新通道**。另：接收端状态复用既有 `ae-receiver-status`（含 `lastIngestAt`），  
按 path 区分最近一次是哪类采集（`lastItemsIngestAt` 加一个字段即可）。

## 4. 界面交互设计

### 4.0 总动线（六步，每步都有界面落点）



### 4.1 店铺登记：表单加「店铺地址」（屏幕一）

- 新字段「店铺地址」：placeholder `https://www.aliexpress.com/store/…/index.html`；
  hint 说明它的真实作用 —— "采集时按地址把商品归到这家店；也是「打开店铺」的链接目标"。
- **平台随地址证据带出**：地址是 aliexpress.com 时，平台下拉默认选中「速卖通」（仍可改）。
  这不是"猜"—— URL 是人刚贴进来的证据，与"从历史文本猜平台"是两回事
  （既有纪律禁的是后者：`shopApi.ts:80-82`）。
- 店铺列表行内：地址以链接形态展示（`打开店铺`），采集过的店显示「已采集 N」徽标。
- 表单其余字段不动；`shop_url` 参与全量提交（编辑时不透传 = 静默清空，同 `platformShopId` 的坑）。

> **1 家店铺还没登记**，它的商品暂时无法认款：「我的店（store/123456）」。
> 到「店铺登记」认下来（地址一填，之后的采集自动归位）。  [现在登记]

### 4.5 界面纪律汇总（给实现者的硬约束）

1. 提示必须是入口（警告条带「现在登记」按钮；接入引导带「复制接入信息」与「打开店铺」链接）。
2. 不预选店铺/平台以外的任何东西；默认值只能来自证据（URL → 平台）。
3. `shop_url` 全量提交透传，漏一处 = 编辑一次静默清空。
4. 新表格直接带图列地板 + `table-layout` 结论，别让 2026-10-12 的窄窗口坑再演一遍。
5. 认款状态三态形状可辨；全零不占位；`null`（没采过）与 `0`（采了 0 个）分开。
6. 分段控件从两段扩三段，既有 `data-act` 名一个不动（`sub-queue` / `sub-mapped` 保留，
   新增 `sub-items`），既有冒烟原样重挂。

## 5. 明确不做（反候选清单）

| 不做 | 理由 |
|---|---|
| 自动建店铺 | 平台/店名是人的确认；未登记走提示条（既有纪律） |
| 自动认款（按标题相似度） | 不可逆错账；映射恒为 manual |
| 用采集数据覆盖已有 manual 映射 | `ae_cost_map` 同款先例：manual 行永不被自动覆盖 |
| 无人值守全店翻页采集 | 合规红线（PROFIT_TRACKER §9）；只做人工触发 + 单页/单条 |
| 采集数据直接写 `pl_shop_sku` 池 | 会破坏池/映射谓词互补不变式（§3.3①） |
| 复活「商品清单」页签 | 它的 Excel 路径无下游，保持收起；采集路径的落点是右栏新段 |
| 第二个认款入口 | 右栏一段 + 左栏直连，同既有形态；不新开页签做"另一个映射页" |
| 采克重/成本 | 平台不可靠/不提供；克重只从建款向导由人补 |
| 采集图直接写 `oi_images`（认款前） | 识别域只收人确认过的绑定；未认款前同图只作建议（§8.3） |
| 按图自动建款 / 合并款 | 公版图会让两个款同图；`oi_styles.fingerprint` UNIQUE 约束下静默合并不可逆 |

## 8. SKU 图片闭环：采集图 → 订单按图匹配（2026-10-12 增补）

> 触发问题：订单导入按「产品图片地址」自动匹配；能否在插件采集商品时把每个 SKU 的图也采下来，闭合这个环？
> 结论：**能，且值得闭** —— 但闭环的关键不在"采到图"，而在图 → 款色的**绑定落点与写入时机**。

### 8.1 现状取证：今天的"按图匹配"是怎么跑的

订单侧图的入口只有一条：带「产品图片链接」列的订单报表导入
（`src/core/services/importSheet.ts:156-170`）→ `order-download-image`
（`electron/order-handlers.ts:548-595`）：

1. `fingerprintUrl` = `sha256(origin + pathname)`（忽略 query/hash）查 `oi_images.url_fingerprint`；
2. 未中 → 下载 → 内容 SHA-256 查 `oi_images.fingerprint`；
3. **任一中即复用既有行** —— 连同它的 `style_color_id` 与 AI 识别缓存（两查询均 `SELECT *`，`order-db.ts:551-558`）。

订单的"归类状态" = 其图片行的 `style_color_id`（列表联表字段 `styleCode` / `styleColor`，
`order-db.ts:104-110`）。所以"同一张图第二次出现 → 订单自动带上款色"这条继承链**已经存在**，
用户看到的"按图匹配"就是它。

今天把 `style_color_id` 写上去的只有三个来源：

| 来源 | 函数 | 性质 |
|---|---|---|
| 映射归款 | `autoAssignByMap`（`order-db.ts:1225-1246`） | itemId → confirmed 映射 → `setImageStyleColor`；**无图订单不参与**（归款落点是把图挂到款色上） |
| AI 识别 | `resolveStyle`（`order-db.ts:679-713`） | VLM → 款式指纹 → `oi_styles` |
| 人工归并 / 回流 | `orderStyleAssign` / `skuBackfillFromOrder` | 人的结论 + 附加指纹 |

两个断点（这就是"环"缺的部分）：

1. **采集帧不带图**：SellerKitExtensions 仓库里 ae-profit 扩展的 content script（`lines[]` 只有
   title / skuProps / qty / price，没有 img src）；且采集帧落 `ae_orders`（利润域），
   与 `oi_orders`（归类域）本来就是两个域。
2. **采集侧没有任何图 URL 落库**：商品池今天只有 Excel 导入的 itemId + 主图链接
   （`src/modules/goods/productIo.ts:527-549`），SKU 级（色级）图完全缺失。
   而订单侧颜色列 39% 是 `Picture color` 这类"以图为准"的占位（`order-db.ts:1238-1240` 注释）——
   **色级一直缺一个客观锚点，SKU 色图正是这个锚点**。

### 8.2 采得到什么 / 不采什么

| 数据 | 来源页 | 落点 | 备注 |
|---|---|---|---|
| 每色代表图 URL | 详情页 SKU 矩阵（选色换主图即该色图） | `pl_shop_items.skus[].imageUrl` | 色 → 图 1:1；尺码不单独配图 |
| 商品主图 URL | 列表 / 详情 | `pl_shop_items.image_url`（§3.3 已定） | 款主图候选 |
| 图归一化指纹 | 接收端现算（按图像 ID 取键，见 §8.9） | `img_key` 列 + sku 行内 | 供 L2 建议级比对（§8.3） |
| 图片二进制 | —— | **不采** | 按需下载：采纳 / 预览 / 内容指纹比对；同 `adoptOrderImages` 纪律（`product-handlers.ts:516-533`） |

> AE CDN 有 `ae01.alicdn.com` 与 `ae-pic-a1.aliexpress-media.com` 两个宿主、常见 `_350x350` 尺寸后缀 ——
> URL 逐字节相等不保证，见 R1。

### 8.3 闭环设计：写入侧一次采纳，读取侧四级证据

**写入侧（认款那一刻，人确认）**：建款向导 / 认款时人对每个色行确认 → 该色 SKU 图经
`shop-item-image-fetch`（§3.6 已规划）下载 → 登记 `oi_images` 行（`source_url` = SKU 图 URL）→
`setImageStyleColor(imageId, 款色id)`。三条边界与既有采纳完全同构：
**只补空不覆盖**（款色已绑图不动）、**失败不外抛**、**只对本次人确认的行**。
这是把 `adoptOrderImages`（订单图 → 款主图）的采纳源扩展到"采集色图"、落点扩展到"款色绑定"——
同一个"顺手采纳"纪律，两个新参数，零新判断。

之后任何订单（同 URL 或同内容）走 `order-download-image` 既有去重分支命中该行 → 继承款色。**环闭上。**

**读取侧（订单导入那一刻，四级证据，强 → 弱）**：

| 级 | 判据 | 动作 | 状态 |
|---|---|---|---|
| L0 | raw_fields 商品ID → confirmed 映射 | 自动归款 + 回流 | 既有 |
| L1 | 订单图**归一化指纹**（img_key）/ URL 指纹 / 内容指纹命中**已绑定**的 `oi_images` 行 | 自动继承款色 | 既有 dedup 复用分支 + 新增 img_key 列 |
| L2 | 订单图归一化指纹（img_key）命中 `pl_shop_items` 已采图 | **只出建议**：徽标「采集中有同图 1005006…·Black」+ [一键认款]（色预填 = 采集证据，人点确认） | **新增**（只读 + 一键走既有写路径） |
| L3 | AI 识别 → 款式指纹 | 既有识别链 | 既有 |

L2 **不静默写任何映射**：公版图（卖家共用供应商图）会让两个款同图，`oi_styles.fingerprint`
UNIQUE 约束下静默写 = 把两个款并成一个。建议级让人看一眼 —— 与本仓"自动的只到建议为止"一致。

### 8.4 界面增量（三处，全部长在已设计的三屏上）

1. **建款向导 SKU 矩阵**：每色行带缩略图（URL 热链 + `@error` 降级，复刻 `ShopProductView.vue:54-61` 模式）；
   档案区「采纳为款主图」勾选（款无主图时默认勾选，既有只补空规则）。
2. **待关联队列行**：L2 命中出「同图建议」徽标（描边药丸 = 只读事实）+ [认到采集款] 按钮 ——
   点击走既有认款弹层，色输入框预填采集证据色（可改）。
3. **店铺商品段**：行内 SKU 数改为可展开看「色 × 图」缩略图（不新增表格列 —— 窄窗口图列地板教训，§4.5-4）。

### 8.5 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| R1 | 订单报表图 URL 与详情页 SKU 图 URL 不同形（尺寸后缀 / CDN 宿主）→ L1/L2 恒不命中 | **已取证关闭（§8.9）**：订单侧实测 100% 原图直链（无尺寸后缀、无 query、单一 CDN 宿主）；唯一系统性差异是**宿主**——`fingerprintUrl` = origin+pathname，跨宿主必不等。对策：新增 `img_key` 列，按**图像 ID**（`/kf/S<32hex+校验位>`）归一化取键，同时容忍宿主差异与尺寸后缀；`fingerprintUrl` 本体不动（它同时是识别缓存键）。剩余待验项只剩详情页是否同图像 ID，采集端首次真实采集即复验 |
| R2 | 公版图撞车 | L2 只建议不写；写入恒经人确认；冲突走既有附加指纹 / 人工归并 |
| R3 | 无图订单仍进不了产品维度 | `autoAssignByMap` 与归款落点都要求 `imageId`，本闭环不改变这点；无图订单的出路是采集帧直连归类域（跨域，本期不做，见 §5） |
| R4 | 热链失效 / 防盗链 | 缩略图 broken 降级既有模式；下载失败不外抛 |
| R5 | 详情页改版拿不到色图 | 选择器集中配置；色图缺失 = 该色行留空（"不存在"与"零"分开），不阻塞矩阵预填 |

### 8.6 验收（反空转）

- **两个应结果不同的输入**：① 同图不同 URL（换 CDN 宿主 / 加尺寸后缀）→ L1/L2 应命中；② 公版图（两个款同图）→ L2 应只建议、不自动归类。
- **归一化指纹判等**：同图像 ID 不同宿主（ae-pic-a1 ↔ ae01）判等；不同 S id 判不等（变异：把 img_key 退回 origin+pathname，跨宿主用例必须变红）。
- **色级断言**：订单图 URL = 色 B 的 SKU 图 → 建议 / 采纳的色是 B 不是 A（变异：把色行 `imageUrl` 写死成主图 URL，断言必须变红）。
- **只补空**：款色已绑图时再认款不换图（夹具：先绑一张，再认同款第二色，断言第一张未被动）。

### 8.9 真实样本取证（2026-10-12 · 芒果店长订单导出）

样本：`芒果店长_783900_1791724889335.xlsx`（用户本人店铺导出；1 张表、12 列、13 行数据）。
这份样本把 R1 从"风险"变成"已测量"，并带来两个方案外发现。

#### 8.9.1 URL 形态（16 个 URL 实例 / 12 唯一）

| 维度 | 实测 | 对指纹的影响 |
|---|---|---|
| 协议 | 100% https | —— |
| Host | 100% `ae-pic-a1.aliexpress-media.com`（单一） | 订单侧内部自洽；**与详情页宿主可能不同**（AE 历史上多用 `ae01.alicdn.com`，方案 §3.2 示例即该宿主） |
| 路径 | `/kf/S` + 32 位小写 hex + 1 位校验字符 + `.jpg` | **图像 ID 稳定**，可作归一化键 |
| 尺寸后缀 | 无（全部原图直链） | 订单侧无此问题；详情页缩略图可能有 |
| Query | 无（无签名 / 时间戳） | 现有"忽略 query"的设计在此既无用武之地、也无副作用 |
| 空值 | 0/13（填充率 100%） | 芒果导出的图列可信，可直接进匹配链 |

> 仓库内既有夹具 `tests/mangoPendingImport.spec.ts:143` 用的就是同形 URL —— 夹具与生产形状一致，
> 本节结论对现网导入路径同样成立。

#### 8.9.2 粒度：URL 就是颜色变体级（关键证据）

- 同一产品ID `1005013246442752`：Color:6 → `S4a90d92f…b.jpg`，Color:10 → `S2ceb403b…w.jpg`（**异色异 URL**）；
- 同产品同色跨订单：Color:1 的两行 URL 完全一致（**同色同 URL**）；
- 12 个唯一 URL 全部只对应 1 个产品ID（本样本无公版图撞车，但 R2 防护不变）。

⇒ **订单图 URL 命中 = 同时命中产品与颜色**。L2 的建议可以带色，认款时色预填有证据。

#### 8.9.3 两个方案外发现

1. **订单侧色值既非色名、也没进 `oi_orders.color`**：颜色以 `(产品属性:Color:4)` 内嵌于「产品信息」
   自由文本（13/13 行覆盖），取值是平台内部色号——裸数字 1–10，仅 1 例 `Picture color4`；
   且 Excel 导入路径的 `color` 恒为空串（`importSheet.ts:179`）。**色级的唯一客观锚点就是图**：
   URL 命中详情页 SKU 图时，顺手建立「色号 → 平台色名（Black…）」翻译，款色与订单两处都拿到可读色名。
2. **多商品行的件数列会多拆**（既有拆分器行为，非本方案引入）：样本第 13 行有 4 个商品块
   （`【N】`块 / `;`分号ID / `\n`换行URL 各 4 份，`orderRowSplitter` 的 `IMAGE_SEPS`/`ID_SEPS`/
   `parseInfoBlocks` 已能按索引对齐），但「产品数量」= 5（**件数 ≠ 商品数**）→ `declaredN=5`
   多拆出第 5 行：缺图、缺 ID、info 保留整段原文。建议：件数列仅在「无【N】块且无分号 ID」时
   才作为 declaredN 权威（复验后进导入稳健性 backlog，不挡本方案）。

#### 8.9.4 导入链兼容性（现成，无需改造）

| 检查点 | 结论 |
|---|---|
| 图列识别 | `IMAGE_COLUMN_KEYWORDS` 含「图片」→「产品图片链接」命中 strict 探测（`orderClassifier.ts:201`） |
| 商品ID 识别 | `ITEM_ID_KEYS` 含 `产品\s*ID`（`shopSku.ts:44`）→ L0 映射链对芒果导出可用 |
| 多商品拆分 | `orderRowSplitter.ts` 的 `\n` / `;` / `【N】` 三件套与样本形态逐字匹配 |
| 店铺 | 「店铺名」列原文进 `resolveShopRef`（未登记走提示条，不自动建店） |

#### 8.9.5 R1 结论（原风险关闭）

**订单侧已无尺寸后缀 / query 问题；唯一系统性差异是 CDN 宿主，而归合化指纹按图像 ID 取键后
宿主差异被消掉。** 剩余待验项只剩一个：详情页 SKU 图 URL 是否同图像 ID（采集端上线时第一次
真实采集即复验，无需额外成本）。
