## 3. 三个点名问题（用实测回答）

### 3.1 商品ID 与厂家产品的关系 —— 怎么处理"比较方便"？

**现状是两套归属链并行**（这是全部问题的根源）：

| 链 | 路径 | 谁在用 | 特点 |
| --- | --- | --- | --- |
| **A. 商品ID 映射** | 订单 `产品ID` → `pl_shop_sku` → `pl_products` | 只有「货与成本 › 映射与关联」页手工维护 | 确定、不需识别、**但拣货链完全不用它** |
| **B. 视觉识别** | 订单图 → 视觉引擎 → `oi_styles.code` → `pl_products` | 拣货 / 缺口 / 成本 / 对账**全走这条** | 靠图猜、会错；**实测识别队列 32 条全 pending，等于没跑** |

> 取证：`electron/picking-db.ts:106-114` 的 JOIN 是 `oi_images → oi_style_colors → oi_styles`，**没有 `pl_shop_sku`**；
> `purchase-db.ts:723` `outstanding()` 同样走识别链。

**项目里其实已经预留了正解** —— `pl_shop_sku` 建表时留了两列：

```
spec       TEXT NOT NULL DEFAULT '*'   -- 一期恒 '*'
variant_id INTEGER NOT NULL DEFAULT 0  -- 一期恒 0
```

`electron/product-db.ts:598` 与 `:1139-1143` 的注释把升级路径写得很明确：

> 「D4：一期只有 `spec='*'` 的生产者（变体表推迟到 P5）。引入变体后这里要改成
> **「精确 spec 优先、回落 `*`」**，否则带规格的订单会整批命不中。」

**⇒ 方便的形态：把映射从「产品级」升到「变体级」**（`商品ID + 规格 → 产品变体`），
然后**拣货链优先查映射、识别降为兜底**。实测支撑：

- **量小**：只需配 **17 个商品ID**（现有 3 条已覆盖 62% 的行）；
- **顺带解决颜色**（§3.2）—— 配对时就把颜色定死；
- **识别从"必经"降为"兜底"**，出错面大幅缩小。

### 3.2 颜色只能靠图片肉眼区分 —— 出路

实测形态见 §1.2。**根因不是"没有颜色字段"，而是颜色没有"权威来源"** ——
字段里存的是**平台给的原文**（`Picture color` = "以图片为准"），所以必须每单看一眼。

**出路（主路一条，够用）**：**让商品ID 成为颜色的权威源**（与 §3.1 是同一件事）——
同一个商品ID 的颜色**定一次**，之后该商品的所有订单自动带色。
按实测，这意味着**人工只做 17 次配对**，而不是"每单看图核一次"。

**辅路（可选，锦上添花）**：建颜色枚举 + 按商品批量设色 ——
现有 `src/lib/colorSwatch.ts:18` 已经有一张 16 色表（目前只用于展示），可作为枚举来源；
枚举还能顺手把 `black` / `黑色` 这类**同色异写收敛**。

> 按 Skill「先用数据检验选项」的做法：实测已能判定**主路可行**（17 个 ID 覆盖 42 行），
> 辅路是否需要由你定（§7 G3）。

### 3.3 按进价算预估金额 —— 能算，且口径已被数据定死

| 来源 | 表/字段 | 粒度 | 实测 |
| --- | --- | --- | --- |
| **实际拿货价** | `purchase_items.price_cents`（`purchase-db.ts:174`） | 款 × 色 × 码 | ✅ **12 行有价 / 15 个款色码** |
| 成本映射 | `ae_cost_map.unit_price_cents`（`ae-db.ts:176`） | 款 × 生效区间 | ⛔ **0 行** |

⇒ **口径不用你选**：`ae_cost_map` 是空的，**只能用 `purchase_items` 的拿货价**（按款色码取最近一次）。

**两个配套动作**：
1. **存量成本回填**：对已有 3 张拿货单跑一次 `syncPurchaseCosts`（`electron/purchase-cost-sync.ts:21`）→ 成本表有值 → 「算钱」页的产品成本不再是缺口；
2. **缺价要标出来**：新品/首次拿货没有价 → 拣货单上明确标「无进价」，**不按 0 蒙**（否则预估金额会偏小且看不出来）。

**预估金额 = Σ(件数 × 单价)**，与「算钱」页同一份取价实现（`src/lib/orderCost.ts:429` `pickUnitCost`），
不会出现"两页同一个数不一样"。

① ⚠️ **exceljs `addImage({ filename })` 不给 `extension` ⇒ 写成 `xl/media/image1.undefined`**，

② ⚠️ **Electron 的 `nativeImage` 解不了 WebP**：`createFromPath` / `createFromBuffer` 对 4 张真实

修法：改由**渲染层**（Chromium 有 WebP 解码）用 canvas 统一转 JPEG 再传 —— 顺带省掉"主进程按

③ ⚠️ **冒烟"失败"却以 0 退出**：`if (failed>0) { console.log(...); process.exit(1); }` 之后再跟

在 Electron 下**不退出** —— 事件循环不空，实测挂住。）

## 8. 验收判据与门禁

**跑通判据（一句话）**：选一天，从「今天」页导入 → 「拣货」页出清单（**无未识别款噪声、每行有图有金额**）
→ 生成拿货单 → 提交后订单变已发货 → 「对账」页看到这家厂家的欠款 ——
**全程不离开一个主线，且"同一条订单"在拣货页看到的金额/厂家，与成本页、对账页是同一个数**。

**门禁**（沿用基线，不改）：

- `npx tsc -p tsconfig.electron.json` / `npx vue-tsc --noEmit` / `npm run verify` / `npm run verify:docs` / `npx vitest run`
- 界面改动 → `npm run build` 后跑 `npm run <页>:ui` 假桥冒烟（`today:ui` 现有 **57** 项、`picking:ui` 44 项）
- **导出的 xlsx 本身要单独验**：界面冒烟只能断言"渲染层把什么传过去了"，验不到 zip 里到底嵌了什么 →
  `npm run picking:xlsx:smoke`（读回产物：媒体扩展名、`[Content_Types].xml`、分表、空值、合计）
- **共享实现被覆盖 ≠ 调用点被覆盖**：抽出去的那个函数测了，仍要有一个冒烟**跑那个 handler 本身**
  （行映射 / 金额口径 / 查图条件 / 取消与上限分支只在调用点可见）→ `npm run purchase:xlsx:smoke`
- 新增断言一律**变异复核**，收工 `grep -rn MUTANT src/ scripts/ tests/`
- ⚠️ 门禁命令**逐条单独看退出码**，别串管道（`npm run build | tail` 会吞掉失败退出码，已踩过）
- ⚠️ **"失败"必须证明退出码非 0**：Electron/CJS 冒烟里 `exit(1)` 之后再跟 `exit(0)` 会让两次 log 都打印
  而退出码是 0 ⇒ **同一段流程只调一次 `process.exit`**（见 §6 S3 执行记录 bug ③）
- ⚠️ **状态 / 层级类改动，冒烟全绿也要拍图看一眼**（同一脚本把 `--dump-dom` 换成 `--screenshot` 即可）——
