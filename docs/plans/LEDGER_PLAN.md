## 0. 一句话结论

记账有**两条正交的轴**：`店铺` 回答"这笔钱算哪家店的成本"，`资金相关人` 回答"这笔钱跟谁结"。两者互不推导 —— 一笔房租可以摊给 5 家店，但只跟 1 个房东结算。

v1.0 的地基（口径隔离：记账 ≠ 统计、分摊是派生数据）不变；v1.1 追加的是**第三件事：往来**。它带来三个必须一次设计对的判据 ——

1. **结算不产生收支**。条目记的是"这笔业务花在哪、算谁的"，结算只把"欠/该收"变成"已清偿"。若结算再生成一笔支出，支出立刻翻倍。
2. **"结算后改相关人"有两种语义，必须拆开**：改错了人（改挂，仅未结算）与 责任转移给另一个人（结转，不改历史）。混成一个按钮，历史结算单会与明细对不上，且事后无法区分是纠错还是转移。
3. **已经结算的那部分金额不能再被改写**。要改只能撤销结算重来 —— 撤销是留痕动作，不是删除。

## 1. 先定口径（本方案的地基）

### 1.1 记账 ≠ 统计：两套口径对照

| 维度 | 「统计」页（`order-cost`，现状） | 「记账」（本方案） |
|---|---|---|
| 口径 | **预测**：订单行 × 款级成本 × 克重 × 运价，算出每行毛利 | **已发生的实际业务收支**（不是银行流水，见 §1.2） |
| 数据来源 | 订单导入 / 采集 / 结算明细，自动派生 | 人工录入（本期唯一来源） |
| 店铺维度 | 靠「店铺归属」把订单行指定到店，未归属单独计数 | `sk_shops.id` 直接写在外键上，无「未归属」状态 |
| 相关人维度 | 无 | `bk_parties.id`（供应商 / 员工 / 房东 / 平台 / 自己） |
| 平台佣金/广告 | 无数据源 → 全局标「未扣」，不按 0 算 | 有票就记一笔，没有就不记 |
| 典型用途 | 这批货赚不赚、哪款赔钱 | 每家店收支多少、这个月还欠谁多少 |
| 结论词 | 毛利 / 毛利率 | **经营结余**（店）、**往来余额**（人）。都不叫利润 |

**两页的数字必然不同，这是设计意图，不是 bug。** 一旦用户在记账页看到"利润"二字，就会拿它跟统计页的毛利比，然后认为其中一页坏了 —— 这个坑本项目已经踩过三次（多套金额口径）。

### 1.2 记账是什么、不是什么（v1.1 修订，原表述不准确）

v1.0 写的是"收付实现：钱实际进出"。加入相关人之后这个说法**站不住**：既然有"未结算"状态，就说明条目发生时钱还没出去。

准确表述：**记账记的是"这笔业务已经发生、金额确定、该算谁的"，不是"我的银行卡流了多少"。** 于是：

- 条目记账时**就**计入店铺收支与相关人往来（业务发生即入账）；
- 结算只改变**往来状态**（未清偿 → 已清偿），**不改店铺收支**、**不再生成收支条目**；
- 因此"店铺支出合计"始终等于所有支出条目之和，与结算进度无关 —— 这是本方案能对平的前提。

### 1.3 四条硬规则

1. **不相加**：任何界面、任何导出、任何图表里，记账金额与订单统计金额**不得进入同一个求和**。两者只能**并排对照**（§7.3）。
2. **不叫利润**：记账侧统一用「收入 / 支出 / 结余 / 往来」，禁用「利润 / 毛利」。
3. **口径标注常驻**：记账页页头固定一行小字「按已发生业务收支记账；与『统计』的订单毛利口径不同，不可相加」——不做成可关闭的引导（可关闭的提示等于没有）。
4. **结算不生成收支**：结算单只挂条目、不改条目金额与店铺归属。任何"结算时顺手记一笔支出"的实现都是重复入账。

## 2. 目标与验收判据

| 目标 | 判据（可测） |
|---|---|
| 记一笔最快 15 秒 | 打开弹层 → 金额 → 科目 → 相关人 → 保存，五步内完成；金额框自动聚焦，回车即存 |
| 公共开支摊得服人 | 保存前就能看到「每家店摊多少」；三个基准切换即时重算；分摊合计与条目金额**分毫不差** |
| 单店收支一目了然 | 选店 + 选月，一屏给出收入/支出/结余/科目占比/公摊明细，无需二次筛选 |
| 汇总能对平 | 汇总页「所有店铺合计」恒等于「总收入 − 总支出」；公共池未摊余额恒为 0，不为 0 时页面显式报警（不静默） |
| **按人能结清** | 往来页任选一人，一屏给出「应收 / 应付 / 净往来 / 已结算 / **未结清**」，且 `未结清 = 净往来 − 已结算净额` |
| **结算不重复** | 同一条目不可能出现在两张有效结算单里（DB 唯一键兜底）；结算单金额恒等于其结算行之和 |
| **结算后换人不毁账** | 批量变更相关人后：若含已结算条目，走「结转」生成往来转移记录，历史结算单金额与明细不变；若强行改历史，必须先撤销结算并留原因 |
| 改错不留脏账 | 修改/作废后派生分摊同步重算；历史作废条目仍可查（不物理删除） |

## 3. 需求范围

**包含**
- 收支条目录入（专属店铺 / 公共）、编辑、作废；每条挂**资金相关人（必填）**
- 科目（分类）管理与预置
- 公共条目分摊：三种基准 + 方案复用 + 保存前预览
- 明细列表（按期间/店铺/科目/收支/范围/**相关人/结算状态**筛选）
- 单店收支视图、全店汇总视图
- **相关人台账**（按人统计收入/支出/净往来/已结/未结，可展开到条目）
- **结算批次**：选人 → 挑未结算条目 → 生成结算单；撤销结算（留痕）
- **批量变更相关人**：改挂（未结算）/ 结转（含已结算）/ 撤销结算后改挂
- 相关人主数据维护（新增/改名/合并/停用）
- 与「统计」页单店收入的只读对照
- 按期间导出 xlsx

**不包含（本期明确不做）**
- 复式记账（借贷/科目余额表/试算平衡）
- 发票、税务、报销审批流
- 银行/支付宝/微信流水导入与自动匹配
- 月结锁定（留 `bk_periods.status` 字段，界面不暴露）
- 多币种与汇率
- **部分结算**（一条条目只允许整条结清，见 §6.3）
- **预付/多付**（结算金额不得超过该人未结清余额，超额直接拦，不做"预付账款"）
- **利息、账期、逾期提醒**（往来只算余额，不算时间价值）
- 与采购付款（`payments` 表）自动对账 —— 采购付款是**供应商维度**的既有流水，本期不互相引用
- 应收应付账龄

## 4. 数据模型

新增域 `ledger`，表前缀 `bk_`（与 `sk_` / `oi_` / `pl_` / `sr_` / `ae_` 并列，避免与 `ae_` 视觉混淆）。迁移键 `ledger.main`，按 `electron/db.ts` 的 `migrate(key, steps)` 版本化；新库由 `dbMigrate(SCHEMA)` 的 `CREATE TABLE IF NOT EXISTS` 一次建到当前形状。

```sql
-- 相关人：身份用 id，不用名字
bk_parties (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  name_key TEXT NOT NULL,              -- 归一键（折叠大小写/空白/全半角）；唯一性建在它上面
  kind TEXT NOT NULL DEFAULT 'other'   -- supplier 供应商 / staff 员工 / landlord 房东
       CHECK (kind IN ('supplier','staff','landlord','platform','other')),
  phone TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT '',
  archived INTEGER NOT NULL DEFAULT 0, -- 停用：新条目不可选，历史与台账照常显示
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  UNIQUE (name_key)
)

-- 科目：收入/支出各自一套；builtin=1 为预置项，可改名可归档，不可删
bk_categories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  kind TEXT NOT NULL CHECK (kind IN ('income','expense')),
  name TEXT NOT NULL,
  name_key TEXT NOT NULL,
  builtin INTEGER NOT NULL DEFAULT 0,
  sort INTEGER NOT NULL DEFAULT 0,
  archived INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  UNIQUE (kind, name_key)
)

-- 条目：唯一真相。金额恒为正数，方向由 kind 决定
bk_entries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  biz_date TEXT NOT NULL,              -- YYYY-MM-DD（发生日，不是录入日）
  period TEXT GENERATED ALWAYS AS (substr(biz_date, 1, 7)) STORED,  -- 由库派生，任何写入方都给不错
  kind TEXT NOT NULL CHECK (kind IN ('income','expense')),
  scope TEXT NOT NULL CHECK (scope IN ('shop','shared')),
  shop_id INTEGER NOT NULL DEFAULT 0,  -- scope='shop' 时 > 0；scope='shared' 时恒为 0
  party_id INTEGER NOT NULL CHECK (party_id > 0), -- 必填：0/空一律拒（与 §6.1 一致；结构层兜底，不靠前端拦）
  category_id INTEGER NOT NULL DEFAULT 0,
  amount_cents INTEGER NOT NULL CHECK (amount_cents > 0),
  basis TEXT NOT NULL DEFAULT '',      -- 公共条目：equal | revenue | manual
  rule_id INTEGER NOT NULL DEFAULT 0,
  method TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','void')),
  void_reason TEXT NOT NULL DEFAULT '',
  voided_at TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  CHECK (scope <> 'shop'   OR shop_id > 0),   -- 专属条目必须指向一家店
  CHECK (scope <> 'shared' OR shop_id = 0)    -- 公共条目不许顺带挂一家店（否则汇总会算两次）
)
CREATE INDEX idx_bk_entries_period ON bk_entries(period, kind);
CREATE INDEX idx_bk_entries_shop   ON bk_entries(shop_id, biz_date);
CREATE INDEX idx_bk_entries_party  ON bk_entries(party_id, biz_date);
CREATE INDEX idx_bk_entries_scope  ON bk_entries(scope, status);

-- 分摊行：**派生数据**，不是第二份真相。恒由 src/lib/ledger.ts 生成，主进程只校验守恒
bk_allocations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  entry_id INTEGER NOT NULL REFERENCES bk_entries(id) ON DELETE CASCADE,
  shop_id INTEGER NOT NULL,
  amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0),
  ratio_bp INTEGER NOT NULL DEFAULT 0,
  UNIQUE (entry_id, shop_id)
)
CREATE INDEX idx_bk_alloc_shop ON bk_allocations(shop_id);

-- 分摊方案：周期性固定开销（房租/工资/软件）存一次，下次一键套用
bk_allocation_rules (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  name_key TEXT NOT NULL,
  basis TEXT NOT NULL CHECK (basis IN ('equal','revenue','manual')),
  shop_ids TEXT NOT NULL DEFAULT '[]',
  ratios TEXT NOT NULL DEFAULT '[]',
  note TEXT NOT NULL DEFAULT '',
  archived INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  UNIQUE (name_key)
)

-- 结算单：一次「跟某个人把钱结清」的资金动作。不产生收支
bk_settlements (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  party_id INTEGER NOT NULL,
  settle_date TEXT NOT NULL,
  direction TEXT NOT NULL CHECK (direction IN ('pay','receive')), -- pay 我付给对方 / receive 对方付给我
  amount_cents INTEGER NOT NULL CHECK (amount_cents > 0),
  method TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','void')),
  void_reason TEXT NOT NULL DEFAULT '',
  voided_at TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
)
CREATE INDEX idx_bk_settle_party ON bk_settlements(party_id, settle_date);

-- 结算行：**一条条目只能被一张有效结算单占用**（部分唯一索引即幂等闸）
-- ⚠️ 不能用内联 `UNIQUE(entry_id)`：撤销结算时若只把结算单置 void，这批条目会永远无法重新结算
--    （撤销功能等于废掉）。改为 `WHERE active = 1`，作废时把结算行 active 置 0：
--    结构上既禁"一条被两张有效单结"，又允许"撤销后重新结算"。
bk_settlement_lines (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  settlement_id INTEGER NOT NULL REFERENCES bk_settlements(id) ON DELETE CASCADE,
  entry_id INTEGER NOT NULL REFERENCES bk_entries(id),
  amount_cents INTEGER NOT NULL CHECK (amount_cents > 0),
  active INTEGER NOT NULL DEFAULT 1
)
CREATE UNIQUE INDEX uq_bk_settle_line_entry ON bk_settlement_lines(entry_id) WHERE active = 1;

-- 往来结转：「A 的余额由 B 承接」。不改历史结算单，不产生收支
bk_transfers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  from_party_id INTEGER NOT NULL,
  to_party_id INTEGER NOT NULL,
  amount_cents INTEGER NOT NULL,        -- 可为负：承接的净往来方向
  transfer_date TEXT NOT NULL,
  note TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','void')),
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  CHECK (from_party_id <> to_party_id)
)

-- 期间：本期只建表不写入（月结锁定留位）
bk_periods (
  period TEXT PRIMARY KEY,
  status TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open','locked')),
  locked_at TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT ''
)

-- 操作留痕：改挂 / 结转 / 撤销结算 / 作废 都要留一条
bk_op_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  action TEXT NOT NULL,                 -- repatch | transfer | settle | settle-void | entry-void
  entity TEXT NOT NULL,                 -- entry | settlement | party | transfer
  entity_id INTEGER NOT NULL DEFAULT 0,
  before_json TEXT NOT NULL DEFAULT '{}',
  after_json TEXT NOT NULL DEFAULT '{}',
  note TEXT NOT NULL DEFAULT '',
  at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
)
```

### 4.1 七个建模判据

| 判据 | 落点 |
|---|---|
| 店铺与相关人只能用 id | 分摊行存 `shop_id`、条目存 `party_id`，**都不存名字**。改名后历史仍是那条记录（本项目已因"名字兼作匹配键"栽过 3 次） |
| 金额不许有符号歧义 | `amount_cents > 0` 由 CHECK 兜底，方向只看 `kind`（条目）/`direction`（结算）。禁止"负数收入"，否则同一笔钱有两种写法，汇总必错 |
| 分摊必须能重算 | `bk_allocations` 无业务写入入口（只有重算函数写它），条目改动时同事务先删后插 |
| 期间不许由前端算 | `period` 落库并由数据层从 `biz_date` 派生，汇总 SQL 直接 GROUP BY |
| 作废不是删除 | 条目 `status='void'` + 原因 + 时间；结算单同理（撤销 = 作废，不是删行） |
| 结算状态不落库 | 条目"是否已结算"**由 `bk_settlement_lines` JOIN 得出**，不在 `bk_entries` 上再存一个 `settlement_id` —— 两处存同一事实必然漂移 |
| 相关人与店铺正交 | `party_id` 与 `scope`/`shop_id` 互不推导：一条公共房租 = 摊 5 家店 + 只跟 1 个房东结算 |

### 4.2 与店铺主数据的引用关系

- 归属：`bk_entries.shop_id` / `bk_allocations.shop_id` → `sk_shops.id`
- 删除保护：`shop-account-delete` 现有"有商品/映射引用时拒绝"的判据**追加一条**：有记账条目或分摊行引用时拒绝删除，提示改为「停用」（`status='exited'`）。停用店铺的历史分摊保留、展示为「已停用」，绝不因为停用而从报表里消失。
  （状态值是 `sk_shops` 实际的四态 `active/archived/banned/exited`，不是早期草案里的 `closed`。）
- 相关人**不**与 `suppliers`（采购供应商）强绑：那张表是采购域的付款对象，与记账域的结算对象是两个切面。需要时用 `bk_parties.kind='supplier'` 打标签即可，不做外键。

## 5. 分摊引擎（店铺轴）

### 5.1 三种基准

| 基准 | 算法 | 适用 | 陷阱与处理 |
|---|---|---|---|
| `equal` 平均 | 参与店铺平分，按分取整，差额按 §5.2 补 | 房租、宽带、软件订阅、会计代账 | 小店与大店平均会引争议 → 允许换基准，但**不做**"按店铺规模加权"（没有可靠的规模指标，会造出第四套口径） |
| `revenue` 按营收占比 | 取各店**同期订单收入**占比（万分比），按比例分 | 平台佣金池、公共广告费、公共打包材料 | 唯一取数口径：复用 `src/lib/orderCost.ts` 的汇总结果（统计页现成能力），**不新写收入 SQL**；某店当期营收为 0 → 摊 0；全部为 0 → 回落 `equal` 并在条目上标「各店无营收，已按平均分摊」 |
| `manual` 手工比例 | 用户填每店金额（分）或百分比；按最大余数法折分 | 只有两家店用的一套工具 | **不做自动补齐**：合计 ≠ 总额直接拦，提示差多少 |

### 5.2 尾差规则（写死一条，别留第二种解释）

`amount_cents` 为整数分。按比例算出的原始值带小数，统一走**最大余数法**：

1. 先取整（向下）得到每家店的基数额；
2. 剩余的分（`amount − Σ基数`，恒 < 店铺数）按**小数部分降序**逐分追加；
3. 小数部分完全相同 → 按 `shop_id` **升序**优先。

恒定成立：`Σ allocation.amount_cents == entry.amount_cents`（0 分误差）。这条守恒是数据层写入前的**硬断言**，不满足直接拒绝写入。

### 5.3 参与店铺集合（默认值不能靠位置）

默认集合 = `sk_shops` 中 `status='active'` 的店铺，**并剔除**本期首日之后才开业（`opened_at` 晚于期间首日）的店铺。

- 依据只看事实字段（`status` / `opened_at`），不看"店名像不像"、不看"哪个先建"；
- 界面在分摊预览区固定显示一行：`参与 5 家 · 已排除 2 家（1 家未开业 / 1 家已退店）`，点开可看是哪两家，并可一键切「全部启用店铺」；
- 排除规则是**建议默认值**，用户可在单据上改，但重算时沿用当初的选择，不会因为店铺后来开业就悄悄变。

### 5.4 重算幂等

条目被改（金额 / 基准 / 期间 / 参与店铺）或作废时：

```
事务内：
  1. 按当前条目状态算出目标分摊行（纯函数，确定性）
  2. 与库中现值逐行比较（shop_id → amount_cents / ratio_bp）
  3. 完全相同 ⇒ 不写（保证 updated_at 不虚动）
  4. 不同 ⇒ DELETE entry_id 全部分摊行 → 批量 INSERT 目标行
  5. 断言 Σ = 条目金额，失败则整个事务回滚
```

判据取**事实值对比**，不取"要不要重算"的推测。

### 5.5 算法只在一处：主进程只做守恒断言

- 分摊计算**只在渲染层** `src/lib/ledger.ts` 实现（纯函数，零依赖，`tests/ledger.spec.ts` 直接覆盖）。
- 主进程 `electron/ledger-db.ts` **不做分摊计算**，只做：入参消毒 → 守恒断言（`Σ alloc == amount`，不满足即拒）→ 事务落库。
- 这样只有一份算法，不需要 `aeMoney` 那种"主进程一份 + 渲染层一份 + parity 用例"的双写负担。
- **例外**：将来若出现非渲染层的写入方（Excel 批量导入、定时生成），必须把算法下沉主进程，并补 parity 用例 —— 这是硬前提。

### 5.6 分摊行的可编辑边界

**本期不允许单独微调某一家店的分摊金额**。要改只能改基准 / 比例 / 参与集合，然后整体重算。

理由：一旦允许"手改一行"，分摊行就变成第二份真相，条目金额改了它不跟着变，汇总立刻对不上，且没有任何判据能区分"这行是算出来的还是人改的"。

## 6. 往来与结算（相关人轴，v1.1 新增）

### 6.1 相关人身份

- **只有 id**：条目存 `party_id`，界面显示名字；改名不影响任何历史归属。
- **必填（已定）**：没有"未指定"这条兜底路径。新建/编辑时相关人为空 → 保存直接拦并聚焦该下拉；数据库 `CHECK (party_id > 0)` 再兜一层。
  - 因此台账里**不存在"未指定"行**，全局恒等式 `Σ各相关人净往来 == 总收入 − 总支出` 严格成立（不用减一个"未指定"桶）。
  - 代价要认：录一条账多一步选择。所以「记一笔」的相关人下拉**记住上次选择**（按收/支各记一个默认），第二次起回车即可。
  - 存量风险为零：本模块是新建域，没有历史数据要补 `party_id`（若将来做批量导入，导入模板把相关人列设为必填列）。
- **编辑旧条目遇已停用相关人**：只要相关人**没被改动**就允许保存（否则改个备注都要先启用某人，历史条目变成"不能碰"）；一旦要换人，新相关人必须未停用。
- **同名不同人**合法（"张伟"可能是两个供应商），靠 `kind` + 备注区分；`name_key` 唯一是为了拦住"张三"与"张三 "这种同一人的两个写法。
- **合并相关人**：A 并入 B 时，A 的历史条目批量改挂到 B（含已结算的按 §6.4 走结转），A 置 `archived`，台账里保留"A（已并入 B）"的只读入口。

### 6.2 往来余额算式（一人一屏的口径）

```
应收 P = Σ(party_id=P, kind='income', status='active')            -- 我该从 P 收
应付 P = Σ(party_id=P, kind='expense', status='active')           -- 我该付给 P
净往来 P = 应收 P − 应付 P                                         -- 正 = P 欠我；负 = 我欠 P

已结算净额 P = Σ pay 有效结算单 − Σ receive 有效结算单
                -- ⚠️ 它是**对净往来的调整量**（付出为正），不是"已结掉多少钱"这种无方向的额度
未结清 P（净额）= 净往来 P **+** 已结算净额 P

-- 分方向余额：结算上限必须按方向取
应收未结清 P = 应收 P − Σ receive 有效结算          -- 这个方向还能收多少
应付未结清 P = 应付 P − Σ pay 有效结算              -- 这个方向还能付多少
恒等：应收未结清 − 应付未结清 == 未结清（净额）

-- 结转（bk_transfers，正 = 增加应收）
结转净额 P = Σ 转入 P − Σ 转出 P
未结清 P（含结转）= 净往来 P + 已结算净额 P + 结转净额 P
应收未结清（含结转）= 应收未结清 + max(结转净额, 0)
应付未结清（含结转）= 应付未结清 + max(−结转净额, 0)
```

> **两处修正（P0 实现时发现，原式有错）**
>
> 1. **未结清是"加"不是"减"**：原写 `净往来 − 已结算净额`。代入"我欠 1000、已付 1000"得 `−1000 − 1000 = −2000`，越结越欠。
> 2. **上限必须按方向取，不能按净额取**：同一个供应商常常既欠我钱（退货/返利）又该我付（新货款）。
>    应收 5000、应付 3000 时净额只有 2000，拿 `|净额|` 当上限会把"该付的 3000"判成超额，这笔账永远结不掉。
>    所以拆出「应收未结清 / 应付未结清」两个数，付出看前者、收到看后者。
>
> 两处都有单测守着（`tests/partyLedger.spec.ts` 的「分方向余额之差恒等于净额」「混方向…」两条）与
> 数据层冒烟（`npm run ledger:smoke` 的 `[7]` 段）。

页面必须同时显示**六个数**：应收 / 应付 / 净往来 / 已结算 / 未结清 / **分方向未结清**。少一个（尤其"未结清"），用户就得自己减，而他自己减出来的口径与系统不一定一致。

**全局对账恒等式**（汇总页的隐藏体检，不通过就红字）：

```
Σ 所有相关人 净往来  ==  总收入 − 总支出      -- 相关人必填 ⇒ 等式严格成立，无"未指定"尾差
Σ 所有有效结算行金额 + Σ 未结清          ==  Σ 净往来
```

### 6.3 结算批次（资金三件套落地）

**一次结算 = 选一个人 → 勾若干条未结算条目 → 生成一张结算单。**

| 项 | 规则 |
|---|---|
| 方向 | `pay`（我付给对方）/ `receive`（对方付给我）/ `offset`（互抵结清，2026-10-27 追加）。前两者**只能结与该方向同类型的条目**：`pay` 只结 `expense`、`receive` 只结 `income`。混着结会把两个方向的余额同时记错，而台账上五个数看起来都"有值"。`offset` 则**必须两类都有**（只勾单边不是互抵，直接拒） |
| 金额 | = 所选条目的金额之和，**不可手改**（手改就会超出或少于条目，制造无法解释的差额）。要少结就少勾几条 |
| 粒度 | **整条结算**，不做部分结算。幂等闸 = `bk_settlement_lines` 上的**部分唯一索引** `UNIQUE(entry_id) WHERE active=1`（不能用内联 `UNIQUE(entry_id)`，否则撤销后这批条目永远无法重新结算） |
| 幂等 | 提交事务内校验：所选条目**全部**满足 `party_id == 本单相关人` 且 `status='active'` 且未被任何有效结算单占用；任一不满足 → 整单回滚并指出是哪条。唯一键冲突也视作拒绝，不重试 |
| 超额拦截 | `结算金额 > 同方向未结清` 时拒绝（本期不做预付/多付）。**判据是同方向余额，不是净额**（见 §6.2 修正 2）。提示"该方向未结清 X，本单 Y"。互抵单按**两侧毛额各自**校验：支出部分不得超过应付余额、收入部分不得超过应收余额 |
| 撤销 | 结算单 `status='void'` + 原因；结算行 **`active=0`（不删）** —— 删了就没有"这张单当时结了哪几条"的痕迹，留着又会被唯一索引挡住重新结算 |
| 不产生收支 | 结算单**不**进 `bk_entries`、**不**影响店铺收支与结余 |
| 留痕 | 结算/撤销各写一条 `bk_op_log` |

**为什么金额不让手改**：一旦允许"条目合计 1000，本次只结 800"，就得引入"部分结算"状态与"预付差额"科目，本期不做；而如果允许手改且不引入部分结算，账面上那 200 就凭空消失了。

### 6.4 结算后统一变更相关人（本次需求的核心，拆三条路径）

界面按**选中条目的结算状态自动路由**，用户不用先判断自己想干什么：

| 路径 | 前置条件 | 动作 | 历史影响 | 留痕 |
|---|---|---|---|---|
| **A 改挂** | 选中条目**全部未结算** | 批量把 `party_id` 改为新相关人 | 无（结算记录本来就不存在） | `bk_op_log(repatch)` |
| **B 改挂 + 留旧账**（默认推荐） | 选中条目**含已结算** | 只把**未结算**条目改挂给新人；已结算条目留在原人（与它的结算单一起）。改挂后原人的未结清恒为 0，**不写 `bk_transfers`** | **零改动**：历史结算单金额、结算行、条目金额全不变 | `bk_op_log(party-merge)` |
| **C 撤销后改挂** | 用户坚持要改已结算条目本身 | 先作废对应结算单（必填原因）→ 条目恢复未结算 → 走 A → 可重新结算 | 结算单变作废态（永久可见），需重新出一张新单 | `bk_op_log(settle-void)` + `repatch` |

> **B 路修正（P0 实现时发现）**：原方案写"未结算条目改挂 **+ 生成一条 `bk_transfers`** 转余额"，
> 这是**把同一笔钱算两遍** —— 条目的余额已经随改挂带过去了，再写一条结转，新人的台账会多出一块
> "承接来的钱"，而原人的余额被扣两次。实测：原人应付 3000（其中 2000 未结算）、改挂 2000 后
> 原人未结清已经是 0，此时再写一条 `transfer 2000` 会让新人多 2000、原人变 −2000。
>
> 正确做法 = 只改挂未结算条目，已结算条目原样留在原人；**验收判据因此变成可断言的**：
> 合并后原人的未结清必须为 0。`bk_transfers` 只在"改挂后仍有非零残额"时兜底写一笔（正常恒为 0），
> 属于异常数据的收尾通道，不是常规路径。

**默认给 B 的理由**：用户说"结算后统一变更相关人"，真实场景多数是**责任转移**（这个人不再对接了/换供应商了/员工离职把账转给同事），而不是"历史记错了"。转移不改历史，账面永远能自证；而 C 会让"那张已经付过钱的结算单"与明细对不上，除非把原因写清楚。

**三条硬约束**：

1. **B 不产生结转**：未结算条目的余额随改挂一起过去，`bk_transfers` 只在"改挂后原人仍有非零残额"时兜底写入（正常恒为 0），金额自动取残额、不可手改。要部分转移就不选这条路径（本期不做部分结转）。
2. **C 必须逐单确认**：一个批次可能踩到多张结算单，界面列出「将作废 N 张结算单（金额合计 X）」，逐张显示相关人/日期/金额，确认后才执行。
3. **变更后立刻可见**：操作完成后旧人与新人的台账同时刷新，并给出结果提示「已改挂 12 条 / 结转余额 ¥1,234.56 至 王五 / 作废结算单 2 张」。**不能只提示"操作成功"** —— 用户没法验证到底改了几条。

### 6.5 相关人相关的边界

| 场景 | 处理 |
|---|---|
| 条目未选相关人 | 保存直接拦，焦点跳到该下拉并提示「请选择资金相关人」；不做"先存后补"（一旦允许空值，台账恒等式就多一个桶，且没人会回头清） |
| 编辑旧条目、原相关人已停用 | 相关人**未改动**时允许保存；要换人则新相关人必须未停用 |
| 相关人被停用 | 新条目不可选；历史条目与台账照常显示「已停用」；结算仍可对该人发起（欠的钱还得还） |
| 相关人被合并 | 源相关人 `archived`，未结算条目改挂到目标人；**已结算条目留在源人名下**（历史与它的结算单一起不动），台账保留只读入口 |
| 改挂时新相关人已停用 | 禁止（提示先启用或选别人） |
| 同一人既是房东又是员工 | 用两条 `bk_parties`（不同 `kind`）或一条加备注；系统不做"多重身份"建模 |
| 结算对象与条目相关人不一致 | 拦截：结算单只能结该人自己的条目 |
| 已作废条目被勾选结算 | 不出现在可选列表（只列 active 且未结算） |

## 7. 算式（每个数字一处实现）

### 7.1 单店

```
店收入 = Σ(scope=shop, kind=income, status=active, shop_id=X) + Σ(alloc of shared income → X)
店支出 = Σ(scope=shop, kind=expense, status=active, shop_id=X) + Σ(alloc of shared expense → X)
店结余 = 店收入 − 店支出
```

**结算进度不影响上面任何一个数**（§1.3 第 4 条）。店铺页不显示"已结/未结"，那是人的维度。

### 7.2 汇总

```
所有店铺结余合计 = Σ 各店结余
总收入 = Σ 全部 active income（含公共）
总支出 = Σ 全部 active expense（含公共）
公共池余额 = (总收入 − 总支出) − 所有店铺结余合计      -- 必须恒为 0
```

`公共池余额 ≠ 0` 只有一种可能：某条公共条目没摊 / 分摊行与条目金额不等。**这必须显示成页面上的一条红色提示，带"去看是哪条"的入口**，不允许静默吞掉。

### 7.3 与统计页对照（只读，不合算）

单店视图底部一块「与统计口径对照」：

| 列 | 来源 |
|---|---|
| 记账收入（本月） | 本模块 |
| 订单收入（本月·统计口径） | `order-cost` 现有汇总（店铺归属后的收入） |
| 差异 | 两者相减，**只展示不解释**，旁注「差异来自未到账订单、退款、平台扣费与手工未录，本模块不做归因」 |

不做自动归因（归因需要结算明细的完整对账，属另一条产品线），也不做"以谁为准"的裁定。

### 8.4 单店

```
店铺 ▾（记住上次选择）  ‹ 2026-10 ›
三张卡：收入 / 支出 / 结余

```

### 8.5 汇总

```
‹ 2026-10 ›

公共池：本期公共收支 X 条，已全部分摊（异常时红字 + 入口）
往来体检：Σ净往来 == 总收入 − 总支出 ✓ / ✗（✗ 时红字 + 定位）
```

## 9. 边界与异常

| 场景 | 处理 |
|---|---|
| 参与店铺为 0（全部停用/未开业） | 不允许保存公共条目，提示「当前没有可参与分摊的店铺，请先在基础数据启用店铺」 |
| 分摊合计 ≠ 条目金额 | 硬拦，提示差额；`manual` 基准下指出哪家填得不对 |
| 金额为 0 / 负数 / 超上限 | 0 与负数拦（CHECK 兜底）；单笔上限 1 亿分（100 万元）防误输，超出提示确认 |
| 修改已作废条目 | 不允许；**恢复为有效**已提供（2026-10-27 落地，`ledger-entry-restore`）：明细勾「含作废」后点该行「恢复」，合计与相关人往来回到作废前同值。被有效结算单占用、或分摊行合计 ≠ 金额时拒绝并提示重记 |
| 修改**已结算**条目的金额 | 不允许（会让原结算单金额与明细不等）。提示：先撤销结算，或作废本条后重记 |
| 修改已结算条目的相关人 | 走 §6.4 的 B/C，不提供直接修改 |
| 修改条目日期跨月 | 允许，`period` 随 `biz_date` 重算，两月汇总自然跟着变（实时算，无物化缓存） |
| 店铺被停用 / 删除 | 停用：历史分摊保留显示「已停用」；删除：有引用时拒绝（§4.2） |
| 科目改名 / 归档 | 允许改名（`name_key` 唯一）；归档后新条目不可选，历史正常显示 |
| 同一笔既记了公共又记了单店 | 允许（系统不猜业务），汇总页可筛选自查；不做"疑似重复"自动检测（判据不可靠） |
| 结算单撤销后又想恢复 | 新建一张结算单重新勾选（不提供"反撤销"，避免状态来回跳） |
| 结转后再对旧人结算 | 旧人未结清已为 0，无可结条目；若旧人还有未勾选的旧条目，仍可结（结转只转余额，不搬条目） |
| 备注含个人信息 | 界面提示「不要在这里记录客户个人信息」；相关人手机号可选填，导出不做二次加工 |

## 13. 明确不做 / 后续版本

| 项 | 为什么不做（现在） | 什么时候做 |

| **互抵结清（应收应付对冲）** | ~~不做~~ **2026-10-27 已落地**：`direction='offset'` 一张单同时核销两边、只走差额（可为 0）。仍**不做部分核销** —— 单据金额恒等于结算行之和（毛额），实际资金流是派生值。见 `docs/notes/2026-10-27-ledger-settle-offset.md` | 已实装 |

| 多币种 | 汇率口径会污染汇总（已有 `ae_rates` 一套，两套基准必漂移） | 有店铺以外币直接结算且需原币留痕时 |

| 复式记账 | 单人场景不需要借贷平衡 | 有会计接手时 |
| 分摊单行手改 | 会破坏"派生数据"性质 | 不做，只放开基准与比例 |
| 自动归因记账与统计差异 | 需结算明细全量对账，属另一条线 | 结算数据完整覆盖后 |
