# 发货台改为「订单维度状态跟踪」方案（2026-11-05）

> **状态（2026-11-05 收工）**：P0 / P1 / P2 已落地，P3b 已落地，**P3a 的 S1 已落地（S2/S3 未做）** ——
> 逐条落地物、**与本文的两处偏离**（五档 → 四档 + `unknown`；「处理最急的一单」→「开始处理」筛清单）
> 以及"按单核对为何不改读 `orderStage`"见 **§9 实施记录**；P3a 的拆批（S1/S2/S3）见 **§10**。
> 下文 §1–§8 保留**决策当时的判断**，不回改（改过的判据在 §9 里写明理由，避免"文档看起来一直是对的"）。

> 触发问题（用户原话）：「发货台中的『按此开始发货』按钮跳转到待发货有歧义，发货台准确的定位
> 应该是发货前的准备工作，准备完成，就代表这个订单已经完成了准备，所以怎么才能以订单维度来
> 跟踪当前订单的状态。现在的流程感觉是相对独立的，让人看不太明白。你看看应该怎么优化」

**一句话结论**：现在这一页把「一条全局流水线」（导入→归类→拿货→对账）当成了主结构，而业务真相是
**每张订单各自并行推进**。歧义不是按钮文案的问题，是**缺少一个"订单准备到哪一档"的派生状态**。
本方案补这一层（零新表 / 零新 IPC / 状态全部由既有事实推导），并把首屏从"步骤页签"改成"订单队列 +
状态分组"。**真正的发货动作仍不在本应用内**（`ship_time` 无回写路径），必须如实告诉用户，
否则"准备完成"会变成一个永远不清零的队列。

## 1. 诊断：四条根因（均带取证）

### 根因 1 · 一个动作词承诺了两件不同的事

`OverviewPanel.vue:181-189` 的实心按钮写着「按此开始发货」，`@click="go('queue')"` 落到
「待发货」页签；而 `QueuePanel.vue:238-245` 明确写着这一屏**只读**：

```
① **只读**。这一屏不做"标记已发货"之类的写操作：发货动作在芒果/平台那边完成，
  这里自己造一份"已发"状态，第二天同步一回来就会与真相打架，用户还得解释哪个算数。
```

⇒ 按钮说"开始发货"，落点却是"还不能发的清单 + 一个写操作都没有"。用户点完的预期
（我要发货了 / 我要处理发货了）与看到的（一屏按截止期排序的只读表）不一致 —— **这不是文案瑕疵，
是承诺与能力不符**。

### 根因 2 · 「待发货」三个字同时是"平台状态"和"流程第 1 步"

- `flowCtx.ts:187` `SHIPPING_TAB_NAMES.queue = '待发货'`，它是带步号 `1` 的页签，
  真实职责是"把单弄进来"（芒果采集 / Excel 备选，见 `QueuePanel.vue:1-8`）；
- `mangoStatus.ts:32-34` `MANGO_BUCKET_LABELS.pending = '待发货'`，这是**订单在平台上的事实状态**
  （由 `isWaitingShip()` 判定，`shippingPulse.ts` 整个清单都靠它筛）。

同一个词指着两个东西：一个是"我要做的动作入口"，一个是"这一单现在处于什么状态"。
用户在两者之间来回切，就会产生"这一页到底是干嘛的"的感觉。

### 根因 3 · 流程按"全局串行"推导，业务是"每单并行"

`TodayView.vue:343-398` 的 `flow` 只由四个聚合数推导：

```ts
const hasOrders = o.total > 0;
const needClassify = hasOrders && g.style > 0;
const needPurchase = pu.gap > 0;
const needRecon = pu.balance !== 0;
```

这套模型的隐含假设是"整批走完一步才进下一步"，所以 `now` **恒为 1 步**（注释里写得很清楚：
"初版各步独立判断 ⇒ 三块橙边，答不出当前该做哪一步"）。但真实处境是：

> A 单还差 1 件货 · B 单已经齐了可以发 · C 单缺买家图卡住 · D 单还没认出色
> —— 四件事**同时**存在于四张不同的单上。

全局串行模型无法表达这种并存：它只能说"现在该归类"或"现在该拿货"，而用户手上其实有 4 类活。
页签上那个 3px 的"当前步"标记因此更像噪音 —— 它答的是"整批"，用户问的是"我这几单"。

### 根因 4 · 订单身份在跨页时被丢掉

订单维度只在两处存在，且都是残的：

| 位置 | 有什么 | 缺什么 |
| --- | --- | --- |
| `orderCoverage.ts:210-250` `groupByOrder()` | 按单聚合、`done` 判定、还差件数 | 只看"货齐没齐"；不含缺图 / 未归类；埋在「拿货」页底部（`PurchasePanel.vue:25-46`） |
| `QueuePanel.vue:344-349` `goClassify()` | 带单号跳归类 | 只传单号、不传"为什么跳"；回来要靠用户自己再找这一行 |

而「拿货」页本身是**款色级**的（`purchase_items` 键 = 拿货单×款×色×码，见
`orderCoverage.ts:1-8`）—— 从"这一单"走进拿货，订单身份就消失了。

## 2. 目标：订单准备状态（派生，零新增字段）

### 2.1 五档状态

订单档 = 该单所有明细行里**最差**的那一档（木桶），并带出"卡在哪几行 / 还差几件"。

| 状态 | key | 判据（全部是已有列 / 已有函数） | 界面给的动作 |
| --- | --- | --- | --- |
| 缺图 | `noImage` | 任一行 `patternStateOf()` = `noImage`（`image_id = 0`） | 回芒果重抓 / 补图 |
| 待归类 | `unclassified` | 无缺图，但任一行 = `unbound`（有图、`style_color_id = 0`） | 去归类核对（带单号） |
| 待拿货 | `waitingStock` | 图款齐，任一行 `covered < qty`（`planCoverage`） | 去拿货（带款色） |
| 已备齐 | `ready` | 全部行 `covered >= qty` | 打开芒果发货页 + 复制单号 |
| 已发出 | `shipped` | `biz_status` 命中 `shipped` 桶（`mangoStatus`） | 自动离开队列 |

**判据复用，不新写一套**（这是本项目最容易出事的地方，见 `docs/notes/2026-10-20-engineering-hard-laws.md`
的「派生非幂等就必然漂移」）：

- 行级三档直接用 `shippingPulse.ts:186-191` 的 `patternStateOf()`；
- 件数与已拿直接用 `orderCoverage.ts:99-184` 的 `planCoverage()`（`resolveQty` 三档回落）；
- 订单聚合复用 `groupByOrder()` 的骨架，只额外带一个 `pattern`；
- 平台状态分桶用 `mangoStatus.ts` 的 `isWaitingShip` / `bucketOfStatus`，**不写 `=== '待发货'`**。

落点：`src/lib` 下新增 orderStage 模块（纯函数 + vitest），签名大致：

```ts
export type OrderStage = 'noImage' | 'unclassified' | 'waitingStock' | 'ready' | 'shipped';

export function orderStages(
  rows: ShippingRow[],                    // 容器已有的 pulseRows（全库、带 imageId）
  opts: { covered?: Record<string, number>; pool?: Record<string, number>; now?: number },
): { orders: OrderStageOrder[]; counts: Record<OrderStage, number> };
```

**零新增 IPC**：输入就是 `TodayView.reload()` 里已经取到的两份
（`ipc.orderShippingRows()` + `ipc.purchaseOrderCoverage()`），按 `oi_order_items.id` join。
⚠️ 缺一侧的行必须表达成"不知道"，**不许默认已备齐** —— 否则"读不到覆盖度"会显示成"货都齐了"，
用户当天就会少发一批货。

### 2.2 为什么不做"状态字段"

- 状态是**事实的投影**，不是人维护的字段。加一列 `stage` 就要有回写路径（归类的、拿货的、平台同步的
  各一处），四处任一漏写就产生"库里的状态与事实不符"，而且没人能一眼看出哪边对；
- 现有 `ship_time` 就是反例：**它没有任何回写路径**（见 §2.3），已经变成一个永远为空的列。

### 2.3 出口闭环：必须先说清的硬约束

`docs/notes/2026-11-02-purchase-coverage-scope.md` §6 已取证：

> `ship_time` 没有任何路径被回写，芒果只抓「待发货」；单在平台发货后本地永远停在未发货。

⇒ 若不解决出口，「已备齐」的单会**永久堆在队列里**，状态做得再准也只是把"看不懂"换成"清不掉"。
两条路，按顺序做：

| 优先级 | 做法 | 代价 | 诚实度 |
| --- | --- | --- | --- |
| P3a（正解） | 采集扩展增抓「已发货 / 全部订单」页，回写 `biz_status` + `ship_time` | 扩展侧 + 帧契约（`docs/notes/2026-11-02-mango-frame-contract.md`） | 订单自动离队，无本地虚构状态 |
| P3b（过渡） | 「已备齐」行的按钮 = 打开芒果待发货页 + **复制单号**，不在本地写状态 | 纯前端 | 队列不清零，但界面明写"备齐后去芒果点发货" |

**不做**：本地"标记已发货"开关。它会和平台数据打架（`PurchasePanel.vue:14-16` 已明确禁止）。

## 3. 页面改造：从"步骤线"到"订单队列"

### 3.1 目标信息架构（6 页签 → 5）

```
发货台（定位：把待发货的订单准备好；真正的发货在芒果点）
├─ 订单          ← 主屏：状态分组计数 + 按单清单（可展开到明细行）+ 每档的主操作
├─ 归类核对      ← 工具：按行批量认款认色（从订单行带入单号）
├─ 订花纸        ← 按需旁路（不动）
├─ 拿货          ← 工具：按厂家开单；「按单核对」改为复用同一份 orderStage
└─ 结算对账      ← 工具：钱（不动）
```

- **「总览」并入「订单」**：现在这两屏都在回答"有多少单、是哪几单"，只差聚合与明细
  （`OverviewPanel.vue` 是聚合、`QueuePanel.vue` 是明细），分成两屏是历史包袱而不是信息层级；
- **去掉步号 `1/2/3/4`**：流程是每单并行的，"第 1 步"暗示必须整批顺序完成，正是"看不太明白"的来源。
  引导改由 §3.2 的状态分组承担；
- **首屏唯一的实心按钮**不再是"开始发货"，而是「处理最急的一单」（落到清单第一条 / 第一个非零档）。

### 3.2 首屏（订单页）结构

```
┌ 采集状态条（保留现状：syncBanner + neverSynced） ─────────────────────┐
├ 状态分组（点一下 = 筛到该档，选中态保持） ─────────────────────────┤
│  缺图 2  ·  待归类 3  ·  待拿货 5  ·  已备齐 4        合计 14 单待发货 │
├ 订单清单（按最晚发货时间排，与今天一致） ──────────────────────────┤
│ [缩略图] 单号        店铺    件数  剩余时间   状态        动作        │
│  ▢      1234…5678   店A     3     还剩 6h   待拿货 差1件  [去拿货]   │
│  ▢      1234…9012   店B     1     剩 2天    已备齐      [去发货]     │
│    └ 展开 → 明细行（款/色/码 · 件数 · 图案状态 · 缺口）              │
└──────────────────────────────────────────────────────────────────────┘
```

要点（逐条都有原因，别简化掉）：

1. **状态不是筛选项而是分组**：四格数字本身就是过滤按钮，`合计` 必须等于
   `summary.pulse.pending`（同一个数、同一份来源，否则又回到"总览说 3 单、清单列 2 行"）。
2. **订单行可展开到明细行**：一单三行、三行可能卡在不同档（这单"缺 1 张图 + 少 2 件货"），
   只给订单级一个 chip 会把原因吞掉。
3. **每行一个主操作**，按状态给且带上下文：`去归类` 传单号（复用 `classifyFocus`），
   `去拿货` 传款色（新增 `purchaseFocus`，拿货页已能按款色过滤）。
4. **状态词与平台词分开**：`待发货` 只用于"平台这一单还没发"（页面口径小字），
   订单行上的 chip 用 `缺图 / 待归类 / 待拿货 / 已备齐`。这两个词族不许混用。

### 3.3 文案与定位（P0 就能改，零结构改动）

| 位置 | 现在 | 改为 | 理由 |
| --- | --- | --- | --- |
| `OverviewPanel.vue:188` | 按此开始发货 | 处理待发货订单 | 按钮做的是"进入准备"，不是"发货" |
| `OverviewPanel.vue:185` title | 从第 1 步「待发货」开始… | 逐单准备（补图 / 归类 / 拿货）；发货要去芒果点 | 一句话交代边界 |
| `TodayView.vue:16-18` 页头说明 | 采集 → 归类 → 拿货 → 对账；订花纸按需，利润在「统计」 | 把待发货的订单准备好（补图 / 归类 / 拿货）；发货在芒果点 | 定位句就是"准备"，与用户原话一致 |
| `QueuePanel.vue:15` 口径小字 | 全部待发货 · 跨天 · 按最晚发货时间排 | 平台待发货 · 跨天；**已在平台发货的单不在这里** | 消除"为什么这单发了我还看得见" |

## 8. 附：为什么不是"看板"

考虑过四列看板（缺图 / 待归类 / 待拿货 / 已备齐）。否决理由：状态是**派生**的，不能拖拽改
（拖了也不会写库，是假动作）；而"看板"这个形态本身向用户承诺了"拖一下就推进"，承诺不起。
状态分组 + 清单在同样信息量下不产生这个错误预期。

本方案为产品设计参考，具体实施请结合公司合规与法务要求确认。

### 与方案的两处偏离（都是实跑后回改，不是省事）

**① 五档 → 四档 + `unknown`（「已发出」不进档位表）。**
方案 §2.1 把「已发出」列成第五档；实跑发现它根本进不了队列 —— `shippingQueue` 只用
`isWaitingShip` 过滤，已发货单**自动离队**。把它画成一档会让"四档之和 + 已发出 = 合计"
这条恒等式变成两个来源，而 `ship_time` 至今**没有回写路径**（应用内不做「标记已发货」）。
所以最终是：**缺图 / 待归类 / 待拿货 / 待核对(`unknown`) / 已备齐**，恒等式为
五者之和 ≡ `pulse.pending`，由 `tests/orderStage.spec.ts` 与 `today:ui` 双向钉住。

**② 「处理最急的一单」→「开始处理」（筛到最卡一档）。**
方案 §3.1 写的是"落到清单第一条 / 第一个非零档"。实跑后改成**只筛不跳**：
合并后没有第二屏可下钻，「跳到第一条」还需要用户自己看懂"为什么是这条"；
而"筛到最卡的那一档"是一个更小、可撤销（再点取消）的动作，且它把"从哪开始"的引导
交给状态分组本身。按钮文案也随之不再承诺"发货"。

## 10. P3a 拆批：S1 / S2 / S3（2026-11-05）

用户问「到芒果抓已发货怎么抓、抓哪些、历史补不补」。核查后的结论与拆批如下。
判据与踩坑细节见 `docs/notes/2026-11-02-mango-frame-contract.md` 的「2026-11-05 续」。

### 结论先行

- **抓取侧零改动**：扩展复制页面自己发的请求体、只改分页，把芒果切到「已发货」就抓那一批。
  但**不用 `source.status` 判批次**（芒果自己的编码，语义随版本变），判据取帧内事实。
- **抓什么**：`gmtSend`（发货时间）/ `logisticsNo`（运单号）/ `logisticsServiceName`（承运商）
  —— 帧里**一直都有**，宿主从来没取，所以 `ship_time` 至今全空。
- **历史补不补**：只补「库里仍有 ∩ 平台已发」的最小集，且**先只回写 `biz_status`**。
  更早的历史不补（芒果列表的保留窗口与状态流转没保证，补出来的样本有偏，比"没有"更误导）。

### 三批

### S1 落地物（不接 UI，先证明"只改主表、明细不动、幂等"）

- `electron/order-db.ts`
  - `ORDER_HEADER_COLS` += `logistics_no` / `logistics_carrier`（新库建表即带）；
  - **v14 迁移** `addShipReceiptColumns()`（存量库补两列，逐列 `PRAGMA` 判存在）；
  - `applyShipStatus(input[], { writeShipTime? })`：只写 `biz_status` / `logistics_no` /
    `logistics_carrier`（`ship_time` 需显式开启），返回 `{updated, unchanged, missing,
    invalid, missingNos, columns}`。
- `electron/mango-ingest.ts`
  - 抽出 `pickOrderNo()` / `pickBizStatus()`（**`toInternal` 与回执共用一份取键顺序**，
    否则"入库写成 A、回执记到 B"，不报错只是有几单永远更新不到）；
  - `toShipReceipt()` / `planShipReceipt()`（纯映射，两套键名都认；`withShipTime` 作为

### S1 的三条不变量（都是实跑 + 变异验证的）

1. **只写四列**：金额与时效（`amount_cents` / `deal_deadline` / `timeout_at`）一个都不写；
2. **幂等**：目标值 == 现值不写（同一批跑第二遍全 `unchanged`）；
3. **空值不算指令**：`''` = "这次没给"，不清空已有值。

变异验证：去掉幂等判定 ⇒ 冒烟 2 项红；去掉空值跳过 ⇒ 2 项红；`pickOrderNo` 只认 `orderId`
⇒ 单测 6 项红（含 `mangoIngest.spec.ts` 原有 3 项，证明抽函数没改变 `toInternal` 行为）。

### S1 里发现并修掉的两个坑

1. **新列写进已发布版本 = 存量库永远拿不到**：`migrate()` 只跑 `version > current`。
   最初把 `ALTER ... ADD COLUMN` 加进 v13（用户库记账已是 13）⇒ 新库有、老库永远没有，
   运行时 `no such column`。改成 v14，并**用真库副本实测**：
   `order.main v13 · logistics=[]` → `v14 · ["logistics_no","logistics_carrier"]`，二次执行不抛错。
2. **`npm run order:smoke` 本机假红**：继承 `ELECTRON_RUN_AS_NODE=1` ⇒ `app` 未定义。
   用 `env -u ELECTRON_RUN_AS_NODE`；并用 `git stash` 对照确认该红**改前就有**。

### 为什么 S1 不接 `ingestMangoOrders`

今天的规整帧**没有带 `shipTime`**（S2 才补），所以"帧里带发货时间就走回执路径"这条支路
永远不会触发 —— 接了等于没接，却把主入库路径改复杂了。S2 补字段后再一次接线，
届时判据天然成立：**带发货时间的单 → 回执；不带的 → 原样 upsert**（待发货批行为零变化）。
