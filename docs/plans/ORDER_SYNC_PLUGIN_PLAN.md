# 订单同步插件化 · 可行性与字段可用性分析

> 目标：取消「芒果店长导出 Excel → 拖进 SellerKit」这一步，改为扩展定时把订单推进来。
> 结论先行：**通道 80% 已存在，但采集落库有 4 个断点，同步进来的单在 POD 链路上是死数据**。先修断点，再谈定时。

---

## 一、结论

| 问题 | 答案 |
|---|---|
| 能不能做成插件同步 | **能**。接收端（`127.0.0.1:46211`）、token 鉴权、限速、幂等入口、`upsertCollectedOrder` 全部现成 |
| 今天就能用吗 | **不能**。4 个断点会让同步来的单「落库了但用不了」 |
| 定时同步的现实上限 | MV3 扩展**无法在浏览器关闭时运行**；「每天定时」真实语义是「浏览器开着时按时跑 + 打开时补跑」 |
| 最大的额外收益 | **`biz_status` 只有采集通道能带上**。报表里没有订单状态列，所以现在 70/70 全空 |

## 三、4 个断点（按严重度排序）

### 断点 1 ★★★ 明细缺商品ID → `variant_key` 恒空

```ts
// order-db.ts:4117 采集路径的明细写入（对比 3985 行导入路径：那里 qty / variant_key 都写了）
INSERT INTO oi_order_items (order_id, image_id, size, raw_fields, color, qty)
VALUES (?, NULL, ?, ?, ?, ?)
```

**`oi_order_items` 根本没有 `item_id` 列**，商品ID 一直是靠 `variantKeyOfRow → extractSkuFields(raw_fields)` 从 `raw_fields` 的「产品ID / 商品ID」键里现抽的。

而采集路径写进去的 `raw_fields` 是：

```ts
rawFields: { 采集帧: JSON.stringify(o).slice(0, 20000) }   // ae-db.ts:738
```

**整帧被塞进一个字符串键里。** `extractSkuFields` 在一层 `{采集帧: "..."}` 上找 `产品ID`，永远找不到 → `itemId = ''` → `variantKeyOf` 有 `if (!item) return ''` → **采集单的 `variant_key` 恒为空串**。

后果：采集单永远「未归类」，拿货配对、图案绑定（`pod_variant_patterns` 以 `variant_key` 为主键）全部落空。

### 断点 2 ★★★ 明细 `image_id` 恒 NULL

上面那条 INSERT 第二个参数直接写死 `NULL`。后果：

- POD 图键判别（色名塌陷链接必须靠 `imageKeyOf(md_images.source_url)`）**完全失效**
- 拣货/算钱页要看图，采集单没有
- 而导入路径是会下载主图的（`importSheet.ts:159-172` 逐行 `orderDownloadImage`）

**采集通道比导入通道少一个"带图"能力**，这是能力倒退，不是设计取舍。

### 断点 3 ★★ 通道互斥：导入过的单不能被采集覆盖

```ts
// order-db.ts:4088
if (existed && existed.source !== 'collect') {
  throw new Error(`订单 ${orderNo} 已由导入通道写入，采集不能整单替换它`);
}
```

设计意图是对的（导入是逐行追加、采集是整单替换，混用会让下次重推删掉导入的行）。但现状是**存量 70 单 100% 是 `import`**，所以插件一开始同步，凡是窗口覆盖到的旧单全部抛错。

而且这个错**不会让整批失败**——`ae-db.ts:746` 只 `console.warn` 后计入 `skipped`。回执里只有一个数字，没有原因。这是典型的静默失败。

### 断点 4 ★★ 整单替换 → 明细 id 全换新

```ts
// order-db.ts:4103-4104
d.prepare(`DELETE FROM oi_order_items WHERE order_id = ?`).run(existed.id);
d.prepare(`DELETE FROM oi_orders WHERE id = ?`).run(existed.id);
```

重推同一单 = 删明细 + 重插，`oi_order_items.id` 全部变。已在源码里处理了 `parcel_lines`（`order-db.ts:4095-4100`），但**POD 侧还没建，现在改还来得及**：

> `pod_sheet_ledger.ref_order_item_id` **不能挂 `oi_order_items.id`**，否则每次重推就悬空。
> 必须改用 `(order_no, variant_key)` 定位，或改用订单行稳定键。

这条今天不写进设计，等建了表再改就要迁数据。

## 四、三条接入路径

| | A 芒果开放 API | B 扩展抓芒果页面接口 | C 下载目录监控 |
|---|---|---|---|
| 前置条件 | 服务商资质 / 套餐开通（**未确认**） | 无需资质 | 无需资质 |
| 可靠性 | 高（官方契约） | 中（改版/登录态会断） | 高（只监听文件） |
| 实现量 | 主进程一个 client + 定时器 | 扩展新增抓取器 + alarms + 域名权限 | 主进程 `fs.watch` + 复用 `importOrders` |
| 解决「手动导出」 | 完全解决 | 完全解决 | **不解决**（仍要手动点导出，但省掉拖拽） |
| 风险 | 资质拿不到就归零 | 芒果改接口 / 风控 / 掉登录 | 无 |

**推荐组合：先上 C（半天，立刻止损），同时做 B（1–2 周），A 并行问资质。**

C 看起来"不够自动"，但它是唯一**今天就能把「导出→拖拽→导入」变成「导出→自动」**的路径，且完全复用现成的 `detectAndImport`（`importSheet.ts:358`）。不要因为不完美而不做——它把每天 3 分钟降到 1 分钟，且零风险。

B 的域名要先确认。现有扩展 `host_permissions` 只有速卖通四个域名 + `127.0.0.1`，**不含芒果店长**；`permissions` 也没有 `alarms`。两者都要加。

## 五、定时同步设计（方案 B）

### 5.1 触发

```
chrome.alarms（每 30 分钟）  ┐
扩展启动 / 浏览器启动        ├→ 检查水位线 → 落后就跑 → POST /ae/ingest
手动「立即同步」按钮         ┘
```

⚠️ **MV3 的现实约束必须写进 UI 文案**：

- Service worker 会被休眠，`alarms` 能唤醒它，但**浏览器没开就不会跑**。
- 所以真实语义是「开着电脑时每 30 分钟一次 + 开机补跑」，不是「凌晨 3 点自动同步」。
- 用户看到「上次同步 2 小时前」比看到「已开启每日自动同步」有用得多。

### 5.2 水位线与幂等

- 水位线存 `chrome.storage.local`：`{ lastOrderTime, lastSyncAt, cursorPage }`
- 每次拉「`orderTime >= lastOrderTime - 10min`」——**往回退 10 分钟重叠**，防边界漏单（跨页翻页时订单时间会跳动）
- 幂等靠 `order_no`：`upsertCollectedOrder` 本身就是先删后插
- **水位线只在整批成功后推进**，中途失败不动，否则漏单永远补不回来

### 5.3 失败处理

| 失败 | 表现 | 处置 |
|---|---|---|
| 芒果返回登录页 | 页面出现登录表单 | **停止**，置 `needLogin`，宿主 UI 显示「需要重新登录芒果店长」 |
| 接口 403 / 风控 | HTTP 403 或验证码 | 停止，退避 1 小时，连续 3 次告警 |
| 本地应用没开 | `POST` 连不上 | 缓存最近 3 批到 `storage`，下次启动补推 |
| 单条校验失败 | 回执 `skipped > 0` | **把失败的单号 + 原因显示出来**，不要只给数字 |

最后一条是现成的坑：`ae-db.ts:749` 只有 `console.warn`，用户在界面上看不到任何东西。**回执必须带 `skippedReasons: [{orderNo, reason}]`**。

### 5.4 与导入通道共存（迁移策略）

存量 70 单全是 `import`。三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| **1. 只同步新单**（推荐先做） | 水位线初始化为「今天」，历史不碰 | 无；历史单继续走导入 |
| 2. 导入单转 collect | `UPDATE oi_orders SET source='collect'` 后由采集接管 | 需保证字段能对上，否则金额口径会变 |
| 3. 放开互斥 | 改成「以最新一次为准」 | **不要**。两套金额口径叠在同一 `order_no` 上，后面算不清 |

选 1：**新的走采集，历史的留着**。`shippingRows()` 已经支持 `source: 'all' | 'import' | 'collect'` 过滤，两个通道并存是既有设计。

## 六、采集订单里有哪些信息可用

### 6.1 报表列的现状（实测 75 行）

| 报表列 | 填充率 | 现在落成 | 现在被谁用 | 判断 |
|---|---|---|---|---|
| 订单号 | 75/75 | `oi_orders.order_no` | 全链路幂等键 | ✅ 已用 |
| 店铺名 | 75/75 | `oi_orders.shop` | 归属/筛选 | ✅ 已用 |
| 下单时间 | 75/75 | `oi_orders.order_time` | 发货台日口径、交期 | ✅ 已用 |
| 尺寸 | 75/75 | `oi_order_items.size` | 拣货/印花 | ✅ 已用 |
| 产品ID | 75/75 | 只在 `raw_fields` | `variant_key` | ⚠️ 靠现抽，见断点 1 |
| 产品信息 | 75/75 | 只在 `raw_fields` | 解析 Color/Size/qty | ◐ 部分用 |
| **产品数量** | 75/75 | `qty` 取的是**块内**数量 | 成本/拣货 | ◐ **口径冲突，见 6.2** |
| 产品图片链接 | 75/75 | `oi_images` → `image_id` | 拣货看图、图键判别 | ✅ 已用（仅导入通道） |
| 订单金额 | 46/75 | `oi_orders.amount_cents` | 算钱 | ✅ 已用 |
| 产品总金额 | 46/75 | 只在 `raw_fields` | 无人读 | ◐ 可核账 |
| 物流费用 | 46/75 | 只在 `raw_fields` | 无人读 | ◐ 可核账 |
| 收货国家 | 46/75 | 只在 `raw_fields` | 仅运费试算时实时读 | ◐ **未入库，无法按国家分析** |

### 6.2 被埋在「产品信息」里的信息

`产品信息` 是个多行文本：

```
【1】Men's Cotton Jacket Parka 2026 ...
(产品属性:Color:10,Size:XL,Ships From:China Mainland)
(产品数量:2 piece)
【2】...
```

已抽的：`Color`、`Size`（→ `oi_order_items.color/size`）。

**没抽的**：

| 埋着的字段 | 实测（75 行） | 判断 |
|---|---|---|
| **`产品数量`（块内）** | 65 行块内=1 且顶层=1（正常）；**8 行块内=1 但顶层=2** | ⚠️ **两个字段互相矛盾**。落库取的是块内（`parseOrderQty`），所以这 8 行存的是 1 |
| **多产品块（`【2】`+）** | **2 行仍是整块未拆**（块内 4 个产品、数量 2/1/1/1，却只落 1 行、`qty` 空） | ❌ 这 2 行实际是 4 件不同 SKU，被压成 1 行 |
| `Ships From` | 74 行 `China Mainland` | 目前全是中国直发，**未来海外仓时这一维决定物流成本和是否超时** |

**关于数量，必须分清两件事**：

1. **8 行的矛盾要人来裁定**：顶层「产品数量=2」与块内「产品数量:1 piece」说的是两个数。在没搞清芒果这两个字段各代表什么之前，**任何"修正"都是在猜**。可能是「整单件数 vs 该产品件数」，也可能是导出时被改写。先拿这 8 单去芒果后台核对原始订单，再定口径。
2. **2 行未拆单是数据问题**：`parseOrderQty` 检测到多块就返回 `null`（`aeMoney.ts:200`），这是刻意的保守设计——但它不负责拆行。拆行由 `orderRowSplitter` 做，这 2 行大概率是拆行上线前导入的存量。**用当前拆行器重跑一遍就能验证**，不要直接改 `parseOrderQty`。

### 6.3 只有采集通道才有的字段（报表里根本没有）

| 帧字段 | 落成 | 意义 |
|---|---|---|
| `status` | `oi_orders.biz_status` | **报表没有订单状态列** → 现在 70/70 全空。这是插件同步最大的额外收益 |
| `currency` + `ae_rates` | `amount_cents` | 多站点原币直接换算，不用等报表给人民币 |
| `fees[]` | 费用科目 | 平台佣金/物流费/退款结构化（实测帧里为空，但通道支持） |
| `lines[].skuId` | 未落 | SKU 级精确配对，比色名更硬 |
| `lines[].styleCode` | 未落 | 商家编码，能直接命中成本表 |
| `lines[].title` | 未落 | 标题关键词 → 图案预填 |

**最后三行是白捡的**：帧协议里已经定义了 `skuId / styleCode / title`，但 `upsertCollectedOrder` 只写了 `size/color/qty`。补上 `skuId` 和 `styleCode` 能同时解决「配对要精确到 SKU」和「成本表命中」两件事，代价是明细表加两列。

### 6.4 优先级（按「改一行代码换多少价值」排）

| 优先级 | 做什么 | 工时 | 换回什么 |
|---|---|---|---|
| **P0** | 采集明细补 `item_id` + `image_id` | 1 天 | 采集单能被归类、能绑图案、能看图（断点 1、2） |
| **P0** | 回执带 `skippedReasons` | 0.5 天 | 同步失败不再是黑盒 |
| **P1** | 拿 8 单去芒果后台核对，裁定数量口径（顶层 vs 块内） | 0.5 天 | 数量错了，成本与拣货全错，且**不报错** |
| **P1** | 用当前拆行器复核 2 行未拆单，能拆就重导 | 0.5 天 | 4 件不同 SKU 不再压成 1 行 |
| **P1** | 明细加 `sku_id` / `style_code` 两列并落库 | 1 天 | 配对与成本命中精度上一档 |
| **P2** | `收货国家` 落成列 | 0.5 天 | 能做「按国家看利润/超时」 |
| **P2** | `Ships From` 落库 | 0.5 天 | 上海外仓时的必要前提 |

P0 的两条是插件同步的**前置条件**，不是优化项。

## 七、落地步骤

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **S0（半天）** | 下载目录监控 → 自动导入（方案 C） | 芒果导出后 5 秒内自动入库，不用拖拽 |
| **S1（1 天）** | 断点 1、2：采集明细补 `item_id` / `image_id`，图片走现有 `orderDownloadImage` | 用 curl 推一帧 → 该单 `variant_key` 非空、`image_id` 非空 |
| **S2（0.5 天）** | 回执带失败原因；宿主显示「上次同步时间 / 失败单号」 | 故意推一条导入过的单 → 界面能看到「已被导入通道写入」 |
| **S3（1 天）** | 扩展：加 `alarms` 权限 + 芒果域名，写抓取器 + 水位线 | 手动触发能拉回今天的单；关掉浏览器再打开能补跑 |
| **S4（1 天）** | 登录态/风控检测、退避、缓存补推 | 登出后扩展停止并提示，不刷错误日志 |
| **S5（1 天）** | 字段补全：宣定数量口径、复核未拆单、明细加 `sku_id` / `style_code` | 数量口径有书面结论；未拆单清零 |

**S0 与 S1 可以并行**，S1 完成前不要开 S3——否则定时同步跑起来的是一堆用不了的死数据。

## 八、红线

1. **不要把 `variantKey` 的口径改成"从嵌套 JSON 里挖"**。正解是让采集路径**像导入路径那样**把 `itemId` 写到能读到的位置，而不是让 `extractSkuFields` 去理解 `采集帧` 这个字符串键。
2. **采集单必须有图**。没有 `image_id`，色名塌陷的 6 个链接（50 个槽位）在采集路径上无法判别图案，等于 POD 方案对采集单失效。
3. **POD 台账不要挂 `oi_order_items.id`**。整单替换会换 id，用 `(order_no, variant_key)`。
4. **水位线只在整批成功后推进**。
5. **不要放开通道互斥**。新旧两条金额口径叠在同一 `order_no` 上，事后算不清谁对。
6. **「每天定时」要如实描述**：浏览器不开就不跑。UI 显示「上次同步时间」，不要显示「已开启自动同步」。

## 九、一句话

> 通道早就修好了，缺的是采集端和**三行 INSERT**。
>
> 真正的收益不是省掉导出那 3 分钟，而是**采集通道能带 `biz_status`、`skuId`、`styleCode`** —— 这三样报表里一个都没有，而它们正好是"发货台知道该干什么"和"成本能算准"的前提。
