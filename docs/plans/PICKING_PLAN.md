## 0. 目标与判据

**目标**：选中一批订单 → 按 **SKU（款 × 色 × 码）** 汇总"要拣什么、各几件、图与供应商在哪" → 可导出拣货单。

**跑通判据（一句话）**：任选一批未发货订单，拣货单里每个 SKU 的**件数**与**图**，
与"订单明细逐单数一遍"的结果一致；缺色/码的行**逐行标出来**，不静默按 0 或按 1 蒙。

## 3. 口径：**默认已定，不打扰用户**（2026-09-29 产品原则：能自动就不让人填）

| 项 | 默认 | 何时才需要回到人 |
| --- | --- | --- |
| 件数 | **订单行数量**；缺则按 1 件**并逐行标出**（不静默） | 只有当"缺数量"的行占比高到影响可用性时，才回去补数据源（导入映射），而不是弹窗要人填 |
| 范围 | **未发货 + 近 30 天**（一键生成）；店铺沿用订单导入时的归属 | 需要更早/按店铺细分时，才展开"更多筛选" |
| 已拿货扣减 | **不扣**（拣货 ≠ 缺口）；另列"已拿"供参考 | 用户明确要"还剩多少没拿"时，走 `outstanding()` |

> 原则：**默认值要写在界面上可见（"未发货 · 近 30 天"），而不是藏在设置里**；用户看不到默认值就会怀疑数字。

## 3.1 P1 取证结论（2026-09-29 实测，只读聚合，不读业务明细）

在用户真实库（`oi_orders` 42 行）上量的填充率：

| 字段 | 填充率 | 结论 |
| --- | --- | --- |
| `color` 颜色 | **42/42 = 100%** | ✅ SKU 粒度可用 |
| `size` 尺码 | **42/42 = 100%** | ✅ 同上 |
| 款编码（经识别链） | **42/42 = 100%** | ✅ 同上 |
| 订单状态 | 全 `pending`（未发货） | ✅ "未发货"默认范围天然可用 |
| **供应商** | **`pl_products` 只有 1/27 填了 `supplier_id`**（`suppliers` 2 行） | ⚠️ **按供应商分组现在几乎全空** |

⇒ 两条据此调整：

1. **拣货按 款×色×码 做准没有障碍**（色/码/款都齐）—— P2/P3 照计划走。
2. **供应商分组先别当主打**：产品→厂家的关联还没维护（1/27）。第一版拣货单**照常出这一列**，
   但缺的行显示 `(未识别供应商)` 并给计数 —— **不静默糊成一组**；要真按厂家分单，先去产品库补 `supplier_id`
   （属于主数据维护，不是本线的开发工作）。

## 3.2 P2 取证结论（2026-09-29 实测，两份真实导出对齐后）

| 事实 | 取证 | 对口径的影响 |
| --- | --- | --- |
| 订单报表**每一行**都有件数 | `订单列表-6.xlsx` 153 行 / 175 个【N】块：块内 `(商品数量:N piece)` **175/175 命中**，块数=商品ID 数 **153/153 一致** | 订单侧可做**逐行**真值来源（拆分后每行只剩自己那一块） |
| 多件是真的存在 | 块级件数分布 **1:165 / 2:8 / 3:2** | 件数必须逐行取；一期"恒按 1 件"会错 6% 的行 |
| **同一商品会以多个 SKU 出现在一张单里** | 订单报表 14 行是"商品ID 重复"（同一 `商品ID` 的多个尺码），结算明细里同样 10 组 `(订单,商品)` 有 **2 行以上**商品行 | ⚠️ **结算的"按商品合计件数"不能逐行复用** —— 直接铺到每一行会翻倍 → 只在 `lines === 1` 时采用（`src/lib/orderCost.ts` 的件数优先级） |
| 结算样本里的商品行件数 | `订单明细-6.xlsx` 商品行 212 行，`商品数量` 分布 **1:212** | 结算侧这一批全是单件 —— 真值优先的顺序在本样本上无法用结果区分，故用**单测**钉住优先级 |
| 「数量」列不可用 | 拆行后它仍是**整行**值（splitter 不清空） | 与 `extractShipping` 同一条理由：**不用它**，取不到就标缺 |

**落地形态**：`qty` / `qtySource`（`settle` / `order` / `assumed`）逐行可见（明细列 + 悬停说明），
缺的行进 `缺件数` 计数，件数 > 1 时界面出一个提示条。

### ⚠️ 由此暴露的**开放项**（P2 未做，需先拍板）

**件数 > 1 的行，成本与运费目前仍按 1 件计** —— 这是**刻意的**，不是漏写：

- `ae_cost_map.unit_price_cents` 是**单件**成本（`purchase-db.costSnapshot()` = `Σ金额 / Σ件数` 实证），
  按件数放大在算术上成立；但**运费**不行：多件合并计费是运价岛的开放项（`shipRateOrders` 一期恒 1 件/行），
  单方面放大成本会让"同一行的成本×N、运费×1"看起来像 bug；
- 两者要一起改才对得上，且会**改变所有已展示的毛利数字** → 属于口径变更，等用户拍板；
- 在改之前：**界面显式提示**（`多件 N 行 · 成本/运费仍按 1 件计`），单测里也用一条断言把这个口径钉住
  （`qty=2` 与 `qty=1` 的 shipping/cost/gross 逐项相同），防止有人"顺手"放大一半。

## 3.3 P3/P4 的两条**刻意决策**（与原计划的偏差，按代码现实回改）

**① 不做 `db` 能力域，只加一个宿主只读通道 —— 因为页面是内建模块。**
原 P3 写的是"新域 `picking`（只读 ≤10 op）"。实际情况：`DB_OPS` 的能力域**只为 UI 岛存在**
（岛的 `manifest.capabilities` 逐调用过权限门），而拣货页与「订单利润」页一样是**内建模块**，
走 `core/services/ipc.ts` 直连宿主通道 —— 加一个"没人消费的域"只会变成死声明（`pluginTriage` 还要为它
维护预算）。⇒ 本阶段只加 `picking-rows` 一条只读通道；**`db` 能力域的声明留给 P5**（岛消费时连带发版）。

**② 聚合与"范围口径"都留在渲染层纯函数，宿主只回投影。**
- 件数要从 `raw_fields` 的「商品信息」块解析（`parseRowQty`）、"已终结的单不该拣"要按**状态原文**判定
  （`bucketOfStatus`）、天数窗要认 `order_time` 的多种写法（`dateKey`）—— 这三件事的唯一实现都在渲染层，
  主进程再抄一份必然漂移（`electron/orderMoney.ts` 末尾已立此纪律）；
- **反证**：`订单列表-6.xlsx` 153 行里，**101 行"订单关闭"的 `发货时间` 是空的** —— 只按 `ship_time`
  筛会把 101 条关闭单当成待拣；而日期若在 SQL 里做字符串比较，`08/30/2026 07:00` 这种写法的行会被
  **静默丢掉**（`'08/…' < '2026-…'`）。
⇒ 宿主的 `WHERE` 只留**机械事实**（`ship_time` 空 且 `status<>'shipped'`、可选店铺、上限），
"剔除谁"由纯层做并**把剔除数报出来**（`excludedFinished` / `excludedOld` / `undated`），界面写在标签上。

> 该批真实数据的默认清单长这样（P3 的实测口径）：153 行 → 101 关闭（剔）· 31 等待买家收货（已发货，剔）·
> 17 交易完成（剔）· **4 行"等待发货" = 真正要拣的**。若不做①（关闭单滤除），清单会多出 25 倍噪声。

**③ P5 的形态：域 op 与内建页**共用同一份纯函数（岛侧零口径）。**
`src/core/plugin/host.ts` 跑在**渲染进程**，所以它能 `await import('@/lib/picking')` ——
于是岛侧 op 可以直接在宿主里做完"取投影 + 取结算件数 + 按 SKU 汇总 + 范围口径"，岛只渲染。
**这否掉了"岛得把口径抄一遍"的方案**（抄一遍必然漂移，而拣货单少一件就是少发一件货）。
> ⛔ **P5 已随 C2 撤回**（2026-09-30）：该 op（`DB_OPS.picking`）与它的守卫 `tests/orderInsightPicking.spec.ts`
> 都删了，因为岛内页签被判为"入口冗余"。**这条设计结论仍然成立**（"宿主 op 里复用渲染层纯函数"的形态
> 现在由 `shipping-rate` / `product` / `excel-copy` 三域活着）——将来若真有岛要消费拣货，
> 照 `docs/notes/2026-09-30-island-read-capability-pattern.md` 的形制开回来即可。
> 当时的守卫写法（岛里不得出现 `aggregatePicking` 等口径实现 + 宿主真的 `await import`，**断言前必须先剥注释**）
> 仍是有价值的样板：`pluginTriage` 里"岛内不自行套费率算式 / 不打包 xlsx"就是同一族。

## 4. 界面原则（本线适用，源自用户 2026-09-29 的三条）

1. **一键式**：主操作只有一个按钮（如「生成待拣清单」），结果页直接给结论（SKU × 件数 × 图 × 供应商）。
2. **不暴露筛选面板**：默认条件以**文字标签**呈现，需要时才展开；不把 5 个下拉摆首屏。
3. **只突出重点**：拣货时用户只关心 图 / 款色码 / 件数 / 供应商 —— 其余（金额、毛利、订单号明细）放次级。
4. **缺数据逐行标**，不弹窗、不阻塞（"缺尺码 3 行"这类计数放行尾）。
5. **顺手回收旧界面的多余控件**（见 P0）——"只管加不管减"会把它变成工具台。

## 4. 为什么是这个顺序

```
P1 先验口径与填充率（色/码到底有没有值）→ 才谈得上"拣货准不准"
P2 数量定了，件数才不是假的
P3 有了口径才建域与 op（否则 op 形状会反复改，而 op 一改就要连带消费岛发版）
P4 页面最后做（它只是 P3 的展示）
P5 发版放最后（版本号是唯一更新判据，攒批一次发）
```

**P1 的价值不在功能，而在取证**：`oi_orders.color` 是 AI 归类写入、`oi_orders.size` 依赖「尺码列」映射，
两者**填充率未知** —— 若色/码大面积缺失，拣货就得先补数据（回到导入映射），而不是先写页面。
