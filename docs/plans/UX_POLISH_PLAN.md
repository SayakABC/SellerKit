## 3. 不采纳 / 改法清单

### 3.1 ❌ 不采纳：把「订单归类」移回默认包（UX-G1 选项 A）
**审查建议**：源头功能无前置依赖，放回默认包收益最大。
**为什么不能**（三条硬约束）：① 与红线 23 冲突 —— 内建占同名 id → 市场同名岛永远没入口；② 留档内建版是旧的（`extensions/order-insight/`，不进构建），维护中在 `ui-plugins/order-insight/dist`（1.5.0 加了拣货页签），"移回"= 复活停更旧实现；③ 默认包大小与语义：把数据源头塞进默认包会让"精简外壳+按需装"反复。
**替代（已进 P1-1）**：留岛，但把"装"变两下点击（按钮 + 首启推荐卡 + 离线文案），收益不变代价小一个量级。

### 3.2 ⚠️ 改法：任务向导 → 先做"只读就绪检查"
**审查建议**（P1-1）把三条链做步骤条。
**判断**：方向对但完整向导代价大且会漂移——"就绪判据"散落各岛（订单量/店铺归一/映射/克重/运价表/成本），宿主只看到一部分，硬做会"向导说就绪、页面算不出"。
**改法**：v1 只做宿主能自证的部分——只读「待办/就绪」卡片，每项 = "现状+缺什么+跳转"，判据只用宿主自己的表（订单行数/未归属店铺数/产品与 SKU 数/运价表快照/成本行数），拿不到的不猜。

### 3.3 ❌ 取证不成立（已过时）
- **C3 的"两个入口互不说明"** —— 成立，但源头是上一步 P5（岛内页签），非历史遗留；处理见 §4-UX-P2。
- **A1 里"拣货页也指向订单归类"** —— 实际没有（`PickingView.vue:67` 只写操作提示）；比"指向不存在"更糟：它**没告诉用户订单从哪来**，且"生成后为空"仍显示"点生成"。

### 3.4 ❌ 不采纳：合并两条重量数据源（E1 深层改法）
审查只建议"互相说明"，我同意；但"统一成一张表"**不做**——这是**刻意的两条源**（订单试算用 `pl_item_weights`／产品试算用 `pl_variants.weight_g`），合并需数据模型变更 + 两条链口径重定，收益远小于风险（运费算错）。

## 5. 与既有约定/门禁的关系
1. **红线 23**：任何"岛功能变内建模块"先读 AGENTS §1.9 与本文 §3.1。
2. **岛侧改动验证套路**（手写岛无单测/类型门禁）：`node --check` → 接线守卫 → 假桥无头冒烟 → 真机 `plugins:island:smoke`。
3. **改 `UiIslandView.vue` 会碰的守卫**：`tests/uiIslandBridgeLifecycle.spec.ts` 与 `plugins:island:smoke`（结构 `:key`/桥重建点一个字不能动，红线 24/25）。
4. **改宿主外壳要同步**：`AGENTS.md` §1.6 文案纪律 · `PROJECT_BASELINE.md` · `CHANGELOG.md`。
5. **门禁**（每轮收尾）：`npm test` + `lint`（0 error）+ `verify` + `verify:docs` + 两侧 `tsc` + `build` + 受影响冒烟。

## 6. 执行顺序
```
P0（零发版一次做完 → 全套门禁 + 冒烟 → 你验收）
  └ 产出：宿主外壳文案与导航说人话、空态可点、插件中心两步可达、装完能重载
```
