# 记账模块审查（功能完整性 / 逻辑漏洞 / 交互 / 可理解性）

> **审查日期**：2026-10-27　**对象**：`src/modules/ledger/**`（16 文件 / 7,403 行）、`electron/ledger-{db,handlers,xlsx}.ts`（3,376 行）、`src/lib/ledger*.ts`（1,928 行）、`scripts/ledger-{db,ui}-smoke`（4,286 行）
> **方法**：静态通读 + 关键路径逐行核对 + 实跑 `npx vitest run tests/ledger*.spec.ts tests/partyLedger.spec.ts`（**159 例全绿**）。未做真机走查，见 §8。

## 0. 结论

**数据层的账算得住，卡在"界面把话说清楚"和"错误发生在看不见的地方"。**

- 金额口径/守恒/幂等/结算不重复这四件最难的事都做对了：分摊算法单点实现（`src/lib/ledger.ts`）+ 主进程只做守恒断言、结算金额结构上不可手填、结算行部分唯一索引兜住重新结算、已结算条目的字段锁定前后端同一判据。**没有发现会算错钱的实现缺陷。**
- 但存在 **2 个阻断级入口缺陷**（「全部日期」下记一笔不可用、台账读取失败反而显示"对账通过"）和 **5 处会造成错账的操作缺口**（导入全选勾进重复行、公共条目无库内查重、批量操作静默截断 500 条、全已结算时自动预选"撤销结算"、单店页下拉不显示当前店）。
- 交互上最伤的是三处"**点了没反应**"：结算被服务端拒绝时错误写在弹层顶部而按钮在底部；记一笔的必填校验只把文字放表单最底部、不聚焦；保存成功的 toast 不告诉你新条目被当前筛选挡住了。
- 可理解性上最危险的一句是往来页页脚「**0 = 已结清**」—— 与"可收 1000 / 可付 1000 恰好对冲为 0"直接冲突，会让用户认为已经两清。

## 2. 阻断级（P0）

### P0-1　点过「全部」之后，「记一笔」不可用且报错莫名其妙

- **取证**：`LedgerView.vue:483` 把 `month` 原样传进弹层；全期间下 `month === 'all'`（`useLedger.ts:35`）；`EntryEditor.vue:544-547` 的 `defaultDate()` 拼出 `'all-01'`，`<input type="date">` 直接置空 → `period` 为 `''` → `loadEligible()` 提前返回（`EntryEditor.vue:819-822`）→ 公共区显示"没有可参与分摊的店铺"，保存先撞"发生日期不合法"。
- **后果**：用户为了翻历史点了「全部」（这是该按钮唯一用途），之后主按钮就坏了。首屏新用户点「全部」一次即触发。
- **修法**：`defaultDate()` 里 `props.month` 不是 `YYYY-MM` 时回落本月 1 日（或今天）；`loadEligible` 用 `period` 为空时按本月取。

### P0-2　往来台账读取失败时显示"对账通过"

- **取证**：`PartyLedger.vue:237-252` 的 catch 只清 `allRows` / `identity`，**没有把 `loaded` 复位**。`identityGap` 由空数组算出 0 → 模板走 `v-else-if="loaded"` 渲染「对账通过：Σ净往来 ¥0.00 = 总收入 ¥0.00 − 总支出 ¥0.00」，同时表格走空态「还没有往来」。
- **后果**：这条横幅是该页"数能不能拿去结账"的唯一门禁。结算/撤销/改挂/导入成功后都会 `reload()`，一次瞬时 IPC 失败就给出**假绿灯 + 空台账**，用户会以为库里的往来丢了。
- **修法**：catch 里 `loaded = false`；`identity` 为 null 时不渲染恒等式结论。

## 3. 会造成错账的操作缺口（P1）

### P1-3　导入「全选」会把"疑似重复"的行一起勾上

- **取证**：`LedgerImportDialog.vue:517` 的 `toggleAllOk()` 遍历 `okRows`，不判 `r.duplicate`；而解析层默认勾选刻意排除重复（`lib/ledgerImport.ts:1348` `selected: ok && !duplicate`），列表上方还写着"N 行像已经记过了（默认没勾）"。
- **后果**：同一份文件导第二次 → 看到"120 行像已记过" → 顺手点「全选」（本意"全都要"）→ 120 行全部重复入账，无二次确认。去重逻辑的全部意义被一个按钮抵消。
- **修法**：`toggleAllOk` 跳过 `duplicate` 行，或全选时弹一句"其中 N 行疑似重复，已跳过 / 仍要包含？"。

### P1-4　公共条目在库里永远查不到重复

- **取证**：`lib/ledgerImport.ts:964-985` 明确 `if (r.scope !== 'shop' || !(Number(r.shopId) > 0)) continue;`（注释承认是为避免 N 次取数）。公共条目只能靠文件内 `seen` 查重。
- **后果**：房租 / 工资 / 平台费正是最常按月重复导入的一类，却恰好完全无保护。重复入账后店铺支出与相关人应付同时翻倍，**分摊守恒断言查不出来**（两边一起翻倍），四项体检也全绿。
- **修法**：公共条目按「日期 + 方向 + 金额 + 相关人 + 科目 + 备注」做库内比对（不需要分摊签名）；或列表接口补 `scope` 之外的分摊摘要字段。

### P1-5　批量结算 / 批量改挂静默只处理前 500 条

- **取证**：`electron/ledger-handlers.ts:84` `idList(v, limit = 500)`，被 `ledger-settle-create`（:278）与 `ledger-entry-repatch`（:297）及 preview（:292）共用；而明细页列表上限 1000 条（`useLedger.ts:162`），「全选」可勾 1000 条（`LedgerView.vue:664`）。
- **后果**：勾 800 条改挂 → 只改 500 条，结果 toast 写"已改挂 500 条"。用户勾选时看到"已选 800 条"，但预览与结果都变成 500，**没有任何提示说明被截断**；且不存在"再点一次补齐"的引导（剩下的 300 条已完成一半操作）。
- **修法**：`idList` 上限提到 2000 与 `listEntries` 一致，或超限直接报错拒绝（"一次最多处理 500 条，请缩小范围"）。

### P1-6　变更相关人：全已结算时被自动预选到"撤销结算后改挂"

- **取证**：`RepatchDialog.vue:277-280` 的兜底顺序是 `[recommended, 'void-then-move', 'move-all', 'move-unsettled']`；全已结算时 `recommended = 'move-unsettled'` 但 `isAvailable` 要求 `unsettledCount > 0`（:252）→ 落到 C 路。后端注释明写「C 永远要用户主动选」（`ledger-db.ts:1797`）。
- **后果**：勾了 5 条已结算条目打开弹层，**默认停在唯一会作废结算单的那条路上**，且此时「推荐」标签是空的（因为 `preview.recommended !== mode`），界面上没有任何"这是最危险的一条"的暗示。填个原因点确认就作废了历史结算单。
- **修法**：兜底顺序去掉 `void-then-move`；该场景改为不预选、要求用户点选，并给一句"所选条目全部已结算，只能撤销结算后改挂"。

### P1-7　单店页店铺下拉不显示当前在看哪家店

- **取证**：`ShopView.vue:33` 的 `<select @change="onShopPick">` **既无 `v-model` 也无 `:value`**，`shopId` 来自持久化偏好（`useLedger.ts:218`）。
- **后果**：应用重启后、以及每次从别的页签切回「单店」（`LedgerView.vue:434` 是 `v-else-if`，组件销毁重建），下拉永远停在「选择店铺…」而数据区显示的是记忆的那家店。用户无法确认在看谁；重新选中同一家店也不会触发刷新（父层 `watch` 值未变）。
- **修法**：`:value="shopId"`（或 `v-model.number`）。

### P1-8　汇总页切月份时，新月份标题下显示上个月的数

- **取证**：`SummaryView.vue:237` `refresh()` 只置 `loading=true`，**不清 `data`**；模板 `v-if="loading && !data"` 因此不成立，旧数据继续渲染，而 `monthLabel` 已经变成新月份（:43）。
- **后果**：点 `‹` 后 metabar 的总收入/支出/结余/条目、店铺表、公共池状态全是上个月的，直到 IPC 返回。**"数字对、期间错"是最难被发现的一类错**，用户会据此做判断。
- **修法**：请求前 `data.value = null`（`ShopView.vue:323` 就是这么做的，两个页面不一致）。

### P1-9　结算被拒绝时，原因写在视线之外

- **取证**：`SettlementDialog.vue:9` 的错误 `<p>` 在 `wb-dialog__body` 第一行；提交按钮在 `:154` 之后的 footer；中间是最大 240px 的条目滚动列表。`:376` 只把 `e.message` 写进 `error`，无 toast、无滚动定位。
- **后果**：超额、条目已被别的结算单占用、余额刚被别处改动 —— 这些**正是必须看原因**的场景，表现为"按钮点了没反应"。用户会连点两三次再怀疑软件。同模块其它失败路径（`LedgerView.vue:960/761`）都走 toast，唯独这里不一致。
- **修法**：失败同时 `toast(..., 'error')`，或把错误块移到 footer 上方并聚焦。

### P1-10　主数据加载失败被静默吞掉

- **取证**：`useLedger.ts:223-228` `init()` 捕获 `loadMasterData` 失败写入 `error`，紧接着 `await load()` 第一行 `error.value = ''`（:179）把它清掉；`loadMasterData` 里 `api.shops().catch(() => [])`（:170）把店铺域异常降级成空数组。
- **后果**：科目/相关人/店铺下拉全空但**没有任何错误提示**；店铺为空时 `EntryEditor.vue:173` 还会主动引导"去基础数据添加店铺"，让用户去重复建店。
- **修法**：`load()` 不要无条件清 `error`（清的是自己的错误，不是别人的）；店铺失败不要降级成 `[]`。

## 5. 交互与可理解性（P2/P3）

**主流程四步走查**（一个第一次用的店主，不看文档）：

| 步 | 结果 |
| --- | --- |
| 记一笔 | ⚠️ 常态可用（金额自动聚焦、回车即存、相关人记住上次）；点过「全部」后不可用（P0-1）；必填错误只在表单最底部且不聚焦（`EntryEditor.vue:1029-1040` 只有金额分支会 `focus()`） |
| 按人查欠款 | ⚠️ 六个数 + 可收/可付都在；但页脚「0 = 已结清」会误导（P2-14） |
| 结清 | ✅ 动线完整、金额与方向上限定死；失败时看不到原因（P1-9） |
| 发现记错人后改挂 | ❌ **断在这里**：明细行点进去是编辑弹层，相关人下拉禁用，提示只说"要改金额请先撤销结算"，**没给改人的出路**；真正的入口是行首复选框 → 底部批量条（无视觉引导）；往来抽屉底部只有「结算未结条目」，方案 §8.3 要求的「变更相关人」**没做**（`PartyDrawer.vue:153-165`），往来页操作列也只有「结算」（`PartyLedger.vue:88-99`） |

其余可理解性问题：

1. **同一字段三套叫法**：`labels.ts:10` 叫「专属/公共」，`EntryEditor.vue:148-163` 叫「这家店 / 公共（多店分摊）」。
2. **「已结算」两个意思**：明细页是状态标签（`LedgerView.vue:276`），往来页是有符号净额（付出为正，`PartyLedger.vue:36/75`）。「未结算」（条目状态）与「未结清」（余额）也常被混读。
3. **合并相关人文案与实现相反**：`PartyManager.vue:93` 写"已结算条目按「结转」处理"，实现是**不写结转**（`ledger-db.ts:1688-1700` 只改挂未结算）。
4. **已并入 vs 手动停用无法区分**：`bk_parties` 没有 `merged_to` 字段，合并只置 `archived=1`（`ledger-db.ts:1719`），台账上只显示"已停用"。用户看到"A（已停用）余额 0、条目空"，不知道钱去了 B。
5. **作废不可恢复，也没说**：前端作废确认（`LedgerView.vue:512-514`）说明了"不删除、不进合计、可查"，但没说"没有恢复入口"；导入错了也没有批量作废 → 只能一条条作废。
6. **导入报"第 N 行"不是 Excel 行号**：`ledger-db.ts:2803/2829` 用载荷序号 `i+1`，而 `ledger-handlers.ts:199-225` 不透传 `rowNo`。跳过 3 行后再失败，提示"第 7 行"，用户去改第 7 行还是失败。
7. **缺「相关人」列时逐行报"相关人必填"**，不说"这份表没有相关人列"（`lib/ledgerImport.ts:812`，方向列有专门分支可对照）。
8. **全期间下的自我矛盾**：`EntryEditor.vue:41-42` 显示"当前在看 all"并承诺"保存后会自动切到 period"，而 `LedgerView.vue:1002` 在 `isAllPeriod` 下刻意不切。
9. **保存成功的 toast 不告诉你账去哪了**：文案只有「已记一笔」（`LedgerView.vue:1007`）。若当前筛选（方向/店铺/未结算）恰好把新条目挡住，用户以为没记上 → 重复录入。
10. **六个筛选项不落盘**：只有月份与方向 `persist()`，店铺/科目/相关人/范围/结算状态/含作废重启即丢（`useLedger.ts:38-53` 声明了这些字段）。
11. **键盘与焦点**：全模块无 Esc 关闭、无焦点陷阱（`role="dialog"` 声明了模态但 Tab 会跑到遮罩后）；整行 `@click` 无 `tabindex`/`role`（`LedgerView.vue:229`、`PartyLedger.vue:53`），键盘用户进不了编辑与抽屉。
12. **遮罩点击即关闭**：`EntryEditor.vue:2`、`RepatchDialog.vue:2`、`SettlementDialog.vue:2` 都是 `@click.self="close"`，含"必填原因"的破坏性弹层也会因此丢掉已填内容。
13. **体检只有公共池给了定位入口**：`SummaryView.vue:119-121` 只有 pool 可点；`partyGapCents` / `allocationGapCents` 纯文字，`brokenEntries` 列了 id 但不可点。方案 §8.5 要求"红字 + 定位"。
14. **空态/截断无提示**：`api.ts:263` 店铺 `limit:500`；`SettlementDialog.vue:339` 与 `PartyDrawer.vue:359` 条目 `limit:1000`；超限静默少数据。

## 6. 值得保留的设计（不要在这些地方"优化"）

1. **金额只有一个算法**：结算金额结构上不接受前端传值（`api.ts:127-138` 不提供 `amountCents`，`ledger-db.ts:1456` 服务端求和），"手改金额"与"勾错条目"因此不可能长得一样。
2. **分摊是派生数据且无业务写入口**：`bk_allocations` 只由 `writeAllocations` 写，写前后各断言一次守恒；`sameAllocations` 取事实值比较，避免 `updated_at` 虚动。
3. **结算状态不落库**：只由 `bk_settlement_lines ... active=1` JOIN 得出（`ledger-db.ts:965-971`），没有第二份真相。
4. **上限按同方向余额**，共享 1000 应付 3000 也能结（`lib/partyLedger.ts:198-250`，实现时修正了方案原文的净额判据）。
5. **口异常常驻且不可关闭**：明细页页头"与统计口径不同不可相加"、结算页"不产生收支"—— 这是本项目踩过三次坑换来的，别做成可关闭的引导条。
