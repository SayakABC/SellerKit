# 「订单 → 拿货」链路简化审查

> 2026-10-20。范围：**订单导入 → 分析商品（款/色/码）→ 按款色码统计拿货 → 记录拿全/拿了多少/花了多少**。  
> 判据不是"代码优雅"，而是**这四个问题的答案各自只有一处实现、且改一次数据不会让答案变错**。  
> 取证 = 源码 `文件:行` + 本机真库（`sellerkit.db`，51 单 / 3 张拿货单 / 42 张订单图）。

---

## 0. 一句话结论

链路本身不难，难的&#x662F;**"分析结果"没有落点**：`oi_orders` 里没有款/色/码三列，  
款色只能经由「订单图 → 色图 → 款色」这条链**间接派生**，于是下游每个消费者都得自己走一遍这条链、  
自己拼一套文本键、自己定义一次过滤范围 —— 目前同一条链路上有 **3 套需求口径、10 处手拼键、3 套金额口径、2 条取图链**。  
昨天用户看到的"图没了 + 全待拿"不是意外，是这套结构的必然产物（色名一改，全部文本键同时失效）。

**最小修法只有一句话：把分析结论落成订单行的三列（款、色、码 + 款色 id），拿货明细改存款色 id；  
需求、已拿、花费各只留一条 SQL。**

## 2. 缺陷清单（按"会算错数"→"只是乱"排序）

### P0 · 会算出错数据

**F1 需求按「行数」、已拿按「件数」——量纲不一致**  
`electron/purchase-db.ts:843` `COUNT(*) AS demand` vs `:814` `SUM(pi.qty) AS taken`。  
一张订单买 2 件时 demand=1、taken=2 ⇒ `missing = -1` ⇒ `:867 if (missing <= 0) continue` 把该款色**整个从缺口里丢掉**：  
用户看不到"这一款还要拿"，直接漏货。真库现状：`raw_fields` 里数量 ≥2 的有 2 行（尚未触发），属**已装好引信的 bug**。

**F2 需求侧是 INNER JOIN —— 未归类的行对缺口完全不可见**  
`purchase-db.ts:844-848` 四个 INNER JOIN。真库 51 行未发货订单里只有 **42 行**能进这条链  
（另外 9 行没有款色归属）；拣货清单用的是 LEFT JOIN（`electron/picking-db.ts:120-124`）⇒  
**清单上有 9 行货，页签徽标与缺口表里没有**。这不是"近似"，是两套事实。

**F3 已拿/取图用「色名文本」当身份 —— 改名即失联**  
`src/lib/picking.ts:57` `takenKey = 款|色|码`、`electron/order-db.ts:1043` `WHERE s.code=? AND sc.color=?`。  
2026-10-20 的归色把 `未分类` 改写成平台色名后：台账 10 行键**命中 0**（拿货页因此"全待拿"）、  
`未分类` 色行下 0 张图（拿货单因此"图全没了"）。

**F4 `outstanding()` 不筛未发货 / 不筛已终结 / 无天数窗**  
`purchase-db.ts:841-850` 没有 `ship_time` / `status` / 日期条件，而清单有（`src/lib/picking.ts:306-322`）。  
已发货但未终结的单会永久挂在"待拿"里；两处数字各自"正确"，用户只能认为它坏了。

**F5 包价单进对账、不进已拿、不进成本分摊**  
`reconciliation` 按 `total_cents`（`purchase-db.ts:755-766`，包价单有金额）、  
`takenLedger` 按明细（包价单无明细）、`costSnapshot` 按明细（`purchase-db.ts:1061`）。  
结果：同一个"这月花了多少"，对账页有、成本页没有。

**F6 编辑已提交单：已拿回滚了，店铺分摊没跟着**  
`updatePurchaseOrder` 删明细重建（`purchase-db.ts:581-586`），但 `purchase_sources` 只在创建时写  
（`purchase-db.ts:453-460`）⇒ `shopAllocation` 仍按旧来源切分，两页对不上。  
且**没有"撤销提交"**：全库唯一写 `status='submitted'` 的地方是 `purchase-db.ts:597`，  
提交后只能编辑或删除，没有"退回草稿"。

### P1 · 结构导致下次还会坏

**F7 "分析结果"没有落点** —— `oi_orders` 无 `style_code/color/style_color_id` 列  
（`electron/order-db.ts:198-212` 的列清单里没有）⇒ 款色只能挂在 `oi_images.style_color_id` 上。  
连带两个后果：`autoAssignByMap` 第一句 `if (!rec.imageId) return`（`:1516`）**无图订单永不归类**；  
任何消费者要用款色，都得自己 JOIN 四张表（现在有 4 处这么写）。

**F8 `oi_orders.qty` 是死列** —— 真库 51 行全 NULL；导入的 INSERT 不含该列（`order-db.ts:1886-1908`）。  
件数在渲染层由 `resolveQty` 四级现算（`src/lib/orderCost.ts:122-139`），而主进程的缺口 SQL 又拿不到它 ⇒ F1。

**F9 归色重算非幂等** —— 9 个触发点（写时 3 类 / 进页 2 / 迁移 1 / 人工 3），  
`setImageStyleColor`、`assignOrderStyle`、`updateOrder`、`upsertSkuMappings` 都**没有"新值==旧值则不写"**。  
`autoAssignByMap:1559` 的守卫判的是"色名像不像平台色名"，字典一变就重定 ⇒ 每重定一次新建一个色行、  
旧行留成空壳（真库 11 个「未分类」空壳）。

**F10 三条取图链、两套键** —— `itemImagePool`（键=归一商品ID，`electron/product-db.ts:2050`）、  
`findStyleColorImagePath`（键=款编码+色名，`order-db.ts:1034`）、`order-image-thumb-batch`（键=本地路径）。  
拿货单用后者、清单用前者，所以"清单有图、拿货单没图"能同时成立。

## 3. 目标模型（最小，能覆盖全部四个需求）

### 3.1 表（只加列，不建新表）

```
oi_orders            ── 订单行（已有）
  + style_code TEXT          分析结论：款编码（''=未归类）
  + color_name TEXT          分析结论：色名（展示用；''=未定）
  + style_color_id INTEGER   分析结论：身份（0=未归类）   ← 匹配只用它
  qty INTEGER                已经存在，只是没人写 —— 导入时写这里

purchase_items       ── 拿货明细（已有）
  + style_color_id INTEGER   身份（0=按原文款色码归类）
  + image_id INTEGER         该行那张图（取图不再靠"款+色名"反查）

purchase_orders / purchase_items / payments ── 不动
```

**规则**：`style_color_id` 与 `image_id` 参与一切匹配与取图；`style_code / color_name / size` 是快照，只给人看。

### 3.2 查询（全部，就这三条）

```
需求 = SELECT style_color_id, size, SUM(qty) FROM oi_orders
       WHERE ship_time='' AND status<>'shipped'  AND 非终结(status)
       GROUP BY style_color_id, size
已拿 = SELECT style_color_id, size, SUM(qty) FROM purchase_items JOIN purchase_orders
       WHERE purchase_orders.status='submitted'  GROUP BY style_color_id, size
花费 = SELECT supplier_id, SUM(total_cents) FROM purchase_orders WHERE status='submitted'
```

**还差 = max(0, 需求 − 已拿)**；「是否拿全」= 该款色码所有尺码的还差都为 0。  
`style_color_id = 0` 的行（未归类）照样参与统计，按 **(商品ID 原文, 色原文, 码)** 归组 —— **不排除、不猜**，界面上标「未归类」。规则见 §3.4。

### 3.4 未归类：既不丢、也不猜

**为什么必须进待拿**：未归类 ≠ 不存在。真库 51 行未发货里 **9 行（18%）** 进不了现有的 INNER JOIN 链，
它们有图、有商品ID、有色码原文，只是没归到款色。把它们排除在需求之外，等于告诉用户"这 9 件不用拿" ——
这是**件数算错**（硬错误、且静默）。纳入后件数正确，归属仍未知，但未知被**写在脸上**。

三种"准确"要分开看，混在一起就会做错决定：

| 维度 | 未归类的表现 | 会不会不准 |
| --- | --- | --- |
| 件数（要拿多少） | 9 件计入需求 | **只有纳入才准**；排除必然少算 |
| 归属（这 9 件是什么款/色） | 单列一组「未归类」，不并入任何款色 | 不知道就不说 —— 标出来即不谎报 |
| 匹配（已拿 ↔ 需求） | 未归类组不与已拿做模糊匹配（除文本唯一命中） | 误差方向安全：宁可"多显示待拿"，绝不"少显示需求" |

**真实库这 9 行的成因（可直接作为修复入口的两种类型）**：

| 类型 | 行 | 商品ID | 能不能自动修 |
| --- | --- | --- | --- |
| 映射悬空（`pl_shop_sku.product_id=9802`，产品已删） | 6 | 2 个 | 不能；但**能自动检出**，重选产品一次覆盖 6 件 |
| 从没配过映射 | 3 | 3 个 | 不能；选产品一次覆盖该商品全部订单行 |

即：**修完 9 件 = 5 次"选产品"**（不是逐行点 9 次）。选完由既有 `reassignOrdersByItemIds` 回填存量订单，
该组自动并入真款色、卡面角标消失 —— 不需要第二次动作。

**界面上的三处提示（缺一处就会有人拿错货）**：

1. 待拿清单顶部一条汇总：「9 件未归类（会影响拿货准确度）：6 件映射已失效 · 3 件未配商品 → 处理」。
2. 卡片角标：未归类组的卡片带「未归类」标签 + 商品图 + 店铺 + 商品ID 后 6 位 + 色码原文（平台色名照抄，不翻译）。
3. 导出 xlsx：未归类行带「未归类」列，合计单独一行，不混进款色行。

**明确不做**：不删行、不改件数、不按"款+码唯一"猜色（今天的 4 行歧义就是这么产生的）、
不在修复前把未归类组藏进"其他"。修复入口放在**问题出现的地方**（卡片上的「归类」+ 顶部汇总条），
不让用户跳到别的模块自己找那 9 行。


### 3.3 与现状的差别（这就是"简化"）

| 现在                        | 之后                        |
| ------------------------- | ------------------------- |
| 款色从图片四表 JOIN 派生，每个消费者各写一遍 | 结论两列落在订单行上，一条 JOIN 都不用    |
| 3 套需求口径                   | 1 条 SQL                   |
| 已拿按文本键                    | 按 `style_color_id`（改名不失联） |
| 取图 2 条链                   | 1 条（拿货明细存 `image_id`）     |
| 色五级 + 9 个重算触发点            | 仍是五级，但只在**一处**落列，且"值未变不写" |

## 4. 分三期（每期独立可跑、可回滚）

### P0 修错数（不动结构，半天）

1. 导入时把 `resolveQty` 的结果写进 `oi_orders.qty`；加一条只补空值的迁移回填存量 51 行（用 `raw_fields` 解析，同 `order.main` v5 的手法）。
2. `outstanding()` 的 demand 改 `SUM(COALESCE(NULLIF(qty,0),1))`，并补 `ship_time='' AND status<>'shipped'` 与非终结过滤 —— **与清单同一口径**。
3. 已拿/取图加"身份优先、文本兜底"：`purchase_items` 能唯一确定 `style_color_id` 的自动填，  
   填不了的留 0 并在拿货页显示「N 行色名已变更，需确认」（不猜色）。
4. 未归类（§3.4）：需求侧纳入并按 (商品ID, 色, 码) 单列成组；顶部汇总条 + 卡面角标；  
   入口按**商品ID**聚合（真库 9 件 = 5 个商品ID），选完产品由 `reassignOrdersByItemIds` 回填 ⇒ 自动归位。

验收：真库上"页签徽标待拿款色数 == 卡面待拿款色数"；已提交的 2 张单在清单上不再是「待拿」；  
拿货单图按"色已定"恢复（真库 1/10 行可确定，其余显式标「色未定」，见 D3）。

### P1 落结构（1–2 天）

1. `oi_orders` 加三列 + 迁移；`autoAssignByMap` 改成"算一次、写两处"（订单行三列 + 图片归属），  
   并加"目标值 == 现值则不写"。
2. 需求/已拿/花费收敛成 §3.2 三条 SQL，删掉 `outstanding()` 与 `TodayView` 的第三套数。
3. 开单时把 `style_color_id` + `image_id` 写进 `purchase_items`；取图只走 `image_id`，  
   `findStyleColorImagePath` 降级为"历史行兜底"。

验收：把某个款色改名（模拟今天的场景）⇒ 清单待拿数、已拿数、拿货单图**三者都不变**。

### P2 删繁（半天，纯减法）

1. 删 F12 的 7 项死代码、F13 的重复入口、F14 `suggestionQty`。
2. 包价单：**删**（已定）。真库 `mode='package'` 为 **0 条** ⇒ 无数据迁移负担。  
   改动面：`PurchaseOrderEditor.vue` 的 `isPackage` 分支与模式切换（`:14/:16/:54/:220/:272/:381/:384`）、  
   `PurchasePanel.vue` 的包价入口与两处文案（`:3/:405/:424`）、`PickingView.vue` 两处 mode 徽标（`:302/:438`）、  
   `purchase-db.ts` 的 `createOrder(totalCents)` / `updatePurchaseOrder` 包价分支 / `computeTotal`。  
   **`purchase_orders.mode` 列保留**（默认 `'detail'`，注释写"历史留痕，代码只有一条路"）——SQLite 删列要重建表，
   收益为零、风险不小；判定标准是"还有没有代码分支"，不是"列还在不在"。
3. `picking-db` 的 itemId 改用 `toSkuKey` 归一（F16）。

## 5. 明确不做（避免过度设计）

- **不做"识别流水线重构"**：五级色顺序本身是对的（图有采集快照作证据），本轮只改"落在哪、谁来写、写完是否幂等"。
- **不做通用 ETL / 事件溯源 / 物化视图**：三条 SQL 足够，量级 51 单。
- **不建"拿货计划"表**：需求是派生的，落表就要处理失效（今天的坑就是这个）。
- **不引入 ORM / 查询层**：现有 `dbQuery/dbRun` 够用。
- **不重写 UI**：页面结构不动，只换数据来源。

### 8.2 真库仍未对齐的一处（事实，不是缺陷）

真库跑真实现后：**已提交的 #38/#39 共 9 行色未定**（#41 草稿 1 行），逐行候选色 2~7 个
⇒ 按 §6 的判据"不能自动定"，只能人认。原因链是**时间顺序**：

1. 2026-10-17 开单/提交时，那些订单行还没归色（当时写进明细的是占位「未分类」）；
2. 之后 AI 归色把订单行补上了 `style_color_id`，待拿侧的色名变成平台真色名（`3` / `Beige` / `红色`…）；

于是"明明拿过货、清单还是全待拿"是**数据滞后**，不是匹配 bug；修法是人在卡面点那枚标签、
用编辑器里的「色未定 · 选一个」给这 9 行定色（配合「同款其余 N 行一起」，最多 3 次选择）。

> ⚠️ 别再想"从 `purchase_sources` 回推身份"：那张表只有 (店铺, 款, 色, 码) 的快照，**没有订单行外键**，
> 它的 `color` 同样是「未分类」—— 回推出来的还是同一个占位值。
